# Release Automation Scripts

Run these scripts from the repository root after installing dependencies with `pnpm install`. Check the locked prebuilt with `pnpm exec clibox --version` (currently `clibox 0.1.6`). Hashing and template rendering use the published npm binary; no Rust build or globally installed clibox is needed. Workflow installation and exceptions are defined in `docs/repository-workflow-contract.md`.

Use **Actions → Release Project → Run workflow** on `main`, choose one of `binpm`, `cargo-mono`, `nodeup`, `with-watch`, `runmoor`, `clibox`, `pnport`, `async-commit-hook`, `tairouter`, and choose `patch`, `minor`, or `major`. The workflow commits the version, validates the exact release source, publishes the selected crate when applicable, and pushes the single release tag. All selectable projects follow this sequence without waiting for main CI; main CI runs independently. For tag-triggered projects, that tag starts the project distribution workflow (including signed binaries, Homebrew where supported, and npm for clibox and pnport) asynchronously; the coordinator does not wait for or report its completion. The pnport tag workflow requires four-host macOS/glibc Linux execution and complete artifact validation for `0.1.0`; Windows x64/arm64 joins in `0.2.0`. Publication also requires the reviewed acceptance gate in the private source manifest, which remains closed while issue #958 has minimum-OS, runtime, or benchmark gaps. A version commit or tag does not open that gate. For `async-commit-hook`, the coordinator prepares only the version and tag; signing, GitHub Release, and Homebrew require a separate manual **Release async-commit-hook** run, while consolidated Public Docs deploys automatically through Cloudflare Pages from `main`. Main pushes no longer publish the Rust workspace. Configuration, concurrency, and recovery are defined in `docs/repository-workflow-contract.md`.

Configure the private `delino-release-bot` app on only `oss` and `homebrew-tap`, with Contents write and Metadata read. Add its always-bypass entry to the applicable organization and repository main rulesets. Store `DELINO_RELEASE_BOT_CLIENT_ID` as an `oss` Actions variable and `DELINO_RELEASE_BOT_PRIVATE_KEY` as an `oss` Actions secret. Generate the key directly into secret storage; never commit it or retain it in logs/artifacts. Keep `CARGO_REGISTRY_TOKEN` only for projects whose planner exports `cargo_publish=true`. clibox and pnport use Cargo only to build and ship through npm and native packages without that token or a crates.io prerequisite. Go and Node projects also neither require nor receive a Cargo registry token.

- `project.mjs`: closed project/version adapters, exact version-only run journal, commit and single-tag pushes, and immutable release-source validation. `RELEASE_PROJECT=binpm RELEASE_BUMP=patch node scripts/release/project.mjs plan` is a read-only local preview requiring no credentials. The plan exports `cargo_publish` from the shared project policy; the coordinator uses it for registry credentials and Rust publication setup before version commits. Other coordinator commands are manual-main workflow operations.
- Rerun the same coordinator run after an interrupted commit, registry, or tag phase to preserve its version. Main CI failures are handled independently and do not require a coordinator retry. For a failed downstream tag workflow, rerun that exact downstream workflow independently; do not retry the coordinator solely for that failure. Existing tags must point to the recorded commit. No recovery path force-pushes, republishes all crates, or automatically overwrites public assets.

- async-commit-hook preparation synchronizes the Go version, all three package manifests and release metadata; it rejects version drift or ambiguous declarations before writing. After preparation succeeds, use the summary link to run **Release async-commit-hook** on `main` with the prepared version explicitly entered. Its default remains `dry_run=true`. Publication still requires the dispatch commit to equal the prepared tag commit; if main has advanced, its existing tag check rejects publication. Never move the tag or use another coordinator run to recover an existing prepared version. The documentation package deploys automatically with the consolidated Public Docs Cloudflare Pages build, and its installers select the latest published stable release by default so that automatic deployment is safe before release publication. Historical-source publication remains outside this integration.

- `generate-checksums.sh`: produces `SHA256SUMS` and Sigstore bundle sidecars (`*.sigstore.json`) for each published artifact.

- `update-homebrew.sh`: renders and optionally pushes Homebrew formula updates to the tap repository `main` branch (binpm, nodeup, and with-watch consume prebuilt multi-OS release artifacts). For binpm, rendered URLs must point to the expected prebuilt archive names for `darwin/amd64`, `darwin/arm64`, `linux/amd64`, and `linux/arm64`; Homebrew is not a source-build fallback channel. In non-dry-run mode, it expects `HOMEBREW_TAP_GH_TOKEN` (or `GH_TOKEN`) with write access to the tap repository and uses `RELEASE_BOT_NAME` and `RELEASE_BOT_EMAIL` resolved from the dedicated app before creating the tap commit (the existing `github-actions[bot]` identity remains the standalone-script fallback). Workflows provide a fresh tap-only installation token, and Git authentication uses an environment-backed credential helper rather than a token-bearing URL.

These scripts are designed for use by release workflows:

- `.github/workflows/release-project.yml` (manual project and SemVer selection)
- `.github/workflows/release-async-commit-hook.yml` (separate manual main publication with exact version and dry-run default)
- `.github/workflows/release-cargo-mono.yml`
- `.github/workflows/release-binpm.yml`
- `.github/workflows/release-nodeup.yml`
- `.github/workflows/release-with-watch.yml`

## Runmoor Homebrew

`runmoor-homebrew.mjs` verifies an existing public Runmoor release and renders its macOS 14+ Apple Silicon Formula. `release-runmoor-homebrew.yml` follows future Runmoor archive publication automatically. For initial publication or recovery, dispatch **Release Runmoor Homebrew** on `main` with the exact published version and source revision. The default dry run verifies signatures and tests installation in ephemeral macOS CI without updating the tap. Set `dry_run=false` to publish the identical tested Formula through the tap-only release bot and verify installation from `delinoio/tap/runmoor`. Do not create a new CLI release or modify an existing tag or asset solely to recover the Formula.

## Native Linux CLI repositories

`linux-packages.mjs` verifies an already-published release, creates nFPM packages and signed APT/DNF metadata, and resumes publication from private R2 state. Use Actions → Publish Linux CLI packages on `main`, with the exact project, version without `v`, and 40-character tag commit. The default `dry-run` performs disposable signing and the full installation matrix. Select `publish` only for the same supported release identity when recovering its package publication. Existing GitHub assets and tags are never replaced.

Build local tools with `docker build -f packaging/linux/Tools.Dockerfile -t delino-linux-package-tools .`. Generate disposable fixtures with `fixture.mjs` inside that image and use `smoke.mjs --fixture <output> --image <supported-image> --architecture amd64|arm64` to exercise package-manager install, update and remove. Production secrets are not needed. Full provisioning, key recovery, cache and Environment ownership are defined in `docs/repository-linux-packages-contract.md`.

## clibox Homebrew

The next `clibox@v<version>` release after integration publishes signed Darwin archives and automatically validates Homebrew on Intel and Apple Silicon before updating `delinoio/tap/clibox`. This is independent of `CLIBOX_NPM_PUBLISH_ENABLED`. Dry runs render the candidate Formula but never publish it or request tap credentials. The release summary reports native Homebrew tests, tap publication and public installation separately. Rerun failed jobs in the original release workflow using the exact source tag and retained artifacts; do not bump a version, move a tag or replace public assets just to recover the Formula. See `docs/packages-clibox-distribution-contract.md`.

## TaiRouter

Choose `tairouter` in **Release Project** on `main` to prepare its version and tag. The tag starts **Release TaiRouter**, which runs fixtures, builds CLI/server artifacts and the Compose archive, and publishes signed GitHub assets and `ghcr.io/delinoio/tairouter:<version>` for Linux AMD64/ARM64. Manual **Release TaiRouter** runs default to `dry_run=true`; enter the exact committed version. Publication requires the existing tag to resolve to that workflow commit. A dry run builds images locally without registry login or publication.

Before enabling npm publication, verify `@delino/tairouter` ownership and publishing authority. Configure its npm trusted publisher for `delinoio/oss`, `release-tairouter.yml`, and environment `tairouter-npm`; then set the repository variable `TAIROUTER_NPM_PUBLISH_ENABLED=true`. The default leaves npm publication disabled while retaining the checked package in GitHub assets. See the [operations contract](../../docs/servers-tairouter-operations-contract.md#publication) for gates, acceptance limits and recovery. This workflow does not start a production deployment.

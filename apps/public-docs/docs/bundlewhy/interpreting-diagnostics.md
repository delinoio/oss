# Interpreting diagnostics

:::warning Availability
bundlewhy is not yet published to npm. Version 0.1.0 is in development. This page describes the prepared 0.1.0 rules.
:::

## Evidence statuses

Every finding states how bundlewhy knows it.

| Status      | Meaning                                                                                                                        |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Confirmed   | Observed in the analysis engine's output or configuration, for the engine used in this analysis.                               |
| Inferred    | Derived by bundlewhy's own analysis. It is not an observed engine decision, and the finding lists the evidence it is based on. |
| Unavailable | The evidence could not be collected.                                                                                           |

An inferred cause is never presented as an engine decision. Treat inferred findings as a well-supported hypothesis to verify.

## Coverage

Each optimization category has a coverage state for the run.

| State          | Meaning                                                                    |
| -------------- | -------------------------------------------------------------------------- |
| Covered        | Verified detectors ran for this category.                                  |
| Not applicable | The category does not apply to the selected engine or build settings.      |
| Unavailable    | The category applies, but no evidence could be collected.                  |
| Partial        | Detectors ran on incomplete input, for example after a partial collection. |

"No findings" in a covered category means the detectors ran and found nothing. That is different from "no coverage": an unavailable or not-applicable category says nothing about your build. bundlewhy never presents missing coverage as a clean result.

Vite dead-code elimination coverage is partial when a mapped source cannot be read or its build-time text is unavailable, or when a guarded environment candidate sits in a part of the generated code that the source map does not map to any source file, including text before the first mapping of its line. An unresolved environment-variable finding may be missing because bundlewhy cannot confirm the generated expression against the original build source. Disabled minification remains not applicable, and a non-default minifier remains unavailable. For Vite, name mangling is also not applicable when the build turns mangling off (`output.minify: false`, `'dce-only'` or `{ mangle: false }`, including values a plugin sets in its `outputOptions` hook), because the name-mangling detector does not run. Rspack's environment-variable detector does not require that Vite-specific source confirmation.

For `vite/ineffective-dynamic-import`, bundlewhy checks every dynamic importer of a module against the emitted chunk graph on its own. An importer is reported when every chunk that holds it already holds the module or loads the module's chunk through static imports, and the evidence lists each requesting chunk. An importer that loads the module through a separate chunk is named as not affected. An importer the graph cannot classify (for example one in a chunk without import data, or one whose static import list names an external module that shares a file name with an emitted chunk) is named as neither reported nor ruled out, never as unaffected. bundlewhy reads the chunk imports from the finished build, after every `generateBundle` hook including those of output-only plugins; if the finished output cannot be matched to the collected chunks, the import data is dropped and no route is proven. An external module is matched to a chunk import by its module id or its `output.paths` replacement. The title follows the chunk layout the graph proves: `does not create a separate chunk` appears only when the module is folded into the chunk of its importer, while a module that has its own emitted chunk that the requester already loads through static imports is reported as `does not defer loading`, with the chunk files listed in the conditions. Findings that rest only on a Rolldown log, or on a mix of both layouts, use the `does not defer loading` title and make no claim about a separate chunk. bundlewhy does not read HTML `modulepreload` links, so it does not use them as proof. Known limits: an external that Rolldown renders under any other string that equals an emitted chunk file is read as that chunk.

For `vite/side-effect-retained`, `renderedExports` lists only the exports that Rolldown renders as chunk-level bindings. An importer bundled in the same chunk can read a re-export facade, a default re-export, a directly exported component or a forwarded value without one, and the collection holds no per-importer binding data. The condition "No export of the module is used" is therefore Met only for a module that declares no export. For a module that declares exports it is Unknown, the finding is Inferred whatever the side-effect declaration says, the title and summary state only what Rolldown reported, and the direction asks to check the importers first instead of changing side-effect declarations. The declaration is still reported in its own condition. The title does not depend on the export-use state or the declaration, so a retained module keeps one diagnostic ID. The effective-declaration guidance below applies to modules that declare no export.

For `vite/side-effect-retained`, the effective side-effect declaration follows Rolldown's precedence, highest first: a `moduleSideEffects` value that a plugin hook sets, the configured `build.rolldownOptions.treeshake.moduleSideEffects`, the package `sideEffects` field, and then Rolldown's own analysis of the code. A package `sideEffects` field can also reach the module through Vite itself and then outrank the configured option. bundlewhy cannot see that value, so when the package declares `sideEffects` and no plugin hook set a value for the module, the condition is Unknown whatever the declaration and the configured option say, and the corrective direction names the package entry to narrow or remove. A configured option decides only for a package that declares nothing: `false`, a module ID list (an empty list included, which marks no module as having side effects), a rule list and `"no-external"` decide, while `true` and a rule list without a matching rule give no verdict; a function is not evaluated and leaves the condition Unknown. A plugin hook value of `true` is not a declaration: it asks Rolldown to analyze the code and skips both the configured option and the package field, so the finding is Inferred, the "declared side-effect free" condition is Unmet, and the direction names the plugin that returns the value. An effective `false` reports the condition as Met. Rolldown may discard such a module even when its code has side effects, so the finding is Inferred from another use of the module (a side-effect import, namespace or re-export use, or an entry) and does not claim top-level side effects. An effective `"no-treeshake"` from a plugin hook, or `true` from the configured option, reports the condition as Unmet, with Confirmed status only for a module that declares no export; a module that declares exports stays Inferred. Any unrecognized plugin hook value also leaves the condition Unknown, and the direction names the unresolved source. The finding title does not depend on the declaration, so a retained module keeps one diagnostic ID when its declaration changes.

The `vite/side-effect-retained` rule also checks the final emitted code. Rolldown's `renderedLength` is measured before minification, so the diagnostic labels it intermediate Rolldown output and never treats it alone as proof that the module is shipped. For each chunk that lists the module, bundlewhy attributes the chunk's generated bytes to source files through the final chunk source map. When every listing chunk has a usable source map and none attributes a generated byte to the module (the source is listed with zero segments or is missing from the map's `sources`), minification removed the module and the rule reports nothing. When some chunk attributes generated bytes, the finding adds a Confirmed `final chunk source maps` evidence entry with the byte count. A source-map source belongs to the module only when its file, its import query and its fragment all match the module's resource identity exactly (`Comp.vue?vue&type=style` is a different resource from `Comp.vue`, and `a.js?raw#one` from `a.js?raw#two`). A source that omits the query or the fragment of the module is a different resource, never a match, even when no other module shares the file. An exact match is Confirmed only when no other collected module could own the same source: for a module with a fragment, none has the identical identity; for a module with a query and no fragment, none shares the file and query under any fragment; for a module with neither, none is backed by the same file. Final emission is unverified, never absent, when a listing chunk is unreadable or has no usable source map, when a chunk leaves generated bytes without any source mapping and attributes none to the module, when the map attributes bytes only to the same file under a different, omitted or additional query or fragment, or when an exact match is shared with sibling modules. An unverified finding is always Inferred, even when the effective declaration would otherwise confirm it, its evidence states that final emission is not verified, and its `No rendered code remains` condition is Unknown (Unmet only when final bytes are attributed to the module). Each chunk's per-source attribution is computed once and shared by size measurement and this check.

Known limits: bundlewhy does not parse a bundler's resource queries or loader chains; it splits a module identifier at the last `!` and a source path at the first `?`, and compares the remainder as text. Source maps that omit the query of a derived module therefore leave the module unverified (Inferred) instead of attributing the file's bytes to it. Pinned by the `vite_side_effect_retained_final_emission_cells` test.

Known limits of the direct-eval source scan: when the engine does not report eval, bundlewhy looks for a direct `eval(...)` call with a lexical scan, not a TypeScript parser. A method declaration named `eval` (`class C { eval(value) {} }`, `{ eval<T>(value: T): T {} }`) is skipped only when its type parameters, parameters, return type and body are followed by a class body or an object literal that the scan can place. Anything it cannot place stays an Inferred finding instead of being hidden: a signature without a body, a statement block, and a line break after `return`, `throw` or `yield` (which ends the statement before the brace). Two shapes keep their finding even though they are method declarations: a comparison whose `<` touches its left operand (`a<b>{ eval(x) {} }` reads as a type-argument list) and a class field that ends in `?` or `!` on its own line before the method. A class expression in the heritage clause (`class C extends class {} { eval(value) {} }`) does not hide the outer class body. A multiline conditional return type (`T extends` followed by a line break) stays part of the signature. A class field that ends in a postfix `++` or `--` completes the field before a method on the next line. An object literal in a JSX attribute container (`<Widget value={{ eval(input) {} }} />`) is recognized. A `<` after `eval` starts type arguments only when it touches the name: `eval<T>(code)` is reported as a generic call, while `eval < value > (code)` is a comparison chain and is not (a TypeScript generic call written `eval <T>(code)` with a space is therefore not reported, and a comparison written without spaces, `eval<value>(code)`, keeps its finding). A real `eval(code)` call elsewhere in the same module is still reported at its own line and column. A `var eval` inside a TypeScript `namespace` or `module` body shadows calls only within that body, including when the namespace name spells characters with Unicode escapes (`namespace \u004e { var eval = helper; }`), judged by the ECMAScript `ID_Start` and `ID_Continue` properties (so `namespace \u037a {}` is a declaration); a malformed escape does not make a namespace, so such a `var` falls back to the whole-source boundary and can hide a call elsewhere.

Known limits of the unresolved environment condition scan: bundlewhy reads the generated code with a lexical scan, not a parser, to prove that an environment read guards a branch. It decides whether `await(` is the unary operator or a call from the surrounding code: it is an operator in a module and inside an `async` function, arrow or method body. The initializer of a class field is evaluated as a separate non-async function, so `await(` in it is a call even when the class sits inside an `async` function; a computed key, a method body and an `async` function nested in the initializer keep their own context. A concise arrow body (`async () => value`) ends at a line break, as automatic semicolon insertion does, unless the next line continues the expression. `yield` is treated like `return` and `throw`: a line break after it ends the statement, so a later `await(` on the next line is a call, except when the next line starts with a slash, which keeps the arrow body open because the scan cannot tell a division from a regular expression without a parse. When a case cannot be decided, the finding is omitted or stays Inferred instead of being invented.

Inlining and constant folding currently have no coverage for either engine. Neither engine exposes those decisions, and bundlewhy has no verified detector for them, so those categories are always shown as unavailable.

## Conditions

Each rule lists the conditions it checks. Every condition has an outcome:

- **Met**: the condition holds in this build.
- **Unmet**: the condition does not hold.
- **Unknown**: bundlewhy could not decide, usually because evidence was unavailable.

## Locations

Locations use your original source positions when a source map maps them to verified build source text. When a chunk has no usable source map, bundlewhy falls back to generated chunk positions, marks source attribution for that chunk unavailable and reports `BW_SOURCE_MAP_MISSING`. In a Vite build, chunks that contain only bundler-owned virtual helpers, such as Vite's preload helper and the Rolldown runtime, have no original source to attribute and are not reported or counted against coverage. Rspack chunks always keep the source-map requirement. A mapped source without verifiable build text also uses a generated location and snippet. The source viewer identifies when the analyzed source revision cannot be verified; it does not show a later live read as analyzed code. Snippets are short excerpts; the UI can show the full source file when a verified build snapshot was stored.

## Dependency paths

Dependency paths show up to three of the shortest static importer chains from an entry point to the module. Use them to find which import brings a module into the build.

## Export usage paths

Rspack diagnostics for a module can include export usage paths. They answer a narrower question than a dependency path: which export of another module depends on an export of this module, and which export depends on that one, going back toward your entry code.

- Each edge in a chain is an export dependency that Rspack reported during the diagnostic build, tagged **Observed by Rspack**. It shows the consuming module and export, the providing module and export, the Rspack dependency ID and the location in the consuming module when Rspack provided them.
- The order and the choice of chains are **derived by bundlewhy**: it follows Rspack's edges from the diagnostic module toward its consumers, shortest chains first, and lists at most five chains of at most 24 edges.
- A named export appears as `export <name>`. "Module or namespace scope (no named export)" means Rspack did not name one export, for example for a namespace import or top-level module code. It is not evidence of a function call.
- A chain ends with one of four notes: no earlier edge was reported (this does not prove that no other consumer exists), a cycle (the first edge returns to an export already in the chain), a limit, or **Chain start not confirmed**. The last note appears when Rspack reported edges that bundlewhy could not use, and one of them may be an earlier edge into the first export, because an endpoint is not a module bundlewhy can identify (for example a concatenated module container) or an export reference bundlewhy can read. The chain may continue beyond that point, and the section states how many edges were left out. A **Truncated** marker names the first limit reached when chains were left out.
- A chain does not show that code ran, that code can be removed or how many bytes a change would save. Missing edges are never filled in.

When Rspack does not provide the data, the section says export usage is unavailable for that diagnostic and gives one of a fixed set of reasons: the Rspack version has no `RsdoctorPlugin`, the project already configures one, the project sets `plugins` to something other than a list (bundlewhy then passes it to Rspack unchanged), the plugin's internal API changed or failed (in which case bundlewhy repeats the diagnostic build without the plugin, in a new process that loads your configuration and its imports from scratch), Rspack did not deliver the graph, Rspack reported no edge for this module (for example a module loaded only through `import()`), or edges that involve modules bundlewhy could not identify (for example concatenated module containers) or export references it could not read were not used. Reasons never quote error messages or your source code. Other diagnostics and the module dependency paths are not affected. bundlewhy adds an observation-only `RsdoctorPlugin` to the diagnostic build and lists it among the collection overrides when the final build used it. Reports saved by earlier versions have no export usage section. Vite diagnostics never have one.

## Corrective direction

Each diagnostic suggests a direction for a fix, together with the safety conditions that must hold before you apply it, for example that a module really has no side effects. bundlewhy does not apply fixes and does not verify that a change keeps your application correct.

## Chunk sizes

For each emitted JavaScript chunk, bundlewhy measures:

- Raw bytes.
- Gzip bytes (level 9).
- Brotli bytes (quality 11).
- Mapped source bytes, where a source map supports attribution. Each generated byte is attributed to at most one source, and unmapped bytes are shown separately.

These are measurements, not savings. bundlewhy never estimates how many bytes a fix would save.

## Retained code is not automatically a defect

Code that a bundler keeps is often kept for a correct reason, such as a real side effect. A diagnostic explains why an optimization did not apply; it does not claim that the result is wrong. Review the conditions and the safety conditions before you change anything.

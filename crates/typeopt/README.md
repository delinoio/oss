# typeopt

Experimental type-aware size optimization in two stages. Stage 1 runs before bundling: the CLI analyzes a single application project with TypeScript type and symbol information plus runtime evidence from source, control flow and uses. It applies eighteen conservative optimization passes, accepts a transformation only when it makes the emitted ESM strictly smaller, and emits ESM for an existing bundler. Stage 2 runs after bundling: it analyzes every JavaScript chunk of the bundler output, including library code, as one closed program and applies the passes whose proofs do not depend on static types (see [Stage 2: bundle mode](#stage-2-bundle-mode)). typeopt never runs your application or bundler.

## Install

Use the repository's Rust toolchain and build from source:

```sh
cargo install --locked --path crates/typeopt
```

The supported native validation targets are macOS arm64 and Linux x64. Source builds download dependencies during installation. Subsequent analysis is local, with no network access, telemetry, persistent cache or user-code execution.

## Use

```sh
typeopt --project ./tsconfig.json --entry ./src/main.tsx --out-dir ./optimized-new
typeopt --project ./tsconfig.json --entry ./src/main.tsx ./src/worker.ts --check
typeopt --project ./tsconfig.json --entry ./src/main.tsx --out-dir ./optimized-new --disable-pass call-inlining --disable-pass property-ambiguation
```

Paths are relative to the current directory. The output parent must exist and the destination must not exist, including an empty directory or symlink. Use a new output path for each run. Inputs are never rewritten. Ctrl+C cancels the operation and removes operation-owned staging files. Exit codes are 0 for success, 1 for analysis/output failure, 2 for invalid CLI arguments and 130 for cancellation handled by the CLI.

All passes are enabled by default. `--disable-pass <id>` excludes one pass and can repeat; an unknown ID is an invalid CLI argument (exit code 2). A disabled pass never runs, including as cleanup inside another pass's transformation; such a transformation is skipped with reason `requires_disabled_pass`. `--check` performs the same analysis, in-memory transformation and size decisions as output mode and prints the JSON report without emitting files. `--verbose` adds compiler diagnostic messages with source-derived arguments replaced by `<redacted>`; `--help` and `--version` describe the CLI. Logs go to stderr and do not include source bodies or environment values. Set `NO_COLOR=1` to disable ANSI colors.

Call inlining accepts function-valued variable bindings only in standalone variable statements. It skips loop-header bindings to preserve the loop's condition and body effects.

Shared rules apply to every pass. TypeScript types only nominate candidates; an annotation never proves a closed call graph, an immutable value, an impossible branch or an intact built-in. Public entry exports, symbols referenced from application JavaScript, external declarations, module namespace objects, unknown calls, unresolved keys, reflection, serialization, prototype mutation, decorators and declaration merging are boundaries. Evaluation order, effects, exceptions (including temporal dead zones), property descriptors, object and function identity and observable names and arity are preserved. When an obligation cannot be proven, the code is preserved and the report records a reason.

## Pipeline

Each round rebuilds the program from the current in-memory text, recomputes every fact, plans candidates for every enabled pass in a fixed order and evaluates each candidate bundle, including its required cleanup, by transpiling the affected modules before and after with equal emitter settings. A bundle is accepted only when the total emitted ESM byte count strictly decreases; cloned code, new bindings and retained effects count, and source maps and reports do not. Rejected candidates never change accepted state. Accepted edits are type-checked; a bundle that introduces type errors is rolled back (reason `recheck_failed`) and the rest are kept. Rounds repeat until no reduction is accepted; property passes run once afterward. Syntax errors in transformed code and compiler failures fail the operation.

When a transformation removes the last runtime use of an import, TypeScript would elide the import and skip or reorder that module's initialization. The pipeline keeps the dependency with a bare `import "specifier";`, unless `residual-dependency-removal` is enabled and the module and its imports are proven to initialize without effects.

## Stage 2: bundle mode

```sh
vite build --outDir ./dist
typeopt --bundle ./dist --out-dir ./dist-optimized
typeopt --bundle ./dist --check --bundle-exclude monaco
typeopt --bundle ./dist --out-dir ./dist-optimized --minify
```

Stage 2 optimizes the output of a bundler rather than the application sources. Stage 1 cannot see dependencies: `node_modules` is external, so every value that reaches a library (for example component props that reach React) is a boundary, and the bundler's own tree shaking and minification already remove most of what stage 1 removes. In the bundle, library code is part of the program, and the size gate measures the shipped chunk text itself. Run stage 2 on any Vite or Rollup ESM output directory, with or without stage 1.

- **Program.** Every `.js` and `.mjs` file under the directory is a module of one program with the standard DOM libraries and no `@types` packages. Static imports and literal dynamic imports in the parsed chunks link them. A chunk that no other chunk imports (HTML entries, workers) is an entry, and its exports are public. Script URLs in `.html` and `.htm` pages resolve with URL semantics against the `<base href>` parsed before each script, with character references (including legacy forms without `;`) decoded; chunks that inline HTML scripts, event handlers or `javascript:` URLs import (JavaScript escapes decoded) are entries, and an import map, an inline import that cannot be resolved, an event handler or a `javascript:` URL in a navigating attribute (`href`, `action`, `formaction`, `src` of a frame, `data` of an object) with a character reference typeopt cannot decode or a computed `import(…)` in any chunk makes every chunk an entry; a chunk that imports a module outside the directory, including a package specifier when no page defines an import map, is rejected. If a chunk contains a literal dynamic import of a package specifier, typeopt keeps the chunk unchanged as a boundary. It leaves the package specifier unresolved in the published bundle and logs a warning with the chunk and specifier. Every chunk that the boundary can import stays frozen. A chunk is optimized only when it is known to run as an ES module: it is an `.mjs` file, has ESM statements or `import.meta`, another chunk imports it or an HTML page loads it with `<script type="module">`. Classic scripts (for example AMD loaders, any chunk that calls `importScripts` or that `importScripts` loads, and any chunk an HTML page loads with a classic `<script>`, even if a module also imports it) are never edited by a pass, because they share top-level bindings through the global scope. `--bundle-exclude <text>` keeps every chunk whose path contains the text byte-for-byte unchanged as a pinned boundary; use it for very large vendor chunks to bound time and memory. A chunk is also an unchecked boundary that no pass edits when its syntax needs it: a `with` statement; the global `eval` used as a value (a direct call or an alias such as `const e = eval`, `globalThis.eval`, or a destructuring such as `const { importScripts: load } = self`); and `importScripts` called through any callee form (`importScripts(…)`, `self.importScripts(…)`, `globalThis.importScripts(…)`, `self["importScripts"](…)`, parenthesized forms) or used as a value that can alias it. A chunk that a worker loads through any of these callee forms is a classic script. Mentions that run no code are not boundaries: `typeof eval`, `typeof (eval)`, `typeof importScripts`, `typeof self.importScripts`, property names such as `obj.eval`, property keys such as `{ eval: 1 }` and module export names such as `import { eval as helper }` or `export { helper as eval }`. At debug level the optimizer logs the rule (`dynamic-package-import`, `excluded-or-classic-script`, `with-statement`, `eval-reference`, `import-scripts-call`, `import-scripts-reference` or `boundary-reachable`) that made each chunk a boundary. Classic, eval, with and importScripts boundaries are rewritten and renamed during publication so they import renamed copies and keep one instance of each module. Dynamic package boundaries are pinned: they and every chunk they can import retain their original names and content. Chunks matched by `--bundle-exclude` are pinned instead: they keep importing the original names of what they reach, so every chunk that an excluded chunk can import (statically or through a literal dynamic `import()`, transitively, boundary chunks included) is frozen as well: it is not edited or renamed, which keeps one instance of each module and keeps `modulepreload` links of a page consistent with the graph its unchanged entry chunk loads. A chunk in another directory that has the same file name as a frozen chunk is frozen too, because references name only the file name and an edited copy would keep the old content hash. The report lists these chunks in `frozen_chunks` with the reason `boundary_reachable` and the excluded chunk that reaches them; the log names each excluded chunk and warns when an unchanged HTML entry chunk freezes the chunks it imports, even when an earlier excluded chunk in path order reaches the same chunks and is the one the report names. Because frozen chunks are never edited, `size.after` and `size.saved` describe only chunks that a page can load as optimized. A large excluded chunk can therefore freeze much of a bundle.
- **Passes.** Bundled JavaScript is not type-checked, so an inferred or JSDoc type can be wrong, not only imprecise. Bundle mode therefore offers only the passes whose proofs rest on syntax, references, points-to flows and runtime facts: `property-shortening`, `property-disambiguation`, `property-ambiguation`, `call-inlining`, `signature-reduction`, `type-directed-control-flow`, `primitive-operation-simplification` and `residual-dependency-removal`. The other passes use static types to bound where class instances and values flow; a library that reads modules off a container with runtime-parsed keys (for example template strings such as `"{{company.name}}"`) defeats that bound. `--disable-pass` removes passes from this set. Every identifier-like token in a string or template literal counts as a mentioned name, because bundled code can parse strings into member lookups. The intrinsic patch scan treats a write to the global object under a computed key as a possible replacement of any global unless the key is a symbol (`Symbol(...)`, `Symbol.for(...)`, or a never-written binding of one, while `Symbol` itself is unpatched) or a string with a known literal start (a template head, `"literal" + x`, or a never-written binding of one), which can only name globals with that start. A reflection helper bound once to `Object.assign`, `Object.defineProperty` or another writer and only ever called is analysed like the direct calls; any other use keeps the conservative record. Unchecked JavaScript has no type errors to recheck, so every transformation rests on its own proof; semantic diagnostics that a chunk already has (for example through `// @ts-check` with inaccurate JSDoc) do not block optimization, and only diagnostics that an edit adds fail the recheck. Candidates are not parsed one by one; the recheck after each round rejects syntax errors, including TypeScript-only syntax in a chunk, and rolls the responsible bundle back (`recheck_failed`).
- **Output.** The output directory is a copy of the input with edited chunks replaced; publication fails when the input directory changed during analysis. Source maps of edited chunks (found through `sourceMappingURL`, inline `data:` URLs included, or next to the chunk for hidden maps) are composed with the edits; an explicit `sourceMappingURL` of an edited chunk that cannot be composed (remote, missing or outside the output) is removed, because it would describe the old code; inserted code maps to the original range it replaced. An edited chunk named with a Vite or Rollup content hash (`<name>-<hash>.js` or `<name>.<hash>.js`; also `.mjs`, `.cjs`, `.css`, `.json` and `.webmanifest` assets, where the hash has 8 base64url characters including a digit, an uppercase letter, `-` or `_`), and every hashed chunk that references a renamed chunk, gets a new hash, and every reference in HTML, JavaScript, CSS, JSON, source maps and web manifests follows. A new hash covers the final content of the chunk and of every renamed chunk it reaches. Only reference positions are rewritten: the name must follow `/`, a quote, `(` or `=` (whitespace may separate it from `=` or from the `(` of a CSS `url(` token that starts its own identifier, so `myurl(` and `--url(` do not count), and precede a quote, `)`, `?`, `#`, whitespace, `>`, `,` or `.map`. Otherwise a browser could combine an edited chunk with a stale cached copy of a chunk it depends on. A name that some reference spells with URL or HTML escapes (`%2D`, `&#45;`) keeps its original file, and every renamed file that original references, next to the renamed one, so that reference still loads the complete original graph; pinned chunks (excluded, and what they import) are never rewritten or renamed and keep the originals that they mention without importing them (for example in a string) the same way. A service worker precache manifest in the Workbox form `{url:"…",revision:"…"}` gets a new revision of the same length for every listed file whose published content changed (for example `index.html` with rewritten chunk names), so the worker does not keep serving stale cached HTML; renamed chunks are listed under their new names. The report's `size.retained` counts the code bytes of such kept originals, which are published in addition to the optimized graph that `size.after` describes. `--keep-chunk-names` disables renaming. `--minify` (opt-in) minifies every chunk typeopt edited with SWC and keeps the result only when it compresses smaller (Brotli quality 11 shrinks, gzip level 9 does not grow); unedited chunks stay as the bundler wrote them, function and class names (including names inferred from bindings such as `const f = () => {}` and from object literal keys) and parameter lists stay so `name` and `length` remain observable, legal comments stay (also those attached to removed code), source maps are composed with SWC's map, and the report's `size.minified` counts the removed code bytes (included in `size.after` and `size.saved`). Bundles with symbolic links and HTML pages with Subresource Integrity attributes or a Content Security Policy with hash sources are rejected before analysis, also with `--check`; compute integrity after typeopt. The report (schema v1) goes to standard output; its `size.metric` is `chunk_text_bytes`, the chunk text without its trailing source map comment, which the size gate measures as well (source maps never count as size); `passes.disabled` lists the passes bundle mode does not offer.
  Legal comments (`/*!`, `@license`, `@preserve`) remain attached to the published chunk, including comments attached to code removed by compression. Typeopt verifies emitted legal-comment identity by kind, exact text, count, and source order; if it cannot verify the notices, it keeps the chunk unminified.

- **Cost.** The size gate measures edited chunk text without parsing each candidate. Each round rebuilds the program, and releasing the previous program frees its parses, but multi-megabyte bundles still need several gigabytes; exclude large vendor chunks when memory or time is limited.

Bundle mode is as conservative as stage 1, but bundled libraries use more dynamic patterns than application TypeScript. Always run your application behavior tests against the optimized directory.

## Output and compatibility

- Numbered `.js` files and adjacent `.js.map` files contain ESM and maps back to original source text. Code that is inserted, deleted, inlined or moved maps to the original range it replaced, across every round.
- `modules.json` contains `schema_version: 0`, a `modules` array and an `inputs` array. Each module has `source`, `source_sha256` (SHA-256 of the analyzed source text), `output`, `source_map` and `kind` (`optimized`, `preserved` or `passthrough`). `optimized` means any accepted runtime transformation, with or without renamed properties. `inputs` lists the tsconfig and extended configuration files (`configuration`) and every other file the compiler read, such as declarations, dependency modules and module-resolution metadata like `package.json` (`dependency`), with their SHA-256. It also lists resolution candidates the compiler probed and found missing (`absent`, no `sha256`), such as `dep.ts` when `./dep` resolved to `dep.tsx`; they follow the positive inputs and are sorted by path, and `bundled:` declarations are never listed. A candidate that appeared while the compiler was analyzing is listed too, so the output is rejected. A candidate that exists with the wrong kind for its probe, such as a directory named `dep.ts` probed as a file, is listed as `mismatch` (no `sha256`) with `becomes` set to `file` or `directory`, the kind that would satisfy the probe; it follows the `absent` entries' ordering and is stale only once the path becomes that kind, since the output remains valid while it keeps its wrong kind. A path that appears later, such as a newly added file that would shadow a resolved path, or the target of a recorded dangling symlink, makes the output stale. Directory listings the compiler enumerates are not tracked. Consumers must reject the output when any module or input changed, any `absent` path resolves to a file or directory, or any `mismatch` path becomes its `becomes` kind (symlinks are followed), because optimized modules can depend on facts from any of them. The `absent` and `mismatch` kinds are additive within schema version 0: an older adapter rejects the digest-less entry as an invalid input snapshot, so regenerate the output with the matching CLI. Source paths are absolute; optimized output paths are relative to the output directory. JavaScript passthrough entries refer to original files and have no new map.
- `properties.json` contains `schema_version: 0` and `properties`. Each record identifies a property group, original source/name, final name, occurrence count and optional preservation reason. It describes property transformations only.
- `report.json` uses `schema_version: 1`. It keeps the v0 statistics (tool and compiler versions, files, object regions, properties, renamed properties, changed occurrences and preservation reasons) and adds `passes.enabled`/`passes.disabled`, `rounds`, `size` (emitted ESM bytes before and after), `pass_summary` (applied bundles, cleanup participation, skipped counts and reason codes per pass), `transformations` (each accepted bundle with its primary pass, cleanup passes, source location and measured byte change) and `skipped` (pass, location and reason). Savings belong to the whole bundle and are never split among its passes. Zero accepted transformations is a valid conservative result, not evidence of application size reduction.

Elapsed time and peak resident memory are measured, without a ceiling. Each round rebuilds and rechecks the program. Stage 1 transpiles each candidate for size evaluation; bundle mode derives the edited chunk size from the edit lengths and rescans static imports only when an edit touches import syntax or the trailing source map comment, without copying the chunk per candidate. Whole-program runs therefore need more time and memory than a single type check. The compiler uses one checker and releases each program's allocation region after its last analysis, recheck or emit operation. Compiler-specific memory settings from the previous backend no longer apply. Performance measurements from that backend do not establish tsrs performance.

Code, mappings and reports are deterministic for identical source paths, contents, configuration, options and tool version, except the `measurements` (elapsed time and peak RSS). The interfaces are experimental. Report v1 replaces v0; adapters must reject unknown schema versions.

## Safety and supported input

Supply explicit application entries and one tsconfig. Workspace imports and declaration files use the compiler's resolver. Project-reference orchestration, CommonJS output, compiler plugins/content mappers, `eval` (including aliases), `with`, `import x = require()`, `export =`, `noCheck`, `noResolve`, `outFile`, declaration-only output and preserved JSX are rejected. Set an ESM module mode and `jsx: "react-jsx"` or `"react"` for TSX. Syntax and type errors fail before publication. Unsupported upstream settings produce compiler diagnostics; they are not silently reinterpreted.

TypeScript modules with a leading `// @ts-nocheck` comment disable the semantic recheck that backs every transformation, so they are treated like JavaScript: they are not transformed and their references are boundaries. `@ts-ignore` and `@ts-expect-error` suppress recheck errors on single lines; every transformation still requires its own proof, but the recheck cannot serve as a second check on those lines.

Bundle mode has its own input rules; see [Stage 2: bundle mode](#stage-2-bundle-mode). The stage 1 CLI owns emission controls: it overrides `noEmit`, declaration/incremental/composite output, `rootDir`, output locations and source-map output settings. It does not change the input tsconfig. JavaScript and node_modules are not transformed; imported JSON and other assets stay in the original project.

Stage 1 preserves intrinsic calls when a runtime import may load external code that patches built-ins. Explicit `node:` imports, Node 24 bare core imports with ambient declarations, and resolved JSON files are exempt. The bare core names match Node 24's host inventory; prefix-only names such as `node:test` are excluded. Resolved userland packages and polyfills, unknown or computed specifiers, and a `.json` suffix without a JSON resolution still report `intrinsic_may_be_replaced`. The scan also covers JavaScript `module.require` and direct aliases of loaders created with `createRequire` from `node:module` or `module`.

This conservative boundary is intentional: types alone do not prove transformation safety. There is no aggressive mode or trusted-declaration opt-out. Always run application behavior tests after bundling. This is an application optimizer, not a library/declaration compatibility tool. To roll back one optimization, rerun into a new directory with `--disable-pass <id>`; to roll back adoption, restore the original build inputs and configuration.

## Vite example

Copy `examples/vite/adapter.mjs` into your build tooling, then add it to the existing Vite configuration:

```js
import { typeopt } from './adapter.mjs';
export default {
  plugins: [typeopt('./optimized-new')],
};
```

Keep existing React/asset plugins and aliases. At build start the example validates every module digest and every recorded input (configuration and dependency files) and fails when any changed, because an optimized module can depend on all of them. It substitutes only `optimized` modules, including modules changed without property renaming. It leaves preserved TS modules to Vite so unrelated modules retain the baseline transpilation. It loads optimized code under original module identities so relative imports, workspace aliases and assets retain their original context. Queries such as `?raw` are handled by the original loaders. Maps compose through Vite. Run Vite and application tests yourself; typeopt never launches them. Remove the adapter to roll back adoption.

This adapter is an example, not a published plugin. Its test environment pins Vite 5.0.12 to match the benchmark. That old benchmark pin is not a recommendation or a security remediation; audit and update your application's dependencies independently.

```sh
node crates/typeopt/benchmark/build.mjs /absolute/excalidraw /absolute/original-build
typeopt-existing --project /absolute/excalidraw/tsconfig.json --entry /absolute/excalidraw/excalidraw-app/index.tsx --out-dir /absolute/existing-new

```

`typeopt-existing` is the CLI built from `existing_typeopt_revision` in `pin.json`, the property-only optimizer that the extended passes are compared against. Reports do not identify the optimizer's source revision, so each optimized build names the repository checkout its typeopt binary was built from. The build helper records that checkout's `HEAD` and whether `crates/typeopt` or `Cargo.lock` has uncommitted changes. `measure.mjs` requires clean checkouts, the existing build at `existing_typeopt_revision` and the extended build at a different revision. The recorded checkout is an attestation by the operator; build each binary from the checkout you name.

The build helper fails unless the checkout `HEAD` and `yarn.lock` SHA-256 match `pin.json` and the worktree, including untracked non-ignored files, equals the pinned revision plus exactly the compatibility patch. Keep build and optimizer outputs outside the checkout. It also fails when the installed Vite version differs from the pin, when `NODE_ENV` or a variable with the Vite env prefix is set but not pinned, or when an ignored `.env*` file exists. It applies the pinned environment to every build and records the verified revision, source tree, lockfile hash, Vite version, effective build environment, the optimizer's report schema, tool version and disabled passes, elapsed time and peak RSS in `typeopt-build.json` (schema 1). Build the pinned application once with its original inputs, then run typeopt with the application entry and build again with the example adapter. Use the same environment, Vite settings, minifier and source-map settings. Keep outputs in separate directories. Compare:

```sh
node crates/typeopt/benchmark/measure.mjs /absolute/original-build /absolute/existing-build /absolute/extended-build
```

The command sums every production `.js`, `.mjs` and `.cjs` file of each build, excluding source maps. It requires the pinned Node, which also fixes the bundled zlib and Brotli, and uses gzip level 9 and Brotli quality 11. It fails unless all `typeopt-build.json` files have identical provenance (revision, source tree, lockfile, Node, Vite, mode, source maps and environment), the original build is not optimized, the existing build used report v0 and the extended build report v1, no local loading reference of a build (HTML module `script` `src`, `modulepreload` `href`, static `import`/`export ... from` specifier or literal `import()` argument, quoted or a template without substitutions, with JavaScript escapes decoded, relative, root-relative or, in HTML, document-relative without a prefix) names a script file that is missing from that same build, whether or not another build emits it (quoted `.js` strings that are not loading references, remote URLs and bare specifiers are ignored, and `broken_chunk_references` lists `source file -> reference` per build), and the extended build's raw, gzip and Brotli totals are each strictly smaller than both other builds. Asset sets may differ, because residual-dependency-removal can remove chunks; the output lists added and removed logical assets (file paths without the Vite content hash) against each baseline. A two-argument form compares an original and one optimized build. Record the result with source revision, exact commands, tool versions, execution time and peak RSS. Fixture results do not substitute for application acceptance. `cargo test -p typeopt --test benchmark_measure` exercises this validation with synthetic builds and skips itself when Node is not the pinned version.

Install browser tooling with `pnpm --dir crates/typeopt/benchmark install --ignore-workspace --frozen-lockfile` and `pnpm --dir crates/typeopt/benchmark exec playwright install chromium`. Serve each build on a separate loopback HTTP port, then run:

```sh
node crates/typeopt/benchmark/browser.mjs http://127.0.0.1:48180 /absolute/original-browser
node crates/typeopt/benchmark/browser.mjs http://127.0.0.1:48181 /absolute/existing-browser
node crates/typeopt/benchmark/browser.mjs http://127.0.0.1:48182 /absolute/extended-browser
```

`browser.mjs` fails unless Node, Playwright and Chromium match `pin.json`, and it requires a new evidence directory. Its `checks_passed` covers only that run. Browser acceptance passes only when `compare-browser.mjs` finds identical normalized observations and PNG/SVG export summaries in both runs; it lists any mismatched checks. The harness normalizes sketch seeds in the imported scene so PNG pixels and SVG geometry can be compared despite time-seeded drawing roughness. It uses the application's download/file-input fallback; it does not validate native OS file pickers. It retains actual scene, PNG and SVG downloads for inspection. Run the same Chromium checks on all three builds: draw shapes/freehand, add/edit text, move/resize, undo/redo, save/reload/import a scene, and export PNG/SVG. Compare scene data and exported results.

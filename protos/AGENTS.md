### Instructions for `protos/`

- Follow the root `AGENTS.md`, the owning project index, and the relevant domain contract before changing a shared API.
- `protos/delibase/v1` is owned by project `delibase`; its source of truth is the versioned `delibase.v1` Protobuf contract.
- Generate Connect-compatible Go and TypeScript artifacts from the root source. Never edit generated output as a second source of truth.
- Checked-in Go artifacts live under `protos/delibase/gen/go`; protobuf-es v2 TypeScript artifacts live under `protos/delibase/gen/ts` and are exported by the workspace package `@delinoio/delibase-connect`.
- The six stable services are `AccountService`, `OrganizationService`, `TeamService`, `CatalogService`, `BillingService`, and `UsageService`.
- Preserve released `delibase.v1` additively. Breaking changes require a new API version and synchronized app/server migration docs.
- Keep UUID v7, signed-int64 money/usage, opaque cursors, Logto user/M2M access-token metadata without raw client secrets, the redacted `x-delibase-forwarded-user-token` forwarded-user context, authenticated invitation bearer-token access without pre-existing membership, caller/operation-scoped idempotency, and stable enum error details aligned with the server and app contracts.
- Keep distinct stable idempotency operations for invitation acceptance and revocation; invitation creation does not carry idempotency fields.
- Keep bounded background usage inside the existing `BillingService` and `UsageService`; never add a seventh service. Human create/revoke and M2M reserve/commit/release/resource-deletion notification use distinct caller-and-operation-scoped idempotency values. Authorized usage is M2M-only, must not require or store a forwarded user bearer, and binds the authenticated service identity into its replay digest; commit/release additionally bind the reservation ID, while resource deletion binds the expected revision.
- Keep `BackgroundUsagePurpose` closed to `REALQA_STORAGE` in v1 with no Deck value, `BackgroundUsagePeriod` closed to `UTC_DAY`, and authorization status closed to `ACTIVE`, `REVOKED`, `ACCESS_LOST`, `RESOURCE_DELETED`, and `OWNER_DELETED`. Preserve UUID v7 owner/resource/service/meter bindings, per-period limits, revisions/timestamps, opaque pagination, and stable substitution/access/status/limit/replay error reasons additively.
- Keep public catalog meter responses sufficient for human authorization creation by exposing stable service identity targets and safe display names, never Logto client identifiers or credentials. Reserve accepts only the current or immediately preceding canonical UTC day according to server time; commit/release use the period stored with the reservation.
- Preserve the stable member-active-reservations reason for organization-member removal and self-leave blocked by held usage.
- Run Protobuf lint, breaking checks, generation, generated Go formatting/vet/tests, and the consuming app type checks when implementation exists.
- Use root `pnpm generate:proto` to refresh the checked-in `delibase.v1` descriptor, generate both runtimes, and build the workspace package `dist`; use `pnpm check:proto` for Buf lint, the descriptor compatibility check, and a clean regeneration diff that includes the descriptor. Local checks compare against the checked-in descriptor before regeneration; CI uses the immutable descriptor from the pull request base or pre-push commit once that descriptor exists there. TypeScript checks use `pnpm --filter @delinoio/delibase-connect typecheck`; Go checks include `go test ./protos/delibase/...` and `go vet ./protos/delibase/...`. CI runs all four validation commands in the change-scoped `proto-delibase` job.
- Changes require synchronized updates to `docs/project-delibase.md`, `docs/protos-delibase-api-contract.md`, `docs/servers-delibase-server-foundation.md`, `docs/apps-delidev-app-foundation.md`, and affected `AGENTS.md` files.

### DevHud Feature Contracts

- `protos/devhud-deck/v1` is the planned authoritative `devhud.deck.v1` source owned by project `devhud`. Generate reproducible Go and protobuf-es v2 TypeScript artifacts under `protos/devhud-deck/gen/go` and `protos/devhud-deck/gen/ts`; the future workspace package is `@delinoio/devhud-deck-connect`.
- Deck exposes exactly `DeckViewService`, `DeckIntegrationService`, and `DeckDeviceService` with the RPCs listed in `docs/protos-devhud-deck-api-contract.md`, including authenticated `ResolveNotificationEvent` and idempotent `DeckViewService.DeleteFeatureData` for either an authorized owner request or an exact delibase M2M account/organization-deletion trigger. Device registration returns a bounded lease plus a single-registration revocation grant; idempotent unregister accepts either matching-account authentication or only that grant so an OS-vault cleanup tombstone can finish after logout/account switch before later registration. Notification resolution requires the matching active registration and current authorization/detail opt-in and never refreshes provider data. The generated client may be consumed by authenticated Deck code under `apps/devhud`, by `apps/delidev-app` only for `DeckIntegrationService`, and by `servers/delibase` only for the service-authenticated deletion trigger. Keep the v1 view kind closed to `GITHUB_PULL_REQUESTS`, use UUID v7/opaque cursors/revisions/idempotency/closed enums, and never transport remote UI, provider tokens, raw auth metadata, or client-authoritative roles/permissions/prices.
- `protos/devhud-realqa/v1` is the planned authoritative `devhud.realqa.v1` source owned by project `devhud`. Generate reproducible Go and protobuf-es v2 TypeScript artifacts under `protos/devhud-realqa/gen/go` and `protos/devhud-realqa/gen/ts`; the future workspace package is `@delinoio/devhud-realqa-connect`.
- RealQA exposes exactly `RealQAPresetService`, `RealQATrackerService`, and `RealQASubmissionService` with the RPCs listed in `docs/protos-devhud-realqa-api-contract.md`, including authenticated opaque-cursor `ListSubmissions` for only caller-authorized retained submission/asset references and idempotent `DeleteFeatureData` for either an authorized owner request or an exact delibase M2M account/organization-deletion trigger. `CreateImageUpload` returns only a signed PUT at the exact RealQA asset origin, never an R2 S3 endpoint. The generated client is otherwise consumed only by `servers/devhud-realqa` and authenticated RealQA code under `apps/devhud`; DeliDev has no RealQA client. Keep the v1 tracker closed to GitHub.com; use UUID v7/opaque cursors/revisions/idempotency/closed enums; enforce typed size/body/asset/billing errors; and never transport provider/R2 secrets, raw originals, submitted title/body/URL/DOM data, arbitrary page HTML/text, public asset indexes, or remote UI/code.
- Human calls to both APIs require feature-audience user tokens plus sensitive memory-only delibase-audience forwarded bearer metadata. Deck `UnregisterDevice` alone may instead accept its single-registration revocation grant, retained only in the OS-vault cleanup tombstone, and only `DeleteFeatureData` additionally accepts the feature-specific delibase M2M identity for a typed lifecycle trigger. Generated clients must otherwise keep credentials out of messages, logs, errors, caches, persistence, and diagnostics. Preserve released v1 contracts additively; breaking changes require a v2 contract and synchronized migration docs.
- Once sources exist, canonical checks are root `pnpm generate:proto` and `pnpm check:proto`, `go test`/`go vet` for each `./protos/devhud-*/...` root, and `pnpm --filter @delinoio/devhud-deck-connect typecheck` plus `pnpm --filter @delinoio/devhud-realqa-connect typecheck`.
- Generation/fixture checks must not publish clients, deploy the future origins, register either separate GitHub App, configure DNS/R2, publish server images/extensions/widgets, or activate the disabled production-facing catalog records.
- Changes require synchronized updates to `docs/project-devhud.md`, both affected app/server/proto contracts, `docs/README.md`, `README.md`, and root/apps/servers/protos `AGENTS.md` files.

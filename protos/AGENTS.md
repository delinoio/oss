### Instructions for `protos/`

- Follow the root `AGENTS.md`, the owning project index, and the relevant domain contract before changing a shared API.
- `protos/delibase/v1` is owned by project `delibase`; its source of truth is the versioned `delibase.v1` Protobuf contract.
- Generate Connect-compatible Go and TypeScript artifacts from the owning component source. Never edit generated output as a second source of truth.
- `protos/delibase`, `protos/devhud-deck`, and `protos/devhud-realqa` are independently versioned generation roots. An implemented root owns its `buf.gen.yaml`, package-local `generate:proto` and `check:proto` scripts, `gen/go`, `gen/ts`, and checked-in `<protobuf-package>.v1.binpb` descriptor. Component generation may clean or write only those owned paths.
- Keep `protos/buf.yaml` as the shared lint/breaking policy and compile component sources from the `protos` import root so descriptor file identities remain stable. The only current `PACKAGE_DIRECTORY_MATCH` exceptions are `devhud-deck/v1` and `devhud-realqa/v1`, whose component ownership paths intentionally differ from packages `devhud.deck.v1` and `devhud.realqa.v1`; do not broaden those exceptions or disable another `STANDARD` rule. Scope every lint, breaking, build, and generate operation to exactly `protos/<component>/v1`; never run an unscoped component generator over all proto roots.
- Root `pnpm generate:proto` and `pnpm check:proto` are deterministic fixed-order aggregates for `delibase`, `devhud-deck`, and `devhud-realqa`. They skip a planned root until its workspace `package.json` exists. Every implemented proto package must expose the same package-local entrypoints so adding it to the workspace automatically activates its aggregate generation and check.
- Each check compares only its source against its own descriptor baseline, regenerates only its own artifacts twice, compares both runs, and rejects a component-local generated diff. The optional CI baseline variables are `DELIBASE_PROTO_BASELINE`, `DEVHUD_DECK_PROTO_BASELINE`, and `DEVHUD_REALQA_PROTO_BASELINE`; never substitute one contract's descriptor for another.
- Checked-in Go and protobuf-es v2 TypeScript artifacts live under each implemented component's `gen/go` and `gen/ts`; generated trees are never a source of truth. Delibase exports `@delinoio/delibase-connect`; Deck and RealQA export the private workspace packages `@delinoio/devhud-deck-connect` and `@delinoio/devhud-realqa-connect` through their roots and versioned component subpaths.
- The six stable services are `AccountService`, `OrganizationService`, `TeamService`, `CatalogService`, `BillingService`, and `UsageService`.
- Preserve released `delibase.v1` additively. Breaking changes require a new API version and synchronized app/server migration docs.
- Keep UUID v7, signed-int64 money/usage, opaque cursors, Logto user/M2M access-token metadata without raw client secrets, the redacted `x-delibase-forwarded-user-token` forwarded-user context, authenticated invitation bearer-token access without pre-existing membership, caller/operation-scoped idempotency, and stable enum error details aligned with the server and app contracts.
- Keep distinct stable idempotency operations for invitation acceptance and revocation; invitation creation does not carry idempotency fields.
- Keep bounded background usage inside the existing `BillingService` and `UsageService`; never add a seventh service. Human create/revoke and M2M reserve/commit/release/resource-deletion notification use distinct caller-and-operation-scoped idempotency values. Authorized usage is M2M-only, must not require or store a forwarded user bearer, and binds the authenticated service identity into its replay digest; commit/release additionally bind the reservation ID, while resource deletion binds the expected revision.
- The released live-usage RPCs still require the forwarded user bearer for reserve, commit, and release and expose no durable finalization grant. The Deck wire contract is implemented, but the Deck server and billed refresh remain unimplemented and its meter remains disabled until a synchronized additive `delibase.v1` change can return a successful-reservation grant bound to the exact reservation, service, maximum, and expiry and accept it only for same-service idempotent commit/release with a fresh M2M bearer. Do not represent this planned prerequisite in generated delibase contracts before the source, server, compatibility checks, and substitution/expiry tests are implemented together.
- Keep `BackgroundUsagePurpose` closed to `REALQA_STORAGE` in v1 with no Deck value, `BackgroundUsagePeriod` closed to `UTC_DAY`, and authorization status closed to `ACTIVE`, `REVOKED`, `ACCESS_LOST`, `RESOURCE_DELETED`, and `OWNER_DELETED`. Preserve UUID v7 owner/resource/service/meter bindings, per-period limits, revisions/timestamps, opaque pagination, and stable substitution/access/status/limit/replay error reasons additively.
- `MarkBackgroundUsageResourceDeleted` transitions an exact matching `ACTIVE` grant to `RESOURCE_DELETED` only at the current expected revision. For the exact bound service/purpose/resource, it returns an existing `REVOKED`, `ACCESS_LOST`, `RESOURCE_DELETED`, or `OWNER_DELETED` status and current revision without transition when the request revision predates closure, so feature deletion cannot be stranded; future/unknown revisions and substitutions fail closed.
- Keep public catalog meter responses sufficient for human authorization creation by exposing stable service identity targets and safe display names, never Logto client identifiers or credentials. Reserve accepts only the current or immediately preceding canonical UTC day according to server time; commit/release use the period stored with the reservation.
- Preserve the stable member-active-reservations reason for organization-member removal and self-leave blocked by held usage.
- Run Protobuf lint, breaking checks, generation, generated Go formatting/vet/tests, and the consuming app type checks when implementation exists.
- Use root `pnpm generate:proto` or package-local `pnpm --dir protos/delibase generate:proto` to refresh the checked-in `delibase.v1` descriptor, generate both runtimes, and build the workspace package `dist`. Use root `pnpm check:proto` or package-local `pnpm --dir protos/delibase check:proto` for Buf lint, the delibase descriptor compatibility check, and a clean component-only regeneration diff. Local checks compare against the checked-in descriptor before regeneration; CI uses the immutable delibase descriptor from the pull request base or pre-push commit. TypeScript checks use `pnpm --filter @delinoio/delibase-connect typecheck`; Go checks include `go test ./protos/delibase/...` and `go vet ./protos/delibase/...`. CI runs aggregate generation checks plus implemented-component Go and TypeScript validation in the change-scoped `proto-contracts` job.
- Changes require synchronized updates to `docs/project-delibase.md`, `docs/protos-delibase-api-contract.md`, `docs/servers-delibase-server-foundation.md`, `docs/apps-delidev-app-foundation.md`, and affected `AGENTS.md` files.

### DevHud Feature Contracts

- Deck device writes carry widget configuration only; widget snapshots and synchronized widget revisions are server-authored. List results expose the synchronized PR revision required by mutations, and `UpdateView` may change notification preferences while owner/kind remain immutable.
- `protos/devhud-deck/v1` is the implemented authoritative `devhud.deck.v1` source owned by project `devhud`. Its isolated descriptor is `protos/devhud-deck/devhud.deck.v1.binpb`; reproducible Go and protobuf-es v2 TypeScript artifacts live under `protos/devhud-deck/gen/go` and `protos/devhud-deck/gen/ts`, and the private workspace package is `@delinoio/devhud-deck-connect`. Root and package-local generation/checks, generated Go test/vet, and TypeScript typecheck are mandatory. This package is private infrastructure, not a public API/plugin SDK.
- Deck exposes exactly `DeckViewService`, `DeckIntegrationService`, and `DeckDeviceService` with the RPCs listed in `docs/protos-devhud-deck-api-contract.md`, including non-dispatching `GetManualRefreshQuote`, authenticated `ResolveNotificationEvent`, and idempotent `DeckViewService.DeleteFeatureData` for either an authorized owner request or an exact delibase M2M account/organization-deletion trigger. `GetManualRefreshQuote` returns only a server-derived price plus an opaque short-lived token bound to the prospective manual `RefreshView` identity after authoritative catalog validation. Creation of a new manual `RefreshView` attempt requires that unexpired token, but an authenticated exact identity-and-digest replay is looked up first and returns or resumes the existing attempt after quote expiry or catalog change. `CreateView`, each logical `RefreshView`, and each logical `RegisterDevice` creation/renewal require client-generated UUID v7 replay identities; refresh exact replay returns the original result/billing disposition without another provider request or charge, while registration exact replay returns the identical registration ID, lease, and single-registration revocation grant. Changed-input reuse conflicts. Idempotent unregister accepts either matching-account authentication or only that grant so an OS-vault cleanup tombstone can finish after logout/account switch before later registration. Notification resolution requires the matching active registration and current authorization/detail opt-in and never refreshes provider data. Deck's future delibase single-reservation finalization grant is server-to-server credential material and must never appear in a `devhud.deck.v1` message, generated client, or client metadata. The generated client may be consumed by authenticated Deck code under `apps/devhud`, by `apps/delidev-app` only for `DeckIntegrationService`, and by `servers/delibase` only for the service-authenticated deletion trigger. Keep the v1 view kind closed to `GITHUB_PULL_REQUESTS`, use UUID v7/opaque cursors/revisions/idempotency/closed enums, and never transport remote UI, provider tokens, raw auth metadata, or client-authoritative roles/permissions/prices.
- `protos/devhud-realqa/v1` is the authoritative implemented `devhud.realqa.v1` source owned by project `devhud`. Reproducible Go and protobuf-es v2 TypeScript artifacts live under `protos/devhud-realqa/gen/go` and `protos/devhud-realqa/gen/ts`; `@delinoio/devhud-realqa-connect` is private and must not be published or treated as a public API/plugin SDK.
- RealQA exposes exactly `RealQAPresetService`, `RealQATrackerService`, and `RealQASubmissionService` with the RPCs listed in `docs/protos-devhud-realqa-api-contract.md`, including authenticated opaque-cursor `ListSubmissions` for only caller-authorized retained submission/asset references, owner-authorized replay-safe `RebindSubmissionStorageAuthorization` for compare-and-swap replacement of an exact `ACTIVE`, `REVOKED`, or `ACCESS_LOST` current storage grant, and idempotent `DeleteFeatureData` for either an authorized owner request or an exact delibase M2M account/organization-deletion trigger. Feature deletion removes scoped presets/submissions/assets plus tracker connection/installation bindings, encrypted provider credentials, and callback/webhook state. `CreatePreset` requires a client-generated UUID v7 idempotency key so exact replay returns the original preset/revision and changed-input reuse conflicts. Submission/upload responses expose the server-derived deadline that leaves the final transfer-reservation hour for verification and commit/release; `CreateImageUpload` returns only a signed PUT at the exact RealQA asset origin that cannot outlive that deadline, never an R2 S3 endpoint. `SubmitIssue` must start by that deadline with a fresh forwarded bearer and resumes server-held stable transfer-finalization and initial storage-authorization-creation attempts; no cleanup worker may invoke the live usage RPCs without that bearer or treat an unresolved authorization attempt as no grant. The generated client is otherwise consumed only by `servers/devhud-realqa` and authenticated RealQA code under `apps/devhud`; DeliDev has no RealQA client. Keep the v1 tracker closed to GitHub.com; use UUID v7/opaque cursors/revisions/idempotency/closed enums; enforce typed size/body/asset/billing errors; and never transport provider/R2 secrets, raw originals, submitted title/body/URL/DOM data, arbitrary page HTML/text, public asset indexes, or remote UI/code.
- Human calls to both APIs require feature-audience user tokens plus sensitive memory-only delibase-audience forwarded bearer metadata. Deck `UnregisterDevice` alone may instead accept its single-registration revocation grant, retained only in the OS-vault cleanup tombstone, and only `DeleteFeatureData` additionally accepts the feature-specific delibase M2M identity for a typed lifecycle trigger. Generated clients must otherwise keep credentials out of messages, logs, errors, caches, persistence, and diagnostics. Preserve released v1 contracts additively; breaking changes require a v2 contract and synchronized migration docs.
- Each feature's `StartGitHubConnection` returns only an ephemeral GitHub.com authorization target. DevHud uses the app contract's typed native system-browser action; DeliDev may use a Deck target only through its separately contracted exact GitHub.com top-level same-tab validator. It is not a generic navigation field and its query data must not be logged, cached, persisted, or reused.
- Each implemented feature package provides the component-local generation/check contract above with descriptor `devhud.deck.v1.binpb` or `devhud.realqa.v1.binpb`. Deck and RealQA do so now. Canonical checks are root `pnpm generate:proto` and `pnpm check:proto`, the matching `pnpm --dir protos/<component> generate:proto`/`check:proto`, `go test`/`go vet` for each implemented `./protos/devhud-*/...` root, and the matching generated Connect package typecheck.
- Generation/fixture checks must not publish clients, deploy the future origins, register either separate GitHub App, configure DNS/R2, publish server images/extensions/widgets, or activate the disabled production-facing catalog records.
- Changes require synchronized updates to `docs/project-devhud.md`, both affected app/server/proto contracts, `docs/README.md`, `README.md`, and root/apps/servers/protos `AGENTS.md` files.

# Runmoor command rules

- Follow `docs/project-runmoor.md` and `docs/cmds-runmoor-foundation.md`; issue #893 is the original product contract and #1312 defines opt-in macOS host execution.
- Linux `systemctl --user` service commands may inherit only caller-provided `XDG_RUNTIME_DIR` and `DBUS_SESSION_BUS_ADDRESS` in addition to the existing minimal command environment. Keep `minimalEnv` unchanged for Tart, guests, and unrelated subprocesses; leave missing selectors unset and do not inherit arbitrary variables.
- `reload` compares the live Unix-socket peer with the native service main process and advances only an older owned user-service manager to the installed CLI. Keep foreground reload and stopped-service behavior unchanged; never download releases or downgrade. Without a pending handoff journal, failed native inspection must fall back to ordinary reload bound to the authenticated peer PID, return the peer's result unchanged, and acquire no service mutation authority. Pending-journal recovery still requires native inspection. Serialize service operations, retain private handoff intent and exact definition/process identities, preserve committed configuration and Stop/pauses across replacement, and never kill a runner or a process group. Use a one-run launchd handoff helper to replace cached definitions; Linux replacement targets only MainPID. Keep the two-minute CLI limit, redact logs and distinguish native fixtures/builds from actual launchd/systemd and job acceptance.
- Explicit `service start` may retire obsolete target-reload intent before spawning only under the service-operation lock, with an inactive native service, a confirmed finished initiator, exclusive state ownership, completed Stop/cleanup, matching installation/storage/configuration and the exact installed target definition. Preserve uncertain and legacy intent, unfinished cleanup and reservations; automatic replacement still preserves Stop. Initiator lookup errors other than confirmed absence do not prove exit.
- Before an interrupted service reload resumes native actions, checks replacement readiness or completes, atomically transfer the private journal's completion ownership to the retry's verified PID/start identity under the service-operation lock. Failed transfer preserves intent and authorizes no native mutation. Retain the journal while that owner is live; legacy records without an initiator remain conservative until recovery claims them.
- While replacement intent is pending, a verified restart of the exact previous service invocation/version must load the journal-owned committed requested snapshot and preserve Stop/pauses. Require matching platform/unit/configuration and installation identity; fail before candidate loading or startup acceptance if snapshot authority is unavailable or mismatched. The previous manager retains the journal without retirement authority. Foreground and no-journal explicit Start keep their existing behavior.
- Keep CLI, TOML v1, SQLite v4 (with ordered atomic v1, v2 and v3 migrations), and versioned JSON contracts synchronized with the English README and Markdown-owned `apps/public-docs/docs/runmoor` documentation at `https://oss.delino.io/runmoor`.
- Generate scale-set, GitHub-style platform and architecture routing labels only when `init` creates a new pool: Docker amd64 uses `runmoor-linux`, `linux`, `x64`; Docker arm64 uses `runmoor-linux`, `linux`, `ARM64`; Tart arm64 uses `runmoor-macos`, `macOS`, `ARM64`; host arm64 uses `runmoor-macos-host`, `macOS`, `ARM64`. Do not synthesize labels for loaded, omitted or manually authored pool labels.
- Use the official pinned `actions/scaleset` client. Persist message effects before acknowledgement; derive demand from statistics, never event counts. Bound advertised and acquired jobs by host and backend capacity using runner-only CPU and combined runner/daemon memory for DinD; recheck eligibility and capacity after a pending poll before acquisition.
- DinD daemon CPU is a runtime container limit, never a separate admission reservation. Preserve its positive bounded configuration, default and engine CPU-limit check. Automatic runner CPU defaults use the full applicable CPU budget. New execution reservations and status costs use runner-only CPU; restart/reload must preserve every already-published execution and preparation reservation until confirmed termination or completed cleanup. Keep TOML/JSON fields and SQLite schema unchanged for this policy change, and distinguish its unreleased availability from releases through 0.2.7 in public guides.
- Use the official split Moby `client` and `api` modules for Docker operations, with automatic API negotiation and the existing local Unix-socket restriction. Preserve result-envelope handling, ownership checks, resource limits, cancellation, and redacted errors when updating the SDK.
- Preserve installation ownership, per-runner resource reservations, original configuration generations, and cleanup progress across crashes. Never adopt resources based only on their names. For Tart, require matching owner-only identity records in the durable Runmoor record and the VM directory before every ownership-dependent operation. Create or clone into a private per-entity staging `TART_HOME` that shares only Tart's private content cache; hold its operation lock while Tart runs, publish the marker through the opened VM directory, and expose the canonical VM name only by a no-replace rename of that marked directory. Before treating a missing canonical VM as absent, promote a marked staged VM; preserve a markerless staged VM with its record and reservation. For inspection, configuration, boot, guest execution and stop, open and verify the VM directory without following symlinks, then pass its descriptor to Tart through a one-command name alias so Tart cannot resolve a replacement at the recorded name. Keep the per-entity run alias until termination is confirmed. Persist detached Tart PIDs and OS-reported process-start identities for runners, setup images, and validation images in private SQLite state; exclude image process state from status JSON. Compare both PID and process-start identity before treating a recorded Tart process as alive, and retain reservations conservatively when older state lacks the identity. An image retry must confirm the previous process exited before replacing its run alias or launching Tart again. Retain image reservations while the run alias exists or its recorded process may still be alive, including while image removal is pending. If the canonical VM path disappears, retain its record and reservation while the run alias exists or the recorded Tart process may still be alive; release them only after the process is confirmed exited. Thread the caller context through the owned start precheck and recheck cancellation immediately before detached start so a cancelled operation cannot launch after Tart's `get` returns. Before delete, hold Tart's config lock while atomically moving the verified directory to a stable per-entity name with a no-replace rename, and retain the lock until Tart confirms deletion. When recovering an already staged deletion, reopen and verify that VM and hold its config lock through the delete. Delete only the staged name and recover interrupted staged deletion from its embedded identity. Preserve markerless legacy VMs with their records and reservations. Serialize each pool's scale-set initialization/publication with retirement; draining pools may resolve pending creation by lookup but cannot begin a new creation or retire while that outcome is unresolved.
- After Tart reports a verified VM stopped, poll its recorded PID and process-start identity within the caller's cleanup context. Keep the run alias and reservation while that exact process remains alive; if the cleanup deadline expires, return retryable cleanup instead of quarantining an ownership conflict. PID/start mismatches confirm the recorded process exited.
- Open SQLite only through an escaped `file:` URI built from the exact absolute database filename. If a path containing `?` has a missing or empty intended database while its former raw-DSN prefix is a regular file, fail before creating state or lock files; preserve both locations and require explicit recovery with complete backups rather than adopting, moving, or deleting either database.
- When a validated reload supplies the same remote scale-set identity, refresh the draining generation's durable cleanup connection and cached client, including on rollback to its original credential reference. Require the existing owner-label and recorded-ID checks before removal; a failed check must retain draining state and block same-identity creation.
- After durable pool retirement, discard its cached GitHub client and mutex and cancel its session loop. Stale work must not recreate these caches or publish a session for a retired/pruned generation; failed retirement commits retain retry state. Eligibility checks must reject a missing pool, including retirement/pruning between a final session message commit and job acquisition.
- GitHub management credentials stay on the host. Do not persist JIT credentials or copy raw workflow output, upstream response bodies, or subprocess stderr into diagnostics.
- Scale down through GitHub's busy-aware removal before terminating an idle execution. Preserve an assignment that wins the race.
- Registration inspection must skip obsolete work and atomically revalidate the current lifecycle before quarantining an absent registration. Preserve committed completion, cleanup, explicit force, remote removal and confirmed termination; warn only after a quarantine commit succeeds. Actual backend/registration ownership errors still quarantine, and absence alone never authorizes termination or reservation release. Existing quarantines require ownership-verified operator recovery.
- Expired preparation recovery also requires busy-aware removal; only explicit force-stop or an established busy-job deadline permits forced cleanup. Recover an unknown job start conservatively from the persisted creation time.
- A delayed GitHub `ErrBusy` may restore `Busy` only when the runner still exists in the exact phase that initiated removal and no completion, force, remote removal, termination, or quarantine outcome has committed. Preserve later lifecycle state and missing records. When no start was observed, derive the deadline from persisted creation time and the original generation timeout.
- Demand at the logical pool's cross-generation runner cap must not evict another pool's minimum-idle capacity. At the two-VM ceiling, Tart demand may displace a warm Tart VM but must preserve warm Docker capacity that cannot release a VM slot. Plan demand with the allocator against already available capacity, selected retirements and deregistered cleanup; preserve remaining minimum-idle runners once that capacity satisfies demand. Planning never releases actual reservations before confirmed termination.
- DinD inspection requires its owned daemon to be running as well as the runner; missing/stopped daemons enter busy-aware cleanup, while changed ownership quarantines without deleting unrelated resources.
- Docker termination verifies deterministic runner/daemon/init names and recorded container IDs without label filters before stopping resources and before confirming termination. Foreign replacements quarantine and retain reservations, including during force-stop.
- Paused or restarting runner containers are unavailable capacity and require busy-aware cleanup without claiming termination.
- Docker jobs never receive the host socket, personal bind mounts, credential environment, or manager state. Each DinD daemon and all of its storage belong to exactly one execution. Disable log retention both on outer containers and by default inside the nested daemon. A bootstrap marker is not readiness: require the runner container to survive a startup observation before clearing preparation failures.
- Detached VM/guest supervisors must use real null output descriptors so parent exit cannot cause SIGPIPE. Guest bootstrap must confirm runner startup, reject already finished or unready status, and count immediate launch failures toward the pool preparation circuit breaker. Guest state uses the canonical fixed helper root independently of inherited TMPDIR.
- Guest validation must distinguish bounded image rejection from transient RPC unavailability and reject invalid images without a readiness retry. Tart commands use argv/stdin, private `TART_HOME`, and `TART_NO_AUTO_PRUNE=1`. Base revisions are never job VMs. Recompute and compare the sealed digest before pool acceptance or cloning a sealed revision for jobs or setup. Sealing and sealed-image hashing must honor operation cancellation and deadlines between bounded file reads, close files, and never publish a partial digest. Setup and validation VMs share the global budget and two-VM ceiling. Image mutations require the manager so it owns sleep inhibition after the CLI exits; image-only startup with no pools or connections must remain usable. Whole-manager shutdown and service waits retain ownership until open setup and pending image removal finish; reject new image work after stop while allowing existing work to finish.
- Accept only stable Tart 2.x.x releases reported as complete SemVer triplets, allowing valid build metadata. Reject prereleases and malformed or other-major versions. Keep Guest Agent pinned to 0.14.2 and report dependency failures without echoing command output.
- Status/doctor must expose capacity waits and image recovery. Force-stop immediately cancels preparation, and reload must not undo a concurrent stop or accept a concurrently removed image.
- Offline doctor must validate a managed pool's committed current image and connection, not classify its unresolved requested TOML as unprepared. Emit one managed-state check per pool, retain genuine pending/expiry/image failures, and never prepare images during diagnosis.
- Doctor runner freshness retains the latest-100 release query and 30-day update window. Bound response acquisition to 8 MiB plus one detection byte, reject oversize before decoding, and decode only complete responses within the limit. Oversize, read/transport failure, and invalid metadata use safe `DEPENDENCY_RETRY` diagnostics without exposing upstream bodies or errors; size exhaustion must report the limit and manual verification/retry guidance.
- Forced preparation cancellation neither increments nor resets image preparation failure counters and must not suspend the pool.
- A suspended pool must retain its safe problem and preparation-failure count across generation replacement. Validated reload may resume only after a change relevant to that failure; scale-set identity changes may auto-resume only recorded remote scale-set ownership failures, never local or unknown ownership conflicts. A runner-version failure cannot be corrected by changing only the DinD daemon image. For preparation failures, compare only the affected backend's preparation timeout and executable/socket, never the job timeout or other backend's settings. Verified managed image replacement may additionally clear a matching three-failure startup preparation circuit breaker. Preserve authentication/ownership and operator lifecycle decisions otherwise. Legacy suspended state without a recorded problem must surface an actionable status/doctor diagnostic without automatic recovery.
- Preparation workers recheck the durable unforced Preparing state immediately before backend preparation, after journaling the JIT registration result. Preserve returned registration IDs and concurrent lifecycle transitions even when context cancellation has not arrived; skipped preparation must not change failure counters. Check cancellation before remote/backend side effects.
- Becoming idle clears the sleep-inhibitor failure and retry deadline together. New runner/image activity must attempt acquisition again; backoff during uninterrupted activity must keep reporting its failure.
- Pending image removal retains sleep inhibition until cleanup is durably complete.
- Temporary Tart exports are owned by the image UUID journaled before export. Clean them after import, during restart reconciliation, and before image removal; persist cleanup failures and never sweep unjournaled archives or follow unexpected symlinks.
- Quarantined executions retain sleep inhibition while their termination remains unconfirmed.
- Image open succeeds only after Tart reports the owned VM running; startup timeout retains an actionable diagnostic and the reservation until reconciliation confirms a stop.
- Owned-image sealing and validation hash `config.json`, `nvram.bin`, and `disk.img` through the already verified VM directory descriptor, opening each file relative to it so a renamed canonical path cannot redirect the digest.
- Interactive first-run Tart setup uses a private journal and a temporary image-only manager. It may request Tart's latest host-supported Apple IPSW but must never bundle Tart or macOS, adopt an unowned VM, overwrite a final config, or seal before explicit operator confirmation and a clean headless Guest Agent boot check. Resume only the journaled UUID and preserve ambiguous outcomes for diagnosis; noninteractive init still requires an existing image/source.
- Image seal and TOML pool configuration share the same guest runner-path validation; reject incompatible paths before reserving or booting a validation VM and preserve accepted path strings exactly.
- Tart guest OS validation uses typed `darwin` support only. Inspect metadata before reserving or booting a mutable image for sealing, and repeat the check before accepting or cloning any sealed base; empty, Linux and unknown guest OS values fail as `IMAGE_INVALID` with macOS guidance. Preserve unsupported existing records for diagnosis and ownership-checked explicit removal.
- Pool-scoped stop must leave other pools running. Drain waits must select the requested pool across generations equally through live control and offline state. Storage relocation requires fully completed execution cleanup and closed image operations, preserving the installation identity.
- launchd start must refresh an already-loaded job from the validated on-disk plist before starting it; do not kickstart a potentially stale cached definition. A failed bootout prevents bootstrap. launchd stop/uninstall must fail and preserve the plist after a failed bootout unless a separate exact-service probe confirms absence in a reachable GUI domain.
- Before launchd stop/uninstall drains or boots out the job, query `launchctl list` with no label and select the exact service row from its documented PID/status/label table. Compare an active process's exact kernel-provided argument vector with the validated plist `ProgramArguments`. A loaded but inactive job has no verifiable process arguments and must fail closed before draining; recheck immediately before bootout. Do not use label-specific list output or parse `launchctl print` output; those are detailed/diagnostic formats, not the documented table interface.
- Before a Linux service start reloads/enables or stop/uninstall drains/disables the unit, inspect `MainPID` and compare an active process's `/proc/<pid>/cmdline` with the validated `ExecStart`. Reject an unreadable or mismatched identity before `daemon-reload`, drain, or disable, so a changed unit cannot replace the loaded stop command or operate on another manager. Check stop/uninstall before draining, reload systemd from the same unchanged validated definition after draining, revalidate the snapshot after reload, and check process identity again immediately before disabling. For inactive or matching services, reload the manager and revalidate the same definition snapshot before enabling/starting. Tell users to gracefully stop a mismatched manager with its original `--config` path; never expose either path in diagnostics.
- Before launchd/systemd service start, stop, or uninstall, securely parse the installed generated definition and require its absolute `--config` path to match the requested configuration. Reject missing, symlinked, foreign-owned, malformed, duplicate, or ambiguous definitions before contacting either manager, opening offline state, invoking OS service commands, or deleting the definition. For requested paths containing `..`, resolve both the original spelling and its lexical normalization, rejecting them if symlink traversal changes the resolved path. Executable and configuration arguments in generated definitions must already be canonical absolute paths before comparison; systemd `ExecStart` and `ExecStop` must agree on both. On Linux, enumerate the full standard systemd user unit search path and reject any competing `runmoor.service` file or Runmoor-specific/service-type drop-in directory outside the installed definition. Stop/uninstall must revalidate the same file identity and contents after draining and immediately before deleting it, preserving any definition replaced during the drain or unload interval.
- Keep unsupported platform implementations compilable so the repository's Windows Go CI remains intact. Systemd user unit search-path tests run only on Linux. Archive download/repack tests require Darwin/Linux private-file and ownership primitives; skip those storage tests on other hosts while keeping release metadata and asset-validation tests portable.
- Run `go test ./cmds/runmoor/...`, supported-host race tests, and `go vet ./cmds/runmoor/...`. Docker integration is opt-in with `RUNMOOR_DOCKER_TEST=1`; Tart integration is opt-in with `RUNMOOR_TART_TEST=1`. Ordinary tests never contact GitHub or install user services.
- Publication must reject conflicting existing tags and existing releases before signing; uncertain remote status is a failure. Discover drafts through paginated release listings, pin their numeric ID through verification/publication, and retain exact source, asset and signing-identity checks. README installation commands select one release tag for downloads and signature verification and check its checksum before extraction.
- Release dry runs never obtain OIDC credentials, sign, publish, or produce pretend Sigstore evidence. Public releases use the stable channel while continuing to disclose the live GitHub and Tart verification gaps.
- Homebrew consumes the verified public macOS ARM64 archive through `delinoio/tap/runmoor`; preserve macOS 14+ Apple Silicon requirements, manual Runmoor service ownership and operator-installed Tart. Follow `packaging/homebrew/AGENTS.md` and the command foundation for signed-release verification, native Formula tests, bot publication and recovery without replacing release assets.

### Automatic runner management

- Follow the automatic defaults and runner management contract in `docs/cmds-runmoor-foundation.md`. Preserve the difference between omitted and explicit resource values, requested configuration and committed execution generations, and global host versus Docker engine capacity.
- Revalidate the committed image before treating an unchanged runner release as ready. Missing/invalid images require preparation and candidate validation; transient dependency/ownership failures retain the current artifact with backoff. Verified repair may clear only the matching image/version suspension, never an operator pause, drain, stop or unrelated failure.
- A validated reload of a suspended managed pool must retain a private, durable recovery decision for the same pool, failure and desired configuration until its candidate publishes. Subsequent unrelated reloads may retain that decision while the relevant correction remains. Do not expose the decision in public JSON or resume before candidate validation.
- Only verified immutable candidates may activate. Preparation is credential-free, lifecycle-tracked, durably reserved, and serialized with image operations. Never update a running job or an operator source image. Pause/drain/stop and stale-candidate checks are authoritative at publication.
- Keep current, previous, source and live execution references during artifact collection. Recover uncertain preparation/commit outcomes by exact journaled ownership; never blindly recreate or force-remove a foreign/referenced artifact.
- Freeze the first successful Tart import as an owned digest before guest mutation. Runner installation retries clone that frozen source, including after restart; imported source revisions cannot be opened or sealed in place. Transfer preparation reservations atomically during import and clone.
- An unavailable startup Docker capacity probe blocks only new Docker acquisition until a successful bounded retry. Keep the engine ceiling separate from host capacity, and retain each execution's original allocation. Paused pools still check release metadata but cannot prepare or activate a replacement; scoped resume must preserve other pending pools' pauses.
- Release and owned-artifact cleanup retries use bounded backoff; share provider rate-limit deadlines across pools and collect unreferenced ready artifacts even after the final managed pool is removed. Retire expired idle runners through the existing busy-aware boundary while preserving busy work.
- Ordinary tests inject release transports and image builders. Real Docker/Tart validation remains opt-in and is distinct from live GitHub job certification.

### macOS host execution

- Follow issue #1312 and the host section of the command contract. Host selection is explicit, macOS 14+ arm64-only and plain-only. Keep default backend selection and authored labels unchanged. Reject host image/source/path, DinD and image-only options.
- Host reservations share CPU/memory/disk and fair scheduling with Docker/Tart; only Tart uses the two-VM limit. Reservations are admission values, not enforced usage limits. Keep immutable verified distributions and distinct per-execution registration, installation, HOME, temporary and work state.
- Host jobs and the manager share one trusted account. Inherit only the documented PATH/DEVELOPER_DIR and minimal execution environment; JIT uses a private memory-only bootstrap pipe. Never persist secrets, arguments or raw runner/workflow output in state or diagnostics.
- On Darwin, pass verified directories through inherited descriptors. Only private child entrypoints may use `fchdir`; never use `/dev/fd` for directory traversal or child cwd and never change the manager's cwd. Validate the inherited owner marker and inode identity, reject symlinked runner directories and fixed entrypoints, and recheck durable Stop/force authority in the worker child before exec. Resolve execution HOME/temp from the descriptor-selected physical directory. Keep helper outcome pipes bounded and close-on-exec, and distinguish execution failures from actual reported-version mismatches without copying stderr into diagnostics.
- Journal directory creation and removal, verify owner markers and opened directory identities, and compare kernel PID/start/group identities. Missing/replaced/escaping resources or uncertain termination retain reservations. Detached supervisors survive manager-only restarts; cleanup signals only verified members and never adopts processes by name. Escaping daemons are unsupported.
- At exclusive startup after completed stop or drained storage relocation, copied ready host distributions may rebind device/inode identities only after matching private installation/token, artifact/version and runner digest checks. Require completed cleanup and unreserved ready artifacts; recover a marker-first interrupted rebind at the same boundary. Never rebind live execution directories or relax runtime ownership checks.
- Host preparation waits for asynchronous supervisor status within its preparation context; fail immediately on ownership conflicts or confirmed early exits, and preserve uncertain launch reservations on timeout or cancellation.
- Detached host supervisors apply job timeouts only after durable Busy authority from assignment or busy-aware removal; idle time never establishes a job deadline. Keep the preparation deadline separate and retain established job deadlines across manager restarts.
- Bound host deadline-state reads to a five-second cadence after startup confirmation, with a cached deadline timer and an authority recheck at expiry; never tie SQLite reads to rapid process-cleanup polling.
- New host tests use injected native/process adapters and temporary state. Native Darwin regression fixtures may build the CLI helper and execute temporary fixture scripts; `RUNMOOR_HOST_VERSION_TEST=1` may verify the official checksummed ARM64 archive with `--version` only. Run host contract fixtures, the existing full unit/race/vet suites, public-docs tests and supported-target cross-builds. Never run actual host jobs, Xcode builds or live GitHub jobs for #1312. Preserve explicit native/account validation gaps in docs and PRs.

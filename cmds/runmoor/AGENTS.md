# Runmoor command rules

- Follow `docs/project-runmoor.md` and `docs/cmds-runmoor-foundation.md`; issue #893 is the product contract.
- Keep CLI, TOML v1, SQLite v2 (with atomic v1 migration), and versioned JSON contracts synchronized with the English README and Markdown-owned `apps/public-docs/docs/runmoor` documentation at `https://oss.delino.io/runmoor`.
- Generate scale-set, GitHub-style platform and architecture routing labels only when `init` creates a new pool: Docker amd64 uses `runmoor-linux`, `linux`, `x64`; Docker arm64 uses `runmoor-linux`, `linux`, `ARM64`; Tart arm64 uses `runmoor-macos`, `macOS`, `ARM64`. Do not synthesize labels for loaded, omitted or manually authored pool labels.
- Use the official pinned `actions/scaleset` client. Persist message effects before acknowledgement; derive demand from statistics, never event counts. Bound advertised and acquired jobs by host and backend capacity, including DinD cost; recheck eligibility and capacity after a pending poll before acquisition.
- Use the official split Moby `client` and `api` modules for Docker operations, with automatic API negotiation and the existing local Unix-socket restriction. Preserve result-envelope handling, ownership checks, resource limits, cancellation, and redacted errors when updating the SDK.
- Preserve installation ownership, per-runner resource reservations, original configuration generations, and cleanup progress across crashes. Never adopt resources based only on their names. Serialize each pool's scale-set initialization/publication with retirement; draining pools may resolve pending creation by lookup but cannot begin a new creation or retire while that outcome is unresolved.
- When a validated reload supplies the same remote scale-set identity, refresh the draining generation's durable cleanup connection and cached client, including on rollback to its original credential reference. Require the existing owner-label and recorded-ID checks before removal; a failed check must retain draining state and block same-identity creation.
- After durable pool retirement, discard its cached GitHub client and mutex and cancel its session loop. Stale work must not recreate these caches or publish a session for a retired/pruned generation; failed retirement commits retain retry state. Eligibility checks must reject a missing pool, including retirement/pruning between a final session message commit and job acquisition.
- GitHub management credentials stay on the host. Do not persist JIT credentials or copy raw workflow output, upstream response bodies, or subprocess stderr into diagnostics.
- Scale down through GitHub's busy-aware removal before terminating an idle execution. Preserve an assignment that wins the race.
- Registration inspection must skip obsolete work and atomically revalidate the current lifecycle before quarantining an absent registration. Preserve committed completion, cleanup, explicit force, remote removal and confirmed termination; warn only after a quarantine commit succeeds. Actual backend/registration ownership errors still quarantine, and absence alone never authorizes termination or reservation release. Existing quarantines require ownership-verified operator recovery.
- Expired preparation recovery also requires busy-aware removal; only explicit force-stop or an established busy-job deadline permits forced cleanup. Recover an unknown job start conservatively from the persisted creation time.
- Demand at the logical pool's cross-generation runner cap must not evict another pool's minimum-idle capacity. At the two-VM ceiling, Tart demand may displace a warm Tart VM but must preserve warm Docker capacity that cannot release a VM slot. Plan demand with the allocator against already available capacity, selected retirements and deregistered cleanup; preserve remaining minimum-idle runners once that capacity satisfies demand. Planning never releases actual reservations before confirmed termination.
- DinD inspection requires its owned daemon to be running as well as the runner; missing/stopped daemons enter busy-aware cleanup, while changed ownership quarantines without deleting unrelated resources.
- Docker termination verifies deterministic runner/daemon/init names and recorded container IDs without label filters before stopping resources and before confirming termination. Foreign replacements quarantine and retain reservations, including during force-stop.
- Paused or restarting runner containers are unavailable capacity and require busy-aware cleanup without claiming termination.
- Docker jobs never receive the host socket, personal bind mounts, credential environment, or manager state. Each DinD daemon and all of its storage belong to exactly one execution. Disable log retention both on outer containers and by default inside the nested daemon. A bootstrap marker is not readiness: require the runner container to survive a startup observation before clearing preparation failures.
- Detached VM/guest supervisors must use real null output descriptors so parent exit cannot cause SIGPIPE. Guest bootstrap must confirm runner startup, reject already finished or unready status, and count immediate launch failures toward the pool preparation circuit breaker. Guest state uses the canonical fixed helper root independently of inherited TMPDIR.
- Guest validation must distinguish bounded image rejection from transient RPC unavailability and reject invalid images without a readiness retry. Tart commands use argv/stdin, private `TART_HOME`, and `TART_NO_AUTO_PRUNE=1`. Base revisions are never job VMs. Recompute and compare the sealed digest before pool acceptance or cloning a sealed revision for jobs or setup. Sealing and sealed-image hashing must honor operation cancellation and deadlines between bounded file reads, close files, and never publish a partial digest. Setup and validation VMs share the global budget and two-VM ceiling. Image mutations require the manager so it owns sleep inhibition after the CLI exits; image-only startup with no pools or connections must remain usable. Whole-manager shutdown and service waits retain ownership until open setup and pending image removal finish; reject new image work after stop while allowing existing work to finish.
- Accept only stable Tart 2.x.x releases reported as complete SemVer triplets, allowing valid build metadata. Reject prereleases and malformed or other-major versions. Keep Guest Agent pinned to 0.14.2 and report dependency failures without echoing command output.
- Status/doctor must expose capacity waits and image recovery. Force-stop immediately cancels preparation, and reload must not undo a concurrent stop or accept a concurrently removed image.
- Offline doctor must validate a managed pool's committed current image and connection, not classify its unresolved requested TOML as unprepared. Emit one managed-state check per pool, retain genuine pending/expiry/image failures, and never prepare images during diagnosis.
- Doctor runner freshness retains the latest-100 release query and 30-day update window. Bound response acquisition to 8 MiB plus one detection byte, reject oversize before decoding, and decode only complete responses within the limit. Oversize, read/transport failure, and invalid metadata use safe `DEPENDENCY_RETRY` diagnostics without exposing upstream bodies or errors; size exhaustion must report the limit and manual verification/retry guidance.
- Forced preparation cancellation neither increments nor resets image preparation failure counters and must not suspend the pool.
- A suspended pool must retain its safe problem and preparation-failure count across generation replacement. Validated reload may resume only after a change relevant to that failure; scale-set identity changes may auto-resume only recorded remote scale-set ownership failures, never local or unknown ownership conflicts. A runner-version failure cannot be corrected by changing only the DinD daemon image. For preparation failures, compare only the affected backend's preparation timeout and executable/socket, never the job timeout or other backend's settings. Verified managed image replacement may additionally clear a matching three-failure startup preparation circuit breaker. Preserve authentication/ownership and operator lifecycle decisions otherwise. Legacy suspended state without a recorded problem must surface an actionable status/doctor diagnostic without automatic recovery.
- Preparation workers recheck the durable unforced Preparing state immediately before backend preparation, after journaling the JIT registration result. Preserve returned registration IDs and concurrent lifecycle transitions even when context cancellation has not arrived; skipped preparation must not change failure counters. Check cancellation before remote/backend side effects.
- Becoming idle clears the sleep-inhibitor failure and retry deadline together. New runner/image activity must attempt acquisition again; backoff during uninterrupted activity must keep reporting its failure.
- Pending image removal retains sleep inhibition until cleanup is durably complete.
- Temporary Tart exports are owned by the image UUID journaled before export. Clean them after import, during restart reconciliation, and before image removal; persist cleanup failures and never sweep unjournaled archives or follow unexpected symlinks.
- Quarantined executions retain sleep inhibition while their termination remains unconfirmed.
- Image open succeeds only after Tart reports the owned VM running; startup timeout retains an actionable diagnostic and the reservation until reconciliation confirms a stop.
- Interactive first-run Tart setup uses a private journal and a temporary image-only manager. It may request Tart's latest host-supported Apple IPSW but must never bundle Tart or macOS, adopt an unowned VM, overwrite a final config, or seal before explicit operator confirmation and a clean headless Guest Agent boot check. Resume only the journaled UUID and preserve ambiguous outcomes for diagnosis; noninteractive init still requires an existing image/source.
- Image seal and TOML pool configuration share the same guest runner-path validation; reject incompatible paths before reserving or booting a validation VM and preserve accepted path strings exactly.
- Pool-scoped stop must leave other pools running. Drain waits must select the requested pool across generations equally through live control and offline state. Storage relocation requires fully completed execution cleanup and closed image operations, preserving the installation identity.
- launchd stop/uninstall must fail and preserve the plist after a failed bootout unless a separate exact-service probe confirms absence in a reachable GUI domain.
- Keep unsupported platform implementations compilable so the repository's Windows Go CI remains intact. Archive download/repack tests require Darwin/Linux private-file and ownership primitives; skip those storage tests on other hosts while keeping release metadata and asset-validation tests portable.
- Run `go test ./cmds/runmoor/...`, supported-host race tests, and `go vet ./cmds/runmoor/...`. Docker integration is opt-in with `RUNMOOR_DOCKER_TEST=1`; Tart integration is opt-in with `RUNMOOR_TART_TEST=1`. Ordinary tests never contact GitHub or install user services.
- Publication must reject conflicting existing tags and existing releases before signing; uncertain remote status is a failure. Discover drafts through paginated release listings, pin their numeric ID through verification/publication, and retain exact source, asset and signing-identity checks. README installation commands select one release tag for downloads and signature verification and check its checksum before extraction.
- Release dry runs never obtain OIDC credentials, sign, publish, or produce pretend Sigstore evidence. Public releases use the stable channel while continuing to disclose the live GitHub and Tart verification gaps.
- Homebrew consumes the verified public macOS ARM64 archive through `delinoio/tap/runmoor`; preserve macOS 14+ Apple Silicon requirements, manual Runmoor service ownership and operator-installed Tart. Follow `packaging/homebrew/AGENTS.md` and the command foundation for signed-release verification, native Formula tests, bot publication and recovery without replacing release assets.

### Automatic runner management

- Follow the automatic defaults and runner management contract in `docs/cmds-runmoor-foundation.md`. Preserve the difference between omitted and explicit resource values, requested configuration and committed execution generations, and global host versus Docker engine capacity.
- Revalidate the committed image before treating an unchanged runner release as ready. Missing/invalid images require preparation and candidate validation; transient dependency/ownership failures retain the current artifact with backoff. Verified repair may clear only the matching image/version suspension, never an operator pause, drain, stop or unrelated failure.
- A validated reload of a suspended managed pool must retain a private, durable recovery decision for the same pool, failure and desired configuration until its candidate publishes. Subsequent unrelated reloads may retain that decision while the relevant correction remains. Do not expose the decision in public JSON or resume before candidate validation.
- Only verified immutable candidates may activate. Preparation is credential-free, lifecycle-tracked, durably reserved, and serialized with image operations. Never update a running job or an operator source image. Pause/drain/stop and stale-candidate checks are authoritative at publication.
- Keep current, previous, source and live execution references during artifact collection. Recover uncertain preparation/commit outcomes by exact journaled ownership; never blindly recreate or force-remove a foreign/referenced artifact.
- Freeze the first successful Tart import as an owned digest before guest mutation. Runner installation retries clone that frozen source, including after restart; imported source revisions cannot be opened or sealed in place. Transfer preparation reservations atomically during import and clone.
- An unavailable startup Docker capacity probe blocks only new Docker acquisition until a successful bounded retry. Keep the engine ceiling separate from host capacity, and retain each execution's original allocation. Paused pools still check release metadata but cannot prepare or activate a replacement; scoped resume must preserve other pending pools' pauses.
- Release and owned-artifact cleanup retries use bounded backoff; share provider rate-limit deadlines across pools and collect unreferenced ready artifacts even after the final managed pool is removed. Retire expired idle runners through the existing busy-aware boundary while preserving busy work.
- Ordinary tests inject release transports and image builders. Real Docker/Tart validation remains opt-in and is distinct from live GitHub job certification.

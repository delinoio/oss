# servers-devhud-release-controller-contract

## Scope

This contract defines the operator-provided deployment boundary used by the dedicated DevHud release workflow. The repository does not select or hard-code the official API hosting provider. An operator may implement the boundary on any platform that can honor the exact OIDC, immutable-image, migration, updater, readiness, and rollback semantics below.

Maintainer recovery, backup/restore, store-delay, withdrawal, and high-severity procedures are documented in `docs/apps-devhud-operations-contract.md`. A CEF pin change is never performed by release-controller automation: it must be reviewed in `apps/devhud/cef-pins.json`, every authoritative Cargo and verifier pin consumer, every matching `Cargo.lock` source entry, the compatibility evidence, and a newly signed candidate before updater publication is considered.

## Identity and authentication

The controller base URL is the credential-free HTTPS variable `DEVHUD_RELEASE_CONTROLLER_URL`; `DEVHUD_RELEASE_CONTROLLER_AUDIENCE` is the exact GitHub Actions OIDC audience. Controller jobs request `id-token: write`, exchange the GitHub Actions request token for a short-lived audience-bound token, mask it immediately, and send it as a bearer credential. The controller must restrict that identity to the `delinoio/oss` `release-devhud.yml` workflow on `refs/heads/main`, the protected release environments, the workflow authorization revision in the token's `sha` claim, and the exact selected source revision. For a normal dispatch those revisions are identical. For an ancestor-recovery dispatch, `authorizationRevision` is the newer `main` dispatch SHA and `revision` is the selected original release SHA; the controller must independently resolve both commits in `delinoio/oss` and accept the pair only when `revision` is an ancestor of `authorizationRevision`. It must reject redirects, long-lived deployment credentials, mismatched project/version/revision/authorization-revision pairs, unknown fields, replay under another release identity, and attempts to mutate an unprepared release.

Every request is schema version 1 and binds project `devhud`, stable version, derived `devhud@v<version>` tag, 40-hex source `revision`, and 40-hex `authorizationRevision`. POST endpoints carry that identity in the JSON body; the GET status endpoint carries it as exact query parameters. Successful mutation and status responses contain `ok: true` plus the same project, version, revision, and authorization revision. Responses and logs must not include environment values, credentials, updater contents, database locators, object-store locators, or provider-private response bodies.

## Endpoints

- `POST v1/devhud/releases/preflight` is read-only. It accepts `publicAssetBaseUrlSha256`, the lowercase SHA-256 of the exact protected public-asset base URL, and must compare it with the same digest of the controller's runtime `DEVHUD_PUBLIC_ASSET_BASE_URL` before accepting the request. It authenticates deployment authority and validates the selected platform plus PostgreSQL and R2 connectivity/configuration. Its response has `ok: true`, the exact project/version/revision request identity, and `checks.postgresql`, `checks.r2`, `checks.public-asset-authority`, and `checks.release-controller` all exactly `true`; omission or any other value fails closed before store submission. The digest is not returned or logged.
- `POST v1/devhud/releases/prepare` accepts the immutable `apiImage` and `sweeperImage` digest references plus an updater input containing its SHA-256 and Base64 bytes. It verifies the digest references and updater digest, stages but does not expose updater manifests, runs the exact embedded migrations, confirms schema readiness, confirms both numeric non-root image users, and confirms that the API and sweeper contain the same administrator assets and migration closure.
- `POST v1/devhud/releases/<encoded-tag>/promote-api` promotes the prepared API and sweeper atomically or leaves the previous pair authoritative. It keeps updater discovery closed. Success requires `/healthz`, `/readyz`, `/admin/`, and Bootstrap to expose the exact release version and project.
- `POST v1/devhud/releases/<encoded-tag>/promote-updater` exposes all ten previously prepared stable signed updater manifests as one release boundary only after the GitHub Release is public. It must never serve a partial target set.
- `GET v1/devhud/releases/<encoded-tag>/status?<identity>` accepts the schema/project/version/tag/revision/authorization-revision query identity and reports closed channel values. Final verification requires `channels.api`, `channels.sweeper`, and `channels.updater` all equal `public` for the exact identity.
- `POST v1/devhud/releases/<encoded-tag>/rollback` is accepted only before any store package becomes public. It restores the previously recorded API/sweeper pair and keeps or restores the prior updater set. Once a store is public, the controller must reject automatic rollback and require a coordinated roll-forward or emergency withdrawal.

All mutation endpoints are idempotent for an identical release identity and identical immutable inputs. A conflicting retry fails closed rather than replacing prepared state.

## Runtime configuration contract

The controller validates and supplies these stable runtime input names without returning their values:

- Core deployment: `DEVHUD_ENVIRONMENT`, `DEVHUD_DATABASE_URL`, `DEVHUD_PUBLIC_API_URL`, `DEVHUD_LISTEN_ADDRESS`, `DEVHUD_TRUSTED_PROXY_CIDRS`.
- Logto: `DEVHUD_LOGTO_ISSUER`, `DEVHUD_LOGTO_AUDIENCE`, `DEVHUD_LOGTO_DESKTOP_CLIENT_ID`, `DEVHUD_LOGTO_IOS_CLIENT_ID`, `DEVHUD_LOGTO_ANDROID_CLIENT_ID`, `DEVHUD_LOGTO_ADMIN_CLIENT_ID`, `DEVHUD_ADMIN_REDIRECT_URI`.
- Identity and uploads: `DEVHUD_IDENTITY_HMAC_KEYS`, `DEVHUD_R2_ENDPOINT`, `DEVHUD_R2_ACCESS_KEY_ID`, `DEVHUD_R2_SECRET_ACCESS_KEY`, `DEVHUD_R2_STAGING_BUCKET`, `DEVHUD_R2_PUBLIC_BUCKET`, `DEVHUD_PUBLIC_ASSET_BASE_URL`.
- Cloudflare controls: `DEVHUD_CLOUDFLARE_API_TOKEN`, `DEVHUD_CLOUDFLARE_ZONE_ID`, `DEVHUD_CLOUDFLARE_RATE_LIMIT_RULE_ID`.
- Updater and sweeper: `DEVHUD_UPDATE_MANIFEST_DIR`, `DEVHUD_SWEEPER_BATCH_SIZE`, `DEVHUD_SWEEPER_INTERVAL`.

The preflight must fail if a required value is absent, invalid for the production server contract, does not match the request-bound public-asset digest, or cannot authenticate to PostgreSQL, R2, Logto, the public asset domain, or the selected deployment platform. The selected Cloudflare Pages project must report `main` as its production branch because the publication workflow deploys the candidate to `main`; a preview-only deployment cannot satisfy the public-doc boundary. The controller must use the server's documented migration command before promotion and must not manufacture, modify, or sign updater material.

## GitHub environment configuration names

The protected environments are `devhud-private-build`, `devhud-publication`, `devhud-store-review-approved`, `devhud-store-publication`, and `devhud-ga`. The following are stable GitHub Actions configuration names; documentation and dry-run output record names and presence only, never values.

Variables:

- Release destinations: `DEVHUD_APP_STORE_APP_ID`, `DEVHUD_GOOGLE_PLAY_PACKAGE_NAME`, `DEVHUD_GOOGLE_PLAY_MANAGED_PUBLISHING`, `DEVHUD_GOOGLE_PLAY_PRODUCTION_RELEASE_SERVICE_ACCOUNT`, `DEVHUD_CHROME_WEB_STORE_PUBLISHER_ID`, `DEVHUD_OCI_REGISTRY`, `DEVHUD_OCI_API_REPOSITORY`, `DEVHUD_OCI_SWEEPER_REPOSITORY`, `DEVHUD_OCI_PRODUCTION_PUSH_PRINCIPAL`. `DEVHUD_GOOGLE_PLAY_PRODUCTION_RELEASE_SERVICE_ACCOUNT` is the exact service-account email that an operator has confirmed holds Google Play `CAN_MANAGE_PUBLIC_APKS` for `io.delino.devhud`; it must match the credential principal before token exchange. `DEVHUD_OCI_PRODUCTION_PUSH_PRINCIPAL` is the exact registry username that an operator has confirmed can push both configured DevHud repositories; it must match `DEVHUD_OCI_REGISTRY_USERNAME` before any network access. `DEVHUD_OCI_REGISTRY` is a host-only registry authority; credentials, paths, queries, and fragments are rejected before any registry credential is sent. Both OCI repository variables must match the OCI Distribution slash-separated lowercase name-component grammar before preflight contacts an external boundary.
- Deployment/readiness: `DEVHUD_RELEASE_CONTROLLER_URL`, `DEVHUD_RELEASE_CONTROLLER_AUDIENCE`, `DEVHUD_PUBLIC_API_URL`, `DEVHUD_LOGTO_ISSUER`, `DEVHUD_PUBLIC_ASSET_BASE_URL`, `DEVHUD_PUBLIC_DOCS_URL`, `DEVHUD_PUBLIC_DOCS_ACCOUNT_ID`, `DEVHUD_PUBLIC_DOCS_PROJECT_NAME`.
- Signing identities and policy: `DEVHUD_CHROME_EXTENSION_ID`, `DEVHUD_MACOS_SIGNING_IDENTITY`, `DEVHUD_WINDOWS_CERTIFICATE_SHA256`, `DEVHUD_WINDOWS_TIMESTAMP_URL`, `DEVHUD_APPLE_TEAM_ID`, `DEVHUD_ANDROID_CERTIFICATE_SHA256`.

Secrets:

- Updater and desktop signing: `DEVHUD_CHROME_EXTENSION_PUBLIC_KEY`, `DEVHUD_UPDATER_SIGNING_KEY_B64`, `DEVHUD_MACOS_DEVELOPER_ID_P12_B64`, `DEVHUD_MACOS_DEVELOPER_ID_P12_PASSWORD`, `DEVHUD_WINDOWS_SIGNING_PFX_B64`, `DEVHUD_WINDOWS_SIGNING_PFX_PASSWORD`.
- Apple signing and store access: `APPLE_API_ISSUER`, `APPLE_API_KEY_ID`, `APPLE_API_PRIVATE_KEY_B64`, `DEVHUD_IOS_DISTRIBUTION_P12_B64`, `DEVHUD_IOS_DISTRIBUTION_P12_PASSWORD`, `DEVHUD_IOS_APP_PROFILE_B64`, `DEVHUD_IOS_WIDGET_PROFILE_B64`, `DEVHUD_IOS_WIDGET_INTENT_PROFILE_B64`.
- Android signing and Play access: `DEVHUD_ANDROID_UPLOAD_KEYSTORE_B64`, `DEVHUD_ANDROID_KEYSTORE_PASSWORD`, `DEVHUD_ANDROID_KEY_ALIAS`, `DEVHUD_ANDROID_KEY_PASSWORD`, `DEVHUD_GOOGLE_PLAY_SERVICE_ACCOUNT_JSON`.
- Chrome Web Store: `DEVHUD_CHROME_WEB_STORE_CLIENT_ID`, `DEVHUD_CHROME_WEB_STORE_CLIENT_SECRET`, `DEVHUD_CHROME_WEB_STORE_REFRESH_TOKEN`.
- OCI and documentation publication: `DEVHUD_OCI_REGISTRY_USERNAME`, `DEVHUD_OCI_REGISTRY_TOKEN`, `DEVHUD_PUBLIC_DOCS_API_TOKEN`.

`GITHUB_TOKEN` is the workflow-scoped GitHub credential. `DEVHUD_RELEASE_CONTROLLER_TOKEN` is minted from OIDC within each controller-facing job and is never stored as a secret. No stable configuration value may be printed, uploaded, copied into release evidence, or passed to static/dry tests.

Private updater, desktop, iOS, and Android signing material is scoped only to `devhud-private-build`. The later `devhud-publication` preflight must not duplicate those private keys: it requires the live destination, controller, store, registry, documentation, and identity configuration plus the dual-use Apple API credentials and Chrome extension public key. The selected candidate's independent revalidation is the signing-evidence boundary. Before accepting the App Store check, preflight uses the same Apple JWT on the read-only Users API authority surface and then validates the exact app bundle identity; a credential that cannot access that authority surface fails before any store mutation. Google Play exposes `CAN_MANAGE_PUBLIC_APKS` as the production-release permission but no read-only capability endpoint, so preflight fails before network access unless the protected production-release service-account prerequisite exactly matches the JSON credential's `client_email`; every later Google operation repeats that principal check. OCI Distribution has no provider-neutral read-only push probe, so preflight likewise fails before network access unless the protected production push principal matches the registry credential username. The later authenticated `/v2/` request proves registry connectivity and credential acceptance only; the operator-confirmed prerequisite binds repository push authority.

## Release boundaries

Infrastructure preparation occurs only after Apple, Google Play, and Chrome review is independently approved and held and the exact public-doc candidate has built successfully. The sole complete signed candidate and its candidate-bound, non-secret release-configuration fingerprint are retained for 35 days so a protected review can use the identical submitted bytes and destinations throughout GitHub's maximum workflow window. The binding is created before the first external release access and contains only schema/project/version/revision, immutable candidate identity, and the fingerprint—not configuration values. A recovery dispatch from a later `main` head accepts an optional exact lowercase 40-hex original revision only when it is an ancestor of that head, resolves the oldest retained artifact for the exact version and revision across every attempt of every matching historical or current recovery run, revalidates its original provenance run, requires the exact retained configuration binding, and refuses to create replacement signing output or adopt changed destinations. Every checkout, plan, controller request, store mutation, document identity, GitHub release target, verification, and rollback remains bound to that selected revision and original configuration even though the recovery workflow itself runs from the newer `main`; every controller request separately binds the newer workflow authorization revision to the OIDC `sha` claim and the selected ancestor. The live preflight probes a generated public-object route, treats its expected `404` as reachable without requiring a root object, and requires the controller's exact runtime public-asset authority to match the protected value's digest. API/sweeper promotion precedes store publication, but updater discovery remains closed. The updater input supplied to controller `prepare` contains only signed manifests and signatures and normalizes path ordering, UID/GID to zero, directory/file modes to `0755`/`0644`, timestamps to the Unix epoch, and gzip timestamps so retries reproduce the identical SHA-256. Before OCI publication, infrastructure preparation, updater exposure, public-doc deployment, protected store publication, cleanup, or final GA performs its first external check or mutation, that environment-bound job must re-resolve the complete fingerprinted variable set and match the retained preflight fingerprint. OCI publication then derives each multi-architecture source archive digest, requires Skopeo to preserve it during the registry copy, compares the resulting and remote digests, and signs only that candidate-bound immutable reference. Store publication, regular GitHub Release publication, updater exposure, and public-doc deployment are serialized. An absent exact App Store version is unsubmitted and is created only after the exact uploaded build is processed; an existing processing or processed build suppresses another transporter upload. A pending, approved-held, or public exact store version suppresses another package upload or submission, while terminal `INVALID_BINARY` is rejected so cleanup does not wait for an impossible transition. A terminal canceled exact App Store review submission is discarded so recovery creates or reuses a live draft instead of mutating the canceled submission. A recovery dispatch after one provider became public admits only the exact public/approved-held set, skips completed mutations, and publishes the remaining approved provider. The final store gate idempotently releases the approved Apple package and uses immediate/default Chrome publication for the approved staged revision before polling every exact version for up to 30 minutes. Same-commit retries require every store to be independently public and repeat no store mutation before resuming the downstream boundaries. An existing draft GitHub Release must expose the selected revision as its exact `targetCommitish` before the workflow removes unexpected assets, replaces the expected inventory, and publishes after reconciliation succeeds; an already-published release must resolve its remote tag to that revision and is immutable, so it is downloaded, authenticated against the retained candidate's signed inventory and provenance, and reused without any asset deletion, upload, or release edit. The deployed `/devhud` response must contain the non-secret version-and-revision identity injected into that exact candidate, and final verification requeries every exact store before resolving the live remote release tag to the source revision and checking the same marker plus the revision-bearing public index, the complete downloaded GitHub asset set, the complete extracted evidence archive inventory, and the exact keyless bundle set. Every published binary, evidence payload, and remotely served updater manifest must match the candidate's signed checksum and bundle, and every signed provenance statement must bind the same source revision. After the protected `devhud-ga` approval wait, the workflow again repeats the independent store, GitHub asset, updater, public-doc, API, OCI, and controller checks immediately before its first GA mutation. No downstream public mutation, cleanup, GA state, or announcement is permitted until the applicable fingerprint and checks confirm the validated identities and channels.

Every failure or cancellation after store submissions begin and before store publication enters automatic cleanup, including a failed or cancelled submission matrix leg, review/docs gate, OCI publication, infrastructure preparation, store-publication mutation, or final store-public polling failure or timeout. Cleanup first queries the exact Apple, Google Play, and Chrome versions and stops without mutation when any is public. It then requires protected operator removal of the held Google Play change, verifies that removal through the release lifecycle API, discovers and cancels the exact Apple review submission and current Chrome submission, and waits until every provider reaches its accepted withdrawn or terminal non-public state. The workflow records a promotion attempt before the remote call. After any such attempt, cleanup queries the exact controller status; it calls rollback when both candidate API and sweeper channels are `public`, skips the mutation only when both are `prepared`, and fails closed when the supposedly atomic pair disagrees, reports another matching state, or cannot be queried. If any package is already public or any held submission cannot be withdrawn, rollback fails closed without reporting restoration success.

## Validation

`scripts/release/devhud-release-controller.test.mjs`, `scripts/release/devhud-live-preflight.test.mjs`, and `scripts/release/package-devhud-updater-input.test.mjs` validate deterministic request binding, reproducible updater input, production-authority prerequisites, updater digests, exact response identity, reachable-empty asset probing, and controller runtime public-asset authority binding. `scripts/release/devhud-candidate-artifact.test.mjs` validates candidate and original-configuration discovery across historical and current run attempts. `scripts/release/devhud-store-release.test.mjs` validates absent/processing/processed App Store build polling, terminal invalid-binary classification, absent-version creation, and idempotent submission/withdrawal reconciliation. `scripts/release/validate-devhud-public-assets.test.mjs`, `scripts/release/devhud-public-release.test.mjs`, and `scripts/release/devhud-public-workflow.test.mjs` validate complete archive and bundle inventory, retained and protected-environment configuration fingerprints, source-bound OCI publication, state ordering, same-commit recovery, exact draft and published release-target validation, release-asset reconciliation, final store reverification, and rollback boundaries. `CI.yml` invokes these only through the deterministic release-fixture suite, with read-only permissions and no secrets; CI cannot call controller mutations, publish an OCI image, deploy, upload to a store, create a release, or push a tag. These tests use static/dry fixtures and never call a controller or publication service.

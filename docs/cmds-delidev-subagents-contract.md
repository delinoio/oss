# DeliDev native subagent observations

## Scope
Issue #1094 exposes native child ownership, lifecycle, available output, model and usage through the existing authenticated session resource boundary. Go owns adapters and publication in `cmds/delidev-cli`; `protos/delidev/v1` and `packages/delidev-api-client` own additive typed identifiers; `apps/delidev` renders read-only session observations. Issue #964 remains the complete product contract.

## Runtime and Language
Go server/Worker/CLI, generated Protocol Buffers/Connect bindings and the React desktop client. This profile supports Codex `0.151.0` API and Claude `2.1.236` API under their existing immutable account/model/relay assignments. The supported managed ChatGPT execution profile retains the same Codex observation and canonical service-model checks without granting API relay authority. Issue #1208 also supports the pinned OpenCode `1.18.32` API foreground task profile described below. Other harnesses and native versions have no child publication profile.

## Users and Operators
Authorized owner and paired clients inspect retained session observations. Only the originally assigned authenticated Worker publishes them. Native task tools may initiate children as part of the original harness execution; product clients receive no create, message, interrupt, restart or child-resume operation.

## Interfaces and Contracts
`SystemService.GetStatus` advertises `SUBAGENT_OBSERVATION_V1`; `EntityKind.SUBAGENT` is additive. Their wire values use main’s established allocation reservations (entity kind 30 and capability 12), leaving existing assignments unchanged. `ResourceService.GetResource`, session-filtered `ListResources`, snapshots and resource events retain their existing authorization and pagination. `delidev session subagents --id <session-uuid> [--limit <1..100>] [--page-token <opaque-token>]` uses the same authenticated resource read. The desktop Subagents disclosure requires the typed capability, refreshes on session/resource revisions and provides bounded first/next pages. Refresh and pagination issue reads only. Each child publication advances the session revision in the same transaction; the desktop uses that revision to refresh the child page and excludes child documents from the bounded transcript/control stream cache.

The desktop validates every member of its complete 50-record child page before rendering any child content. Require the original session envelope, kind/schema/revision/product identity, exact supported harness/version, execution/root/native hierarchy, closed bounded observation shape, ordered source coverage and matching first/last/latest source identities. Validate usage families and normalized-counter parity without rounding original native integer tokens, reject duplicate keys, and retain the original JSON strings for inert display. A malformed/foreign record or an inconsistent identity/known-parent graph makes the whole page unavailable and disables next-page traversal. Parents outside the bounded page remain permissible. Retained output/model/usage may come from earlier supported coverage; the latest task/activity omission cannot erase them or attribute them to its own incoming fields. This client validation remains an observation check, never new child authority or evidence of native execution.

The original Worker publishes `subagent-observed` through `WorkerService.PublishExecution`, with the same UUID-v7 receipt, exact monotonic sequence and immutable execution/native root/turn ownership. Each batch contains at most 128 observations and 512 KiB encoded data. Validate the complete batch before resource, session or event publication. Child records use separate UUID-v7 product IDs and retain exact native IDs, root, parent, optional original parent tool, harness/version, execution, first/last publication sequence and original source identifiers. The execution tree admits at most 1,024 retained nodes, 128 live nodes and 512 KiB of metadata. Reject foreign parents, cycles, duplicated batch identities, reused product/native ownership, reparenting, changed original tool references and terminal regression atomically. Same-session native ownership cannot be reused by another execution. One bounded batch ownership query checks retained native/product/execution identities and original Claude parent-tool claims before writes, including terminal children from earlier executions of the same session. A fresh native/product child identity cannot reuse an earlier tool claim. The query avoids per-child scans of large source-coverage documents. Exact receipt replay returns the original result and creates no duplicate resource or event.

Codex consumes canonical `collabAgentToolCall` and `subAgentActivity` items, including the latter’s string-valued activity kind. Spawn ownership comes from the original sender/receiver relationship; activity paths cannot invent a parent. Child thread-start notifications cannot allocate ownership: retain them only after a spawn or validated descendant inventory has proved the same child and parent. An unmatched start remains discarded metadata until that independent ownership evidence is available. Read-only `thread/list` with `ancestorThreadId`, `useStateDbOnly=true` (no rollout metadata scan/repair) and child source filters validates exact native session-tree, parent, provider and version metadata. Bounded `thread/turns/list` reads the latest child turn with full items. Descendant inspection never calls child `thread/resume`, input or control operations. History reads have a 30-second cancellable deadline and are limited to 16 list pages and a 128-node complete observation batch; overflow returns failure without partial publication. Every root completion performs the same state-DB-only inspection, including executions without prior spawn/activity evidence; missed notifications cannot grant child-free cleanup or continuation. Known child notifications never become root transcript/usage. Codex records reject Claude-only task/tool fields atomically. An explicitly observed original requested model cannot be replaced by later reports. Requested spawn models remain distinct from observed settings models; thread metadata or parent configuration cannot supply an absent observed model.

Claude composes original `local_agent` tasks with acknowledged root Agent/Task proposals, or a nested Agent/Task tool retained from that parent's verified content. A new Claude native child must first publish `claude-task` with its original task metadata and that verified parent-tool relationship. Content/history sources update only already retained exact ownership; copying task metadata onto either source cannot create a child. Apply this requirement to root and nested children and reject the complete batch atomically before publication. Each original parent tool owns at most one child; validate that unique claim across the complete batch and retained tree before publication, including after child completion. Distinct original tools may own independent children. Task depth, agent type, description and explicit background/transcript/ambient flags remain native observations. Later explicit task flags and description patches are acknowledged before changing retained metadata; skip-transcript cannot be cleared after it was observed true. Task receipts omit output/model fields absent from the current task source, while retained last-available values remain readable. Forwarded user/context and tool-result messages supply history proof only, never recent assistant output. Original session/input/turn and parent-tool identity bind child content independently of root-result arrival. Ordered text/thinking blocks retain native kinds and message identity; opaque bodies/signatures/media remain unavailable. Task summaries and output locators cannot supply verified child transcript or authorize file reads. Stored-history projection follows the existing private derived-path, complete transcript, original forwarded-message proofs and exact task/tool/agent sidecar verification, including retained native description and spawn depth. Missing description/depth leaves stored history unavailable. Project output/model/usage only from the verified selected leaf ancestry; abandoned sibling branches remain outside the published observation. It remains a stored observation, never a synthetic stream or continuation checkpoint. Missing, unavailable or unsupported history preserves the already retained observations.

Statuses are pending, running, paused, completed, failed, interrupted, shutdown or unavailable. Unavailable cannot establish terminal cleanup. Native shutdown may refine a terminal status; it cannot reopen, and late Codex turn completion/history retains the explicit shutdown lifecycle. Root completion cannot finish children; a terminal child cannot finish its running descendants. Exact owned child observations may arrive after root completion, before independent cleanup confirmation. Live children keep the process/cleanup obligation open. Closed children still require the original process and workspace cleanup report. Sessions with observed children use version-1 paused completion and cannot acquire version-2 continuation or history-recovery authority from this profile. The same-account Codex Fork boundary independently requires a version-2 checkpoint, so even a completely closed observed child tree cannot authorize Fork.

Output is an explicitly partial recent native text subset, not a reconstructed complete transcript. Publication rejects any supplied output with an omitted or false partial marker before committing any member of its batch; absent output remains unavailable. Output, requested model, observed model and usage are nullable; missing remains unavailable, including an unobserved model even when a requested model is known. A record retains its last available output/model/usage when a later status report omits it. Original source coverage is retained without truncation, capped at 4,096 reports per node and the existing resource document bound.

Incoming telemetry is validated before merging retained last-available facts. `claude-task` cannot supply output or an observed model. `codex-activity` cannot supply output, observed model or requested model. `codex-collaboration` can supply its native partial text and original spawn model, but not an observed model or content blocks. Codex history and Claude content/history retain their independently verified output/model profiles. Existing source-specific usage validation remains mandatory. A later task/activity omission can leave earlier verified content/model/usage readable without attributing those retained fields to the new report.

Usage records retain exact nullable decimal-string counters and closed `child-cumulative` or `child-response` scope. Codex native cumulative/last/context metadata, Claude task counters and Claude provider-response metadata remain exact validated JSON strings, preserving large integer spelling, zeros, nulls, cache/thinking/tool details and native report families. Each source coverage entry retains only the usage actually supplied by that report. The Worker runner routes forwarded child provider usage only through the child-content adapter; its root-only usage adapter ignores only an exact acknowledged child report with unchanged session/input/turn, parent-tool, model and usage. The bypass binds the original report's model presence and value at receipt acknowledgment, including receipt replay, independently of the child's retained last available model. Clearing a reported model or inventing an originally absent model blocks publication; a genuine missing model remains unavailable in that report. A child tag alone cannot bypass original root-source validation. These counters never enter response billing rows, cost estimates, budget arithmetic or parent-inclusive totals. Reports with overlapping scopes are not added; unavailable counts are not zero and a total is never fabricated from partial counters.

Shared Worker/server batch validation requires a nonempty report of at most 64 KiB whenever usage is supplied. Only `codex-history` carries Codex `total`/`last`/`modelContextWindow` usage with the pinned six-field token-count schema and existing native nonnegative/required-count validation; normalized total/input/output exactly match its cumulative fields. `codex-collaboration` and `codex-activity` carry no usage. `claude-task` requires all three native unsigned uint64 task counters (`total_tokens`, `tool_uses`, `duration_ms`), cumulative scope, exact normalized total and unavailable input/output. `claude-content` and `claude-history` require response scope and the closed Claude provider graph, with its signed nonnegative integer counters, nested cache/thinking/tool/fallback/iteration metadata and bounded native enums; normalized input/output match exactly and total stays unavailable. Nullable parity distinguishes unavailable from measured zero. Unknown or case-aliased fields, duplicate keys at any depth, wrong families/scopes, invalid native counters and counter mismatches reject the complete batch before any durable write. Claude numeric counters are converted only in a temporary validation copy to reuse the existing shared decimal-string provider schema; retained native JSON bytes are never rewritten. Absent native reports are represented by unavailable usage, not unproved normalized counters.

## Codex child configuration
Issue #1101 adds independent `SystemCapability.CODEX_SUBAGENT_CONFIGURATION_V1` 22 and `WorkerCapability.CODEX_SUBAGENT_CONFIGURATION_V1` 11, reserved by that original issue before activation in the approved integrated PR. A server capability does not establish native or account acceptance. Unsupported original Workers receive explicit update guidance before the execution claim is committed.

Map only `agents.default_subagent_model`, `agents.default_subagent_reasoning_effort` and numeric `agents.max_concurrent_threads_per_session` in the pinned `thread/start`, `thread/resume` and same-account Fork configuration. Empty model/effort and zero concurrency omit their native keys. Concurrency retains the existing uint32 representation without a product maximum of 64; explicit efforts are bounded exact strings whose support is decided by native execution. Approval-review model remains unsupported. Root model/effort observations retain their independent validation.

Before the first snapshot digest, resolve an explicit child native model to exactly one canonical model from the parent's API provider or subscription service. Require Codex compatibility under the same selected account. Retain its UUID, revision and exact native model in the immutable execution configuration. Continuation and active authority recheck the original UUID/native identity and account compatibility, never resolve today's Agent or a replacement model. Catalog renaming/removal cannot substitute another child model. No new migration is needed for this additive snapshot field; historical omitted snapshots retain their exact digest.

The API relay admits only the immutable parent and explicit child model, with the same account, connection, provider and cancellation lifetime. Narrow each HTTP request to its own canonical model ID before diagnostics and response-reference persistence. A child's native response cannot authorize a parent's previous-response lookup. Title authority remains one model. Existing omitted child-model profiles retain their original root-only API relay. Requested child defaults and spawn models are distinct from independently observed child settings. Worker and server validate both requested and supplied observed model against an explicit snapshot before atomic publication, while absent observed values remain unavailable. These settings grant no child control or continuation authority.

The desktop gates editing these Codex fields on the typed server capability, displays exact saved child references in the execution snapshot, and leaves child observations in Subagents. The existing authenticated configuration RPC, CLI JSON configuration and generated resource client carry the same options and snapshot. Saving an Agent does not establish native execution or actual model use.

## OpenCode foreground children

Issue #1208 activates independent System capability 23 and Worker capability 12, retaining the shared authenticated resource/CLI/desktop and ordered Worker publication boundaries. OpenCode dispatch requires the negotiated Worker profile and exact pinned installation. The original owned native configuration fixes `subagent_depth=1` and leaves experimental background support disabled; the complete effective configuration remains independently compared.

A foreground child requires both the original accepted root task message/part/call metadata and an independent authenticated child-session read proving its exact `parentID`, project, directory, pinned version, creation boundary, same provider/model and original subagent type. A product `opencode_tool` reference joins the already acknowledged root tool UUID to its native message/part/call. The first source is `opencode-task`, with no output, observed model or usage. Bounded early child arrivals remain private until both ownership proofs agree and cannot acknowledge root input. The Go API relay validates complete foreground task arguments before executable tool-call frames reach native code, rejecting task reuse/background/unknown fields even when split across provider frames. Task reuse, nesting, promotion, background execution, alternate model/variant and child questions/permissions are unsupported; no child response or control is introduced. The common native tool wrapper's original truncation flag/locator remains inert metadata and grants no file reads.

Child events trigger independent original-session history reads recorded as `opencode-child-history`; an event trigger is not mislabeled as direct content. The complete bounded 1,000-message page must have no next cursor, exactly one original task prompt and independently owned chronological assistant/part history. Preserve original message/part IDs, same account/model, available partial output, terminal state and exact response counters, including cache/reasoning and unavailable total. Never add child counters to root units, prices or inclusive aggregates. Unsupported content and incomplete pages fail rather than being truncated or synthesized.

Every root completion reads its independent child inventory, including roots without earlier task observations. Known task completion or omitted active status cannot establish child settlement. Every native success/error projection requires the assistant completion time, ended text/reasoning and terminal tools through one closed child message/part predicate. Unclosed histories retain running partial output and usage; busy status remains running even when the native parts have closed. Original Stop uses native parent interruption and independently reads the complete known child inventory before original process cleanup; it never adds a child abort endpoint. Pinned 1.18.32 can cancel a foreground child without persisting its assistant terminal record. Retain that unfinished native history and publish `opencode-child-scope-cleanup` with the original verified interrupted Stop and joined process cleanup, reporting `interrupted` rather than native success or failure. The server independently requires the original canceled job, root input part and interrupted task, and binds the identical Stop proof across child and root publications. HTTP success or an omitted active status cannot create this source. Unknown, missing or unsupported children keep recovery and cleanup obligations open; cleanup failure never publishes child closure. Remove the pinned unfinished-history workaround when the native profile durably settles every aborted child, retaining independent process cleanup. Event-stream transport reconciliation cannot borrow the root-only proof for a child-bearing history. Both native and Worker checkpoint retention reject observed children even after they close; complete cleanup reports remain version 1 and paused. Actual account/platform acceptance remains separate from isolated native scripted-provider execution and fixture/build validation.

## Storage
Existing generic session-owned resource storage retains child observations; there is no destructive migration, backfill or new secret table. Execution progress retains bounded ownership metadata only. Durable request receipts retain the exact original event payload. Resource updates, revision advancement and event/session publication occur in one transaction, including rejection after root completion. Output and observations remain protected retained conversation data with existing session/server retention; no cloud storage or telemetry export is introduced.

## Security
Revalidate original Worker/process/job and client authorization under the existing publication/read contracts. Ownership derives from native identity evidence, never paths, prose, requested models, task summaries or model-proposed identifiers. No account/provider fallback, child-control capability or reconnect replay of native side effects is granted. Claude history uses only the existing verified owned transcript reader. HTML/text/native JSON is rendered inertly; unsupported opaque content stays private. Tests use isolated temporary state and controlled native/provider fixtures without user credentials.

## Logging
Use existing structured redacted publication and owned-process diagnostics with job/execution identity, closed event kind and stable failure class. Retain missing history as unavailable and its existing bounded history-read diagnostics. Never log child output, task descriptions, model-proposed paths, transcript bodies, native reports, secrets or provider diagnostic text.

## Build and Test
Run `go test -race ./cmds/delidev-cli/...`, `go vet ./cmds/delidev-cli/...`, `pnpm proto:check` and `pnpm test` in `apps/delidev`. Focused fixtures cover nested/two-child ownership, atomic foreign/cycle/reuse rejection, exact receipt replay, late completion, unavailable versus requested/observed models, exact overlapping usage, ordered Claude content, read-only Codex history operations and live-child cleanup. Hydrate required LFS assets, explicitly generate required package/embed `dist` and remove generated `dist` before finishing. Fixture verification is distinct from unperformed real-account, native platform and release acceptance.

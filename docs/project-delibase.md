# Project: delibase

## Goal
Provide reusable organization, team, catalog, billing, and metered-usage infrastructure for DeliDev and future mini-app services.

This index establishes the documentation and ownership contract for issue [#722](https://github.com/delinoio/oss/issues/722). The repository contains the delibase Go/PostgreSQL runtime and its tests; this contract is not evidence that the API is publicly activated or deployed.

## Project ID
`delibase`

## Domain Ownership Map
- `servers/delibase` (`server`): Go/PostgreSQL/sqlc service and its operational configuration.
- `protos/delibase` (`api`): shared `delibase.v1` Protobuf and generated Connect-compatible client boundary.

`servers/internal` is repository-shared Go infrastructure consumed by this project. It remains a shared package boundary and is not silently assigned to delibase or another unrelated project.

## Cross-Domain Invariants
- Canonical API origin: `https://delibase.deli.dev`; this is a future canonical origin and must not be represented as an active deployment in this issue.
- The six Connect services are `AccountService`, `OrganizationService`, `TeamService`, `CatalogService`, `BillingService`, and `UsageService`, all under `delibase.v1`.
- Human APIs use Logto user access tokens except for anonymous `CatalogService` reads. Live-user usage mutations require a Logto M2M token plus the dedicated, redacted `x-delibase-forwarded-user-token` metadata key for end-user context; bounded authorized-usage mutations require only the M2M bearer and must never require or store a forwarded user bearer. Delibase validates issuer, the canonical `https://delibase.deli.dev` audience, expiry, scopes, service allowlists, organization membership, and effective team access. Raw Logto client secrets remain provider-side and are never accepted as API credentials. Authenticated invitation preview and acceptance use the invitation bearer token instead of a pre-existing local account, organization membership, or team access; acceptance creates the active local account with a privacy-safe non-empty placeholder display name when needed, and records each account's first acceptance before granting memberships so a removed account cannot reuse the link to restore access.
- Team operations establish organization membership before resolving requested team identities so non-members cannot distinguish existing team IDs from absent ones.
- Repository-shared packages under `servers/internal` validate and context-bind Logto user/M2M authentication, require explicit fail-closed route policies, rotate cached JWKS keys without blocking fresh cached-key validation or accepting unsafe redirect targets, strip raw credential headers, propagate request/trace IDs across unary and streaming failures, map authentication failures to vetted stable reasons while treating only explicit signing-key provider unavailability as a retryable dependency failure, enforce conservative HTTP handler/CORS defaults under partial configuration, recursively redact diagnostic containers, emit allowlisted shape-validated pseudonymous `slog` events, and generate UUID v7 IDs. They do not own or infer delibase authorization or billing state.
- Delibase owns local user profiles keyed immutably by their original unique Logto `sub` values, organizations, memberships, roles, teams, invitations, catalog configuration, billing ledger, reservations, and audit records. Logto owns identity authentication; Polar owns payment settlement and invoices.
- Polar uses the selected official production/sandbox API by default. A compatible provider API override is optional and must be HTTPS without credentials, query, or fragment.
- Persisted entity IDs use UUID v7. Money is signed 64-bit USD micro-units; meter usage is signed 64-bit integer units. Overflow, negative reservations, and invalid precision are rejected.
- PostgreSQL constraints, transactions, and organization-scoped locks enforce at least one active Owner and exactly one Polar customer for every committed organization, immutable organization/team-membership and provider identities, immutable retained slug aliases and one-way organization deletion, at most one active subscription with retained historical subscriptions, newer Polar reactivation of scheduled-canceled subscriptions while revoked subscriptions remain terminal, retained organization-scoped refund provider-order bindings and monotonic provider-event/reversal/chargeback state whose increases transactionally match retained paid-cycle reversal totals, immutable paid-cycle provider/subscription/period identities and original period bounds whose reversal totals increase only to match retained refunds, append-only ledger, reservation, webhook inbox, integration-outbox, deletion-job, and audit behavior, validated running balances, serialized team hierarchy moves, organization-scoped billing references, non-overlapping effective price/billing-period windows, valid invitation acceptance state, effective catalog price and meter-TTL reservation snapshots, storage-derived active reservation creation times, active-account, effective-team-access, credit-capacity, and active-subscription current-period overage-capacity revalidation for immutable usage-record-driven reservation commits, overage settlement within required snapshotted billing-period windows, credit-only settlement without a period snapshot when no period contains the commit, matching hold-release ledger entries before reservation release/expiry, a deferred one-to-one Polar-outbox requirement for every nonzero-overage usage record whose payload matches the immutable organization, usage-record ID, Polar event-name snapshot, commit timestamp, and overage micro-units, immutable integration-outbox event bodies and deletion-job targets, held credit/overage splits, and concurrent reservation limits against available credits plus active-subscription current-period configured overage. Outstanding refund shortfall after a renewed paid grant carries into the renewed current period, while append-only reconciliation adjustments remove carried shortfall when reordered grants clear the organization-level debt. Deleting organizations cannot accept new reservations, while authoritative Polar refunds and chargebacks continue against retained billing history. Active reservations retain live organization/team/membership, service-allowlist, and Polar-meter references; finalized usage and billing history retains snapshots without blocking operational deletion, and blocker-gated deletion or membership removal fully expires relevant TTL-ended reservations before checking those references. Webhook inbox rows retain bounded validated payloads for retries, while immutable audit rows accept only empty system or pseudonymous actor references and allowlisted request metadata that rejects credential-shaped correlation identifiers; automatic reservation expiry, explicit reservation release, hosted billing-portal sessions, and subscription checkouts have distinct typed audit events.
- Polar usage delivery omits credit-funded settlement and reports only nonzero locally settled overage as chargeable USD micro-units.
- Persisted Polar meter identifiers must satisfy the provider request-shape boundary before migration copies them into immutable usage snapshots. Global usage expiration must paginate beyond full failed-organization candidate pages so healthy later organizations remain eligible in the same batch.
- Subscription checkout creation durably claims one provider-idempotency attempt per organization before the provider call. The same request digest may recover an ambiguous or post-provider-success failure, while distinct keys remain blocked. Successful checkout expiry, audit, and idempotency finalization is atomic and removes the attempt; a definitive provider rejection clears it. An unexpired successful checkout blocks another checkout until expiry. Billing summaries prefer an active subscription, otherwise expose an unexpired checkout as checkout-pending, and select the newest provider event from inactive subscription history.
- Delibase reliability enqueueing participates in caller-owned sqlc transactions. Accepting account or organization deletion atomically enqueues one immutable Deck lifecycle call and one immutable RealQA lifecycle call, both keyed by the delibase deletion-job UUID. Separate feature-scoped M2M identities may invoke only the corresponding API's typed `DeleteFeatureData` lifecycle mode; absent feature data is an idempotent success, and DeliDev browser code never receives either identity. Multi-worker delivery uses skip-locked leased claims and claim-token compare-and-set transitions. Exactly 12 normal attempts use capped exponential backoff with injected jitter; retained dead letters retry every 24 hours until success, including automatic recovery when a twelfth claim expires after a crash. Handler, event, operation, deletion-job, audit-event, decision, and result identifiers are stable typed values rather than free-form worker controls.
- Organization, team (including confirmed non-`General` subtree deletion and Admin organization-deletion exclusion), invitation (including distinct acceptance/revocation idempotency operations), account-deletion, credit, reservation, settlement, refund, cancellation, and webhook semantics are defined in the server and proto contracts and must remain additive/versioned. Idempotency keys are scoped to the authenticated user subject and operation for human RPCs, or the authenticated service identity and operation for M2M RPCs; live-user usage digests additionally bind the forwarded user subject. Authorized reserve/commit/release digests bind authorization, authenticated service, purpose, resource, UTC period, and units, with commit/release also binding the reservation ID; resource-deletion digests bind authorization, service, purpose, resource, and expected revision.
- Issue #756 adds bounded background usage without a seventh service. `BillingService` owns human create/get/opaque-list/revoke methods and `UsageService` owns M2M-only authorized reserve/commit/release plus idempotent feature-resource deletion notification. Public catalog meters expose stable service authorization targets and safe names without Logto client IDs or credentials. UUID v7 grants bind the authorizer, personal or organization resource owner, payer organization/team where applicable, exact service identity/meter, `REALQA_STORAGE`, feature-resource UUID, `UTC_DAY`, maximum units, closed lifecycle status (`ACTIVE`, `REVOKED`, `ACCESS_LOST`, `RESOURCE_DELETED`, or `OWNER_DELETED`), revision, and timestamps. Reserve accepts only the current or immediately preceding UTC day according to server time; commit/release use the reservation's stored period. Membership/deletion flows never wait on a grant; affected grants fail closed immediately, every reserve rechecks current access, and stable reasons classify substitution, access loss, invalid status, period-limit overflow, and altered replay. Deck has no background purpose.
- Held usage reservations block organization-member removal and self-leave with the stable member-active-reservations reason.
- Root Protobuf sources live at `protos/delibase/v1/`; generated artifacts are derived and must not become a second source of truth.
- Reproducible generated consumers live at `protos/delibase/gen/go` and `protos/delibase/gen/ts`; the latter is the private workspace package `@delinoio/delibase-connect`. Root `pnpm generate:proto` generates both runtimes and builds the package's loadable `dist` exports; `pnpm check:proto` is the canonical compatibility entrypoint.
- The issue scope is artifact-only: validate/build the app, validate/generate the API, test/build the server artifacts, and allow only pushed core `delibase@vX.Y.Z` tags whose derived OCI version is at most 128 characters to publish the exact validated, signed, and attested `ghcr.io/delinoio/delibase:vX.Y.Z` two-platform OCI index. Each architecture receives its own SPDX JSON inventory. The public version tag is created only after both inventories and GitHub provenance/SBOM attestations succeed, and an existing version may be accepted only when it already resolves to the same digest. A serialized newest-version gate alone advances `:latest`. Do not activate or deploy either service.

## Change Policy
- Any API change updates this index, the app index/contract, the server contract, the proto contract, and the relevant `AGENTS.md` files.
- Any shared Go package change updates this index, [servers-internal-foundation](servers-internal-foundation.md), the server contract, and `servers/AGENTS.md`; shared packages remain unassigned unless a later ownership decision explicitly changes the boundary.
- Any data, billing, identity, team, or authorization change updates all affected contracts and their validation commands together.
- Changes to artifact scope, tag triggers, GHCR image names, Pages output, or configuration ownership update this index and the affected domain contracts before CI/release changes.

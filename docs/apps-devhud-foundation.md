# apps-devhud-foundation

## Scope

- Project/component: `devhud` / `app`
- Canonical client/native implementation path: `apps/devhud`
- Status: active base application plus shared native authentication/session foundations and one registered closed internal production tool, RealQA, on macOS, Windows, and Ubuntu only. The app consumes the private `devhud.realqa.v1` generated package through a closed native protobuf procedure table and separate exact-origin signed-PUT command, and contains the dependency-injected preset/destination/template, capture/review, submission/reconciliation, billing-grace, deletion, and rebind product surface. The signed-out base shell remains usable, iOS and Android retain the empty mobile shell with no RealQA entry or authority, and prior-bound offline access is limited to capture/edit/encrypted drafts until online reauthentication. The existing platform capture/editor, AES-256-GCM local-draft, unpublished Chrome MV3/native-host, native Logto PKCE, concrete macOS 14+, Windows 11 x64/ARM64, Ubuntu X11/XWayland/native-Wayland, and bounded diagnostics foundations remain in force. Deck remains unregistered, and there is no visible/distributed widget, production Chrome identity, public extension/store publication, DNS/R2 provisioning, deployment, catalog activation, or rollout.
- The dependency-injected Deck refresh controller, private `devhud.deck.v1` generated client, client-owned refresh timing, preflight, widget freshness, and notification-resolution foundations are implemented but remain unregistered and disconnected from a live native transport.
- The implemented dependency-injected RealQA online-submission coordinator consumes encrypted draft envelopes, enforces the exact 60,000-byte preflight and a fresh public-screenshot warning/confirmation for every attempt, reuses one persistent UUID v7 across create/reconciliation, sequences private uploads, and retains the encrypted draft for cancellation, overflow, and failed or ambiguous outcomes. Its native encrypted-vault and closed Connect/signed-PUT bindings are restricted to the authenticated desktop composer.
- The current implementation includes tray-resident desktop window lifecycle, transactional global shortcuts, explicit autostart, pointer-monitor HUD placement, preview DevTools, a typed local update action, cross-window theme reconciliation, surfaced startup integration failures, provider-owned persisted System/Light/Dark state, internal registry filtering, target-isolated desktop CEF and mobile system-webview runtimes, five exact window/platform capability manifests, bundled-resource response hardening, deny-by-default CEF networking, scoped native commands, Swift/Kotlin shared-data adapters, non-distributed native widget fixtures, generated native host sources, and deterministic local and host validation commands.

## Runtime and Language

- Frontend runtime: React with TypeScript, built by Rsbuild.
- Native runtime: Tauri Rust application under `src-tauri`.
- Desktop runtime: Tauri's upstream CEF runtime from the `feat/cef` line, pinned exactly to commit `f49ebda2fdba5755456b0f049e32593ca0ea331a` with `@tauri-apps/cli-cef` `3.0.0-alpha.6` in lockfiles. The implementation must not build from a moving branch.
- Mobile runtime: standard Tauri iOS WKWebView and Android System WebView. Mobile must not compile, link, embed, or launch the desktop CEF runtime.
- Desktop operating systems: macOS 14 or newer, Windows 11, and Ubuntu 24.04 LTS.
- Desktop architectures: separate x64 and ARM64 builds for each supported desktop operating system.
- Linux display support: X11, XWayland, and native Wayland capture through the interactive `xdg-desktop-portal` approval boundary.
- Mobile operating systems and architectures: iOS 17.0 or newer on `arm64` production devices and `x86_64` CI simulators; Android 10/API 29 or newer on `arm64-v8a` and `armeabi-v7a` production devices and `x86_64` CI emulators.
- UX baseline: English-only, System/Light/Dark themes with System initially selected, Toss Design Guidelines, and WCAG 2.2 AA. The product uses the DevHud wordmark and minimal `DH` lettermark; a complete brand system is out of scope.

### Visual asset foundation

- The visual boundary is intentionally limited to the existing DevHud wordmark and a reusable `DH` lettermark. Its canonical source is `apps/devhud/assets/source/devhud-lettermark.svg`; `pnpm assets` deterministically generates the Tauri desktop PNG, ICO, and ICNS icons, tray/menu-bar templates, installer/application/launch images, iOS app and launch catalog images, Android launcher densities, and English store-listing images under `apps/devhud`.
- Asset regeneration removes obsolete manifest entries only when their resolved paths remain inside the approved generated-asset directories; malformed or traversal paths are ignored during cleanup.
- The documented `mobile:generate:android` and `mobile:generate:ios` workflows reapply and validate canonical assets after Tauri regenerates each native host, so generated launcher, AppIcon, and LaunchLogo resources cannot silently revert to platform defaults.
- Generated PNGs use the same blue/white treatment in System, Light, and Dark contexts; opaque iOS catalog icons, Android launcher icons, store listings, and Windows/Linux tray assets are 8-bit RGB, while transparent outputs such as macOS tray templates are 8-bit RGBA. The ICO and ICNS desktop containers wrap deterministic PNGs generated from the same source. The Google Play listing uses a distinct 512×512 icon and an opaque 1024×500 feature graphic. `pnpm check:assets` validates dimensions, PNG color formats, decoded alpha coverage, native container signatures, contrast, safe names, source hash, deterministic regeneration, Tauri inclusion, native host inclusion, and accessible store metadata.
- The iOS release application consumes only its generated app/launch asset catalog and the Android release application consumes only generated launcher resources. The compile-only WidgetKit/AppWidgetProvider projects receive no release asset dependency and remain unembedded/unregistered. No widget artwork, product tool illustration, campaign graphic, website asset, or broader brand system is included.

### CEF desktop runtime

DevHud uses Tauri's pinned CEF runtime directly for desktop builds. Desktop implementation and release validation covers the following behavior on macOS, Windows, and Ubuntu, for x64 and ARM64 where supported:

- CEF sandbox startup using only bundled frontend assets.
- Tauri IPC and capability enforcement.
- Tray/menu-bar lifecycle, global shortcuts, launch-at-login integration, theme handling, DevTools, explicit process shutdown, and clean helper-process cleanup.
- Signed or sign-ready DMG, NSIS, AppImage, and deb packaging.
- Tauri updater compatibility and signed updater bundles.
- No orphaned CEF processes after normal shutdown. Cleanup evidence must observe at least one CEF helper before shutdown and zero helpers afterward.
- Ubuntu 24.04 operation under both X11 and Wayland through XWayland.

DevHud must not fork Tauri, WRY, or `cef-rs`, and must not carry local source patches to the upstream runtime. Runtime, product, mobile, packaging, and release work may proceed against the exact pinned dependency while preserving these upstream-only dependency boundaries.

## Users and Operators

- Primary actors: an individual developer using the signed-out base shell, and an authenticated DeliDev user using a bounded Deck or RealQA feature.
- Secondary actors: organization Owners/Admins managing organization feature resources, DevHud maintainers, release operators, and feature-service operators.
- System actors: the desktop tray, global shortcut, launch-at-login and updater facilities; WKWebView; Android System WebView; Logto; the future Deck/RealQA services; separate Deck and RealQA GitHub Apps; the RealQA Chrome native host; GitHub Releases; TestFlight; and Google Play.
- Explicitly excluded actors: remote mini-app publishers, external plugin/tracker authors, arbitrary remote UI providers, GHES/custom-host operators, and unauthenticated users attempting to enter Deck or RealQA.

## Interfaces and Contracts

### Internal tool registry

The registry is an internal, closed contract, not a plugin interface. `ToolDefinition` must contain:

- a stable lowercase kebab-case `toolId`;
- English name, description, and search keywords;
- a supported-platform enum set;
- a required-capability enum set; and
- an internal UI entrypoint.

Tools may support a subset of platforms. Each shell exposes only tools supported by the current platform and granted capabilities. Capability values are closed and enum-backed; a new capability is introduced only with the tool that needs it. Production registration is currently empty; tests may use fixture definitions. Deck and RealQA may later be added as explicit internal registrations governed by this document and their server/proto contracts. No external plugin authors, third-party tools/trackers, user-authored scripts, runtime code downloads, remotely supplied UI, arbitrary remote assets, or plugin SDK are authorized.

The native boundary exposes only scoped Tauri commands required for settings, application lifecycle, diagnostics, updates where supported, the versioned widget-state record, and separately contracted Deck/RealQA windows and native operations. Diagnostics export is one record-free command with no destination argument: its native host owns the save picker and returns only `exported` or `cancelled`, while failures return a stable classification without a path or underlying exception. DevHud exposes no CLI or public/local API. The only future loopback listener is the one-shot random-port desktop Logto callback at the stable registered `/auth/callback` path; the only future mobile link is the verified Deck callback `https://deli.dev/auth/devhud/callback`; the only extension bridge is the exact-origin signed RealQA Chrome Native Messaging host. Business operations remain the versioned feature Connect contracts, carried by a private Rust transport adapter available only to authenticated feature windows. The sole signed-out exception is native lifecycle cleanup calling exactly `DeckDeviceService.UnregisterDevice` with the OS-vault single-registration revocation grant and no webview-supplied input. The adapter accepts a closed generated service/procedure identifier and bounded protobuf payload, maps it to a compile-time exact feature origin, injects either memory-only user authorization or that procedure-specific cleanup grant as native metadata, rejects redirects, and returns a bounded Connect response. It accepts no caller URL, HTTP method, header map, or generic request. RealQA image upload is a separate native operation that accepts only the short-lived capability returned by `CreateImageUpload`, requires exact `https://assets.realqa.deli.dev` origin and PUT method, binds the declared content type/checksum/size, rejects redirects, and cannot issue GET or another request. RealQA capture is a separate desktop-only typed native procedure set available only to its authenticated feature window: it enumerates bounded display/window choices, starts or cancels a user-initiated closed region/window/display/multi-monitor mode with an explicit pointer flag, uses the platform picker or `xdg-desktop-portal` where required, and returns only the selected pixels plus bounded geometry/source metadata to the editor/draft boundary. It exposes no continuous stream, arbitrary screen read, caller process handle, raw OS API, or cross-window capture authority. Native errors remain stable enum-backed classifications.

Authenticated full-feature RealQA client code must import the private `@delinoio/devhud-realqa-connect` workspace package through its root or versioned `./devhud-realqa/v1/*` exports and must not copy generated declarations into `apps/devhud`. The package defines serialization only: native code owns full-feature credential metadata injection and the closed procedure/origin transport. DeliDev's sole exception is the separately contracted browser `RealQATrackerService` connection/destination manager in its two existing settings sections; public browser extensions and plugin authors must not consume the package.

Authenticated Deck and RealQA windows receive no generic opener, but they may invoke two typed native system-browser actions. The connection action accepts only the ephemeral authorization target returned by that feature's `StartGitHubConnection`, requires HTTPS GitHub.com with no credentials, fragment, non-default port, encoded path separator, or path traversal, and permits only `/login/oauth/authorize` with that feature's configured GitHub App client ID and exact registered callback or `/apps/<the configured feature GitHub App slug>/installations/new`; query data is allowed only on those authorization shapes and is never logged, cached, persisted, or returned to another window. The Deck pull-request action accepts only validated owner/repository segments and a positive decimal pull-request number, constructs exactly `https://github.com/<owner>/<repository>/pull/<number>` natively with no query or fragment, and is the sole path for commenting, approving, or requesting changes in GitHub. Both actions open the OS system browser without navigating the bundled webview, are available only to their authenticated feature window and purpose, reject every other host/path/input, and grant no arbitrary URL or opener-plugin authority.

### Signed-out shell and bounded authentication

- Base Home, Settings, Diagnostics, reset, tray access, and the foundation empty state remain usable while signed out. Deck and RealQA entry points require authentication and do not inject account state, provider results, or remote UI into the signed-out shell.
- Use Logto Authorization Code with PKCE in the system browser. Desktop opens a one-shot random-port `127.0.0.1` loopback listener at the stable registered `/auth/callback` path. Deck on iOS/Android uses only the verified `https://deli.dev/auth/devhud/callback` universal/app link. RealQA has no mobile callback because it is desktop-only. A new mobile authorization discards any callback queued before its transaction begins, and startup ignores a drained callback when no authorization transaction is pending so retained-session restoration can proceed.
- Persist only the authorized features' refresh grants, device-session key, the non-secret auth cleanup-required tombstone written before vault deletion, and an active or cleanup-pending Deck registration's single-purpose `UnregisterDevice` revocation grant in the OS secure vault. The auth tombstone survives failed deletion and blocks retained-grant trust after restart until cleanup succeeds. Access, ID, and forwarded tokens remain in memory. Native transport injects the Deck bearer through `authorization` and its paired forwarded bearer through `x-devhud-deck-forwarded-delibase-token`; it receives and submits the cleanup grant only through `x-devhud-deck-device-revocation-grant`. Permit one active DeliDev account per OS user/device.
- Each feature's authorization request includes only that feature's exact API resource/scope and its paired delibase forwarding resource/scope. Opening another feature may run a same-account incremental authorization for only that feature; success preserves the prior feature's separately rotating refresh grant, and cancellation, failure, or an attempted account switch preserves the active session and prior grants, while switching accounts still requires logout. API bearer validation requires only the resource permission scopes, never OIDC-only sign-in scopes. Each feature later uses the resulting exact feature-audience bearer plus a memory-only delibase-audience forwarded bearer. On restart, an available authorized feature grant must refresh and validate the issuer, audience, scope, subject, and device binding before restoring the signed-in memory state; request-level transport failures and explicitly retryable OAuth endpoint responses fall back to the gated prior-session-offline state, whose frontend snapshot lists only the exact retained feature bindings that remain safe for offline entry, and a rotated refresh grant returned before retryable bearer verification fails is vaulted before that fallback. Structurally valid legacy v1 and subject-only v2 device-session records remain gated prior sessions offline, with RealQA drafts unavailable until online token validation for the exact issuer, client, and subject atomically migrates them to the binding-bearing v3 shape; migration never adopts an ambiguous subject-only draft namespace or key. Missing configuration and invalid or revoked refresh grants do not restore a session; a definitively invalid RealQA feature or paired delibase grant is removed before the failure returns so a later offline restart cannot regain draft access through stale credentials. A signed-out authentication start clears a demonstrably malformed or unsupported retained auth record before opening the browser so reauthentication can rebuild it; real vault-access failures and well-formed device bindings remain fail-closed, and a well-formed binding still requires logout before an account switch. A cleanup-required state after failed logout/reset vault deletion locks feature use and cannot authorize a Chrome capture from the retained grant. No client log, diagnostic, local record, webview cache, widget snapshot, draft metadata, or Chrome message may contain these tokens.
- `DEVHUD_LOGTO_ENDPOINT` and `DEVHUD_LOGTO_APP_ID` are public native authentication configuration, never secrets. Desktop reads them from its launch environment; iOS and Android embed them during Rust compilation so normally launched mobile applications do not depend on a shell environment. Desktop also reads the public `DEVHUD_REALQA_GITHUB_APP_CLIENT_ID` and `DEVHUD_REALQA_GITHUB_APP_SLUG` values natively to validate the exact RealQA GitHub authorization handoff; missing or malformed values disable that handoff without widening it. An unconfigured build keeps the signed-out shell available and reports authentication as unavailable.
- Authentication authorizes Deck/RealQA entry, not arbitrary DeliDev pages, browser navigation, remote frontend assets, or a generic account/plugin surface.
- The frontend session provider exposes only restore/start/logout state actions, safe value-free failures, and the closed set of feature bindings available to the active session so a Deck-only account is offered incremental RealQA authorization before entry; it has no token getter, URL input, generic request, or browser persistence. Native restore and mobile callback polling run away from the Tauri main thread so vault and Logto/JWKS latency cannot freeze the local shell. The native core consumes callback state exactly once, verifies the tenant endpoint's exact `/oidc` issuer plus audience/subject/expiry/nonce/scope through the exact `/oidc/jwks` path, derives only closed OIDC endpoints, rejects bearer substitution, and never serializes access, ID, or forwarded bearers across IPC.
- Desktop stores one record containing per-feature refresh grants and the device-session key in the platform credential vault. iOS uses a non-synchronizing, this-device-only Keychain item; Android uses Keystore-backed encrypted preferences excluded from backup and transfer. A keyed issuer/client/subject binding inside the device-session key rejects identity switching without persisting a separate account record.

### Deck client contract

- Deck product surfaces remain planned for desktop, iOS, Android, desktop tray,
  global shortcuts, opt-in notifications, WidgetKit on iPhone/macOS, and
  Android widgets. Their implemented private client contract is
  `@delinoio/devhud-deck-connect`; future runtime calls use
  `devhud.deck.v1` at the exact inactive origin `https://deck.deli.dev` through
  the private native Connect transport.
- The implemented dependency-injected Deck refresh controller owns all timing:
  it targets five-minute polling only while its desktop, mobile, or
  OS-background client is active and currently permitted; `stop` cancels
  in-flight preflight work and removes every later timer. It requests only
  views attached to a widget, notification, or shortcut or opened in the prior
  30 days. A widget uses a bounded one-shot controller and cancellation signal.
  A failed candidate is reported without skipping later candidates unless the
  owning client was cancelled. No timer, request, retry, or continuation
  survives its owning client.
- Before any automatic, widget, manual, view-open, or shortcut refresh, the
  client generates the prospective logical refresh's UUID v7 identity and
  calls `DeckViewService.GetRefreshPreflight` with both the origin and active
  client kind. A catalog mapping with a reservation TTL shorter than 86,400
  seconds is unavailable for Deck. Every new `RefreshView` attempt carries the
  returned opaque short-lived token bound to that identity/origin/client
  combination. The client preserves the identity and token across an ambiguous
  transport retry. Per-view attempt storage uses an atomic claim so concurrent
  invocations dispatch the one retained identity/token and cancellation cleanup
  cannot delete another claimant's attempt. A manual confirmation displays the
  returned server-derived price in the explicit
  cache-bypass/billed-GitHub-request warning; cancellation performs no refresh
  call. Deck clients receive no background authorization or
  billing-finalization grant, and an unfinished attempt can advance only
  through a later active exact client retry with a fresh forwarded-user bearer.
- Deck maintains one unified shortcut-conflict registry with the generic DevHud shortcut and RealQA shortcuts. Up to 20 synchronized per-view definitions/account/device use the same closed modifier/key values as the base structured shortcut contract. Device writes send configuration only; the effective conflict state and synchronized revision are server-authored after local registration, and conflicts become inactive without silently replacing another binding.
- Notifications are view-specific opt-in and DND-aware. The client may change the view preference through `UpdateView`. Default text is exactly `Deck view updated`; detailed repository/PR titles require per-device opt-in, and push payloads contain opaque event IDs only. An online authenticated client may call `DeckDeviceService.ResolveNotificationEvent` for its matching active registration; it displays detail only after the server revalidates current view/repository access and otherwise falls back to the generic text without refreshing provider data.
- List rows carry the synchronized PR revision that the client must pass to `MutatePullRequest`; stale conflicts reload, compare, and reapply rather than guessing or omitting the revision. If a successful mutation response sets `refresh_required`, the client refreshes the PR and does not retry the already-accepted mutation; the response intentionally omits stale pull-request detail.
- Each widget selects one view. New widgets show counts only; titles require per-widget opt-in. Device registration/update sends only widget identity, selected view, family, and privacy configuration; it never authors snapshot contents or synchronized widget revisions. Widget actions may open or request refresh and never mutate PRs. OS scheduling is best effort and must not claim five-minute freshness.
- A minimal encrypted widget snapshot with freshness/offline state is Deck's sole offline PR-data exception. The normal application displays offline/connection state rather than a cached PR list. Online PR rows use the returned individual/team reviewer identities for deterministic grouping, use current assignees and labels to populate removal actions, render the explicit open/closed/merged lifecycle state separately from draft state, and offer only the returned supported mutations and merge methods. Before presenting an advertised assign-user, request-reviewer, or add-label picker, the client uses the bounded `ListPullRequestMutationCandidates` search and its synchronized revision rather than requiring exact names or probing a mutation.
- On authenticated startup and after a stale device conflict, call `DeckDeviceService.GetDevice` with the stable device ID to reload the current registration, lease, server-authored shortcut/widget state, and revision before compare/reapply. For each logical `RegisterDevice` creation or lease renewal, generate one UUID v7 idempotency key and preserve it across ambiguous retries until the exact registration ID, lease, and revocation grant response is installed; never create a second logical registration after a lost response. Initial registration omits `expected_revision`; renewal submits the current device revision and reloads/reapplies after a stale-revision response instead of overwriting newer mutable device state. Logout and `Reset DevHud` first call `DeckDeviceService.UnregisterDevice` while authenticated, then delete local Deck tokens, PR data, snapshots, and shortcut effective state without deleting server views/connections. The single-registration revocation grant remains valid through the lease. If unregister is offline or ambiguous, locally disable that registration, delete the platform push token, and retain only its registration ID, lease expiry, and revocation grant as a cleanup tombstone in the OS secure vault. Retry with that grant before any later Deck registration even after an account switch; terminal unregister/absent-registration success or observed lease expiry deletes it. The grant authorizes only `UnregisterDevice`, and the client never displays an opaque push event unless it still has the matching active account/device registration. Disconnect and owner-scoped idempotent `DeckViewService.DeleteFeatureData` follow the Deck server contract.

### RealQA client, capture, and Chrome contract

- RealQA is planned only for macOS 14+, Windows 11, and Ubuntu 24.04. Desktop capture supports region, window, display, multi-monitor, pointer inclusion, move/resize after initial selection, mixed DPI/negative coordinates/hot-plug, X11/XWayland, and native Wayland through `xdg-desktop-portal`.
- The inactive native capture foundation models these modes with signed logical desktop geometry, per-display rational scaling and display-local pixel regions, opaque source IDs, deterministic hot-plug snapshot identities, a closed backend/failure interface shared by macOS, Windows, and Linux adapters, and fixture backends. Prompt-required and denied permission states fail before display/window source enumeration or selection adjustment. A backend frame must exactly match the resolved single-display source pixel size or, for a window or multi-monitor output spanning displays, the logical-layout canvas at the highest participating display scale; mirrored and overlapping display regions are included only once and unselected gaps remain blank. On macOS 14+, the concrete adapter uses `SCScreenshotManager` for bounded single-frame capture and the Core Graphics preflight/request APIs for explicit permission discovery and recovery guidance. It enumerates current ScreenCaptureKit displays/windows on each snapshot refresh, handles Retina, mixed-scale, negative-origin, display removal, closed/minimized windows, protected output, repeated capture, pointer inclusion/exclusion, and cancellation through typed outcomes, and composites selected display-local frames into the validated shared-core canvas. Windows 11 injects a Windows Graphics Capture implementation on x64 and ARM64. It binds each display snapshot to the per-monitor device-interface identity in addition to the current GDI source, and derives window geometry from DWM visible extended-frame bounds so invisible resize borders cannot enlarge or rescale the captured WGC item. It enumerates only opaque display/window choices, exposes only bounded path-free process names and window titles, rechecks permission, display topology, selected source lifetime, minimized/closed/protected state at capture time, applies the explicit include/exclude pointer choice, and copies the first bounded frame into owned RGBA before the shared core validates and encodes it. Across both native adapters, only bounded opaque IDs, logical geometry, sanitized metadata, and exact-size RGBA buffers cross the native-adapter boundary; native objects, handles, monitor device-interface identities, errors, authority, raw paths, and partial pixels do not cross frontend IPC or diagnostics. Ubuntu X11/XWayland capture reads only the selected root/window drawable, rechecks the display snapshot immediately before capture, composites the XFixes pointer only when requested, blanks unselected multi-monitor gaps, and exposes only bounded process-name/window-title metadata without a PID, handle, path, or raw property. Native Wayland never enumerates compositor windows or reads compositor pixels directly: an opaque source transfers selection to the interactive Screenshot portal, advertised portal targets determine available modes, cancellation/denial remains closed, and only the approved file is decoded into a validated in-memory frame. Because the Screenshot portal has no cursor option, native-Wayland pointer inclusion is advertised unavailable rather than guessed from compositor-specific behavior. Portal-owned region adjustment and application-owned Windows/X11 region adjustment are explicit capability values. The exact `realqa-capture` window may inspect/request capture permission, inspect capabilities, enumerate, adjust, begin, or cancel capture; the exact `realqa-composer` window may sanitize and account for images in memory and may invoke only the narrow user-confirmed, pointer-excluding primary-display fallback for a restricted browser page. The composer receives none of the generic source-enumeration or selection commands, and neither window receives generic screen/filesystem/process/store/shell/network authority.
- The RealQA window initiates capture only through the typed native procedure set above after a user action. Native code rechecks the requested closed mode, current platform support, selected source lifetime, OS capture permission, decoded-pixel/session limits, and portal result before returning a bounded capture; denial, cancellation, source disappearance, hot-plug, or permission loss returns a stable value-free classification and no partial pixels.
- The implemented composable nondestructive editor supports crop, arrow, rectangle, freehand, text, numbered markers, blur/pixelate, color/line width, and immutable undo/redo history through pointer and keyboard interaction with screen-reader instructions and applied-edit status. Each accepted source carries a native revision, and replacing a source under the same session/image identity resets its image-specific editor state. The active crop becomes the preview and input viewport, and native validation rejects later operations outside that crop so direct approval requests preserve the same boundary. Text preserves supported ASCII casing and normalizes unsupported glyphs before preview so native flattening renders the same content. Because blur and pixelate previews are source-derived, the editor permits one such effect before annotations and then disables both effect tools; pixelation previews the source pixels at the selected native block scale instead of substituting an opaque pattern, and both effect backing stores scale down above their four-megapixel retained-preview cap without changing native output. When a capped source or effect preview cannot represent the native pixelation block grid or blur radius, the editor announces and persistently displays that the approved output may show more detail. Accepted source pixels remain in the native local composer session while the React draft carries only a native-generated source preview bounded to 2,048 pixels per edge plus operations; all retained composer sources also share the 250 MiB encoded-byte budget across session identities. A matching image removal or session reset invalidates an acceptance that is still sanitizing or decoding, so it cannot recreate cleared native state. Neither path serializes the full source into upload, logging, diagnostics, clipboard, or server state. Approval sends only image/session identity, the expected native source revision, the validated closed operation list, and PNG/WebP choice through `realqa_composer_flatten_image`. Native code bounds operation, freehand-point, text, color, and identifier values while deserializing direct approval requests, rejects a stale revision before rendering, admits at most one process-wide CPU-heavy acceptance or flatten operation through a shared permit before either decode/re-encode path, spawns flatten blocking work only after obtaining that permit, always starts from retained source pixels, validates coordinates, crop, styles, effects, counts, sequence, aggregate freehand points, and aggregate raster work including each blur/pixelate pixel pass, deterministically applies effects/annotations with blur scratch memory bounded by effect radius rather than region area, crops last, re-encodes through the shared bounded image-safety boundary, strips metadata, and returns the only type accepted by the future upload-payload helper.
- `devhud.realqa-draft.v1` is a separate desktop-only local record family, not a fourth generic base-persistence key. Each UUID-v7 draft is atomically written as one versioned AES-256-GCM file under an opaque account namespace. Its bounded independently encrypted summary header precedes a compact binary encrypted body, allowing list operations to authenticate only bounded summaries without reading/decrypting raw image payloads and preventing JSON byte-array expansion; the serialized/encrypted body also has an explicit upper bound. Associated data separately binds each payload kind to the family, authenticated-account binding, and draft ID; a distinct random per-account device key is stored only in the OS secure vault. Native commands derive the account binding from retained authentication and accept no subject, key, path, arbitrary record name, or raw image from React. The encrypted body contains the UUID-v7 submission retry identity, optimistic revision, local timestamps, editable title/body, synchronized preset/destination/repository-definition references, individually removable environment/URL/DOM values, composer-retained raw originals, and nondestructive operations. Loading and image restoration run on the native blocking pool, restore originals into a native composer session, and return only bounded previews/revisions plus operations; raw originals are never uploaded, synchronized, logged, diagnosed, or placed in server persistence. Logout and reset hold the draft lifecycle boundary while invalidating accepted composer sources and queued browser captures before authentication, draft storage, or pairing cleanup proceeds.
- After prior successful RealQA login/device binding, offline capture/edit and encrypted account-bound drafts are allowed. A retained offline session can create a missing draft key because its still-vaulted RealQA grant and device binding prove prior entry. First-time offline entry is denied, and the native submission preflight requires a current online-reauthenticated session plus the exact draft revision. Logout clears tokens and in-memory access so drafts lock/hide without deleting the separate draft key; a later login deriving the same account binding restores them, while another account selects a different key and namespace and cannot enumerate or decrypt them. Successful submission invokes the same revision-checked local removal used by explicit deletion. Corrupt/future envelopes, unavailable vaults, failed atomic writes, and stale concurrent revisions fail with value-free classifications while preserving the previous valid record. `Reset DevHud` preflights and clears drafts, the draft-key credential, tokens, every effective shortcut, and extension pairing; it cannot revoke Chrome-owned permissions.
- Preset synchronization carries preset logic, destinations, repository issue definitions, declaration-ordered process/title URL rules, and shortcut definitions. Capture/optional-host permission, native shortcut registration outcome, and extension pairing remain device-local and are never overwritten by synchronization. Chrome inference accepts only the active-tab HTTP/HTTPS URL. Desktop inference uses exact case-sensitive process names and the documented bounded common-regex title subset, rejects nested or ambiguous repeated groups before JavaScript RegExp evaluation, caps compiled patterns at 2,048 instructions, accepts at most 64 total rules including disabled entries, evaluates enabled rules in declaration order, skips unsafe expansions, and leaves an editable blank URL on no match. Both paths reject URL credentials, warn without rejecting localhost/private hosts, and strip query/fragment by default while retaining those parts only inside the encrypted draft for an explicit restore/edit action. Every suggested environment, URL, and DOM field remains independently removable.
- The signed Chrome MV3 extension targets Chrome 150, the stable desktop major when this implementation landed. ## Storage

- `devhud.settings.v1` has schema version `1` and contains only a System/Light/Dark theme enum, reserved launch-at-login boolean, and optional structured shortcut. A shortcut contains one or more unique modifier enum values and a key enum; unchecked shortcut strings are invalid.
- `devhud.shortcut-effective-state.v2` has schema version `2` and is a closed, device-local effective-registration record. The unified registry permits one generic DevHud binding, at most 20 accepted Deck definitions per account/device, and at most 20 accepted RealQA preset definitions per device. Definitions remain feature-owned (Deck may synchronize them; RealQA remains device scoped), while registration outcomes are local. Deterministic owner ordering resolves collisions; each owner is planned once, and an unavailable, over-limit, malformed, conflicting, permission-denied, or failed registration is inactive/unchanged and never silently replaces another active binding. Logout clears only the matching account's effective Deck registrations; Reset DevHud clears every effective registration before record removal and process cleanup.
- `devhud.widget-configuration.v1` has the exact JSON shape `{"version":1,"configuration":{"slots":[{"slot":"primary","toolId":"stable-tool-id"}]}}`. `slot` is one of the unique `primary`, `secondary`, or `tertiary` enum values, and `toolId` is validated as stable lowercase kebab case. Production configuration is `slots: []`; `fixture-diagnostics` exists only in native/frontend tests and is never rendered as a sample tool.
- The base frontend uses a dependency-injected three-record storage adapter on desktop CEF and standard Tauri mobile runtimes. Native IPC exposes only record-specific read/write commands, not filesystem paths, a default store, arbitrary keys, or generic value operations. Desktop RealQA uses the separately typed encrypted draft-family adapter described above; it does not extend `PersistenceKey` or weaken unreadable-record write blocking for the three base records. On iOS, widget configuration uses App Group `UserDefaults`; on Android it uses the dedicated `devhud-widget-state.preferences_pb` DataStore and only the exact versioned preference key.
- Local writes are atomic and serialize each record so call order yields last-successful-write-wins behavior. A failed write leaves the previous valid record intact and restores the provider-owned state to that value.
- Each successful mobile widget write or reset requests a platform widget refresh. With no embedded/registered widget the live refresh reports zero affected Android widgets or reloads no installed iOS timeline. Refresh failures are logged as widget-bridge failures, but do not reject or corrupt the successfully validated stored record.
- iOS excludes both the application-local record directory and future App Group container from device backups. Android backup and extraction rules exclude all application/DataStore domains from cloud backup and device transfer so local state is not restored onto another device.
- Unsupported future schema versions are rejected without reading them into state or overwriting stored data. Corrupt, incompatible, or unreadable data surfaces actionable confirmed-reset guidance without raw stored data in UI, errors, or logs. An unreadable record remains write-blocked until it can be read successfully or the user completes Reset DevHud.
- Base-shell local state is retained until the user chooses `Reset DevHud` or uninstalls the app. Deck widget snapshots and RealQA encrypted drafts follow their separate lifecycle rules above.
- `Reset DevHud` uses an accessible modal confirmation whose initial focus is the destructive action, whose focus stays trapped, whose `Escape` and explicit Cancel actions close without mutation, and whose close restores focus to the Reset trigger. Before any reset mutation, native code resolves and validates the three exact record paths, the exact managed-log directory, the desktop CEF profile target, and the mobile widget adapter. A failed precondition reports a stable value-free storage classification and leaves valid data intact.

A native integration or pre-removal persistence failure reports that the reset failed, attempts to restore the previous working integrations, and records any rollback failure with its effective state. A failed record rollback that leaves a stable record present reports a partially retained reset and reloads both providers from the effective records. Cleanup failure after all stable record paths are absent remains a failed reset, discloses that transaction stages or application browsing/profile data may remain, and keeps integrations disabled so runtime state matches the next launch. A native widget deletion failure after application records are removed reports partially retained state. All classifications and logs omit stored values and paths. Repeated reset is idempotent.

- Tauri, `tauri-build`, the private bridge's `tauri-plugin` build support, the directly selected desktop `tauri-runtime-cef` sandbox dependency, and the mobile-only `tauri-runtime-wry` dependency are pinned to commit `f49ebda2fdba5755456b0f049e32593ca0ea331a`; `@tauri-apps/cli-cef` is pinned to `3.0.0-alpha.6`, while `@tauri-apps/cli-mobile` aliases the standard Tauri CLI exactly at `2.11.4`. Do not maintain a Tauri, WRY, or `cef-rs` fork or local patch, and do not replace the revision with `feat/cef` or another moving branch.
- The signed-out DevHud shell remains local and service-independent. Only authenticated Deck and RealQA may consume DeliDev/Logto identity, their versioned Connect APIs, and memory-only delibase-audience forwarding. They must not consume arbitrary DeliDev catalog/routes/contracts or move implementation into DeliDev/delibase paths.
- Future canonical feature origins are `https://deck.deli.dev`, `https://realqa.deli.dev`, and `https://assets.realqa.deli.dev`. They are inactive identifiers: this contract does not configure DNS, deploy services, create R2 infrastructure, inject production secrets, register GitHub Apps, or activate catalog entries.
- Deck and RealQA use separate GitHub Apps. Production-facing catalog records for both remain disabled. The client network exceptions are exactly those listed in Security; no remote configuration or online operational dependency is available to the signed-out base shell.

### Release, beta, signing, and publisher contract

- Trigger the target release from `devhud@v0.1.0`. Publish it as a regular GitHub Release, not a prerelease, after privately building and validating every platform.
- Publish separate x64 and ARM64 macOS DMGs; separate x64 and ARM64 Windows NSIS installers; separate x64 and ARM64 Ubuntu AppImage and deb packages; target-specific signed Tauri updater bundles and manifest; `SHA256SUMS`; platform signatures; SPDX SBOMs; and GitHub artifact provenance.
- Produce signed iOS and Android builds for TestFlight and Google Play beta channels, with minimal `DH` store assets in the corresponding listing material. Open the GitHub Release, TestFlight external group, and Google Play open-testing release in the same release window after private validation. If external beta review rejects the empty mobile foundation, use TestFlight internal testing and Google Play closed testing without adding a sample tool.
- Publishing requires every signing and publisher prerequisite; never publish an unsigned public release. Required protected secrets/variables are the Tauri updater signing key and password, macOS Developer ID certificate and password, Windows signing certificate and password, Apple team ID, App Store Connect issuer/key IDs and private key, iOS distribution certificate/password/provisioning profile, Android keystore/store password/key alias/key password, and Google Play service-account credentials.
- On a broken desktop release, withdraw it from update discovery, annotate the release, and direct users to manually reinstall the previous signed installer. Do not implement automatic downgrade. Mobile updates remain managed by normal TestFlight and Google Play beta channels.
- Track the pinned upstream `feat/cef` commit monthly and perform an urgent `0.1.x` update when a high-risk Chromium/CEF security fix affects DevHud.
- Required operator runbooks are release, signing, updater withdrawal, manual rollback, store submission, CEF pin update, diagnostics, and support. No dedicated DevHud website or documentation deployment is part of this contract.

## Change Triggers

- Update [project-devhud](project-devhud.md), this document, the affected Deck/RealQA server and proto contracts, `docs/README.md`, `README.md`, and root/apps/servers/protos `AGENTS.md` files for ownership, path, identifier, runtime, platform, UI, storage, auth, provider, security, diagnostics, support, or exclusion changes.
- Update package manifests, workspace membership, Turborepo configuration, CI workflows, release workflows, signing configuration, public `PRIVACY.md`/`SUPPORT.md`, issue templates, and runbooks in the same change when implementation or operations are introduced.
- Update the project and relevant domain contracts before changing any tool registry entry, native command, screen ID, widget/extension registration, link behavior, network exception, account behavior, provider, telemetry, DeliDev integration, or API. Only the issue #755/#757 boundaries documented here are authorized.
- Update the release and upstream-monitoring material when the CEF pin, updater selection, supported artifact, signing prerequisite, beta channel, rollback, or security response changes.

## Out of Scope

- Any developer tool other than the explicitly contracted Deck and RealQA registrations; current production registration remains empty.
- Any currently published/embedded widget or extension. Deck widget distribution and the RealQA Chrome artifact require their implementation, privacy/security tests, external production identities, signing, and a separate publication change; fixtures must remain invisible to users.
- Live Activities, Control Center controls, watchOS, Wear OS, RealQA widgets/mobile UI, and non-Deck desktop widgets. Native Wayland is excluded from the base shell, except RealQA screen capture through `xdg-desktop-portal`.
- External plugins, remote mini-apps, user-authored scripts, runtime code downloads, arbitrary remote UI/assets, and public tool/tracker/plugin SDKs.
- Any DeliDev/catalog/account/organization/billing/API/route behavior outside the bounded auth, settings-management, and feature billing contracts. Production catalog activation remains excluded.
- Any authentication, backend, synchronization, cloud/object storage, tenant data, or account behavior outside Deck/RealQA.
- CLI commands, generic localhost/public APIs, additional Connect services, arbitrary webhooks/public routes, generic custom schemes/links, or extension bridges beyond the exact contracted exceptions.
- Remote telemetry, crash reporting, analytics, advertising, user tracking, online dashboards, remote alerts, feature flags, and kill switches.
- Settings import/export, migration from an existing application, account migration, and cloud synchronization.
- macOS App Store, Microsoft Store, Linux package repositories, or a production App Store/Google Play release; beta channels are limited to TestFlight and Google Play as defined above.
- Automatic update downgrade.
- A dedicated DevHud website or documentation deployment, Korean or other localization, a complete brand identity, and a marketing system.
- DNS/R2 provisioning, API deployment, production secrets, GitHub App registration, GHCR publication, Chrome Web Store publication, widget publication, catalog activation, or operational rollout.
- Numeric production performance SLOs/alerts or other production operational services.

# servers-delibase-server-foundation

## Scope
- Project/component: `delibase` / `server`
- Canonical path: `servers/delibase`
- Canonical future API origin: `https://delibase.deli.dev`

## Runtime and Language
- Runtime: Go service
- Persistence: PostgreSQL with ordered migrations and sqlc for all queries
- API: `delibase.v1` Connect RPC, with signed Polar webhook REST as the explicit non-Connect exception.
- Stateful structure must provide explicit service, contracts, logging, database, generation, and configuration boundaries before runtime rollout.
- The runnable foundation lives at `servers/delibase/cmd/delibase`, registers all six generated handlers, exposes `/healthz` and PostgreSQL-backed `/readyz`, and shuts down gracefully. `AccountService`, `TeamService`, and `OrganizationService` (including invitations) use authenticated PostgreSQL/sqlc transactions. `BillingService` implements summaries, hosted billing actions, limits, ledger and role-filtered usage reads, and human background-authorization create/get/list/revoke. `UsageService` implements database-backed live-user reserve/commit/release and M2M-only authorized reserve/commit/release/resource-deletion transactions, while a local expiration worker returns catalog-TTL holds independently of Polar delivery. The authorized handlers use the ordered PostgreSQL/sqlc lifecycle boundary and the normal billing pipeline; the checked-in RealQA catalog fixture and all client surfaces remain disabled, so this artifact change does not activate production behavior.

## Users and Operators
- DeliDev users and organization Owners, Admins, Members, Team Admins, and Team Members.
- Authenticated mini-app backend services reporting integer metered usage.
- Maintainers operating PostgreSQL, Logto, Polar, artifact builds, and tagged GHCR releases.

## Interfaces and Contracts
- Six versioned Connect services: `AccountService` (account state/onboarding/deletion), `OrganizationService` (organizations, slugs, roles, invitations), `TeamService` (hierarchy, moves, subtree deletion, memberships/access), `CatalogService` (anonymous public enabled app/meter metadata, authorization targets, and effective-dated USD micro-unit prices with version metadata), `BillingService` (summary, checkout, portal, limits, ledger/usage reads, and human background-authorization create/get/list/revoke), and `UsageService` (live-user and authorized reserve/commit/release plus authorized feature-resource deletion notification). No seventh service is permitted.
- Server implementations import generated messages from `github.com/delinoio/oss/protos/delibase/gen/go/delibase/v1` and Connect interfaces from its `delibasev1connect` child package; handlers must not redefine transport contracts.
- Human calls require a Logto user access token except for anonymous `CatalogService` reads. Live-user usage mutations require a Logto M2M token plus the `x-delibase-forwarded-user-token` Connect metadata key carrying a forwarded end-user Logto token. Authorized-usage mutations use explicit `ModeM2M` policies and never require or store the forwarded bearer; middleware strips any credential headers before handlers. Raw Logto client secrets are provider-side credentials and are never accepted in inbound Connect metadata. Validate issuer, the canonical `https://delibase.deli.dev` audience, expiry, scopes, M2M service meter allowlists, membership, and effective team access server-side; redact credential metadata from all logs, traces, errors, and diagnostics.
- Every HTTP path and Connect procedure must declare an explicit shared authentication mode. Anonymous catalog reads use `ModePublic`; protected route omissions retain the invalid zero value and fail closed.
- Shared authentication attaches only typed Logto user/service claims to context and removes both credential headers before handlers execute. `sub == client_id` identifies the Logto client-credentials/M2M shape; user and M2M validators reject each other's token type. Delibase retains the canonical-audience `auth.NewValidator` constructor; the additional reviewed feature-audience constructor cannot alter its accepted audience. Delibase then resolves the user/service against its own local state and remains the sole authority for organizations, memberships, roles, teams, meter allowlists, billing, and usage decisions.
- List APIs use opaque cursors. `CatalogService` lists only enabled apps/meters using UUID-keyset cursors (default 25, capped at 100), and detail reads safely return `NotFound` for disabled, absent, or not-currently-priced resources. Catalog detail/list meter responses include the exact effective price-version UUID so later usage reservations can pin it. Errors use Connect status codes and vetted stable enum-based reasons for auth, authorization, slug, invitation, team depth/cycle, subscription, overage, reservation, idempotency, deletion, and resource-state failures. Shared authentication distinguishes bearer and forwarded-user reasons; explicit signing-key provider outages fail closed as retryable `Unavailable` dependency failures, while unknown keys and algorithm/type/curve mismatches are invalid credentials. The shared safe-error boundary drops arbitrary response metadata, unrecognized protobuf details, and free-form detail fields; the outer request metadata interceptor adds only validated request and trace IDs to unary and streaming failures.
- Persisted IDs are UUID v7. Local accounts keep their original Logto `sub` for their lifetime. Slugs are globally unique/changeable, and retained aliases cannot be rewritten or deleted outside their organization-deletion cascade. Teams have one organization, nullable parent, names unique among siblings (including root teams), maximum five levels below the organization, downward inherited access, and an undeletable/non-renamable protected `General` team. Hierarchy validation serializes moves within an organization so concurrent updates cannot create a cycle or exceed the depth limit. Deleting another team requires explicit confirmation, deletes its subtree only when no active usage reservation exists there, and historical usage/audit records retain immutable team ID/name snapshots.
- Invitations are hashed bearer links, seven-day valid, revocable, and reusable by distinct users. Preview and acceptance require an authenticated user plus a valid invitation bearer token, but not a pre-existing local account, organization membership, or team access. Acceptance locks the organization before creating or locking the active local account with a privacy-safe non-empty placeholder display name when absent, then locks the invitation and revalidates invitation state so organization deletion cannot race membership creation and account deletion follows the same organization-before-account lock order. The storage boundary rejects revoked or expired acceptance, supplies the acceptance timestamp, and records an account's first acceptance before memberships are granted; a different idempotency key cannot consume the same invitation again for that account or restore access after removal. Acceptance and revocation use distinct idempotency operations; invitation creation is not idempotent. An invitation may grant only Organization Admin or Member; Member invitations must target a team and assign Team Admin or Member. Owner may be granted only by an existing Owner after the user has joined, and existing membership roles are not silently changed.
- Every `TeamService` read or mutation establishes organization membership before resolving a requested team identity. Existing and absent team IDs therefore return the same organization-membership-required failure to non-members.
- Organization roles: Owner (full access and deletion), Admin (management, billing, limits, full usage, but no Owner management or organization deletion), Member (app use, shared credits, and accessible team usage, but no invoices/full ledger/subscription/overage controls). Owners and Admins are implicit Team Admins for every team. Every committed organization has at least one active Owner; organization creation and its initial active Owner membership commit atomically, and account status changes cannot leave an organization without a usable Owner.
- Mutations against an existing organization acquire its row lock before locking or creating an account, matching reservation insertion and account deletion; a completed idempotency replay may return before those business locks.
- Held usage reservations retain their live organization membership and block organization-member removal or self-leave with `ERROR_REASON_MEMBER_HAS_ACTIVE_RESERVATIONS`.
- A durable background authorization binds its UUID v7 identifier to the human authorizer, personal/organization feature owner, payer organization/team, exact authenticated service/meter, `REALQA_STORAGE`, feature-resource UUID, `UTC_DAY`, maximum units, closed status, revision, and timestamps. Public catalog meter reads expose stable service authorization target UUIDs and safe names without Logto client IDs or credentials. Create/revoke are human-and-operation idempotent; reserve/commit/release/resource-deletion notification are independently service-and-operation idempotent. Reserve/commit/release digest-bind authorization/service/purpose/resource/period/units, with commit/release also binding the reservation ID; resource deletion binds authorization/service/purpose/resource/expected revision. Reserve accepts only the current or immediately preceding canonical UTC day according to server time; commit/release use the reservation's stored period. Every reserve rechecks active account/organization/team access and the exact immutable binding before holding funds. Substitution, lost access, non-active status, period-limit overflow, and altered replay fail with stable closed reasons. Deck is not a valid purpose.
- Membership, role, team, account, organization, connection, and feature-resource deletion must never be blocked by a background grant. Their transaction makes affected grants unusable immediately using `ACCESS_LOST`, `OWNER_DELETED`, or `RESOURCE_DELETED` as appropriate; explicit revocation uses `REVOKED`. Before deleting an external feature resource, its authenticated bound service calls `MarkBackgroundUsageResourceDeleted`, which idempotently transitions an `ACTIVE` matching grant to `RESOURCE_DELETED` only at the current expected revision. An exact bound-service call against an already `REVOKED`, `ACCESS_LOST`, `RESOURCE_DELETED`, or `OWNER_DELETED` grant returns that closed status and current revision without another transition even when the caller's expected revision predates closure; future/unknown revisions and immutable-binding substitutions fail closed. This lets feature cleanup finish without reopening or rewriting a closed grant. Authorized settlement reuses the existing reservation, credit-first, overage, billing-period, append-only ledger, Polar outbox, reconciliation, audit, and seven-year pseudonymized-retention rules and has no unmetered fallback.
- Account deletion locks the account's organizations in stable order and fully expires TTL-ended holds before evaluating active-reservation and last-Owner blockers; organization, membership, leave, and team-subtree deletion flows likewise drain relevant TTL-ended holds before evaluating active-reference blockers. Account deletion then disables local access and, in the same acceptance transaction, enqueues immutable Deck and RealQA lifecycle calls keyed by the delibase deletion-job UUID. It removes operational data, queues Logto deletion, signs out, retries all external deletion work, and retains only pseudonymized financial/audit references for seven years.
- Completed account and organization deletion leaves append-only pseudonymous tombstones with an explicit minimum seven-year retention boundary. A deleted Logto subject is retained only as a SHA-256 digest so an unexpired access token cannot recreate the account after the Management API deletion succeeds. The raw subject exists only in the disabled operational account row while the durable Logto deletion job still needs it and is removed after successful delivery.

## Storage
- PostgreSQL tables/migrations cover users, organizations, memberships, slug aliases, teams, invitations, catalog/meter enabled state, required reservation TTLs, effective-dated USD micro-unit prices, service-identity and integer-unit mappings, and Polar meter mappings, plus the fixed monthly Polar product mapping, Polar subscriptions/periods, checkout attempts, paid-cycle/refund and refund-created shortfall records, append-only ledger entries, reservations, webhook inbox, integration outbox, deletion jobs, audit events, and retained background-authorization resources/transitions. Authorization bindings and terminal transitions are immutable, transitions are append-only with a seven-year retention floor, normal reservation/usage rows snapshot the exact authorization context, and a partial unique index permits at most one committed settlement for each authorization and canonical UTC day. Each committed organization has exactly one Polar team customer, keyed by the organization UUID as Polar `external_id`, and cannot drop that customer before its organization-deletion cascade. Organization/team-membership identity, Polar subscription identifiers, and Logto service-client identifiers are immutable. An organization has at most one active subscription; inactive subscription rows remain retained as provider history, a newer Polar update may reactivate a scheduled-canceled subscription, and revoked subscriptions remain terminal. Retained refunds preserve their provider-order binding and monotonic provider-event/reversal/chargeback state, and reversal increases must transactionally match the retained paid-cycle total. Retained paid cycles immutably snapshot their provider order, subscription, billing period, and original period bounds; their cumulative reversed amount may increase only to match retained refunds, and they block deletion of their referenced subscriptions and billing periods. Startup fetches the configured provider product from the selected production/sandbox API and verifies one active fixed monthly USD `$10` base price before persisting a mapping that is database-constrained to a `10,000,000`-micro-unit price and paid-cycle grant; startup fails if the provider product, persisted product, or environment differs from that contract.
- Database constraints prevent overlapping price windows for one meter and overlapping billing periods for one organization, keep subscriptions and ledger periods in the billed organization, require overage-funded usage settlement to identify the billing period containing its storage-derived commit time, allow credit-only settlement to omit a billing-period snapshot when no period contains the commit, snapshot a selected period window into retained ledger history, validate each ledger entry's running balance under an organization lock, acquire that organization lock before reservation snapshot locks on billing periods or subscriptions, bind reservation price snapshots to the effective catalog version, derive active reservation creation times in storage, bind expiry to the meter TTL, require overflow-safe reservation unit-price totals, reject direct committed inserts and all reservation deletes, require matching credit/overage release entries before release or expiry, revalidate authoritative credit and active-subscription current-period overage capacity at commit, and cap committed units at the reserved maximum. Reservations and committed usage retain immutable team, pseudonymous user, service, meter, price, client-reference, and optional credit-only billing-period snapshots; a deferred invariant requires each committed usage record with nonzero overage to own exactly one durable Polar usage-event outbox row whose payload matches its organization, usage-record ID, Polar event-name snapshot, commit timestamp, and chargeable overage micro-units rather than total catalog usage.
- Money is signed 64-bit USD micro-units (`10,000,000` = $10.00); usage is signed 64-bit integer units. Reject overflow, negative reservations, and invalid catalog precision.
- Usage-service migration rejects persisted Polar meter identifiers that the provider request boundary cannot accept before copying them into immutable reservation or usage snapshots.
- Polar supplies one monthly $10 product: each successfully paid cycle grants exactly $10.00 rollover credit; unused credits do not expire; metered overage is invoiced by Polar. Taxes/fees do not alter the grant.
- Delibase ledger is authoritative for operational balance, holds, authorization, and DeliDev display; Polar is authoritative for payment settlement and invoices. Refund/chargeback reverses its grant and makes consumed shortfall overage subject to the limit, including when the organization has already been marked deleted and only retained billing history remains. Refund-to-paid-cycle and shortfall-to-refund references remain organization-scoped. A renewed paid grant carries any remaining organization-level refund shortfall into the renewed current billing period, and append-only reconciliation adjustments remove the carried amount when a reordered paid grant later clears that debt.
- Owner/Admin must set a non-negative monthly overage limit; zero is default. Committed and held overage count against the current Polar period. Lowering the limit below current committed or held overage blocks new reservations while preserving enough effective capacity for already-held commitments to settle; it never reverses usage or mutates append-only ledger entries. Cancellation/revocation/past-due preserves existing credits but grants no credits and prevents new overage reservations.
- `ReserveUsage` requires organization/team/meter IDs, max units, client reference, and idempotency key; under an organization lock it fully returns TTL-ended holds, then atomically verifies that deletion has not started, the active organization membership, enabled service/meter mapping, current team-name snapshot, effective catalog price, meter TTL, available settled credit minus active holds, and committed-plus-held overage against an active subscription's effective billing-period limit before accepting the exact credit-first hold split. New client references are canonical, credential-safe, and unique per service; migration preserves benign legacy syntax and duplicate correlation values as immutable grandfathered snapshots. Reservation identity, snapshots, limits, holds, references, and timestamps are immutable after creation; only a storage-timestamped held-to-committed/released/expired transition is allowed, and committed state can originate only from the validated immutable usage-record insert path. Commit rechecks that the reservation account is active and retains effective team access, that authoritative settled credit still backs active credit holds, and that an active current subscription period still backs committed-plus-held overage; it applies actual units (never above reserved), consumes no more held credit or overage and uses credit first, derives the commit timestamp in storage, releases unused holds, attributes actor/team/service, and queues only nonzero locally settled overage to Polar. Release/expiry requires ledger entries returning the full held credit and overage amounts; late commit fails. Usage-operation idempotency remains scoped to the authenticated service identity and operation, while the request digest binds the forwarded user subject so reuse across end users conflicts. Global expiration batches report ledger-inconsistent rows while continuing later releasable expirations in the same organization, isolate remaining organization-level failures, and continue eligible organizations later in the same batch.
- Idempotency is authenticated-caller/operation scoped: human RPCs use the user subject and M2M RPCs use the service identity. The same key and payload returns the original result; a different payload conflicts. PostgreSQL transactions/row locks prevent over-allocation. Polar webhooks are signature-verified and persisted idempotently with a validated JSON-object payload of at most 1 MiB before success. The reusable `internal/reliability` enqueue functions accept transaction-bound sqlc queries so business mutation and queue insertion commit or roll back together. Webhook provider/event identity, integration/operation/idempotency identity, and deletion type/idempotency identity are duplicate-safe; a duplicate with changed immutable input conflicts. Deck and RealQA lifecycle outbox rows carry only the typed account/organization target and deletion-job UUID, use separate feature-scoped M2M identities, may invoke only the matching `DeleteFeatureData` lifecycle mode, and treat an absent target as terminal success.
- Global expiration keyset-paginates across candidate-organization pages so full pages of ledger-inconsistent or otherwise failed organizations cannot starve healthy later organizations in the same batch.
- Subscription checkout creation first durably claims one expiring provider-idempotency attempt per organization. The same provider key and request digest may recover an ambiguous or post-provider-success failure, while distinct keys remain blocked. Provider creation then runs under the organization billing lock; successful checkout ID/expiry, audit, caller-scoped idempotency response, and attempt removal commit atomically. A definitive provider rejection clears the attempt. An unexpired successful checkout blocks another checkout for that organization even under a distinct idempotency key. Billing summaries prefer an active subscription, otherwise report an unexpired checkout as checkout-pending, and use provider-event recency to select inactive subscription history.
- Reliability handlers are registered only under stable typed handler identifiers derived from allowlisted webhook event, integration operation, or deletion-job values; database or request text never selects an arbitrary handler. Workers claim one due row atomically with `FOR UPDATE SKIP LOCKED`, a unique claim token, and a bounded lease. Completion and failure compare that token, so stale or crashed workers cannot repeat a state transition. Claiming increments the attempt count, including attempts that crash. Expired claims become eligible again; if the twelfth normal attempt crashes, lease recovery transitions it to retained dead-letter state.
- Normal delivery has exactly 12 attempts with capped exponential backoff and injected jitter. A failed twelfth attempt becomes dead letter immediately. Dead-letter rows retain their original event, first dead-letter timestamp, normal-attempt count, and cumulative dead-letter-attempt count; they become eligible every 24 hours without jitter until a handler succeeds. Successful dead-letter delivery keeps retained dead-letter history while setting the terminal processed, delivered, or completed state. Webhook inbox events, integration-outbox events, and deletion jobs cannot be deleted, and retry updates cannot rewrite their event identity/payload, integration-outbox event bodies, deletion-job targets, idempotency key, or pseudonymous actor.

## Security
- Logto is the identity trust boundary; delibase owns local authorization and data. Polar owns hosted payment consent, cards, receipts, invoices, cancellation, and payment recovery; delibase never handles card data.
- Store only invitation token hashes. Never persist or log Logto/Polar tokens, webhook secrets, authorization headers, `x-delibase-forwarded-user-token`, forwarded user tokens, card data, or raw billing PII. Queue payloads reject sensitive key and value shapes before persistence. Append-only audit rows use stable typed event identifiers and accept only empty/system or keyed pseudonymous actor references plus bounded allowlisted request correlation/method/procedure metadata whose correlation identifiers also pass the shared credential-shape redaction boundary. Decision and result are stored on every row and no audit update or delete path exists.
- Routine actor fields must use only the exact keyed `actor:v1:<32-lowercase-hex>` output, and the root redacting handler must recursively sanitize typed diagnostic maps and slices.
- PostgreSQL failure fails mutations closed. During Polar outage, authorize within local credits/overage and queue events; checkout creation makes no local mutation if Polar is unavailable.
- Organization deletion is one-way once `deleted_at` is set: it hides access immediately, blocks usage, forfeits remaining credits without refund, and atomically enqueues immutable Deck and RealQA lifecycle calls keyed by the delibase deletion-job UUID. It queues cancellation for every nonterminal Polar subscription (including subscriptions materialized by delayed webhooks after deletion), deletes operational org/team/member data, and retains seven-year pseudonymized financial/audit records. Active reservations retain live organization/team/membership references and therefore block deletion; finalized reservation and usage rows retain immutable identifier/name snapshots without keeping operational rows alive.

## Logging
- Use `log/slog` structured events with request/trace ID, pseudonymous actor, organization/team/service/meter/reservation IDs, decision, result, and safe error classification.
- Audit authorization, organization/role/invitation/team, billing-limit, checkout/billing-portal-session/subscription/refund, reservation/settlement, deletion, and webhook decisions immutably without secrets or raw PII. Automatic reservation expiry and explicit release use distinct typed audit events, as do hosted billing-portal sessions and subscription checkouts.

## Dependencies and Integrations
- Consumes root sources at `protos/delibase/v1` and shared packages under `servers/internal`.
- Integrates with the future DeliDev origin at `https://deli.dev`, Logto, Polar, PostgreSQL, the planned Deck/RealQA APIs only for durable service-authenticated deletion lifecycle delivery, and tagged GHCR artifact publication.
- Catalog is checked-in validated configuration with explicit mini-app metadata, app/service UUID v7 identities, app/meter enabled state, required reservation TTLs, effective-dated signed-int64 USD micro-unit prices, canonical precision-zero integer unit definitions, service-to-meter allowlists, and Polar meter mappings. The production file may intentionally be empty; test fixtures contain at least two apps and meters. Synchronization runs transactionally and idempotently after migrations/startup, disables omitted mutable entries, retains referenced mappings, and inserts/ends price versions instead of rewriting price history. Startup validation rejects malformed documents, duplicate IDs, invalid/negative TTLs or prices, invalid precision, overflow-invalid values, missing or duplicate unit/service/Polar mappings, invalid mapping references, and incompatible price dates; disabled entries are excluded from anonymous reads and new usage authorization, while active reservations retain their service allowlist and exact Polar meter mapping until finalized, and effective-dated price changes pin reservation versions. No runtime catalog mutation API or operator UI.
- The disabled Deck meter is identified within app key `devhud` by meter key `deck_github_pull_request_refresh`. Its unit name is `provider_refresh`, precision is zero, effective price is exactly 50 USD micros/unit, and only the Deck service identity is allowlisted; one dispatched logical GitHub provider refresh is one unit. The immutable UUID v7 app/meter/service/price identities and Polar mapping are assigned in the later catalog-activation change, not inferred from or added to the checked-in disabled validation fixture. A different unit, precision, service mapping, or price requires a synchronized delibase/Deck contract change before activation; Deck fails unavailable before provider dispatch when authoritative catalog metadata does not match this contract. The live-usage API requires the current forwarded user bearer on reserve, commit, and release and exposes no durable finalization grant. Deck calls each RPC only during the active authenticated client request with its memory-only bearer. An exact later active client retry may idempotently finish the same reservation with a fresh bearer, but no Deck scheduler, billing worker, stored bearer, background authorization, detached continuation, or post-client GitHub/delibase call is authorized.
- The planned disabled RealQA meters are identified within app key `devhud` by meter keys `realqa_image_transfer` and `realqa_image_storage`, and only the RealQA service identity is allowlisted to either. Transfer uses precision-zero unit `encoded_mib` at exactly 500 USD micros/unit; one submission reserves `ceil(accepted_declared_encoded_bytes / 1_048_576)` units and commits `ceil(verified_uploaded_encoded_bytes / 1_048_576)` units after one aggregate rounding. `verified_uploaded_encoded_bytes` sums the accepted declared lengths of successfully verified PUTs rather than server-sanitized output lengths, so the commit remains within the reservation even when re-encoding grows an object. Storage uses precision-zero unit `mib_day` at exactly 2 USD micros/unit; its `REALQA_STORAGE` authorization maximum is `ceil(verified_retained_bytes / 1_048_576)` units per UTC day, and daily settlement is `ceil(retained_image_byte_seconds / (1_048_576 * 86_400))` units after one aggregate rounding. RealQA durably checkpoints each completed day and processes the oldest unresolved checkpoint while it is the immediately preceding day accepted by `ReserveAuthorizedUsage`; once accepted, commit/release may finish later against the reservation's stored period. It never silently skips a checkpoint: failure to establish the reservation before the next rollover begins non-billable, never-back-billed grace at the missed period's start and blocks new submissions. A current-day authorized settlement is otherwise reserved for a durable deletion or rebind cutoff that prevents later accrual from being attributed to the old authorization. A zero numerator produces no reservation, commit, or background authorization request, because delibase requires positive reservation/authorization maxima; RealQA records a zero storage day locally without an authorized-usage mutation. Checked wide-integer overflow fails closed. Immutable UUID v7 meter/service/price identities and Polar mappings are deferred to the later activation change; the checked-in disabled validation fixture remains non-authoritative and cannot activate public or metered behavior, and any mapping change requires synchronized delibase/RealQA contracts before activation.
- Configuration ownership: this service owns server non-secret configuration, database/catalog settings, CORS, API origin, and secret environment variable names; Logto/Polar own provider-side configuration; DeliDev owns browser-safe client configuration; shared defaults belong to `servers/internal`. Required non-secret variables are `DELIBASE_API_ORIGIN`, `DELIBASE_CORS_ALLOWED_ORIGINS`, `DELIBASE_CATALOG_PATH`, `DELIBASE_LOGTO_ISSUER`, `DELIBASE_LOGTO_AUDIENCE` (which must equal `https://delibase.deli.dev`), `DELIBASE_LOGTO_JWKS_URL` (an HTTPS URL without credentials, query, or fragment), the Management API `DELIBASE_LOGTO_M2M_CLIENT_ID`, and `DELIBASE_POLAR_PRODUCT_ID`. Optional non-secret variables are `DELIBASE_HTTP_ADDRESS`, `DELIBASE_SHUTDOWN_TIMEOUT`, `DELIBASE_POLAR_ENVIRONMENT`, and `DELIBASE_POLAR_API_URL`; the provider environment accepts only `production` or the explicit opt-in `sandbox`, and the API override accepts only a compatible HTTPS URL without credentials, query, or fragment. Required secrets are `DELIBASE_DATABASE_URL`, `DELIBASE_LOGTO_M2M_CLIENT_SECRET`, `DELIBASE_POLAR_ACCESS_TOKEN`, `DELIBASE_POLAR_WEBHOOK_SECRET`, and the distinct minimum-32-byte `DELIBASE_LOG_PSEUDONYM_KEY`. The Logto issuer plus M2M client pair owns Management API account deletion; raw client credentials are never accepted inbound. The image bundles only the disabled RealQA storage catalog fixture and supports a read-only mounted catalog through `DELIBASE_CATALOG_PATH`; the fixture cannot activate public or metered behavior. The browser-safe client variables are `PUBLIC_DELIBASE_API_ORIGIN`, `PUBLIC_LOGTO_ENDPOINT`, `PUBLIC_LOGTO_APP_ID`, and `PUBLIC_LOGTO_AUDIENCE`; they must not contain secrets, and both API origin and audience use the same canonical value. No variable may be logged or baked into the image, and required variables fail closed when absent.
- Feature lifecycle delivery has two additional outbound-only configuration sets. Deck uses required non-secret `DELIBASE_DECK_LIFECYCLE_API_ORIGIN`, `DELIBASE_DECK_LIFECYCLE_LOGTO_AUDIENCE`, and `DELIBASE_DECK_LIFECYCLE_LOGTO_M2M_CLIENT_ID` plus required secret `DELIBASE_DECK_LIFECYCLE_LOGTO_M2M_CLIENT_SECRET`; RealQA uses required non-secret `DELIBASE_REALQA_LIFECYCLE_API_ORIGIN`, `DELIBASE_REALQA_LIFECYCLE_LOGTO_AUDIENCE`, and `DELIBASE_REALQA_LIFECYCLE_LOGTO_M2M_CLIENT_ID` plus required secret `DELIBASE_REALQA_LIFECYCLE_LOGTO_M2M_CLIENT_SECRET`. In production, each origin and audience must equal that feature's canonical API origin (`https://deck.deli.dev` or `https://realqa.deli.dev`), the two client IDs must identify distinct Logto client-credentials applications, and each identity may receive only the scope needed for its matching `DeleteFeatureData` lifecycle mode. When lifecycle enqueue/dispatch is implemented, startup fails before accepting account/organization deletion or claiming lifecycle work if either set is absent, partial, malformed, shares a client identity, or targets the wrong origin/audience. These client secrets are used only to obtain outbound feature-audience access tokens, are never accepted inbound, and must not be logged, persisted, baked into images, or exposed to DeliDev. Until the planned feature APIs and dispatch clients exist, no lifecycle variable, secret injection, or working delivery is claimed.

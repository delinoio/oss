# DeliDev session acceptance and input queue contract

## API format generations

Capability 9 changes only the current account generation for new sessions. All
original execution authorization and continuation resolve the immutable assignment's
connection ID, including proxy requests, subsequent tools, Resume, Fork, Sidechat,
compaction, title and auxiliary execution. Retained profile/health/validation supply
original admission evidence; current account enablement, quota/exhaustion, cleanup,
Worker existence, session restrictions and budget still apply. Changing or validating
a new format cannot replace original history or interrupt a valid original stream.
New routing requires current-format validation and Worker compatibility. Incompatible
Workers are marked for explicit reconfiguration without changing accepted executions.
Follow the [account contract](cmds-delidev-accounts-contract.md#connected-api-format-changes).


## Direct execution startup

[Direct startup](cmds-delidev-execution-startup-contract.md) replaces mandatory installation/protocol inspection for negotiated v4 execution jobs. First, continued and scheduled execution retain the same atomic input, configuration, account routing, leases, budget and Worker authority. The actual process must publish readiness before its API relay can infer. A failed attempt with positive no-send and original cleanup proof keeps its rejected input and immutable assignment; explicit revision-checked Resume creates a distinct same-selection attempt. Uncertain input or cleanup retains original recovery. A retried first execution has a separate native root ID without rewriting the initial selection; continuation and title attribution use that successful original lineage.

## Scope
`cmds/delidev-cli/internal/domain/session.go`, `internal/store/sessions.go`, `internal/server/sessions.go`, `internal/server/session_workspace.go`, `internal/server/session_workspace_recovery.go`, `internal/server/session_dispatch.go` and `internal/cli/sessions.go` own durable session acceptance, ordered input, revision-checked edits, visibility and workspace preparation controls. `internal/domain/execution.go` and `internal/store/execution.go` provide the private first-execution configuration/selection transaction primitive. `internal/domain/execution_events.go`, `internal/server/execution_events.go` and the Worker publication components implement the private core native-event path. Authenticated `SessionService` acceptance and workspace controls are implemented end to end through the CLI/server and real SQLite.

Workspace preparation and first Codex API execution are integrated through durable outbound Worker jobs. Creation initially retains `outcome=not-started`, `dispatch=blocked`, a readiness-pending problem and the current workspace job. Once preparation and current dispatch checks succeed, the coordinator atomically claims the earliest input, freezes the configuration/account/route and queues its immutable native assignment. The owning Worker independently validates actual filesystem/native/provider authority before sending. Native Stop/Archive, FIFO continuation, explicit Resume, selected-input Steer and non-secret question responses are integrated for the pinned Codex API profile. Public approval response delivery is also integrated; exact approval acceptance/recovery, protected answers, general native recovery and additional fork profiles remain pending; bounded same-account Codex forks follow [their contract](cmds-delidev-forks-contract.md). Acceptance, a ready workspace and an assignment are separate from successful native execution.

## Durable PR Associations

Stable zero-to-many PR associations are separate session/project-owned `pull_request` resources under the [integration contract](cmds-delidev-integrations-contract.md). Dedicated owner/client link/unlink RPCs and `session pr` commands retain exact remote identities after Archive/restart without changing session revisions, dispatch, native ownership or queue state. New links require fresh project-scoped GitHub detail and post-read configuration/generation rechecks; retained reads/unlink remain available after project/profile reconfiguration. Association metadata is not current problem evidence or remediation eligibility.

## Runtime and Language

Go with the root dependencies, existing Connect transport and private SQLite authority. No client-owned database or in-memory-only acceptance queue.

## Users and Operators
Owner and paired clients may accept sessions and manage their inputs. Worker credentials cannot call these owner operations. Each session keeps its selected execution machine independently of whichever client later views it. Creating-client provenance is server-derived from authentication; source labels distinguish manual and external CLI intent without granting authority.

## Interfaces and Contracts
Native child observations follow the [subagent contract](cmds-delidev-subagents-contract.md). The original assigned Worker may publish exact child updates after root completion and before cleanup confirmation. Root or intermediate-parent completion never completes running descendants. Live/unavailable children block cleanup, while closed trees still require independent original process/workspace cleanup. Observed-child sessions retain version-1 paused completion; child history cannot authorize version-2 continuation or recovery.

`session create --input FILE|- [--wait]` accepts the closed `domain.CreateSession` document. Every path selects exactly one Agent Worker, never separate harness/account/model overrides. Project sessions default to Worktree; projectless creation requires explicit `general-chat`. Initial mode defaults to `execute`; `plan` preserves the intended native mode for the pinned Codex first-turn profile. RPC creation defaults to `MANUAL`, while the CLI always supplies `EXTERNAL_CLI`.

Optional `name_mode` is `manual` or `automatic`; omission remains the original manual JSON and receipt identity. Automatic mode rejects a supplied `name` and returns the server-owned `New session` placeholder immediately. The one title operation is queued only after the original first successful native turn and confirmed cleanup; its auxiliary Worker lane, exact original authority, status and separate usage purpose follow the [automatic title contract](cmds-delidev-session-titles-contract.md).

```json
  "machine_id": "<canonical execution Worker UUID-v7>",
  "project_id": "<canonical project UUID-v7>",
  "workspace": "worktree",
  "starting": [],
  "prompt": "Inspect the parser and explain its current behavior.",
  "mode": "execute"

```

Each optional starting entry has `repository_id` and a typed `reference`. Selections must belong to the project's repositories; every repository needs a configured checkout on the chosen enabled machine. General Chat cannot select a project or Git references. Local cannot select starting references. Creation requires `--local-worker-dir PATH` pointing to the invoking computer's private paired Worker scope. The CLI validates its type, selected machine, exact endpoint and authenticated server identity/protocol before submitting its credential in the dedicated `CreateSessionRequest.local_worker_token` field. The server independently authenticates that Worker in addition to the owner/paired client, derives immutable `session.local_origin` machine/device IDs and rechecks the Worker credential inside the acceptance transaction. Credentials never enter the document, jobs, receipts, events or logs. Local selection explicitly shares the existing checkouts; a machine ID or loopback URL alone cannot authorize it. Remote viewers and controls retain the original machine; Worktree/General Chat reject the extra Local authority.

Creation validates the selected Agent Worker's current relationships and the project's Agent restriction, then atomically creates the session, first input and workspace job. The preparation request freezes the ordered repository list, primary repository, canonical Worker checkouts, per-repository base/starting references and effective automatic-fetch selection. Session starting-reference overrides apply by repository identity; automatic fetch requires both the global setting and repository setting. This is workspace preparation input, not an execution snapshot. For execution, it retains selections only; it does not freeze Agent Worker settings/templates, choose an account or advance routing. Account-less Agent drafts may be retained as blocked sessions. First dispatch rechecks current project/account/machine/native restrictions, resolve all effective settings and exact instructions, and commit the immutable snapshot and account routing state together immediately before execution. Later configuration changes must not rewrite an established execution snapshot.

The first-execution transaction and private remediation planner share one read-only configuration/template/account resolver. Its preview owns no input, account reservation, immutable snapshot or routing update; only a subsequent claim may commit those facts after resolving current configuration again. Native account/installation compatibility checks are likewise shared with assignment construction. A preview followed by configuration changes cannot freeze its former account or bypass the ordinary first-dispatch checks.

`session get --id ID` reads current metadata. `session list` supports `--project-id`, `--include-archived`, `--limit` and `--page-token`; ordinary lists hide only fully archived sessions. Generic explicit resource reads/snapshots can still retrieve retained archived records. Lists use canonical identity order and signed filter-bound cursors, with at most 200 records and 3 MiB of stored document bodies per page.

`session enqueue --id ID --input FILE|-` accepts `{"prompt":"...","mode":"execute"}`. Its transaction increments a session-owned acceptance sequence and retains the exact intended mode, content revision and `queued` delivery state. Concurrent requests use this durable order, never client clocks or UUID generation order. Queues are capped at 1,000 pending inputs and 4 MiB of pending prompt text; one input is at most 256 KiB of well-formed NUL-free UTF-8. Accepted blocked/paused sessions retain follow-ups; archiving/archived sessions reject new input. Queueing never supplies an approval or resumes paused work.

`queue list --session-id ID` returns acceptance order with byte/record-bounded pages and session-bound sequence cursors. `queue edit --session-id ID --id ID --revision N --input FILE|-` accepts only a `prompt` field, preserving accepted mode and sequence while incrementing content and resource revisions. `queue remove` (also `queue delete`) requires the same identities/revision. Only `queued` input can change; claimed, accepted, uncertain or removed input fails. Removal replaces content with an empty durable `removed` tombstone, updates pending counts/bytes, and excludes the entry from queue lists. It does not reuse its identity/order or resurrect content on receipt replay.

The session's `preparation` carries the current job ID and a closed `pending`, `stopping`, `ready`, `failed`, `canceled` or `uncertain` state. `SessionChange.workspace_job` returns that current job alongside session/input metadata in one read transaction, including on receipt replay. Its successful output is the canonical Worker manifest. Publication checks version, exact session/machine/mode/input digest, every ordered repository and source checkout, explicit references, resolved commits, primary directory, ownership and the Worker OS path grammar. A malformed successful result becomes uncertain and is not retained as a usable manifest. The job outcome and preparation state commit atomically. Worker replacement/revocation also propagates uncertainty to the owning session.

`session prepare --id ID --revision N [--wait]` explicitly retries a confirmed failed/canceled preparation, retaining the original request even if project/repository settings later change. Legacy sessions without a preparation derive one from current configuration. Pending/claimed/ready attempts return their existing job instead of preparing twice; uncertain ownership requires reconciliation, and archived sessions must first be restored. Preparing a paused session does not resume its input. `--wait` on create/prepare waits up to 25 seconds within the command deadline, retains accepted session/job identities on timeout/failure, and refreshes session metadata. Timeout leaves the actual queued/claimed state visible; it is not successful preparation. An accepted failed job returns its safe typed problem with the identities.

`session stop|archive|restore|resume --id ID --revision N` uses closed typed controls. Before any native claim, Stop pauses dispatch while retaining `not-started`; Archive additionally requests retained visibility to become archived. Undispatched preparation is canceled atomically before Worker claim. Claimed preparation receives a durable cancellation bound to that exact job; the session reports `stopping`, and Archive stays `archiving` until a terminal result proves preparation has finished or cleanup succeeded. Already-ready workspaces are retained. A success racing cancellation is recorded as ready, with Archive completion only after native preparation has ended. Uncertain ownership leaves recovery required and Archive pending. Cancellation never stops the whole Worker stream or changes another job's context.

Restore (also `unarchive`) clears fully archived visibility only and keeps dispatch paused. Queue contents and outcome remain unchanged. Resume may claim the first input of a prepared, never-executed active session after the same current validation as automatic dispatch. A failed Resume preserves pause and queue/routing state. After a verified preceding native execution, Resume uses the continuation gate below, including retaining explicit intent for a future input when the queue is empty. Records with running/previous harness execution cannot be declared stopped by workspace-only controls. Future harness controls must durably pause first, revoke execution authority and confirm owned native cleanup before reporting success; Stop and Archive have different terminal/process/forward ownership boundaries in the normative issue. `session recover-workspace --id ID --revision N [--cleanup] [--wait]` reconciles an uncertain preparation on its original machine. Acceptance preserves the original job and commits a separate `recover-workspace` job, `preparation.recovery_job_id`, paused dispatch and `recovery=reconciling`. `SessionChange.recovery_job` returns its current record. Concurrent identical recovery actions reuse their pending job; a different pending action conflicts. Failed/canceled/uncertain recovery requires a new explicit request, while exact accepted receipts never repeat filesystem work.

The server sends the exact original claimed revision/instance/document digest and immutable preparation input. The Worker must match these against the original private journal before native reconciliation. Missing, corrupt or mismatched journals cannot authorize cleanup. After bounded owned-process reconciliation, a complete matching manifest is checked at its exact owned paths, with no replacement links, the original detached commit, common Git directory and worktree registration. Ready content, including working changes, is retained even when `--cleanup` was requested. A changed commit/branch, missing files or incompatible ownership remains uncertain; recovery never fetches or prepares again.

An incomplete manifest requires explicit `--cleanup`. Cleanup validates the accepted ordered ownership prefix, preserves original checkouts, reconciles native processes and Git registration, and retains a private per-original-job cleanup proof outside the removed tree. The proof and synchronized removal permit retry after interruption between deletion and completion publication. A missing root alone is never proof of cleanup; it requires that proof or an exact durable original failure/cancellation journal that already confirmed cleanup. Canceling recovery preserves original uncertainty and pending Archive until a later recovery confirms its outcome.

Recovery publishes the original job outcome and session state together: proven ready becomes `ready`, proven cleanup becomes `canceled` and permits explicit `session prepare`, recovery clears, dispatch stays paused, and pending Archive completes. No native harness execution or automatic input resend follows. Native conversation recovery remains a separate pending integration.

Optional session estimated-cost budgets follow the [usage contract](cmds-delidev-usage-contract.md). Creation may include a budget; dedicated Get/SetSessionBudget and `session budget get|set|remove` provide authorized lifetime evidence and revision-bound explicit changes. Both initial and continuation acceptance check the selected-currency known historical subtotal before routing/input claim. Reached thresholds block even an empty Resume with `budget_reached`, preserving queue/in-flight work. Below/unknown evidence warns and permits work without verified compliance. Budget edits do not Resume, Restore, cancel work or clear unrelated recovery; exact receipts return current state.

`session rename --id ID --revision N --name NAME` changes only the bounded title. Creation, enqueue, edits/removal, rename and controls use UUID-v7 request receipts and the same server serialization boundary. Mutations requiring an existing revision reject stale writes; retries of an accepted identical request return current referenced records. An old creation/enqueue/edit receipt cannot restore earlier content or repeat dispatch. Unsupported or pre-acceptance validation failures do not claim a successful receipt. No future schedule/remediation/fork source is accepted through this initial external creation schema.

Worker-owned interactive terminals follow the
[terminal contract](cmds-delidev-terminals-contract.md). They have independent
UUID-v7 process owners and do not take the agent execution lease. Agent Stop
preserves them; every Archive publication atomically requests exact selected-
session closes and remains pending until all native resources confirm cleanup.
Late agent/title/recovery writes use the same central barrier. Session/terminal
storage deletion rejects unconfirmed terminal cleanup. Viewing/disconnecting
does not create or close a shell, and unknown ownership never permits PID cleanup.

## Storage
### First-execution transaction primitive
`Tx.ClaimInitialExecution` is an internal transaction primitive used by the public first-dispatch coordinator. It requires exact current session/input revisions, transient `dispatch=ready`, no previous execution/snapshot, active archive visibility, no recovery, a successful matching preparation job, and the earliest queued input. The coordinator validates the exact selected configuration and creates its immutable Worker job in the same transaction; any failure rolls back ready state, snapshot, input ownership, routing and job. A database claim alone grants no native capability or API relay credential.

Immediately before the claim, the transaction reads the current Agent Worker, canonical model/provider, global routing default, ordered template revisions/contents, project restrictions and candidate account state. It stores requested harness/model/native model/effort/options, ordered weighted account references, the resolved routing policy, and exact additive instructions. Template composition preserves every byte and joins ordered contents with two LF bytes; it never replaces base instructions or truncates a template. Each template remains bounded to 128 KiB and combined instructions to 256 KiB including separators. The complete JSON snapshot and enclosing entity retain the 1 MiB storage bound; overflow rejects the entire claim. A SHA-256 digest binds the exact encoded configuration, including source revisions. Native default settings remain unspecified in the snapshot and require separate effective observations.

The transaction rechecks current model compatibility, machine enablement, project Agent/account restrictions, current account health/connection/exhaustion and provider authentication compatibility, then computes the actual six-policy route using the persisted per-Agent Worker state. The initial selected account and non-secret connection identity, full candidate/exclusion/quota observation, immutable configuration, first input identity and acceptance time are retained in `session.initial_execution`. The claim also writes a distinct execution ID and native request ID on the input, marks delivery `claimed`, sets session dispatch `claimed`, and advances routing state in the same state/event/receipt transaction. Outcome remains `not-started`, and pending queue capacity remains charged until proven native acceptance. Subsequent execution claims preserve this original selection and retain their exact predecessor; explicit account changes/history remain separate pending lifecycle work.

A failed transaction, mismatched native preflight or stale input revision rolls back all snapshot, queue and routing changes. The caller must return reference-only receipts. An identical accepted receipt never repeats selection after restart, and another request cannot replace a first snapshot. Later template/Agent/global policy edits cannot mutate the embedded snapshot. Current restrictions, connection readiness and native compatibility still apply on every later execution; a frozen configuration never waives them. Routing preview reads the same persisted state without reservations. Multiple contradictory routing owners return recovery-required instead of choosing an arbitrary record.

### Public first dispatch
The lifecycle-joined server coordinator scans up to 50 eligible sessions per one-second tick with an identity cursor and a 3 MiB aggregate page bound. Each claim has a five-second context; shutdown cancels and joins the coordinator before closing relay, credential or database owners. The scan includes only never-claimed, not-started, active, recovery-free sessions with ready preparation and pending input. Paused/restored sessions require explicit `session resume`; preparation retry/recovery cannot implicitly resume them. Previously claimed or uncertain work is never automatically redispatched.

The commit rechecks an enabled machine with a current Worker instance/heartbeat (45-second lease), unique detected Codex `0.151.0` installation and successful native protocol observation, the original complete preparation result with its Worker's path grammar, current Agent/model/project/account restrictions and exact supported option mapping. General Chat, prepared single/multiple-repository Worktree and authenticated Local checkouts are supported by the Codex profile. Local dispatch rechecks the retained originating Worker device and exact preparation origin; a viewing client cannot replace that provenance. The selected account must be an enabled usable API connection with matching successful credential or explicit keyless-endpoint validation; provider protocol must be OpenAI Responses with matching authentication. Stored credentials, version detection, model catalog entries and a handshake alone cannot establish selected-model inference capability. The check authorizes a bounded native attempt under those recorded conditions; actual model acceptance and effective native settings remain independently observed by the Worker and provider. No inference, HTTP, credential read or server-filesystem interpretation of Worker paths occurs in the claim transaction.

Configuration, ordered template contents, route/connection, original mode/prompt and fresh native identities are captured in one immutable `execute-session` job. The owning Worker must still prove the real workspace lease, exact executable/private runtime, effective native provider/settings and current scoped relay grant before sending. Unsupported native events fail explicitly; this profile does not promise all Codex tools or other harnesses. The current execution job is joined into `SessionChange.execution_job` and CLI `execution_job`, including original creation/control receipt replay. `session create --wait` continues to wait only for workspace preparation; it is not an inference-completion wait.

A failed automatic check rolls back the entire prospective claim before separately publishing a stable blocking problem. It neither consumes input/routing nor creates a snapshot or replayable failed claim receipt. Unchanged problems do not produce recurring revisions/receipts. Current session revision checks prevent this diagnostic update from overwriting concurrent Stop/Archive/recovery. Unclaimed readiness is checked again on later scans, so correcting configuration or connecting the Worker can unblock the original queued input. Stop/Archive, input edit/removal, first Resume and claim serialize through SQLite; old accepted control receipts return current ownership and cannot cancel a newer accepted execution.

### Native core-event publication
`WorkerService.PublishExecution` is a Worker-only private publication boundary for an already claimed execution assignment. It verifies the current Worker process, exact immutable job revision, session/configuration/input ownership, supported native identity profile and a contiguous per-execution sequence. The initial closed event kinds are thread binding, input acceptance, message start, assistant text append, message completion, native token observations, generic notices and turn completion. The adapter must normalize native payloads first; raw protocol extensions and native diagnostic bodies cannot enter this RPC.

Thread binding stores observed model/effort/tier/permission/approval separately from requested immutable settings in `session.execution`; explicit selections must match and unavailable default observations remain null. Input acceptance binds the native turn, changes that exact input to `accepted` and releases its pending count/bytes once. It does not send another prompt. Message publications use stable UUID-v7 product IDs with a unique indexed session/native-thread/native-turn/native-item mapping. User messages must match the exact accepted input identity and text. Role, input and established phase cannot change; a previously unavailable phase may become observed. Appends and final text are bounded to 256 KiB, with no truncation. Final text must include the retained prefix. There are at most 10,000 messages and 100,000 normalized publications per execution.

A successful terminal event requires every started core message to be complete. Failed/stopped outcomes preserve partial messages. Native terminal outcome is retained separately from current product pause/archive/recovery: late completion during cancellation cannot clear Stop, claim completed Archive, replace an earlier failure or clear recovery. Terminal publication revokes subsequent API inference but leaves the claimed job and active execution ownership intact until separate owned-process cleanup reporting. The same publication boundary covers each distinct continuation execution. Its binding must preserve the preceding native root and exact observed defaults; no completed turn from any earlier terminal inbox source may be rebound to fresh input.

The Worker `ExecutionPublisher` owns one private locked outbox per immutable assignment. It binds job/revision/document digest, Worker instance, server/device identity and last acknowledged sequence; a pending record contains one typed event and its UUID-v7 request ID. The exact envelope is synchronized before RPC. Lost/invalid acknowledgments or failed synchronization block further publications and retain uncertainty. Explicit `ReplayPending` sends only that same event request, never native input. A confirmed acknowledgment is synchronized before its pending payload is removed. Changed assignments/processes cannot inherit the journal. Core Codex normalization allocates stable per-native-item product identities and refuses further events after uncertain publication; unhandled extensions explicitly return unhandled and require a dedicated adapter or an unsupported execution result, never silent omission by a production dispatcher.

The actual Worker job loop now invokes this composition for an independently accepted immutable first Codex assignment. It retains the operation journal before side effects, claims the prepared workspace, creates a private retained runtime, registers a digest-only relay grant, starts the exact thread/input and publishes every supported event. An unhandled native event stops execution for reconciliation rather than being silently dropped. Public first dispatch now queues this composition. Remaining tool/approval families, protected answers, usage aggregation and native recovery remain pending.

Native usage publications create immutable `usage` resources under the owning session/project with a Worker-retained UUID and exact sequence. The server supplies execution, account, connection, canonical provider/model, harness/version and native thread/turn attribution from the assignment. `session.execution.latest_usage_id` points to the latest observation; cumulative and last-request counters are retained separately without summation, monotonic rewriting or cost inference. A reused observation ID cannot replace history, and receipt replay cannot create another observation. Nullable native fields remain unavailable. These resources are observations only; aggregate deduplication across resets/resume/forks/children, pricing, actual costs and budgets remain pending. Exact native response completions now use the separate [deduplicated usage ledger](cmds-delidev-usage-contract.md), with original assignment attribution and `latest_response_usage_id`; they do not sum or replace cumulative observations. Generic warning publications update a count and last closed notice kind atomically without native diagnostic text. Neither notice nor usage publication changes dispatch, quota health or terminal outcome.

### Native command and patch records
The five normalized tool forms are `tool-started`, `tool-completed`, `tool-output`, `tool-input` and `tool-patch`. They create/update `message` resources with role `tool` and a dedicated typed payload; tools are never assistant text. The existing schema-v8 identity index binds every native item across both text and tool messages, forbidding another product ID or message family from adopting it. Matching execution/thread/turn ownership, contiguous publication and immutable command/source/cwd are checked before mutation. A completed tool cannot accept more updates. Tool failure/decline completes that item but does not determine the native turn outcome; successful turns require every started item to be complete.

Records retain separate native start/completion snapshots, nullable streamed command output, sequenced terminal-input observations and sequenced patch revisions. Aggregate native output is not required to extend streamed output and never replaces it. Unknown exit/duration/process/output values stay null. Parsed actions and plugin/source metadata remain advisory native provenance. Paths, process IDs and reported tool results cannot grant product terminal/file access, answer approvals or broaden permissions.

Individual text fields and accumulated command output use the 256 KiB message bound, command actions and changed files are capped at 1,024, and each tool publication payload is capped at 512 KiB of encoded JSON to leave room for its envelope/outbox. Each tool retains at most 1,024 input observations and 1,024 patch revisions, subject to the existing 1 MiB complete resource limit and 10,000-item/100,000-event execution bounds. Exceeding a bound leaves prior content, identity and sequence unchanged; content is never truncated. Exact outbox/receipt replay cannot append the same output or revision twice. Native history remains required for explicit reconciliation after a publication failure.

### Native artifacts and turn progress
`artifact-started`, `artifact-delta` and `artifact-completed` publish plan/reasoning items as dedicated `artifact` transcript records. They share native-item uniqueness and the completed-item success gate with messages/tools. Records retain the initial snapshot, each ordered delta with native part index and execution sequence, and the final authoritative snapshot. A completed plan may replace the entire streamed draft; no assistant-message prefix rule applies. Reasoning content is limited to explicitly observed parts, and null JSON string elements cannot become fabricated empty content. Completed artifacts reject further mutation and cannot change kind or owner.

`progress-observed` publishes an immutable `progress` transcript record for each structured plan or aggregated diff update. These turn-level facts have no native item ID and do not enter the native-item index. Plan explanation and step statuses remain exact; an explicit empty diff remains an observation. `session.execution.latest_plan_id` and `latest_diff_id` reference the newest retained records without rewriting earlier observations. Reusing an observation ID cannot revise history. Progress neither completes a turn nor grants repository/file-review ownership, permissions or approval authority.

Artifact/progress publications have a 512 KiB encoded payload bound, individual text fields use the 256 KiB message limit, and reasoning indices/parts and plan steps are bounded to 1,024. Artifact stream retention allows at most 10,000 deltas under the existing 1 MiB complete resource limit. Execution event limits bound turn-progress history, while native artifacts also share the 10,000-item limit. A bound failure preserves earlier evidence and sequence for explicit reconciliation; no text, array or history is silently truncated. Outbox restart replay retains the exact observation identity and cannot duplicate a delta or progress snapshot.

### Selected queued-input Steer

`session steer --id SESSION --input-id INPUT --revision INPUT_REVISION --execution-id EXECUTION --turn-id TURN` uses the dedicated owner/paired-client `SteerQueuedInput` RPC and common durable `--request-id`. The revision belongs to the selected queue entry, not the session. The request ID is also the immutable `steer` resource ID. Acceptance returns the attempt plus the current session/input/execution-job references; `steer get --id ID` and ordinary resource reads expose delivery state. Reference-only actor-bound receipt replay returns current state without reclaiming input or repeating native work.

The server atomically checks the exact active execution/turn, original input mode, current pinned Codex installation, original account connection and live Worker/server-epoch authority. Paused, archived, recovery-pending, completed, question/approval-waiting and unconfirmed-answer states cannot accept a new attempt. Only one unresolved Steer may exist per session. Acceptance claims precisely the selected queue entry, retaining sequence/content revision and charging its existing capacity until native acceptance; it does not select the oldest entry or reorder remaining FIFO input. Concurrent edits/removal, other Steer attempts, dispatch, Stop/Archive and question responses serialize through the same store boundary. Each execution permits at most 4,096 attempts and 4,095 total accepted inputs, including its primary input.

`WatchWork.steer_input` is metadata-only and targets the active immutable job without waiting behind the ordinary job queue. The owning Worker journals its claim identity before `ClaimSteerInput`. The claim validates current authority and the exact original attempt/queue binding, including on receipt replay, before returning the original prompt. Lost/changed/foreign claim replies never authorize sending. The Worker serializes claim, native delivery, inspection and publication with transcript, question and terminal events; its native adapter also checks current waiting flags and the exact active turn. The original mode, snapshot, model, account and permissions remain unchanged. There is no start, cancel/resume or other emulation fallback.

Before one `turn/steer`, the Worker synchronizes a content-free send-intent journal. Native acknowledgement establishes acceptance; a definitive stale/unsupported/preflight rejection leaves the selected input queued. An uncertain reply automatically triggers a bounded exact native-history inspection on the original connection before any possible retry. Missing or inconclusive history preserves `uncertain` delivery, paused recovery and original ownership; no native send is replayed. Both journal and `steer-observed` publication contain only identities, content digests and closed delivery/evidence/error codes. Publication verifies the original Worker claim and native scope, commits queue capacity and ordered `accepted_inputs` exactly once, and permits that accepted input's exact user-message content in the transcript.

A late native acceptance or definite rejection may resolve one earlier uncertain observation under the same claim. The original observation/sequence remains immutable alongside a separate resolution/sequence. Positive acceptance removes ordinary FIFO eligibility and records its binding; definite rejection returns the input to its original FIFO position. Neither resolution clears an existing recovery gate or resumes execution. Confirmed acknowledgement remains acceptance even if independent native-history inspection fails; that failure separately preserves recovery. Contradictory or repeated fresh resolutions fail; exact publication receipt replay cannot repeat accounting.

Stop, Archive, account disconnect, a newly pending question and terminal/lost-Worker reconciliation retire an attempt that has not been claimed, preserving the queued input. Stop or a question after a Worker claim cannot prove absence of native delivery: the attempt stays owned until its exact report, and terminal/lost ownership makes unresolved delivery uncertain. A matching committed native fact may still publish after targeted cancellation or account loss, while live send authority is denied. These transitions never treat a cancellation request, interrupted stream, missing journal or native terminal event as proof that the Steer was rejected. Steer resources and Worker journals belong to the session's future coordinated deletion/backup boundary.

### Subsequent turns and explicit Resume

The shared lifecycle-joined coordinator scans first-dispatch candidates and sessions with a retained automatic or explicit continuation intent, under the same 50-record/3 MiB/five-second transaction bounds. A successful version-2 completion can authorize FIFO progress; Stop, Archive, Restore, native failure/interruption, unresolved answer acceptance and recovery keep dispatch paused. `session resume` requires active visibility, no active execution/recovery, exact terminal publication, accepted input and verified cleanup. Resume rechecks current readiness even with an empty queue, then retains `next_execution_intent=explicit-resume` for the next accepted input. Enqueue alone never grants that intent. An accepted old Resume receipt cannot undo a subsequent Stop.

The continuation transaction resolves one exact current execution job, validates its version-2 completion against the entire preceding progress and accepted queue entry, and rechecks the original machine's current lease/installation, preparation manifest, selected account connection/validation/exhaustion, provider/model compatibility and project restrictions. It does not resolve changed Agent settings/templates, rerun routing, substitute accounts or perform native/network/filesystem work. Failed checks roll back the entire prospective claim. A separately revision-guarded stable blocking diagnostic may be retained without erasing concurrent pause/recovery or consuming input. Legacy completion evidence without a bound native checkpoint cannot be upgraded or continued implicitly.

`session.initial_execution` remains immutable. Each later claim sets `current_execution` to a fresh execution/input with the explicitly retained account/connection (the original selection unless changed through the stopped-account operation below), claims only the oldest queued entry and assigns fresh native request identities. Queue capacity remains charged until native acceptance. The immutable version-2 `ExecutionJobInput.continuation` retains the exact preceding `ExecutionProgress`, accepted completion/checkpoint digest, original history execution ID, predecessor assignment-input digest, prior prompt digest/mode, history-verification request UUID and automatic versus explicit intent. Thus replacing the live progress never erases prior cleanup, observed settings, artifact references, notices or terminal facts. Prior inputs remain accepted and cannot reenter the executable FIFO; every earlier native terminal turn remains in an immutable inbox source and cannot be rebound. Session receipts and Stop/Archive resolve current execution ownership while preserving original selection history.

The Worker claims the dedicated continuation workspace lease against the exact closed predecessor and independently reconciled process scope. It reads the digest-bound private checkpoint under that lease. Each turn receives a new retained runtime, job/process owner, publication outbox and memory-only relay credential; only `CODEX_HOME` points to the original validated private history root. It resumes that exact native thread and verifies its latest terminal turn, ordered original input digests and complete original effective defaults/permissions before sending the new input once. Failed/interrupted predecessors require the durable explicit intent. Neither missing/changed history nor a failed check permits a replacement thread, account fallback, prior input resend or reconstruction of evidence. The successor checkpoint preserves the original history root, while binding its own new assignment, terminal turn and completion digest.

Per-request relay authorization and every event/completion/control recheck current selection. A completed predecessor's token, fresh stale event or fresh stale completion report cannot authorize or mutate its successor. Exact earlier receipt replay only acknowledges its retained fact. New thread bindings must match the predecessor's native root and observed settings; input acceptance must carry a previously unused native turn. Historical usage/content is not republished as fresh observations. Native `thread/goal/cleared` on resume is a validated content-free absence observation only; populated or foreign goal events still require their own adapters.

Require paused dispatch with no retained Resume intent, active execution, recovery, Steer ownership, outstanding interaction acceptance, Archive or uncertain/running/queued title work. Independently match the exact accepted predecessor input, terminal progress, settled original job and version-2 cleanup/checkpoint report. Only the pinned Codex API profile is eligible. No routing or modified Agent/template resolution occurs.

The native relay records the closed `full-history` versus sticky `account-bound` mode before provider side effects. Previous-response, conversation and Responses item references are account-bound; missing legacy observations remain unknown. Switching requires full-history evidence and rejects unknown or account-bound histories. The pinned HTTP-only Codex profile resumes the original native thread with complete retained history in a fresh process, without restoring a previous transport response cache. Every switched request independently forbids provider-owned remote history, including references already registered under B. This protects the boundary even if a later native request contradicts the original portable-history evidence.

An unchanged pair needs no alternate predecessor scope. After native history/settings verification, the new input is attributed to B. Ordinary FIFO continuation thereafter stays on B; there is no automatic fallback. The original current execution stays attributed to A until that new claim. Retain up to 1,024 changes without eviction; selection overflow fails atomically. New JSON fields are additive and omitted on historical records; no SQLite schema migration or historical rewrite is required.

Subscription switching, provider/model changes, active or uncertain sessions and a new account outside the initial snapshot remain unsupported. Unknown or required account-bound provider state is retained for its original account rather than reconstructed, stripped or silently rerouted. ### Worker continuation and completion
The runner supports prepared Worktree repositories, authenticated existing Local checkouts or an isolated General Chat directory with the exact Codex `0.151.0` API profile. Multi-repository execution uses every original prepared path in project order, the designated primary cwd and independently checked native runtime/writable roots. The Worker journal prevents another native send after either a completed result or interrupted operation.

`ReportWork` accepts closed completion profiles containing execution/input/native-thread/native-turn identities, the last acknowledged event sequence, the native terminal outcome and verified cleanup. Version 1 retains the original terminal evidence. Version 2 additionally requires a canonical lowercase SHA-256 `native_checkpoint_digest` binding the exact Worker-private continuation checkpoint; a version-1 report cannot carry that field or be silently upgraded into continuation proof. The Worker closes and joins the native client, independently reconciles its workspace lease's owned process index, synchronizes the immutable native checkpoint and then journals/reports its version-2 completion. Failure to retain that checkpoint requires recovery even when native terminal success was already observed. The server matches the report against the retained terminal publication and exact claimed job, preserves its exact checkpoint digest, marks `session.execution.cleanup_verified`, and clears active execution only when recovery is absent. For this first native profile, the same verified report completes pending Archive; uncertain reports cannot do so. A healthy version-2 success restores ready dispatch with automatic continuation intent only if the session was still claimed, active, recovery-free and without unresolved interactions. Empty queues remain ready for later input. Version-1 history, failure, Stop, Archive and recovery never gain automatic intent. Failed/stopped native outcomes retain their independent product state. Completion receipts contain only the job reference and expand current metadata after rechecking Worker ownership.

The checkpoint binds original assignment-input/configuration digests, session/machine/job/account/connection/history ownership, terminal facts, native session/turn, original input mode/content digest and complete effective defaults/permissions. It contains no prompt, response, instruction contents, tool output or credential. Its native path context stays private on the Worker. The file contains the version-1 terminal facts; the version-2 report adds the synchronized file's digest afterward to avoid a self-referential hash. A continuation must match both the accepted server report and this exact immutable file under exclusive workspace ownership before native history verification. Missing/corrupt/foreign/replaced/oversized checkpoint or history roots are never created, rewritten or inferred from a successful-looking native history. A retained file alone cannot resolve a lost server report, uncertain semantic interaction acceptance or current account authorization.

Execution progress now retains `accepted_inputs`, an ordered list of input UUIDs and canonical lowercase SHA-256 prompt digests. The primary input is first; all identities are distinct, and the list is capped at 4,095 entries so native continuation retains one tracking slot for the successor. First input publication records its binding after acceptance, and the Worker derives checkpoint inputs only from its acknowledged publication state. Continuation rechecks each binding against the exact retained queue session, execution, mode, native request identity and prompt digest; native request identities cannot be reused across these entries. Selecting a later same-turn input must not skip an earlier still-queued ordinary input on the next FIFO turn. A successor cannot reuse any accepted predecessor input identity.

The private checkpoint reader compares the entire ordered list and has a 1 MiB file bound, including the complete maximum input set without truncation. A legacy absent `accepted_inputs` field represents only the original single input. It cannot read a multi-input checkpoint by dropping additional entries or reconstructing them from native history. Exact file digest, original assignment/configuration/account/defaults and independent cleanup requirements remain unchanged. The dedicated public Steer acceptance/claim/control/publication path adds a same-turn binding only after native acceptance; creating its durable attempt or Worker claim alone cannot add that binding.

Incomplete output, publication uncertainty, mismatched native identities/cursor, missing cleanup or a failed Worker report retains active ownership and recovery rather than inventing successful cleanup. A claimed but unacknowledged input becomes uncertain without freeing queue capacity; accepted inputs stay accepted. Worker replacement and device revocation propagate this same recovery state atomically with job invalidation. Account disconnection separately pauses selected-account sessions and persists targeted cancellation without changing claimed envelopes; queued assignments become canceled, and missing native completion evidence remains recoverable after the Worker stops. Previously observed success/failure/Stop, partial transcripts and pending Archive remain intact. None of these uncertainty transitions resends input, completes Archive or reconciles a native history automatically.

### First-native Stop, Archive and Restore
The existing session controls now target the unique immutable first-execution job when a first snapshot is present. Missing or ambiguous job ownership rejects the control. Exact old Stop/Archive receipts return current references and cannot undo a later Restore.

The Worker distinguishes a targeted cancellation from loss of the owning stream. Afterwards a still-authorized Worker synchronizes one metadata-only interrupt request and gives native interruption, remaining event publication and terminal observation a shared 15-second deadline. A definitive native conflict may race already completed native work; the Worker can consume the bounded retained terminal facts but cannot retry the interrupt.

# AIPRouter console design

This specification defines the approved console design alongside the [console behavior contract](apps-aiprouter-console-contract.md). Illustrative names, usage figures, addresses and connection states are fictitious. Visual examples do not establish runtime or accessibility acceptance.

## Surface and visual system

Multilingual responsive web console for personal AI provider configuration, organization management, and a separate instance operator workspace. Target desktop 1440×1000, tablet 768×1024, mobile 390×844; support 320 CSS pixels without page-level horizontal scrolling. Treat the boards as concept layouts, not pixel-exact viewport captures.

Use a calm, light, Toss-informed hierarchy: one main task per page, plain action labels, generous spacing and progressive disclosure. Page background #F7F8FA, white cards, primary text #191F28, secondary text #4E5968, blue #1D4ED8 actions, pale blue selected surfaces, red #B42318 destructive actions. Use system sans-serif, 16px body, 14px labels, 28–32px desktop headings and 24px mobile headings, line-height at least 1.5 for body text. Use an 8px spacing rhythm, 12px card corners, 8px control corners, 44px minimum primary control height, and explicit text labels for statuses. Validate actual rendered contrast before acceptance; the raster preview is not accessibility evidence.

## Language selection

The approved language selector and responsive behavior are specified in the [console localization contract](apps-aiprouter-console-contract.md#localization). Place this control above all console surfaces. Keep existing page hierarchy, permission boundaries and destructive-action semantics when localizing content.

## Navigation and ownership

Desktop: 232px sidebar, top organization switcher with role, personal navigation, conditional organization navigation, account menu at bottom. Main area has a single h1, scope subtitle, page action and content. Personal links: Overview, Providers, Routing, API keys, Usage, Connect a client. Organization section, available to owners/administrators: Members, Invitations, Organization usage, Audit, Settings. Account menu: Account, optional Instance console, Sign out. Operator entry is separate from organization roles.

The switcher shows organization name, current role, current selection, search and Create organization. Empty search results explain that no memberships match. Switching clears the prior organization's visible data, closes resource dialogs, updates the URL scope, then loads the selected scope. Confirm before abandoning unsaved form edits. Never copy providers, pools, routes or keys into the next organization. A persistent subtitle says “Your settings in Acme Studio”; provider and routing pages say “Only yours in Acme Studio.” A role badge is descriptive, never an authorization cache.

Mobile: 56px header with labeled menu button, brand and organization switcher. Navigation opens as a modal drawer with grouped links and current page. No reduced desktop sidebar or competing bottom navigation. Cards stack; tables become labeled record cards with accessible per-record action menus. Filters collapse into a Filters sheet with active-filter count and Clear filters. Wide charts have text summaries and equivalent data tables; layouts must not require drag gestures.

## Roles

Members manage only their own providers, accounts, pools, routing, API keys, usage and client connections within the selected organization. Owners and administrators retain exactly the same personal-data boundary. Organization usage exposes per-member usage, estimated cost, model and error metadata, never credentials, prompts or response bodies. Do not show an “inspect provider” link on member details.

Administrators can invite/remove ordinary members and edit organization settings. They cannot change the owner or other administrators. Owners can appoint/demote/remove administrators, transfer ownership and delete the organization. Hide unavailable actions and explain important blocked actions, such as a sole owner's attempt to leave. Recheck on mutation; if authority changes while open, dismiss privileged editors, remove unavailable navigation and show “Your permissions changed. This action is no longer available.” Preserve login after demotion.

Instance operators see only whole-instance health/aggregates, request limits, retention, approved destinations, common price overrides and instance audit. No organization/member drilldown, impersonation, suspension, provider configurations, or raw request data. Deployment configuration owns operator assignment; the console has no Add operator control.

## Sign-in and onboarding

Sign-in offers “Continue with your identity provider” only. Missing or unverified email produces an explicit blocking error and a retry path after correction at the identity provider. Do not offer password signup or merge-by-email. Session expiry asks the user to sign in again and never automatically submits a pending mutation. Logout invalidates the session.

No-membership landing page: “Choose your organization,” pending invitation cards, and Create organization. A single organization-name field receives focus when the create form opens. Do not auto-create a personal organization. Invitation detail identifies the organization, intended email, role and expiry. Wrong verified email shows “Sign in with the invited email address”; expired, canceled, already-used and superseded links have distinct outcomes.

Overview includes a five-step checklist: Choose organization → Connect personal providers → Configure models/routing → Create API key → Connect a client. Completed steps remain navigable. Do not mark a step complete merely because a dialog opened. The guide is recoverable from Overview, not a blocking tour. Returning users see connection health and personal usage above the checklist.

## Providers and routing

Provider list: provider name, personal account label, authentication method, last verified status and actions. Statuses: Not connected, Connecting, Connected, Reconnect required, Cooling down, Connection failed and Unknown status. Status cannot be conveyed by color alone. Empty state: “Connect your first provider” with a clear personal-ownership explanation. Connect flow chooses a supported provider and supported authentication method. API-key inputs are masked and have explicit reveal controls; OAuth shows redirect/pending/canceled/failed states. Never redisplay stored secrets. Replacement is a new secret entry. Provider support must follow the [compatibility inventory](servers-aiprouter-compatibility-contract.md), not the illustrative cards.

Pools live under Providers and contain only the user's accounts in this organization. Routing lists model aliases and ordered primary/fallback connections. Editor offers only this user's eligible accounts/pools, shows the configured order and unavailable dependencies, validates duplicate names and missing connections, and requires explicit Save. Explain provider-specific policies through contextual help; do not suggest a universal retry count. Private/local HTTP destinations show an operator-policy error when disallowed. There is no local executable backend, workspace selector or execution permission UI.

Disconnect confirmation names the account, affected pools/routes and future-request effect. Do not silently remove dependent routing or imply external provider-account deletion. If a dependency requires repair, offer a route link. Connection failures preserve safe form values, but secrets must not enter URLs, diagnostics or notifications.

#### Provider OAuth setup dialog

Connect provider (OAuth) and Reconnect open one setup dialog before authorization starts. It uses setup-scoped styles (`oauth-setup`) so other dialogs are unchanged: white surface, 12px corners, max width 640px, 24px padding (16px and 16px side clearance below 768px) and internal scrolling within the viewport. Content order: title “Authorize {catalog provider name}” with the 44px Close control; the explanation “Use the callback and regional settings required by your provider.” with the smaller line “Leave optional settings empty to use the provider defaults.”; the “Authorization” group; a quiet “Before you continue” notice; the collapsed “Regional and advanced provider settings” disclosure; and an in-flow footer, separated by a divider, with Cancel and “Start authorization”. All controls are at least 44px tall.

The Authorization group shows the “Authorization method” select only when the provider catalog advertises methods. Options are exactly “Provider default” (the method is omitted from the request) plus the advertised non-unspecified methods labeled Browser sign-in (PKCE), Device code, Browser approval, Provider token and Native callback; an unknown future method uses the existing safe fallback label. The console never guesses options. Callback URI is a prominent URL input with autocomplete off and initial focus. It is not universally required because provider and method requirements stay server-authoritative. Its helper says that native callbacks and most PKCE providers need the exact registered callback URI, that the server starts no local listener and that the resulting callback is pasted in the next step. The “Before you continue” notice says that starting authorization does not mean the connection is complete.

The disclosure is closed by default and keeps all nine optional fields: Login provider, SSO region, API region, Start URL, API base URL, Authentication base URL, Portal URL, Registration URL and Client ID. The Callback URI and the five URL fields are validated locally on submit with per-field “Enter a valid URL.” messages associated through `aria-describedby` and `aria-invalid`; after a failed submission the first invalid field receives focus and a closed disclosure opens first. Focus moves only on a failed submission; editing a field clears its error without moving focus away from it. Values are trimmed and only nonempty values are sent. Opening or closing the disclosure never submits.

“Start authorization” is the only submission. It calls `beginProviderOAuth` once with the selected organization, provider ID, account name and, for Reconnect, the connection ID, shows “Starting…” while pending (also announced politely) and ignores duplicate submits. A confirmed start opens the existing Provider authorization dialog and reports “Authorization started.”, never Connected. A recoverable failure keeps the dialog and all entered options open for retry, shows the error with its safe request ID when available and associates it with the fields; failures from earlier unrelated page actions are not shown. Cancel, Close and Escape before submission issue no request. Dismissing during a pending request makes no cancellation claim; the page feedback and the next dialog reflect the actual outcome. Scope, session or authority changes remount the page, which clears the setup state and never replays the request.

#### Provider authorization dialog

The “Provider authorization” dialog (`OAuthDialog`) separates the authorization state, the next step, view dismissal and explicit cancellation. It opens only from the existing Connect and Reconnect entry points and never replays an old attempt.

Header: the named heading with the 44px “Close dialog” control, a text state badge (Pending, Completed, Canceled, Expired, Failed or Unknown status; never the raw enum name and never color alone) and “Expires {date} UTC” from the server `expiresAt` with an explicit timezone. While the attempt is pending a persistent notice reads “Closing this dialog does not cancel authorization.”.

Pending, manual variant (the method is not DEVICE or BROWSER_POLL and no `pollIntervalSeconds` exists on the current or original authorization): step “Sign in with your provider” with the “Open provider sign-in” link, then step “Finish authorization” with the masked “Authorization code, token, or callback URL” input (initial focus, `autocomplete="off"`, no reveal, copy or persistence) and the labeled “Authorization state” field only when the server sent no `callbackState`. “Complete authorization” stays disabled until a non-blank code and a state exist. The link renders only for HTTPS or `http` on `localhost`/`127.0.0.1`, opens in a new tab with `noopener noreferrer`, and is replaced by a safe explanation otherwise. Completion keeps the existing `oauthCompletion` parser: a PKCE callback URL must carry a `code` and a `state` equal to the expected state, a bare code is accepted and native payloads keep their trimmed full value. A rejected submission keeps the dialog and the typed values and shows the safe error associated with the input.

Pending, polling variant: the same sign-in step, the provider user code only when one is returned, and the status “Waiting for provider approval. This page checks the provider at its current polling interval.”. There are no manual completion controls and no percentage. The status query still refetches every `max(5, current ?? initial ?? 5)` seconds and stops on a terminal state or a query error. After an error the dialog no longer claims healthy polling: it shows the safe error with “Try again” and the notice that automatic checks stopped. Initial loading and retry show one polite status; routine polls are not announced. Polling never extends expiry or implies approval.

Footer: “Cancel authorization” is a separate red-text action that calls `cancelProviderOAuth` once; “Close”, the close icon and Escape only dismiss the view and never call it. The helper reads “Cancel authorization stops this attempt. Close leaves it pending.”. The mutation state belongs to the owning Providers page, so a pending request cannot be submitted twice, a dismissed dialog does not imply rollback, and the final outcome (“Provider connected.”, “Authorization canceled.” or the safe error) is shown on the page after the dialog closes. Success is reported only after server confirmation; a failure keeps the dialog and typed values.

Terminal states show one distinct message and only “Done” (which refreshes personal resources and closes): Completed with a connection ID “Provider connected. Your connection is ready in this organization.”; Completed without a connection ID states that no connection was reported and does not claim a usable connection; Canceled, Expired, Failed and unrecognized or unspecified states each have their own text that points to Connect provider or Reconnect for a new attempt. No terminal state offers retry, completion or cancellation controls.

Organization, session or membership loss unmounts the page state, which discards the dialog, the typed code and the state value; reopening never recovers them. Secrets never enter diagnostics, URLs or browser storage.

Layout uses dialog-scoped styles (`oauth-dialog`): white surface, 12px corners, a maximum width of 640px and 24px padding. Below 768px the dialog keeps 16px side clearance and 16px padding, actions stay in the document flow at full width, controls are at least 44px tall and the dialog scrolls internally within the viewport height. Content wraps at 320 CSS pixels and 200% zoom. Automated tests cover the variants, terminal states, dismissal versus cancellation, duplicate prevention and scope loss; rendered layout, contrast and zoom are verified in browser acceptance.

## API keys and client connection

Key list: name, masked identifier, ordinary/CLI type, created date, expiry or “No expiry,” status and Revoke. Create form asks for name and expiry, with an explicit no-expiry option. One-time result shows a copyable raw key, warning “This key is shown only once,” and Done. Do not persist the raw value in browser storage or subsequent list views. Copy confirmation is announced accessibly. Leaving the result never suggests that the same secret can be recovered.

#### One-time key result dialog

The result dialog appears only after the server confirms ordinary issuance; pending or failed creation keeps the create dialog feedback and never shows the result early. Content order: title “Your new API key” with a 44px “Close dialog” control, the context line “Your key in {organization name}.” (wrapping, no extra lookup), an amber warning panel with bold “This key is shown only once.” plus “Store it securely before closing this dialog.” (visible text and a decorative icon, not an alert), the labeled read-only single-line monospace “API key” input holding the full unchanged value, an outlined “Copy API key” button with its status, the helper “You cannot view this key again after closing.”, and a footer with one primary “Done”. The input is described by the warning and helper, and the Copy button is described by its status region.

Initial focus is the input. Tab order is Close, input, Copy, Done, contained in the dialog. Escape, Close and Done each clear the raw value and dismiss; focus returns to the persistent “Create API key” trigger. Done is not gated on copy and there is no acknowledgement checkbox. Copy calls the clipboard once per explicit click with exactly the raw value; the status starts empty and becomes “Copied.” only after fulfillment or “Copy failed. Select and copy the value manually.” on rejection. The single polite status region never contains the key. Failure keeps the dialog open, the field selectable and Copy retryable. The console never copies automatically on open or close, and a clipboard result that settles after dismissal shows nothing. The raw value stays only in the owning page state: never in storage, query cache, URL, history, logs or the later list. Organization, session, membership or authority teardown removes the dialog and status with that state.

Layout uses result-scoped styles (`key-result`) so other dialogs are unchanged: white surface, 12px corners, max width 560px and 24px padding on desktop. Below 768px the dialog keeps 16px side clearance and 16px padding, the input uses `min-width: 0` and scrolls its own text, Copy and Done become full width, all actions are at least 44px tall, and the dialog scrolls internally within the viewport height. The status line reserves one line; long keys, long organization names and wrapping failure text must not overflow at 320 CSS pixels or 200% zoom. Automated tests cover content, focus, copy outcomes and teardown; rendered layout, contrast and zoom are verified in browser acceptance.

Revocation dialog identifies the exact key and organization: “New requests stop immediately. Responses already sent to a provider may finish.” Confirm with “Revoke key”; focus Cancel initially. Expired/revoked records cannot be reactivated. Distinguish failed revocation from successful revocation. The UI must not report success before server confirmation.

Connect a client provides the selected server and organization plus instructions from the verified CLI interface; this proposal does not invent CLI commands or platform support. Explain that the CLI previews settings changes and asks before applying them. Separate confirmation is required if a client stores the remote key in its settings. Show actionable help for OS credential-store failure, outstanding key revocation and restoration conflicts; never offer a plaintext credential fallback. Restoration-conflict guidance preserves settings/backups and explains manual recovery separately from server revocation status.

## Device approval

The browser approval page is a focused layout, accessible independently from the console sidebar. If needed, a single code input receives focus. Show server address, device label, original one-time code, organization selector, key expiry selector including No expiry, and time remaining from the original ten-minute deadline. Copy: “Confirm this code matches your CLI. Approve only a connection you started.” Approve connection and Deny are explicit actions; opening a URL or signing in never approves automatically.

States: sign-in required, code entry, invalid code, pending approval, submitting, approved/waiting for CLI storage, connected after confirmed handoff, denied, expired, and failed delivery. Do not show the raw CLI key in the browser. An approval success message says “Return to your CLI to finish”; it must not claim local storage succeeded. Polling/retries do not extend the original deadline. Unclaimed expiry explains that the issued key was revoked. On local storage failure, direct the user to API keys if compensating revocation remains incomplete. The browser does not purport to inspect the OS credential store.

## Usage and estimated cost

Personal usage defaults to Last 7 days, with date range, model and outcome filters. Show request count, confirmed tokens when available, known estimated cost, and counts missing usage/prices. Copy example: “Known estimated cost $4.82 · 3 requests with unknown cost.” Missing values say “Unknown,” not 0 or an unexplained dash. Charts show gaps for unknown data and include textual/table equivalents. Clearly label currency and the display timezone. This is estimation, not billing.

Request metadata rows include time, model, outcome, confirmed usage, estimated cost and safe request ID; no prompts or response bodies. Detail explains price provenance and that the applied estimate is fixed for that request. A price update never changes historical display. Differentiate upstream error, gateway error, cancellation, rate limit, unknown usage and usage-recording failure. Do not infer complete totals when records could not be written. Organization usage adds a member filter only for owners/administrators. No export button.

## Members, invitations, transfer and audit

Members show identity, role, joined date and permitted actions. Search and pagination work on desktop and mobile. Remove-member confirmation explains immediate key invalidation and deletion of that membership's personal provider/configuration/temporary state, with retained usage subject to retention. A user rejoining must configure personal resources again.

Invitations show invited email, role, delivery status, created/expiry dates and permitted Resend/Cancel actions. Distinct statuses: Pending delivery, Retry scheduled, Rate limited, Sent, Delivery failed, Accepted, Expired, Canceled and Superseded. Resend has a visible cooldown and accessible explanation: minimum one minute, organization cap of 100 send attempts/hour. Show server-provided next-attempt time when deferred. Final delivery failure says the link is invalid; manual resend creates a new seven-day invitation and invalidates the previous link. Never label an SMTP delivery attempt as acceptance.

Owner nominates an existing member for transfer. Show one pending transfer with nominee, expiry and Cancel transfer. Replacing it explains that the previous request becomes invalid. Nominee acceptance page names the organization and resulting roles: nominee becomes owner; previous owner becomes administrator. Seven-day expiry and membership/authority failures are explicit. The current owner retains ownership until acceptance. There is no owner-role dropdown that transfers immediately.

Organization audit shows timestamp, actor, action, safe target and outcome. Filter by action/actor/time. Include permission changes, invitation lifecycle, key issuance/revocation and provider-connection changes. Do not embed secret values or content. Instance audit is in the operator workspace only and includes instance-setting changes. Anonymized actors remain identifiable as “Deleted user,” not a guessed identity.

## Operator workspace

Separate “Instance console” header with “Back to organizations.” Navigation: Health, Request limits, Retention, Destinations, Price overrides, Audit. Banner: “Whole-instance health and aggregates only.” Health shows whole-instance availability, request/error aggregates and cleanup/recording health with Unknown/Unavailable states; no clickable organization breakdown.

Instance health (`/instance/health`, `Health` in `apps/aiprouter/src/admin/instance-health.tsx`, re-exported by `operator.tsx`): one h1 “Instance health” (subtitle “Whole-instance availability and request aggregates.”), the quiet scope text “Whole-instance health and aggregates only.” rendered once in the body (the shell banner is unchanged), then two cards. “Availability” has a “Refresh health” button, the hint “Health refreshes every 30 seconds” and three read-only status blocks in a description list: Service, Database and Usage recording. Each shows the text Healthy, Degraded, Unavailable or Unknown; UNSPECIFIED, absent and unrecognized wire values are Unknown, and only Healthy receives success styling. The console derives no health, and never infers cleanup health from failure counts. Under a divider, “Last successful cleanup” uses the shared timestamp helper with the viewer timezone, and “Consecutive cleanup failures” shows Unknown whenever there is no cleanup-success timestamp (even when the wire scalar is 0) and the exact count otherwise. “Recording failures can leave request totals incomplete.” sits next to the recording status. Health polls on the existing 30,000 ms interval, with no arguments; usage never polls. Manual refresh refetches health only, keeps focus on the button (it uses `aria-disabled`, not `disabled`), ignores duplicate activation, shows “Refreshing…” and announces “Health refreshed.” politely only after a manual refresh; automatic polls never change focus, labels or announcements and only dim the last successful values while fetching. The card always keeps its header, so a health failure replaces the values with the shared error notice (“Try again” refetches health only) and old values never look current. Initial loading shows the “Loading health…” skeleton.

“Instance usage aggregates” has the “From (UTC)” and “Through (UTC)” native date inputs (initial range: now minus seven times 86,400,000 ms through today, queried immediately on every valid edit) and the helper “Dates include the full selected days in UTC.”. Blank or reversed dates show the alert “Choose a valid start and end date.” associated with both inputs, send no usage request and hide previous totals while health stays usable. Above the totals, “Request totals may be incomplete” appears as an amber callout when usage recording is Degraded, Unavailable or Unknown, or when the health request failed (Unknown recording adds “Unknown recording health does not confirm complete totals.”). The sentence “Recorded metadata may be incomplete if usage recording failed.” is always shown above the totals, even when recording is Healthy; the console never claims that totals are complete. The metrics are a description list in the order Requests, Failed requests, Confirmed input tokens, Confirmed output tokens and Known estimated cost. Counts use exact bigint formatting, absent optional tokens or costs read Unknown while a present zero reads 0, and every returned currency is listed separately with its code and exact decimal string. The lines “{n} requests with unknown cost”, “{n} missing usage” and “{n} missing price” stay separate and are never summed. A zero-request summary keeps these fields and adds “No recorded requests in this period.”; an absent summary shows “Usage summary is unavailable.”. The footer reads “Estimates, not billing. Currency is shown with each known cost. Price changes apply to new requests only.”. Usage has its own “Loading usage aggregates…” skeleton and error notice with a usage-only “Try again”; a new date range hides previous totals until its own response arrives, so a late response for an earlier range cannot replace the current display. This presentation composes the existing `UsageSummary` values separately; the shared `Summary` used by organization usage is unchanged. No organization or member selector, drilldown, export or new request argument exists.

Request limits: default 120 requests/minute and 10 concurrent requests, applied per user within each organization. Range validation: 1–6,000 and 1–100 respectively. No unlimited option or instance-wide concurrency input. The page shows one h1 “Request limits” (subtitle “Applied per user within each organization.”) and one card headed “Per-user limits” with two paired rows: label and helper on the left, a required native integer number input with a visible unit (“requests / min”, “requests”) on the right. Server values are always shown; defaults are only helper text. A neutral “How these limits apply” panel follows the fields. The in-flow footer shows the quiet status “No unsaved changes” or “Unsaved changes” beside the primary “Save changes” button (disabled until an edit, while saving, or when settings are unavailable). Limits save directly with no confirmation dialog, Cancel, reset or in-page rebase control. Invalid values are never coerced to zero or unlimited: an attempted invalid submit shows field errors (“Enter a whole number from 1 to 6,000.” / “Enter a whole number from 1 to 100.”) associated with the inputs plus a focused error summary and sends no mutation. Save sends the complete settings draft with the originally reviewed `expectedRevision` once; a background refetch never replaces the draft or advances that revision, and an ABORTED conflict keeps the draft and revision without retry. Stacked layout applies at 600px and below. Retention (`/instance/retention`): one h1 “Retention” with subtitle “Set how long instance records remain available.”, the quiet scope label “Instance policy” and one card “Record retention” (helper “Enter whole days within each allowed range.”) with three divided rows in order: Request metadata (1–90 days, default 30), Daily aggregates (30–730, default 365) and Audit records (30–365, default 90). Each row has a descriptive label, a helper such as “1–90 days · Default: 30”, a required whole-day number input with the visible unit “days” and the caption “Saved: N days” taken from the retained reviewed snapshot; accessible names stay “Request metadata (days)”, “Daily aggregates (days)” and “Audit records (days)”. Defaults are explanatory only and never replace unavailable saved values; missing settings or retention show “Instance settings are unavailable.” with “Try again”. A neutral panel “Before reducing retention” states that records older than the new limits become unavailable and are eligible for deletion and that existing backups follow operator policy, with no deletion counts, savings estimates, erasure or restore claims. The in-flow footer shows “No unsaved changes” with a disabled “Save changes”; an increase-only valid draft shows “Unsaved changes” and saves directly with no dialog; any reduction (counted against the saved snapshot, not defaults) shows “Unsaved changes · N reduction(s) to review” (“1 reduction”, “2 reductions”) and “Review reductions”; reverting every field to its saved value disables saving, and an invalid draft disables submission. Invalid values (empty, zero, negative, fractional, non-finite, out of range) stay editable, are never submitted as zero, and show associated field errors (“Enter a whole number from 1 to 90 days.”, “… from 30 to 730 days.”, “… from 30 to 365 days.”) plus an error summary whose links focus the invalid fields. The “Reduce retention” dialog (subtitle “Review these changes before saving.”) shows a semantic table with columns Record type, Saved, New and Change (Reduced, Increased or Unchanged) built from the retained snapshot and the validated draft, the warning sentences, a neutral “Cancel” (initial focus), a red “Reduce retention” action and “Close dialog”; Cancel, Escape and the close button dismiss without a mutation, keep the draft and return focus to “Review reductions”. Mixed increases and reductions use the same dialog and one complete-settings mutation. While pending the action reads “Saving…”, repeat activation is disabled and the page announces “Saving… Closing a dialog does not cancel a submitted change.”; the dialog may be dismissed and the final page feedback persists; “Changes saved.” appears only after server confirmation, and the response replaces the snapshot and draft. The payload is the complete settings (request limits and every destination ID, origin and CIDR list, including empty lists) with the originally reviewed `expectedRevision`; background refetches never replace typed values or advance that revision. On ABORTED the draft and snapshot are kept and the page shows “This record changed. Refresh and review before saving again.” and “Your retention draft is preserved. Reload the current settings and review your changes before submitting again.” with a “Reload current settings” button that exists only in this state (in the dialog while it is open, otherwise on the page). Reload calls the existing `getInstanceSettings` RPC, keeps the three typed retention values, replaces every untouched field (request limits, destinations, revision) and the saved snapshot from the fresh complete settings, shows “Current settings loaded. Review your draft before saving.”, closes the old dialog and requires a new explicit submission (with a fresh review if any reduction remains). A failed reload keeps the original revision and draft and keeps submission disabled; nothing is saved automatically. Permission, session and offline handling are unchanged and a rejected mutation is never replayed after sign-in. At 600px and below the rows stack and the dialog table collapses into labelled record groups. Approved destinations (`/instance/destinations`): one h1 “Approved destinations” (subtitle “Control additional origins for the whole instance.”), the quiet scope label “Instance policy” and a neutral panel “Public HTTPS is allowed by default” explaining that additional approvals permit precise private or local origins, that CIDR restrictions also apply to public HTTPS, that a nonempty CIDR list applies to every resolved address for the explicit origin (an address outside it is blocked and never falls back to the default public-HTTPS rule) and that DNS and redirect checks still apply. The white card “Policy draft” shows a derived state label computed from the retained snapshot, the draft and the editor inputs (“Matches saved policy”, “Unsaved changes”, or “Destination edit in progress” when only editor inputs are dirty) plus the persistent helper “Changes take effect only after review and save.”. Each staged rule shows its full origin and either “Restricted networks” with every CIDR on its own wrapping monospace line or “Exact-origin approval” and “No CIDR narrowing.”; stable rule IDs are never shown or editable. “Edit approval” and “Remove approval” carry origin-specific accessible names (“Edit approval for {origin}”), and Remove changes the draft only. The inline editor under a divider is headed “Add destination” or “Edit destination” (with “Editing {origin}”), has the labeled fields “Exact origin” (helper “Scheme, hostname and port only. No path, credentials, query or fragment.”, associated validation message) and “Allowed networks (optional)” (helper “CIDR ranges, one per line or separated by commas.” and the note that leaving networks empty removes narrowing, including for public HTTPS), the buttons “Add to review” / “Update review” and “Cancel destination edit” (shown while inputs or an edit selection exist) and the note “Updates the draft only.”. Origins must be canonical `http`/`https` origins (`URL.origin` equals the typed value) and not duplicate another staged origin; CIDR text is split on whitespace and commas and the server owns prefix validation. Edit and Remove for all records stay disabled while the editor is dirty or an edit is selected. “Review and save changes” is enabled only with a staged change, no pending save, no dirty editor and complete request-limit and retention settings; during an active editor “Finish or cancel the destination edit before review.” is shown and Enter cannot bypass the disabled boundary. Edit approval focuses “Exact origin” and scrolls the editor into view, cancelling an edit returns focus to that record’s “Edit approval” button, and staging moves focus to the staged record heading with a polite status; nothing takes focus on page load. Loading shows the skeleton “Loading destination policy…”, a failed query shows the error with “Try again”, missing settings show “Instance settings are unavailable.”, and a saved empty list shows “No additional destinations approved.” with the default-policy explanation. “Review and save changes” opens the “Save destination policy” dialog (subtitle “Review the complete policy before saving.”, the badge “Draft · not saved” and a neutral panel “Default policy remains active” stating that public HTTPS is allowed by default and that an explicit CIDR restriction blocks addresses outside its networks, including public HTTPS). “Additional destinations after save” lists the complete resulting draft as a semantic list; each rule is labelled Added, Changed or Unchanged by comparing the retained snapshot and the draft by stable rule ID (new rules have empty server IDs and only a local render key, and no replacement ID is ever synthesized). A changed origin shows “Previously {origin}”; changed networks show labelled Before and After CIDR blocks; a rule without CIDRs reads “Exact-origin approval · no CIDR narrowing”, and clearing previously nonempty CIDRs adds “Network restrictions removed. Clearing previous networks broadens access for this origin.”. Nonempty lists state that all resolved addresses must match and that outside addresses are blocked, including public HTTPS. A separate “Approvals to remove” section (hidden when nothing is removed) lists saved rules absent from the draft with their previous networks and the sentence “Future connections that require this approval will be blocked.”; removed https origins that had CIDRs also read “Removing a CIDR restriction on a public HTTPS origin returns that origin to the default public-HTTPS policy.”. Removing every approval replaces the result list with “No additional destinations will remain approved. Public HTTPS remains allowed by default; private or local destinations that need approval will be blocked.” and sends an empty array as a real clear-all. The footer note reads “Nothing changes until the server confirms the save.”, Cancel is neutral and “Save destination policy” uses the blue primary tone (the shared `Confirm` takes an additive `tone` prop that defaults to the red danger tone, plus an optional `footerNote`); initial focus is Cancel, and Cancel, Escape and “Close dialog” dismiss without a mutation, keep the draft and return focus to “Review and save changes”. Save sends the complete settings (limits, retention and every retained rule ID) with the originally reviewed `expectedRevision`; a refetch never replaces the draft, editor inputs or revision, and success adopts the server settings and revision. While pending the action reads “Saving…”, duplicate submission is disabled and the dialog and page announce “Saving… Closing a dialog does not cancel a submitted change.”. INVALID_ARGUMENT shows the safe error plus “Check the exact origins and CIDR prefixes. Duplicate canonical origins and invalid network prefixes are not accepted.” and keeps rejected CIDRs correctable. ABORTED shows “Your draft and network entries are preserved while you stay on this page. The saved policy changed. Reloading discards your unsaved draft. After reload, re-enter your changes and review the complete policy before saving.” with no adoption or reload button: recovery is the browser full-page reload behind the existing unsaved-change warning, after which the form starts from the freshly fetched settings and revision, the operator re-enters and re-reviews the changes, and the new mutation uses the fetched revision. Permission or session loss dismisses the review and form with the existing permission message, and a rejected save is never replayed. Destination approval identifies the precise destination and affected policy; no provider-secret configuration. Price overrides show model, units, currency and provenance, explain “Applies to new requests only,” and preserve historical estimates. Changes show validation, pending, success and failure states without erasing entered safe values.

## Destructive and account flows

Use named-action dialogs, never generic “Are you sure?” dialogs. Cancel is visually neutral; irreversible actions use red. Esc, close button and Cancel dismiss before submission. During an in-flight mutation, dismissal does not falsely imply rollback; report the final result in the page after dismissal. Prevent duplicate submission.

Delete organization is owner-only. Require exact organization-name confirmation; disable submission until the entered value matches. The board illustrates button placement and destructive color, not its disabled styling. Explain immediate deletion of credentials, settings, temporary state, usage and organization audits; new requests stop, already-dispatched responses may finish. Explain existing backups follow operator policy. Do not promise instantaneous backup erasure. Leave organization uses a separate confirmation with the narrower membership consequences. Block leaving as sole owner with Transfer ownership and Delete organization alternatives.

Account deletion first lists owned organizations that must be transferred or deleted. Once clear, explain removal of memberships and personal identity, anonymization of surviving usage/audit records, and operator-controlled backup expiry. Require an explicit final “Delete my account” confirmation. Do not offer deletion as an error recovery action.

## Shared states and accessibility

Every data page has a skeleton with an accessible loading message; first-use empty state with one primary action; no-results state with Clear filters; retryable error with safe request ID; permission-denied state; and stale/offline state that never shows unconfirmed mutation success. DB unavailability must not imply cached authorization permits actions. Changing organizations or losing membership must clear previously scoped content immediately. Preserve only safe unsaved data; do not retain secrets after session/scope loss.

Target WCAG 2.2 AA: landmarks, skip link, ordered headings, real links/buttons, associated labels, error summary plus field errors, visible focus, keyboard access, accessible name for every icon, and status text independent of color. Design target 44×44px touch controls, at least AA minimum targets. Check 4.5:1 normal text and 3:1 large text/non-text control contrast. Focus must not be obscured by sticky headers or action bars. At 200% zoom and 320 CSS pixels, reflow content without losing actions. Respect reduced motion.

Dialogs trap focus, have a named heading, support Esc and return focus to their trigger. A single critical input receives focus when its form appears, including organization name, invitation email, code entry and typed deletion confirmation. Otherwise focus the heading or safest action. Use polite live regions for copy/save completion; assertive announcements for blocking errors only. Never announce a countdown every second. Announce meaningful expiry thresholds once. Do not rely on hover for help or menus.

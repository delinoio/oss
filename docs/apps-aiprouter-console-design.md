# AIPRouter console design

This specification defines the approved console design alongside the [console behavior contract](apps-aiprouter-console-contract.md). Illustrative names, usage figures, addresses and connection states are fictitious. Visual examples do not establish runtime or accessibility acceptance.

## Surface and visual system

Multilingual responsive web console for personal AI provider configuration, organization management, and a separate instance operator workspace. Target desktop 1440×1000, tablet 768×1024, mobile 390×844; support 320 CSS pixels without page-level horizontal scrolling. Treat the boards as concept layouts, not pixel-exact viewport captures.

Use a calm, light, Toss-informed hierarchy: one main task per page, plain action labels, generous spacing and progressive disclosure. Page background #F7F8FA, white cards, primary text #191F28, secondary text #4E5968, blue #1D4ED8 actions, pale blue selected surfaces, red #B42318 destructive actions. Use system sans-serif, 16px body, 14px labels, 28–32px desktop headings and 24px mobile headings, line-height at least 1.5 for body text. Use an 8px spacing rhythm, 12px card corners, 8px control corners, 44px minimum primary control height, and explicit text labels for statuses. Validate actual rendered contrast before acceptance; the raster preview is not accessibility evidence.

## Language selection

The approved language selector and responsive behavior are specified in the [console localization contract](apps-aiprouter-console-contract.md#localization). Place this control above all console surfaces. Keep existing page hierarchy, permission boundaries and destructive-action semantics when localizing content.

## Navigation and ownership

Desktop: 232px sidebar, top organization switcher with role, personal navigation, conditional organization navigation, account menu at bottom. Main area has a single h1, scope subtitle, page action and content. Personal links: Overview, Providers, Routing, API keys, Usage, Connect a client. Organization section, available to owners/administrators: Members, Invitations, Organization usage, Audit, Settings. Account menu: Account, optional Instance console, Sign out. Operator entry is separate from organization roles.

The switcher shows organization name, current role, current selection, search and Create organization. Empty search results explain that no memberships match. Switching clears the prior organization's visible data, closes resource dialogs, updates the URL scope, then loads the selected scope. Confirm before abandoning unsaved form edits. Never copy providers, pools, routes or keys into the next organization. A persistent subtitle says “Your settings in Acme Studio”; provider and routing pages say “Only yours in Acme Studio.” A role badge is descriptive, never an authorization cache.

Mobile: 56px header with labeled menu button, brand and organization switcher. Navigation opens as a modal drawer with grouped links and current page. No reduced desktop sidebar or competing bottom navigation. Cards stack; tables become labeled record cards with accessible per-record action menus. Filters collapse into a Filters sheet with active-filter count and Clear filters. Wide charts have text summaries and equivalent data tables; layouts must not require drag gestures.

## Roles

Members manage only their own providers, accounts, pools, routing, API keys, usage and client connections within the selected organization. Owners and administrators retain exactly the same personal-data boundary. Organization usage exposes per-member usage, estimated cost, model and error metadata, never credentials, prompts or response bodies. Do not show an “inspect provider” link on member details.

Administrators can invite/remove ordinary members and edit organization settings. They cannot change the owner or other administrators. Owners can appoint/demote/remove administrators, transfer ownership and delete the organization. Hide unavailable actions and explain important blocked actions, such as a sole owner's attempt to leave. Recheck on mutation; if authority changes while open, dismiss privileged editors, remove unavailable navigation and show “Your permissions changed. This action is no longer available.” Preserve login after demotion.

Instance operators see only whole-instance health/aggregates, request limits, retention, approved destinations, common price overrides and instance audit. No organization/member drilldown, impersonation, suspension, provider configurations, or raw request data. Deployment configuration owns operator assignment; the console has no Add operator control.

## Sign-in and onboarding

Sign-in offers “Continue with your identity provider” only. Missing or unverified email produces an explicit blocking error and a retry path after correction at the identity provider. Do not offer password signup or merge-by-email. Session expiry asks the user to sign in again and never automatically submits a pending mutation. Logout invalidates the session.

No-membership landing page: “Choose your organization,” pending invitation cards, and Create organization. A single organization-name field receives focus when the create form opens. Do not auto-create a personal organization. Invitation detail identifies the organization, intended email, role and expiry. Wrong verified email shows “Sign in with the invited email address”; expired, canceled, already-used and superseded links have distinct outcomes.

Overview includes a five-step checklist: Choose organization → Connect personal providers → Configure models/routing → Create API key → Connect a client. Completed steps remain navigable. Do not mark a step complete merely because a dialog opened. The guide is recoverable from Overview, not a blocking tour. Returning users see personal usage and connection health above the checklist.

Overview (`/overview`) reads in this order: header "Your workspace" with the subtitle "Your settings in {organization}." and a primary "Create API key" link; a quiet inline note that the page is private to the user and that providers and routing are separate in every organization; the "Last 7 days" usage summaries; a wider "Request activity" panel beside "Personal connections" (single column below 1024px); then "Get connected" and "Your routing" side by side when space permits, stacked in reading order on narrow screens. The summaries keep the existing rolling seven-day range and RPC inputs, state that times are in UTC, and list each returned currency separately with missing cost, usage and price counts. "Request activity" reuses `UsageTrend` (daily counts, the accessible daily data table, "Daily usage pages" pagination, Unknown gaps, no synthesized zero days) and links "View usage" to the organization-scoped Usage page. "Personal connections" shows at most four existing connections with name, provider, status text and a scoped link to Providers, with no invented routes or last-verified timestamps. "Get connected" is a vertical list in which every step, completed or not, is a link scoped to the organization; each step shows status text: Complete, Not yet complete, Checking… while its query is pending, or Status unavailable when it failed, so unresolved data never settles progress. Predicates: Choose organization is always complete; Connect personal providers needs any READY connection; Configure models/routing needs any enabled route with at least one target; Create API key needs any ACTIVE key; Connect a client needs any CLI key with a last-used time and does not require ACTIVE. "Your routing" shows at most four routes with target counts, "Enabled · check connection health" or "Disabled", and a scoped "View all" link. Each data region (summary, daily activity, connections, routes, API keys) has its own labeled loading state, its own "Could not load …" error with request ID and Try again, and a first-use message that links to the existing setup action. The page content is keyed by organization and user, so switching scope or losing membership never shows the previous scope's records. `UsageTrend` accepts additive `title`, `description`, `action`, `emptyHint` and `className` props whose defaults keep Personal Usage unchanged.

## Providers and routing

Provider list: provider name, personal account label, authentication method, last verified status and actions. Statuses: Not connected, Connecting, Connected, Reconnect required, Cooling down, Connection failed and Unknown status. Status cannot be conveyed by color alone. Empty state: “Connect your first provider” with a clear personal-ownership explanation. Connect flow chooses a supported provider and supported authentication method. API-key inputs are masked and have explicit reveal controls; OAuth shows redirect/pending/canceled/failed states. Never redisplay stored secrets. Replacement is a new secret entry. Provider support must follow the [compatibility inventory](servers-aiprouter-compatibility-contract.md), not the illustrative cards.

#### Connection editor

The Connect provider and Edit connection variants share one dialog (`connection-editor`, max width 720px, 24px padding, 12px corners; below 768px it keeps 16px side clearance and 16px padding). The dialog scrolls internally within the viewport height and the Cancel/Save footer stays in normal document flow. Every control is at least 44px tall. The subtitle is “Only yours in {organization}.” on create and “{account} · {provider} · {organization}” on edit. Content is grouped under h3 headings in this order: “Provider and authentication”, “Account details” and “Connection settings”; there is one Cancel/Save footer for the whole draft, no per-section Save and no tabs. The footer also carries the quiet line “Your credentials stay private to you.”.

Create: “Find a provider” (placeholder “Search supported providers”) receives initial focus, followed by “Provider” and “Authentication”, which lists only the auth kinds of the selected catalog provider. Changing the provider resets provider-specific configuration, selects its first supported auth kind and discards any typed secret so a key never carries over to another provider; changing the auth kind also discards the typed secret, and a key is only sent for API-key authentication. Catalog states never offer invented providers: while loading the select is disabled and “Loading supported providers…” is announced, an unavailable catalog shows the safe error with “Try again”, an empty catalog shows “No supported providers are available right now.” with “Try again”, and a search without matches shows “No supported providers match “{query}”.” with “Clear search”. Save is disabled until the catalog is ready and has providers. OAuth create replaces “Connection settings” with the authorization-handoff notice and the primary action reads “Continue with OAuth”, which opens the existing OAuth setup without sending a mutation.

Edit: the Provider and Authentication identity is a read-only summary (no search or selects), and “Account label” receives initial focus. The replacement API key starts empty with the helper “Leave empty to keep the current key. Stored secrets are never shown again.”; an empty value sends no key. OAuth edit shows configuration without key and base URL fields; “No authentication” shows no key field and explains that no key is used.

“Account details” holds the required, trimmed “Account label”, the optional “Base URL” (non-OAuth, placeholder “Provider default”) and the masked API key with an adjacent “Reveal key”/“Hide key” button that exposes `aria-pressed` and `aria-controls`. “Connection settings” holds “API format” and the collapsed “Advanced connection settings” disclosure inside the same draft.

“Advanced connection settings” is a native disclosure (`details`, not tabs), collapsed by default, with four independent collapsed nested disclosures that share the one draft and the one Save: “Endpoints and provider settings” (Responses and Chat completions endpoint paths, Vertex project/location overrides, Azure minimum output-token budget 1-2147483647), “Model API formats” (exact-ID Chat or Responses overrides with duplicate checks), “Request compatibility policies” (optional-boolean policies, service-tier overrides and Responses item-ID repair, keeping absent, present-empty and configured values distinct) and “Custom headers” (saved names only; Replace requires re-entering every retained header; Clear is independent of configuration). On edit the “Configuration changes” Keep/Replace/Reset selector sits above the nested disclosures and is independent of the “Header changes” Keep/Replace/Clear selector inside “Custom headers”. Reset hides the configuration disclosures but keeps “Custom headers”, so a reset never changes headers unless they are cleared. Any configuration change switches to full replacement that retains every displayed unchanged value. Disclosure summaries are real keyboard-operable controls at least 44px tall with a visible focus ring. The disclosures change layout only: Create and UpdateProviderConnection requests are identical to the previous flat layout for equal input.

Validation runs on submit (`novalidate` form) so errors can be explained: each invalid control gets `aria-invalid` and a message associated through `aria-describedby`, and a focused alert summary (“Fix these items before saving.”) links to every field; advanced-settings errors appear in the summary only. Editing a field clears its message. A rejected save keeps the editor and every safe draft value (including a typed key, which stays masked) and shows the safe error with its request ID and “Try again”, which resubmits only on an explicit click. While pending the Save button reads “Saving…” and is disabled, repeat Enter is ignored and the dialog repeats “Closing this dialog does not cancel a submitted change.”. Dismissing the dialog during a save discards the editor state and the page feedback reports the final result. Organization, session or membership loss remounts the page through the shell, which discards the draft and secrets; nothing is resubmitted automatically.

Pools live under Providers and contain only the user's accounts in this organization. Routing lists model aliases and ordered primary/fallback connections. Editor offers only this user's eligible accounts/pools, shows the configured order and unavailable dependencies, validates duplicate names and missing connections, and requires explicit Save. Explain provider-specific policies through contextual help; do not suggest a universal retry count. Private/local HTTP destinations show an operator-policy error when disallowed. There is no local executable backend, workspace selector or execution permission UI.

Disconnect confirmation is a dedicated named dialog scoped to the Providers action (maximum width 640 CSS px); other confirmation dialogs keep the shared layout. It is titled “Disconnect {account label}?”, shows “{provider display name or ID} · {organization name}”, “Only your connection in this organization.” and the complete wrapping read-only connection ID, and stays bound to the selected connection ID. The consequence paragraph reads “Future requests can no longer use this connection. Your external provider account is not deleted.” Never promise cancellation of dispatched requests, deletion of pools or routes, upstream credential deletion or undo.

An “Affected configuration” group holds “Account pools” (pools with a member for the selected connection) and “Direct routes” (routes with a target that is the selected connection) as real lists, one row per resource keyed by stable ID; duplicate labels are never merged and pool-mediated routes are not listed as direct routes. A neutral warning keeps “Routes through these pools also need review.” and “Disconnecting does not remove or repair dependent routing.” with the organization-scoped “Review routing” link. Each category resolves independently from the complete cursor enumeration: pending shows “Checking dependencies…”; only a settled successful empty result shows “None”; failure shows “Could not load account pools.” or “Could not load direct routes.” plus “Dependencies could not be loaded. Review routing before disconnecting.”; a refresh keeps the last loaded rows under “Refreshing dependencies…”; a failed or paused (offline) refresh keeps them under “Last loaded data; could not refresh.” plus “Dependency information may be out of date. Review routing before disconnecting.” Failure, pending and stale states are never rendered as “None”, and one category stays visible when the other fails. Dependency state never disables Disconnect, and known data is a review aid rather than an atomic snapshot.

The footer stacks Cancel then “Disconnect provider” (full width on mobile), with Cancel initially focused. While the request is pending the button reads “Disconnecting…” and is disabled, with the polite note “Closing this dialog does not cancel a submitted change.” The dialog submits one deletion with the selected organization and connection IDs, closes only after confirmed success, reports “Provider disconnected.” on the page and keeps identity, dependencies and the safe error visible for retry after failure. An error and the “Disconnecting…” state belong to the connection that was submitted and are not shown for another connection. While any disconnect request is outstanding, including one whose dialog was dismissed, the confirmation for every connection stays disabled so a submission is never silently dropped. An organization change closes the dialog. Focus returns to the trigger, or to the Providers list group when the row was removed. Connection failures preserve safe form values, but secrets must not enter URLs, diagnostics or notifications.

#### Provider authorization dialog

The “Provider authorization” dialog (`OAuthDialog`) separates the authorization state, the next step, view dismissal and explicit cancellation. It opens only from the existing Connect and Reconnect entry points and never replays an old attempt.

Header: the named heading with the 44px “Close dialog” control, a text state badge (Pending, Completed, Canceled, Expired, Failed or Unknown status; never the raw enum name and never color alone) and “Expires {date} UTC” from the server `expiresAt` with an explicit timezone. While the attempt is pending a persistent notice reads “Closing this dialog does not cancel authorization.”.

Pending, manual variant (the method is not DEVICE or BROWSER_POLL and no `pollIntervalSeconds` exists on the current or original authorization): step “Sign in with your provider” with the “Open provider sign-in” link, then step “Finish authorization” with the masked “Authorization code, token, or callback URL” input (initial focus, `autocomplete="off"`, no reveal, copy or persistence) and the labeled “Authorization state” field only when the server sent no `callbackState`. “Complete authorization” stays disabled until a non-blank code and a state exist. The link renders only for HTTPS or `http` on `localhost`/`127.0.0.1`, opens in a new tab with `noopener noreferrer`, and is replaced by a safe explanation otherwise. Completion keeps the existing `oauthCompletion` parser: a PKCE callback URL must carry a `code` and a `state` equal to the expected state, a bare code is accepted and native payloads keep their trimmed full value. A rejected submission keeps the dialog and the typed values and shows the safe error associated with the input.

Pending, polling variant: the same sign-in step, the provider user code only when one is returned, and the status “Waiting for provider approval. This page checks the provider at its current polling interval.”. There are no manual completion controls and no percentage. The status query still refetches every `max(5, current ?? initial ?? 5)` seconds and stops on a terminal state or a query error. After an error the dialog no longer claims healthy polling: it shows the safe error with “Try again” and the notice that automatic checks stopped. Initial loading and retry show one polite status; routine polls are not announced. Polling never extends expiry or implies approval.

Footer: “Cancel authorization” is a separate red-text action that calls `cancelProviderOAuth` once; “Close”, the close icon and Escape only dismiss the view and never call it. The helper reads “Cancel authorization stops this attempt. Close leaves it pending.”. The mutation state belongs to the owning Providers page, so a pending request cannot be submitted twice, a dismissed dialog does not imply rollback, and the final outcome (“Provider connected.”, “Authorization canceled.” or the safe error) is shown on the page after the dialog closes. Success is reported only after server confirmation; a failure keeps the dialog and typed values.

Terminal states show one distinct message and only “Done” (which refreshes personal resources and closes): Completed with a connection ID “Provider connected. Your connection is ready in this organization.”; Completed without a connection ID states that no connection was reported and does not claim a usable connection; Canceled, Expired, Failed and unrecognized or unspecified states each have their own text that points to Connect provider or Reconnect for a new attempt. No terminal state offers retry, completion or cancellation controls.

Organization, session or membership loss unmounts the page state, which discards the dialog, the typed code and the state value; reopening never recovers them. Secrets never enter diagnostics, URLs or browser storage.

Layout uses dialog-scoped styles (`oauth-dialog`): white surface, 12px corners, a maximum width of 640px and 24px padding. Below 768px the dialog keeps 16px side clearance and 16px padding, actions stay in the document flow at full width, controls are at least 44px tall and the dialog scrolls internally within the viewport height. Content wraps at 320 CSS pixels and 200% zoom. Automated tests cover the variants, terminal states, dismissal versus cancellation, duplicate prevention and scope loss; rendered layout, contrast and zoom are verified in browser acceptance.

#### Hosted helpers dialog

The Providers page shows a “Hosted helpers” card with “Configure hosted helpers”. The card (`HostedHelpers` in `apps/aiprouter/src/hosted.tsx`) owns the save action and its feedback region, so a save submitted before the dialog closes still reports its final outcome there: while pending the region reads “Saving… Closing this dialog does not cancel a submitted change.”, success announces “Hosted helper settings saved.” and a rejection shows the safe error without a success claim. While the dialog is open the same pending text and error appear inside the dialog instead, so each outcome is announced once. Opening the dialog clears the previous outcome unless a save is still pending; a success closes only the dialog that submitted it. The shared unsaved-change flag belongs to the open dialog: a successful save clears it only while the dialog that submitted the change is still open, so a save that finishes after the dialog was dismissed or reopened never clears the flag of a newer draft elsewhere on the page. The shared `useAction` hook is unchanged for other consumers apart from the additive `notice` and `reset` members and an optional `ownsDirty` argument of `run` (default: always clear).

The named dialog (`hosted-dialog`) has a maximum width of 800px with 24px padding on desktop, 720px on tablets (below 1024px) and 16px side clearance and padding below 768px, scrolls internally within the viewport and uses the “Close dialog” icon. Initial focus moves to the dialog heading (the shared `Dialog` takes an additive `focusHeading` prop that makes the heading programmatically focusable); Escape, Cancel and the close icon dismiss without rollback and return focus to “Configure hosted helpers”. Below the heading it shows “Only yours in {organization}.” (“Only yours in this organization.” when the page supplies no name) and “Helpers use their own selected accounts, not the account serving the main request.”. A compact notice “Save replaces all helper settings. Removing a configuration does not always disable the provider default.” appears under the intro whenever an Advanced disclosure of a configured section is expanded. The permanent notice (heading “Save replaces all helper settings”, text “Unchecking a configuration removes its saved settings; it does not always disable the provider default. Select Disabled to explicitly disable search or image understanding.”) sits immediately before the footer, which holds neutral “Cancel” and primary “Save helper settings” (“Saving…” while pending; stacked full-width below 768px with Cancel first). The save sends `updateHostedSettings` once with the entire draft; duplicate submission is blocked while pending.

The form holds three outlined section cards in fixed order: Web search, Image understanding, and Image and video generation. Each card has its own disclosure button (the section title, with `aria-expanded` and `aria-controls`), all start expanded, and the nested “Advanced search settings”, “Advanced vision settings” and “Advanced media settings” disclosures start collapsed. Collapsing hides the section body without unmounting it, so it never changes the draft or the request. A collapsed card shows a neutral summary, “Configured” or “No saved configuration”, that describes only whether the draft object exists and never implies enabled, compatible or connected. Inside each card the explicit presence checkbox (“Configure web search”, “Configure image understanding”, “Configure image and video generation”) creates an empty schema object or removes it; rechecking starts from an empty object and discarded values are not restored. An expanded absent section shows its unchecked checkbox plus “No saved configuration”. There are no enable switches and no per-card save: the single footer Save sends the whole draft. The compact notice under the intro counts only Advanced disclosures whose section is configured and expanded. Short paired controls use the scoped `hosted-grid` (two columns of at least 280px, one column below 768px). When the browser blocks submission on an invalid control, the form reveals the enclosing collapsed section and Advanced disclosure so the control can take focus.

States share one dialog so heading focus stays put: loading shows “Loading hosted helper settings…”; a failed initial load shows the safe error with “Try again” and no editor or Save. A failed refetch over cached settings never replaces the editor or an open draft; instead the dialog shows “Hosted helper settings could not be refreshed, so the settings shown may be out of date. Save is unavailable until they load.” with the safe error and “Try again”, and Save stays disabled until a refetch succeeds. Personal connection and pool enumeration is separate: while pending the dialog shows “Loading personal connections and pools… Save is unavailable until they load.” and Save is disabled; an enumeration error shows “Personal connections and pools could not be loaded. Save is unavailable until they load.” with the safe error and “Try again”, which refetches only the failed queries and never replaces the draft, and Save stays disabled; loaded but empty resources show “No personal connections or pools available.”. The server error detail carries only a reason and request ID, so the console shows form-level errors and does not focus a field error summary. Organization, session or membership loss unmounts the card and discards the dialog and its data without replay.

Server-side limits stay with the server. Target model IDs and the two media overrides allow 512 UTF-8 bytes and each X handle allows 256 UTF-8 bytes, while up to 20 handles are accepted per list and only one list may be used. The console does not count bytes and does not mirror those limits with `maxLength` on target model ID inputs or handle lists, because HTML `maxLength` counts UTF-16 code units and would reject valid multibyte input or accept invalid input. The only client cap is the existing `maxLength={512}` on the “Image model override” and “Video model override” inputs, which is kept unchanged. Non-ASCII values are preserved in the draft and sent unchanged; an over-limit value is rejected by `updateHostedSettings`, and the console shows the safe error with the draft retained and no success claim. `apps/aiprouter/test/configuration.test.tsx` pins this with boundary fixtures at 512 and 513 bytes for ASCII, two-byte and three-byte model IDs and overrides, and at 256 and 257 bytes for handles in both lists. Further regression tests keep nested Advanced and outer section collapse from changing the draft, and keep form submission blocked while personal resources load or fail.

### Shared form primitives

Editor dialogs share these primitives in `apps/aiprouter/src/ui.tsx` and `apps/aiprouter/src/validation.ts`. All copy comes from the localized source catalog:

- `Field` accepts an optional `error`. The control receives `aria-invalid="true"` and `aria-describedby` listing the hint and error ids; the error text is plain text, not color alone.
- `ErrorSummary` renders an assertive alert that titles “Fix the following before saving” (catalog key `fixTheFollowingBeforeSaving`) and lists every cause that disables Save. Items with a `fieldId` link to and focus the owning control.
- `utf8ByteLength` and `exceedsUtf8Bytes` measure values with `TextEncoder`. Service limits such as the 512-byte route alias and provider model ID are UTF-8 byte limits, so HTML `maxlength` and `String.length` must not be used.
- `Dialog` accepts an optional `subtitle` (also exposed as the dialog description, together with any `describedBy` id) and a `DialogSize` option: `Default` (520px), `Wide` (720px) and `Large` (up to 880px with 32px, 24px and 16px padding on desktop, tablet and mobile). The legacy `wide` prop maps to `DialogSize.Wide`. The `.field-grid` class lays out two columns and collapses to one below 600px.
- The routing editor uses `DialogSize.Large` and the subtitle “Only yours in {organization}.”

### Routing editor

The Create route / Edit routing dialog reads in this order: Route details, JEV decision settings (JEV only), Ordered targets, Reasoning retention, the consequence note, the error summary and server errors, then Cancel / Save routing. All sections save only through Save routing.

- Route details: Model alias (focused on open, required, trimmed on save), Routing strategy (default Fallback for new routes) and Enabled (default true) with the note “Retry behavior follows each provider's policy.” The trimmed alias must be unique among the other routes and at most 512 UTF-8 bytes (`utf8ByteLength`, never `maxlength`).
- Ordered targets are outlined cards labelled with the numeric position and Primary / Fallback n. Each card has Connection or pool, Provider model ID (non-blank after trim, sent unchanged, at most 512 UTF-8 bytes), Weight (1–1000 with an associated explanation; the service accepts a wider Weighted range and this boundary is intentionally unchanged), the Target reasoning and model profile disclosure, Move up and Remove target. Rows keep a stable identity while reordering; priority equals position on save. A saved target that is no longer available stays selectable as “Unavailable target” and blocks Save.
- Target count rules are part of the Save predicate and surface as a group error associated with Add target: Direct exactly 1, JEV 1–64, Fallback / Weighted / Round robin 1–100. The 64-target cap applies only to JEV. An excess draft keeps every row; it never truncates.
- Field errors use `Field` `error` (`aria-invalid` and `aria-describedby`). The error summary lists every cause that disables Save with links to the owning controls, including JEV and retention causes. Required-field errors stay quiet until the user first changes the form; limit, duplicate and unavailable-target errors show immediately.
- JEV decision settings is an outlined group, shown only for JEV, between Route details and Ordered targets, described by “Choose an independent personal decision service or an ordinary routing model. Decision routes cannot use JEV chains or cycles.” Decision source (Connection / Route alias) clears `decisionConnectionId`, `decisionModel` and `decisionServiceModel` on switch and keeps timeout, pin and quota. Decision timeout accepts 0 (4000 ms effective) or a whole number from 1000 to 120000; Session pin duration accepts 0 (off) or a whole number from 60 to 86400. Decision service model is limited to 512 characters. Changing away from JEV clears the decision configuration and omits `jevDecision`; returning does not restore it.
- Advisory quota signals and Override quota thresholds are independent. Off removes the thresholds object; on creates a present object with omitted thresholds. Each threshold is a finite percentage from 0 to 100, an empty value serializes as omitted (limited 70, nearly exhausted 90 effective) and an explicit 0 stays distinct from omitted. Moderate (if set) must be below the effective limited, which must be below the effective nearly exhausted. Thresholds are validated while signals are off. Each threshold shows its own associated error naming the effective bound.
- Reasoning retention separates object presence (Configure reasoning retention) from enablement (Retain readable reasoning during compaction). Context limit (0–100, fractions allowed) and Token limit (whole number 0–4,294,967,295) are optional, preserve absent versus explicit 0, and are validated even while retention is disabled, each with an associated error.
- The Advisory quota signals and Reasoning retention disclosures open themselves when they contain a blocking error so the error and its control are never hidden; the error summary links to the owning controls. JEV and retention causes are listed per field, not as generic messages.
- A polite live region announces Move up, Add target, Remove target and the saving state; blocking errors use the assertive error summary and server error alert. Move, add and remove restore focus to a logical control in the same card list. Server rejection keeps the dialog, draft and selections; success closes the dialog only after the server confirms.

### Pool editor

The Create pool / Edit pool dialog uses the `DialogSize.Editor` size (up to 760px, 24px padding on desktop and 16px below 768px), the subtitle “Only yours in {organization}.” and the Close dialog button. It reads in this order: Pool details, Session affinity, Your connections, in priority order, the unchanged Native OAuth pool settings disclosure, the error summary and server errors, then Cancel / Save pool. Only Save pool submits; the disclosure never submits or clears values. This section covers the basic form; the native settings internals are documented with their own groups.

- Pool details: Pool name (focused on open, required, trimmed on save) and Strategy (Priority by default on create, Round robin, Least recently used; edit keeps the saved strategy). The trimmed name must be at most 200 UTF-8 bytes (`utf8ByteLength`, never `maxlength`), must not exactly match (case-sensitive) another personal pool, and the edited pool is excluded from the duplicate check.
- Session affinity: one checkbox, “Keep generic OAuth sessions on the same account”, false on create and the saved value on edit, with the help “Opt in for providers that support generic OAuth session affinity. Codex and Anthropic retain their provider-specific session rules.” It is independent of native settings.
- Connections are numbered, vertically stacked member cards in the current order (“1 · First”). Each card shows the connection name (or “Unavailable connection”), a Weight input (whole number 1–1000, visible for every strategy), Move up and Remove. The visible button text stays “Move up” and “Remove”; the accessible names add the connection (“Move up First”, “Remove First”). Move up is disabled on the first card. Cards keep a stable identity per connection and their `nativeOptions` through reorder and weight edits. “Top connection has first priority.” explains the order; priorities are reassigned 0..n-1 in displayed order on save and are never sorted by native priority.
- “Add a connection” lists only READY personal connections that are not already members. When none exist it says “No available connections to add.”; when all are already members it says “All available connections are in this pool.”; while dependencies load the group shows “Loading your connections…” and a member whose connection has not loaded is labelled “Loading connection” rather than unavailable.
- Member count is 1–100. An empty draft shows “Add at least one connection.” (quiet until the first interaction); a draft above 100 keeps every row, shows “A pool can contain at most 100 connections. Remove connections before saving.” and blocks Save. A member whose connection cannot be found stays visible as “Unavailable connection”, is reported in the summary and blocks Save until removed; it is never replaced.
- Save is enabled only when dependencies (connections and existing pool names) have loaded without error, the name is valid, 1–100 members have valid weights and known connections, and the native settings validate. ## Destructive and account flows

Use named-action dialogs, never generic “Are you sure?” dialogs. Cancel is visually neutral; irreversible actions use red. Esc, close button and Cancel dismiss before submission. During an in-flight mutation, dismissal does not falsely imply rollback; report the final result in the page after dismissal. Prevent duplicate submission. The provider disconnect dialog follows [Providers and routing](#providers-and-routing) for its dependency, pending and focus rules.

Delete organization is owner-only. Require exact organization-name confirmation; disable submission until the entered value matches. The board illustrates button placement and destructive color, not its disabled styling. Explain immediate deletion of credentials, settings, temporary state, usage and organization audits; new requests stop, already-dispatched responses may finish. Explain existing backups follow operator policy. Do not promise instantaneous backup erasure. Leave organization uses a separate confirmation with the narrower membership consequences. Block leaving as sole owner with Transfer ownership and Delete organization alternatives.

Account deletion first lists owned organizations that must be transferred or deleted. Once clear, explain removal of memberships and personal identity, anonymization of surviving usage/audit records, and operator-controlled backup expiry. Require an explicit final “Delete my account” confirmation. Do not offer deletion as an error recovery action.

## Shared states and accessibility

Every data page has a skeleton with an accessible loading message; first-use empty state with one primary action; no-results state with Clear filters; retryable error with safe request ID; permission-denied state; and stale/offline state that never shows unconfirmed mutation success. DB unavailability must not imply cached authorization permits actions. Changing organizations or losing membership must clear previously scoped content immediately. Preserve only safe unsaved data; do not retain secrets after session/scope loss.

Target WCAG 2.2 AA: landmarks, skip link, ordered headings, real links/buttons, associated labels, error summary plus field errors, visible focus, keyboard access, accessible name for every icon, and status text independent of color. Design target 44×44px touch controls, at least AA minimum targets. Check 4.5:1 normal text and 3:1 large text/non-text control contrast. Focus must not be obscured by sticky headers or action bars. At 200% zoom and 320 CSS pixels, reflow content without losing actions. Respect reduced motion.

### Page not found

The React fallback for an unresolved route is a standalone surface with no shell: one `main` landmark labelled by the single h1 “Page not found”, one white recovery card (max-width 520px, 1px #D5DBE3 border, 12px radius, no heavy shadow) on the #F7F8FA body, and left-aligned content in this order: the non-heading label “PAGE UNAVAILABLE” (14px, secondary text), the h1 (32px desktop, 24px at 480px and below), the paragraph “We couldn’t find this page. Check the address or return to your organizations.” (16px, secondary text) and one real anchor “Back to organizations” styled as the primary action (#1D4ED8 with white text, 8px radius, 44px minimum height, 20px horizontal padding). The anchor `href` is exactly `pageHref("overview")` (`/overview`); it never carries the organization selector, `organization_id`, `org`, `page`, tokens, `user_code`, `transfer_id`, `error`, `return_to`, any other query value or the fragment from the unknown address, and the unknown pathname, query and fragment are never rendered, copied or logged. Spacing: 120px top space and 40px card padding on desktop, 80px and 32px (32px side gutters) at 768px and below, 32px and 24px (16px gutters, full-width action) at 480px and below, 24px minimum bottom space. The card uses normal document flow with no fixed height, no transform centering and no horizontal overflow at 320px or 200% zoom.

The surface renders synchronously and fetches or mutates nothing. The address bar stays unchanged on load: no `history.replaceState`, no automatic redirect and no history back, so `/missing?page=keys` and `/instance/not-a-section?organization=studio` keep their address and still render this fallback. On mount the h1 receives programmatic focus (`tabIndex=-1`); the link is never auto-focused, Tab reaches the single link and Enter follows it. There is no dialog, focus trap, live-region alert or animation, and the visible focus ring is a 2px #1D4ED8 outline with 3px offset. Styles use the dedicated `.not-found*` classes; the shared `.standalone` rule used by sign-in, device, invitation, ownership and in-app notices is unchanged. This React screen is not the server HTTP 404: the service allowlist still sends unknown paths without `index.html`.

Dialogs trap focus, have a named heading, support Esc and return focus to their trigger. A single critical input receives focus when its form appears, including organization name, invitation email, code entry and typed deletion confirmation. Otherwise focus the heading or safest action. Use polite live regions for copy/save completion; assertive announcements for blocking errors only. Never announce a countdown every second. Announce meaningful expiry thresholds once. Do not rely on hover for help or menus.

# apps-delidev-app-foundation

## Scope
- Project/component: `delidev` / `app`
- Canonical path: `apps/delidev-app`
- Canonical future origin: `https://deli.dev`

## Runtime and Language
- Runtime: browser PWA
- Primary language: TypeScript with React
- Build: Rsbuild; output: `apps/delidev-app/dist`
- The development server defaults to port `4173`; `DELIDEV_APP_DEV_PORT` is the temporary local override consumed by the package-owned `dev` task. Root `pnpm dev` may set it to a logged free port when the default is occupied without changing the canonical default.
- Use React Query and `@connectrpc/connect-query` for server state and Connect RPC integration.
- English-only, responsive desktop/mobile UI for current Chrome, Edge, Firefox, and Safari.
- Follow Toss Design Guidelines and WCAG 2.2 AA. The wordmark is text `DeliDev`; the PWA uses a simple `D` lettermark. A complete brand system is out of scope.

## Users and Operators
- Anonymous developers browsing catalog metadata and pricing.
- Authenticated organization Owners, Admins, and Members; Team Admins and Members.
- Platform maintainers operating the future Pages, Logto, Polar, delibase, and Deck connection-management integrations.

## Interfaces and Contracts
- Stable routes: `/`, `/apps`, `/apps/:appSlug`, `/auth/callback`, `/onboarding`, `/invite/:token`, `/o/:orgSlug/apps`, `/o/:orgSlug/members`, `/o/:orgSlug/teams`, `/o/:orgSlug/billing`, `/o/:orgSlug/usage`, `/o/:orgSlug/settings`, `/account`.
- Deck mobile reserves the planned credential-sensitive callback route `/auth/devhud/callback`. Before Deck mobile activation, `apps/delidev-app` must emit a dedicated non-SPA callback artifact plus `/.well-known/apple-app-site-association` and `/.well-known/assetlinks.json`, scoped only to that path and application ID `dev.deli.devhud`. Fixture association identities are permitted in CI; release artifacts require externally injected Apple Team ID and Android release-certificate SHA-256 values and must fail closed when either is missing. The service worker, SPA fallback, logs, analytics, and caches must never consume or retain callback query/fragment credentials.
- The existing `/account` and `/o/:orgSlug/settings` sections expose implemented Deck GitHub connection management. This client consumes only `DeckIntegrationService.GetGitHubConnection`, `StartGitHubConnection`, `ListGitHubInstallations`, and `DisconnectGitHubConnection`; installation rows display the returned stable GitHub account login/kind rather than an opaque provider installation ID. Personal users and organization Owners/Admins manage exactly one selected owner scope; organization Members receive only management guidance and initiate no Deck request. It must not call Deck view procedures including `GetRefreshPreflight` or `RefreshView`, consume pull-request data, mutations, devices, notifications, or widgets, or add a top-level Deck route.
- The Deck settings client treats the `StartGitHubConnection` target as a one-use memory-only handoff. Before top-level same-tab navigation, a Deck-specific helper requires HTTPS GitHub.com with no credentials, fragment, non-default port, encoded path separator, or path traversal and permits only `/login/oauth/authorize` with the configured Deck GitHub App client ID and exact callback URI or `/apps/<the configured Deck GitHub App slug>/installations/new`. It rejects every other shape without navigation, never returns the target to another component, and keeps its query data out of history-state payloads, logs, analytics, caches, and persistence. This helper grants no arbitrary URL, popup, remote-resource, or generic navigation surface.
- `/account` and `/o/:orgSlug/settings` expose RealQA GitHub.com connection and destination discovery through only the six generated `RealQATrackerService` RPCs. The browser bundle imports only the generated common-message and tracker subpaths and must not contain preset/submission descriptors. No RealQA top-level route, catalog activation, preset editor, submission UI, upload, or lifecycle-deletion call is authorized. Personal users manage their own binding. Organization Owners/Admins may install, bind, reconnect, and disconnect the owner-scoped installation; Members may start only their caller-scoped OAuth authorization and see only repositories returned by the server for their own GitHub identity. The UI never derives repository visibility from installation ownership, hides repository/schema rows whenever their current refresh fails, and exposes issue-disabled/caller-submit permission states before requesting repository schemas.
- RealQA connection, installation, repository, and schema reads are zero-retention memory/network-only server state. Human calls carry a RealQA-audience bearer plus the exact memory-only `x-delibase-forwarded-user-token` delibase-audience bearer. Mutations are disabled offline. Disconnect requires the current connection revision and retains one UUID v7 idempotency key for an ambiguous retry; success announces that provider credentials were removed while presets and repository mappings remain disconnected records. Repository schema discovery displays generated Markdown-template and Issue-Form metadata, including issue type, input/textarea prefill, textarea render language, and dropdown multiplicity, without rendering provider-supplied HTML or code.
- The RealQA `StartGitHubConnection` target is consumed directly from the generated response without entering React Query mutation data. Its feature-specific helper rejects GHES/custom hosts, HTTP, credentials, fragments, non-default ports, encoded separators, traversal, unexpected parameters, wrong App slug/client ID, and a mismatched callback. It allows only the configured GitHub.com OAuth or App-installation shape and then performs top-level same-tab navigation. Authorization state/query data and the server-owned callback URL never enter DeliDev storage, history state, logs, diagnostics, analytics, or service-worker caches; DeliDev has no callback route for this server-owned flow.
- `/apps` and `/apps/:appSlug` are public. Organization context, billing, usage, invitation preview/acceptance, onboarding, and account management require authentication. Only accounts whose server-authoritative state requires onboarding may enter `/onboarding`; completed accounts redirect to `/account`. Invitation preview and acceptance authorize with the invitation bearer token and do not require the user to be an existing organization or team member.
- Consume the five human-facing `delibase.v1` Connect services: `AccountService`, `OrganizationService`, `TeamService`, `CatalogService`, and `BillingService`. `UsageService` is server-to-server; the browser must not issue live-user or authorized reserve, commit, or release mutations or hold M2M credentials.
- Consume protobuf-es v2 messages and `GenService` descriptors through the
  workspace package `@delinoio/delibase-connect` and, only for bounded
  settings connection management, the private workspace packages
  `@delinoio/devhud-deck-connect` and
  `@delinoio/devhud-realqa-connect`; the RealQA package is restricted to
  `RealQATrackerService`, and Connect Query remains responsible for browser
  server-state integration.
- Logto browser authentication supplies user identity; delibase decides local profile, organization, team, billing, and authorization state. The browser never handles card data; Polar-hosted Checkout and Customer Portal own payment UI.
- On first authenticated entry, require organization name and globally unique user-selected slug before allowing entry. In the same transaction, create the local user keyed by the unique Logto `sub`, then create the default organization, Owner membership, protected `General` team, and creator Team Admin membership exactly once. Use the same organization transaction for every additional organization.
- Support multiple organizations, changeable globally unique slugs with retained aliases/old-slug redirects, nested teams up to five levels, invitations with replay-safe acceptance/revocation results, and role-aware pages according to the delibase contract. Human idempotency keys are scoped to the authenticated user subject and operation. Complete-onboarding, create-organization, create-team, and invitation-acceptance retries reuse the pending operation key until the request succeeds or their inputs change; organization-slug retries reuse it until account refresh and navigation succeed or the slug input changes; subscription-checkout retries keep their account-and-organization-scoped pending key and normalized return URL in route-surviving memory until the hosted-checkout redirect; account-deletion, organization-deletion, team-subtree-deletion, and invitation-revocation retries reuse it until success or cancellation, and the invitation bearer token is the acceptance input boundary.
- Background-authorization UI remains within the billing/usage sections of `/account` and `/o/:orgSlug/settings`; no new top-level route is allowed. It discovers stable service authorization UUIDs and safe names from public catalog meter metadata, uses only the human `BillingService` create/get/opaque-list/revoke methods, keeps grants and summarized current-period usage network-only and memory-only, disables mutation offline, and retains distinct create/revoke idempotency keys across ambiguous retries. It never receives Logto client IDs or credentials and never calls the M2M-only usage or resource-deletion methods. Owners/Admins receive organization-wide list/revoke visibility, Members only grants they created, and RealQA may show only its own grant status, payer, current daily units, billing failure, and rebind/revoke controls. Deck has no v1 purpose and cannot use this flow.

## Storage
- Cloudflare Pages serves a static artifact with SPA fallback; no server-side app runtime is activated by this issue.
- Service worker/cache may contain only the versioned static shell and anonymous public catalog data. Never cache authenticated organization/team data, balances, ledger, usage, RealQA connection/installation/repository/schema data, authorization targets, tokens, invitation tokens, or other sensitive data.
- Show an offline state and disable server-backed actions while offline. Access, refresh, and ID tokens remain memory-only. Planned Deck connection calls additionally use a Deck-audience token plus memory-only delibase-audience forwarded bearer metadata with matching subjects; neither token nor connection response may enter persistent storage or the service worker. PKCE state and non-sensitive one-shot protected return paths may use same-tab session storage solely across the Logto redirect and must be consumed on callback; invitation returns use a state-bound sealed handoff that never serializes the bearer token in plaintext, and invitation metadata uses a token-free canonical path. None may enter local storage, React Query persistence, or the service worker.

## Security
- Treat Logto as the identity trust boundary, delibase as the DeliDev-domain authorization boundary, and each Deck/RealQA service as authoritative for its connection management. Do not infer owner scope, GitHub permissions, or connection authority from client state.
- Protect authenticated routes and do not infer authorization from cached UI state. Do not log tokens, invitation tokens, billing PII, or authorization headers.
- Dialogs close with `Esc`, restore focus, and expose complete keyboard/screen-reader states; critical single-input forms autofocus their first input.
- Pages configuration is artifact-only. No public DNS, Pages project activation, or deployment is authorized here.

## Logging
- Client diagnostics must use safe classifications and request/trace correlation without token, payment, invitation, or sensitive organization data.
- Keep dependency and offline errors distinguishable from authorization errors in UI states; do not claim an unavailable backend is operational.

## Build and Test
- Shared client checks are aggregate `pnpm check:proto`, delibase-only
  `pnpm --dir protos/delibase check:proto`,
  `pnpm --filter @delinoio/delibase-connect typecheck`, the Deck component
  check, and `pnpm --filter @delinoio/devhud-deck-connect typecheck`. Required
  local checks for the connection-management implementation are
  `pnpm --filter delidev-app typecheck`, `pnpm --filter delidev-app lint`,
  `pnpm --filter delidev-app test`, `pnpm --filter delidev-app build`, plus PWA,
  accessibility, and browser smoke validation. The app typecheck, test, and
  build commands build each consumed generated Connect client first so they
  work from a clean checkout.
- CI must validate the production static artifact, SPA fallback, manifest/service worker, sensitive-cache exclusions, responsive accessibility, and Connect client generation compatibility. The deterministic build must leave the checked-in `apps/delidev-app/dist` artifact unchanged.
- Deck mobile implementation additionally validates the dedicated callback artifact, exact callback-only Apple/Android association rules, no redirects for either well-known file, injected release identities, and exclusion of callback requests from SPA/service-worker caching.
- `pnpm --filter delidev-app test:pwa` validates the installable manifest, generated SPA fallback, versioned shell, canonical metadata, and allow/deny cache rules. `pnpm --filter delidev-app test:browser` covers Chromium, Edge, Firefox, WebKit, and representative mobile Chromium/WebKit viewports.
- Rsbuild writes the static app to `apps/delidev-app/dist`; `scripts/postbuild.mjs` copies `index.html` to `404.html` and produces `sw.js` from the exact generated shell file set. Cloudflare Pages `_redirects` provides the primary SPA fallback.

## Dependencies and Integrations
- Depends on `protos/delibase/v1` and its generated TypeScript Connect client. Connection management additionally depends on `protos/devhud-deck/v1` and `protos/devhud-realqa/v1` plus their generated TypeScript clients, without transferring ownership of those contracts from `devhud`.
- Calls the future `https://delibase.deli.dev` API origin; the canonical delibase browser-safe build variables are `PUBLIC_DELIBASE_API_ORIGIN`, `PUBLIC_LOGTO_ENDPOINT`, `PUBLIC_LOGTO_APP_ID`, and `PUBLIC_LOGTO_AUDIENCE` (the latter is `https://delibase.deli.dev`). These values are non-secret and must never contain tokens or provider secrets; required values fail closed when absent.
- Deck connection management calls only the exact future `https://deck.deli.dev` origin and treats it as the Deck Logto audience. Its additional browser-safe build variables are `PUBLIC_DECK_API_ORIGIN`, `PUBLIC_DECK_LOGTO_AUDIENCE`, `PUBLIC_DECK_GITHUB_APP_CLIENT_ID`, `PUBLIC_DECK_GITHUB_APP_SLUG`, and `PUBLIC_DECK_GITHUB_CALLBACK_URI`; production origin/audience are exactly `https://deck.deli.dev`, and missing, malformed, or non-GitHub/cross-origin authorization configuration disables the connection action before RPC or navigation. These values contain identifiers and an exact callback URI only, never a GitHub client secret or token. The app must not send Deck tokens to delibase or delibase tokens as the primary Deck authorization bearer.
- RealQA tracker settings call only `https://realqa.deli.dev`, which is also the RealQA Logto audience. Browser-safe variables are `PUBLIC_REALQA_API_ORIGIN`, `PUBLIC_REALQA_LOGTO_AUDIENCE`, `PUBLIC_REALQA_GITHUB_APP_CLIENT_ID`, `PUBLIC_REALQA_GITHUB_APP_SLUG`, and `PUBLIC_REALQA_GITHUB_CALLBACK_URI`; production origin/audience and callback are pinned to `https://realqa.deli.dev` and `https://realqa.deli.dev/github/oauth/callback`. Missing or malformed values disable the RealQA controls without disabling core DeliDev authentication. These values contain identifiers only, never a client secret, GitHub token, or OAuth state.
- Pages owns static hosting; GHCR is unrelated to this app and must not be used as its deployment path.

## Implemented Client Boundaries
- Account and organization settings compose the bounded generated RealQA tracker manager described above. It keeps the one-use start response outside React Query, uses zero-retention tracker queries, never persists either audience token, presents server-returned permission and revision states, and includes explicit cache-policy, GHES rejection, UUID v7 retry, role/filtering, schema discovery, offline, dialog-focus, accessibility, and browser-route regression tests. This settings integration does not activate the RealQA catalog entry or full feature.
- Public pages use a dedicated anonymous Connect transport for `CatalogService`. Protected routes use a separate transport interceptor that requests a Logto access token for exactly `https://delibase.deli.dev`, attaches it only to the current request, and sends `Cache-Control: no-store`.
- React Query state is memory-only. Public catalog requests may be served by the service worker; protected account, organization, invitation, team, billing, ledger, and usage queries have no persistent browser cache.
- The service worker recognizes only the four checked-in `CatalogService` read method names, requires an absent `Authorization` header, and keys cached POST responses through a synthetic body digest. Every other RPC is network-only.
- Missing or invalid public configuration fails closed: public catalog requests show a dependency error and Logto controls remain disabled. The environment contract remains browser-safe and contains no provider secret.
- Initial service-worker control does not reload the page. Later updates wait for user confirmation, activate through `SKIP_WAITING`, reload on controller change, remove prior version caches, and retain only the new versioned shell and public catalog cache.
- Logto uses an injected browser client whose access, refresh, and ID token state is memory-only and which removes legacy state for the configured app from local storage. Its PKCE sign-in session and non-sensitive protected return path use same-tab session storage. Invitation return paths are sealed with a key derived from the high-entropy OIDC state, restored only by the matching callback, and removed from storage immediately; abandoned sealed handoffs are discarded on the next same-origin load.
- Public catalog, organization member, team hierarchy, and usage-record lists use opaque cursor pagination with explicit load-more actions.
- The account surface creates additional organizations through the same atomic organization transaction used by onboarding and then enters the returned canonical slug.
- Protected routes provide one memory-only, server-authoritative account-state boundary to onboarding, account, and organization children. The organization shell uses that state for an accessible organization switcher, while resolving every requested slug through delibase and replacing alias URLs with the current canonical slug without dropping the remaining path, query, or fragment.
- Organization settings expose the name and changeable-slug RPCs, refresh server-authoritative shell data after successful name updates (including a partial save when the following slug update fails), and follow the returned canonical slug after slug changes.
- Account and organization settings compose the generated `DeckIntegrationService` through a separate exact-origin, procedure-restricted transport. Each request acquires Deck- and delibase-audience user tokens in parallel, adds the forwarded token only as sensitive request metadata, and retains neither token. Connection and installation loads run in parallel and validate the returned owner scope before rendering; more than one installation, pagination, missing stable identity, or a substituted owner fails closed without exposing row data. The start response bypasses React Query, validates and immediately consumes its one-use GitHub.com target, and stores only a safe non-sensitive settings return path for the dedicated callback artifact. Disconnect confirmation contains focus, closes with `Esc`, restores focus, retains the exact connection/revision input across ambiguous retry, refreshes after stale revision, and explains server cleanup versus separately uninstalling the GitHub App. Every mutation is disabled offline.
- The organization shell loads the server-authoritative caller role. Owners can promote multiple Owners and manage every organization member; Admins can manage Admins and Members but never Owners. Member role updates, removal, self-departure, last-Owner rejection, and active-reservation rejection remain server-authoritative and expose stable blocker guidance. Settings provide self-departure to every role and confirmed organization deletion only to Owners.
- Team capability controls use `ListEffectiveTeamAccess`, including downward ancestor inheritance, rather than inferring access from the organization role. Owners and Admins remain implicit Team Admins everywhere; direct or inherited Team Admins may create children beneath administered teams, manage direct Team Admin/Member assignments, and rename, move, or confirm subtree deletion where authorized. The five-level and cycle filters are preflight affordances only; delibase remains authoritative. General exposes membership management but never rename, move, or delete controls. Team management dialogs remain open while a direct-membership mutation is unresolved so its outcome and replay key are retained. Subtree deletion requires an explicit user confirmation and retains its replay key through retry while active-reservation blockers remain distinguishable.
- The member surface lets Owners and Admins create reusable invitation links, page through active invitations, and revoke them with replay-safe retries; creation bearer tokens bypass React Query and remain only in component memory. Invitation preview distinguishes invalid, revoked, and expired server states and explains that an existing member's organization role is unchanged.
- Billing composes a shared-balance surface with an Owner/Admin-only administration surface. Members receive and render only `available_credit`; manager-only components own subscription/payment state, current-period context, held credit, held/committed overage, exact non-negative overage settings, hosted checkout/portal mutations, and the opaque-cursor full ledger. The summary and independent ledger load concurrently. The UI presents the $10 monthly/10,000,000-micro-unit grant and rollover model, zero-default and lower-limit blocking, canceled/past-due credit behavior, refund/chargeback reversals, queued Polar delivery, and reservation finalization without issuing `UsageService` calls or calculating a charge. Checkout and portal responses are memory-only, use zero mutation-cache retention once unused, show the error from the latest action, and navigate only to credential-free HTTPS `polar.sh` hosts. Checkout retries retain their account-and-organization-scoped pending idempotency key and normalized return URL across route unmounts until hosted navigation succeeds. Successful overage updates apply the returned authoritative summary before the dialog closes. Portal retries retain their component-local pending idempotency key and normalized return URL across ambiguous response failures and replace both after a successful session response; card collection, invoices, receipts, cancellation, and recovery remain entirely on Polar.
- Usage composes shared available credit with server-filtered opaque-cursor records. Owners/Admins see organization-wide period and credit/overage attribution; Members receive only personal and effectively accessible-team records and no organization billing fields. Rows preserve committed time, team snapshot, pseudonymous account/service, meter, units, unit price, total, credit/overage split, client reference, and delivery state. Polar-pending rows expose an outage/queue state while explaining that the local ledger remains authoritative and no browser charging occurs.
- Account and organization settings compose one background-authorization manager over the generated human `BillingService` get/opaque-list/revoke methods. `/account` requests the caller's complete server-visible set across organizations; organization settings filters by payer organization. Both rely on the server-authoritative per-row role boundary, which returns complete organization visibility to Owners/Admins and creator-only visibility to Members. Lists summarize safe resource identifiers, status, current held-plus-committed period units, maximum units, and revision; a network-refreshed detail dialog adds owner, payer, team, purpose, billing-failure availability, and status-specific recovery guidance without service credentials or provider data. Billing failure remains unavailable until an authoritative service field exists and is never inferred from authorization status. Revocation requires a focused, focus-contained, `Esc`-dismissible confirmation, restores focus, disables offline, retains one key and expected revision across ambiguous retries, replaces keys rejected by definitive idempotency/replay conflicts, applies the successful authoritative response before best-effort reconciliation, reports replay outcomes, and refreshes after conflict, access-loss, or closed-status errors. Authorization queries use zero-retention memory state, opaque pagination, and the authenticated no-store transport; all four background-authorization RPC paths are covered by the service-worker sensitive-cache deny tests even though this UI issues only list/get/revoke.
- Missing balance wrappers render as unavailable while explicit zero remains zero. A configured overage limit with a missing value wrapper is not editable. The overage dialog focuses its critical input after remembering the opener, contains keyboard focus, closes with `Esc`, restores focus, retains one idempotency key across ambiguous retries for unchanged input, locks its amount while an update is pending, and disables submission offline. Billing, balance, ledger, usage, checkout, portal, and overage request data remain network-only and are excluded by the explicit service-worker allowlist and all browser persistence.
- Connect error details are decoded through the generated `ErrorDetail` schema for permission, last-Owner, invitation, hierarchy, protected-General, active-reservation, slug, deletion, subscription, overage, numeric, price, reservation lifecycle, and idempotency states. Dialogs are rendered as body-level modals, make the background inert and hidden from assistive technology, contain focus, close on `Esc`, and restore the invoking control. Account deletion announces request and accepted progress before invoking Logto sign-out.

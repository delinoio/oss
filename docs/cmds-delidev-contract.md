# DeliDev command, server, and Worker contract

## Scope
`cmds/delidev-cli` produces the `delidev` binary for macOS, Windows, and Linux. It contains the standalone CLI and the identical bundled-sidecar server/Worker entry points. The complete issue is retained in [requirements](cmds-delidev-requirements.md); record implementation and verification progress in pull requests, issues and CI logs/artifacts.

## Runtime and Language
Go, using the root module and pinned dependencies. Business logic is independent of desktop presentation. Initial version is `0.1.0` (unreleased).

## Users and Operators
One server owner, authenticated paired desktop/CLI devices, and outbound execution Workers. Agent Worker configurations are distinct from execution machines.

## Interfaces and Contracts
`delidev notification` exposes this client's preferences, metadata candidates, original display claims and terminal reports through the same authenticated Inbox service used by desktop clients. It never shows an OS notification itself, starts a server, marks an inbox entry read or answers a request. Reconnecting and receipt replay cannot issue another display grant. See the [inbox notification contract](cmds-delidev-inbox-contract.md) for exact commands, defaults, states and JSON precision.

`delidev server overview` reads the same authenticated `SystemService.GetOverview` used for desktop status presentation. It returns observation time, exact active-execution and unanswered-request counts, registered/connected Worker counts and server UTC day boundaries as versioned CLI JSON. Counts and millisecond boundaries are canonical decimal strings, including explicitly measured zero, so generic JSON consumers retain 64-bit precision. It neither starts the server nor changes session, interaction or Worker state. Failed reads are unavailable, not zero; see the [diagnostics contract](cmds-delidev-diagnostics-contract.md).

`delidev server start|stop|status` is the explicit infrastructure boundary; `server ensure` is the bounded local controller operation for automatic recovery of an already configured running scope. Normal product commands require a running server. JSON output is versioned, carries stable IDs and typed failures, and is separated from stderr progress. Mutations require a UUID-v7 request identity; identical retries return the accepted result, while reuse with different parameters fails. Writes use expected entity revisions.

Issue #1137 adds infrastructure-only `server desktop-launch`, `server desktop-retry` and `server desktop-status`. A fresh main desktop host owns one launch: initialize/reopen a compatible ordinary owner scope only after original database ownership has joined, or reuse the authenticated compatible server. If a stopping server still answers, that fresh launch joins the original store ownership barrier before publishing replacement intent; ordinary Start keeps its live-stopping conflict. Retry is explicit and retains Stop suppression; status is a read-only current-readiness observation and cannot write running intent, spawn or pair. Ordinary product commands never implicitly start a server, explicit `server start` keeps its original behavior, and `server ensure` still requires matching running intent. Desktop launch, Retry and read-only observation independently validate the authenticated status listener against the requested local listener and stored endpoint before reuse. A compatible legacy live server may be reused, but its absent lifecycle remains absent: status does not prove TLS paths or allowed origins, and its eventual exit cannot acquire desktop-authored restart configuration. Read-only status distinguishes absent legacy evidence from explicit Stop and may authenticate the live legacy listener; after it exits, observation reports unavailable and ensure remains stopped. Ordinary explicit legacy adoption remains unchanged. Automatic ensure, desktop launch/Retry and observation share one 35-second aggregate deadline across admission, controller joining, original ownership and readiness, below the native 40-second command envelope. Nested waits may shorten that deadline but never reset it; cancellation is checked before acquiring uncontended admission/controller locks, before intent publication and immediately before spawn. An interruption after intent publication retains truthful recovery-required state; a spawned detached server may still become ready. Ordinary explicit Start retains its prior per-phase bounds. No new product RPC or data migration is added.

`server desktop-host --mode launch|retry|ensure [--listen IP:PORT --allowed-origins ORIGIN,ORIGIN]` is the app-owned local process boundary. It shares desktop startup admission and existing Stop/configuration rules. Reuse returns the existing version-1 envelope and exits; a newly admitted server runs in this process, publishes a ready envelope with its exact startup generation, releases admission/controller locks at readiness and publishes the final stopped envelope only after server/store joins. The aggregate startup deadline ends at readiness. Business logs remain in the private `server.log`; control stdout carries bounded versioned envelopes only.

Its private stdin accepts one newline-terminated closed version-1 `stop` action of at most 256 bytes. Stop suppresses only this process's original startup generation before cancellation. EOF or malformed input grants no Stop. The host command handles standard-output/error SIGPIPE as failed delivery, including a readiness reply lost during desktop startup; ordinary CLI pipe behavior is unchanged. A desktop crash therefore leaves a running sidecar available; normal Quit sends Stop and, after 35 seconds, may force only its retained original child. Borrowed CLI/service/remote servers and independent Workers are preserved. Forced process exit is distinct from native/session cleanup. No Connect or SQLite schema change is introduced. See the [desktop shutdown boundary](apps-delidev-desktop-contract.md#app-owned-sidecar-shutdown).

Desktop native pairing and credential inspection may select `--join-existing` only for the owner's fixed `desktop-client` scope. This joins the original recovery lock under a bounded cancellable deadline, then repeats its complete original-evidence checks before reading or pairing. Concurrent fresh hosts reuse the same committed client or exact pending journal; contention cannot become another pairing, speculative recovery or credential replacement. Ordinary local pairing and remote pairing keep their existing behavior.

Desktop launch/retry and ensure acquire native-service control admission before startup/lifecycle/store ownership and retain it through intent publication and spawn. Rechecks pin the original registration decision against concurrent install/start/remove. A registered scope may provide compatible live reuse; it cannot admit a detached competitor or automatic service-manager mutation. Stopped or unready registrations report `service-managed` to desktop launch; malformed/foreign evidence is preserved. Concurrent fresh hosts wait for bounded admission and reuse the same server. Read-only observation validates current lifecycle and compatibility instead of returning cached launch readiness after Stop. See [desktop](apps-delidev-desktop-contract.md) and [service ownership](cmds-delidev-user-services-contract.md).

The private versioned `server-lifecycle.json` records desired running/stopped state, a UUID-v7 generation and the digest of the original listener/TLS paths/exact origins. Automatic ensure requires intact running intent and matching configuration, probes authenticated compatibility before every launch, and never clears a stop. Explicit start may replace stopped intent only after the previous server is unavailable; a stopping live server is preserved. Paired client and Worker scopes cannot invoke local startup or recovery, even when their saved endpoint names another server.

The controller startup lock serializes launch attempts; a separate lifecycle lock serializes intent writes with the child's complete native startup barrier. Detached children receive an exact startup generation and reject canceled/superseded requests before opening the database. The child completes and releases this lifecycle barrier before the HTTP server can answer any request; authenticated readiness therefore permits immediate reuse or explicit Stop independently of later readiness logging and maintenance startup. StopServer validates its request and transaction authorization, commits restart suppression before its durable receipt/acknowledgment, and retains the original process epoch in that receipt. A subsequent database failure conservatively leaves suppression in place without claiming shutdown. Replaying an old stop against a new process cannot stop it. A same-user offline owner `server stop` may persist suppression after an unavailable endpoint but returns recovery-required because shutdown/cleanup is unconfirmed. Corrupt or inaccessible lifecycle records are preserved and block automatic reset. These infrastructure records do not authorize session Resume or prove Worker cleanup.

Server defaults to `127.0.0.1:46310`; an explicitly configured `::1` or listener is supported. Conflicts fail. Non-loopback listeners require TLS. Authentication applies to loopback too, and origins use an exact allowlist. The server exposes actual bound addresses and compatible version/data-scope identity. Connect server streams use durable ordered cursors, coherent snapshots, indexed messages, bounded pages/buffers, and explicit resnapshot errors.

`ResourceService.WatchEvents` emits only store kinds with a supported nonzero public `EntityKind`. Private routing events remain durable for server ownership but are omitted from public streams. Each skipped row advances the server's cursor, including full private pages; the next public event retains its original durable sequence. Public cursors can therefore have sequence gaps. Reconnect and retention validation use the same durable history, and count-bounded paging, synchronous backpressure and session scoping remain unchanged. No public routing enum, capability or client execution authority is added.

The default private data directory is the operating system's user configuration directory plus `delidev`; `--data-dir` selects an explicit scope. `owner.json` is an owner-only local bootstrap credential and never appears in command output. `server.json` contains only the actual endpoint and compatible scope/version identity. The database pins the server identity; missing or mismatched owner material cannot silently re-pair an existing scope. Detached explicit startup holds a separate startup lock and waits for authenticated readiness; when TLS files are supplied, that local readiness transport pins the exact configured certificate and verifies its lifetime/server use instead of requiring a DNS certificate to name the bind IP. Wildcard IPv4/IPv6 listeners are dialed through their corresponding loopback addresses. This applies to explicit startup/reuse only; ordinary and remote product clients retain standard hostname/CA verification. A failed or uncertain launch directs the user to status and the private structured server log. A stop receipt binds the targeted server start time so retrying an old stop cannot stop a replacement process.

Configuration commands accept `--input FILE|-`; writes accept `--request-id UUID-V7`, and edits/deletes require the current `--revision`. A generated request ID is returned in the version-1 result/error envelope. Explicit remote connections use `--server URL --token-stdin`; stdin credentials are never placed in argv or ordinary output. Normal resource reads cannot create a data directory. A terminal with no document/credential input returns `missing_input` instead of waiting indefinitely.

`device create-pairing --type worker|client --name NAME` writes a five-minute, single-use pairing document in a private file and returns only its path and public grant metadata. Pipe that document into `worker pair --worker-dir PATH --code-stdin` or `device pair --device-dir PATH --code-stdin`. Pairing journals its generated credential and exact request before contacting the server. A paired client uses its directory with `--data-dir`; Worker credentials cannot run owner product commands. `worker start --worker-dir PATH` runs the outbound foreground Worker explicitly and holds an exclusive private scope lock. Reconnects reuse the same process identity and report receipt; process replacement preserves unconfirmed jobs as uncertain. `repository inspect --machine-id ID --path PATH [--preferred-remote NAME] [--wait]` returns an accepted job; `job get/list` exposes durable progress. Worker inspection never fetches. Repository create/edit requires a credential-free remote_url and permits an empty checkout list. URL-only registration completes its durable save job without a Worker, local proof, network connection or clone. Optional connected checkouts queue fresh validation on every configured Worker. The command accepts `--wait` for bounded completion. Only all-success validation can atomically publish the canonical checkouts; missing remotes or a concurrent revision change leave configuration untouched. Failed `--wait` results retain the last observed accepted job alongside a typed nonzero error, including cancellation, timeout and unresolved job uncertainty; waiting never cancels or repeats the accepted operation. Automatic fetch defaults to true when omitted.

Entity kinds, workspace modes, harnesses, account modes, lifecycle/recovery/archive/delivery states, source kinds, capabilities, routing and overlap policies are closed typed enums. IDs cannot collide across kinds. First-execution snapshots and account selection commit atomically with routing state. Stop, Archive, restore, outcome, and recovery are independent; restore never dispatches.

The private first-execution transaction primitive now resolves exact ordered instructions/current configuration and atomically retains the immutable snapshot, initial account/connection, actual routing observation, input claim and routing cursor/rotation state. The public coordinator now checks current readiness and queues the exact first Codex assignment in that transaction, automatically after workspace preparation or through explicit first Resume. The Worker executes it through the relay/outbox and reports verified terminal cleanup. The server additionally accepts registered credentials for the pinned OpenCode first-input Chat Completions profile, with the same live ownership and revocation checks. The Worker binding coordinator and server also compose original native settings/session and stored-input acceptance through the durable outbox. The dedicated OpenCode mapper additionally retains exact user/assistant text parts and separate plain-text reasoning artifacts with immutable native parent identities and independently validated completion. Its local Read adapter retains the original proposal, applied input, independent tool result/error and typed native metadata. Separate native usage observations preserve overlapping step/message sources and native counter meanings without changing exact-response accounting or budgets. The original event composer additionally binds terminal publication to native settled state, complete supported projections and independently compared stored history, preserving process cleanup and completion reporting as separate work. Original OpenCode completion now additionally joins acknowledged terminal publication, fresh native history and owned process cleanup into the version-1 report boundary; full production workspace/job orchestration remains separate. These integrations do not enable public OpenCode dispatch, remaining native families or Stop publication. See the [session contract](cmds-delidev-sessions-contract.md) for required readiness and rollback boundaries.

Workers continuously receive their outbound stream while a native operation runs. Connection loss/revocation or a 45-second heartbeat timeout cancels that operation and retains its journal after owned cleanup. The server keeps later jobs queued until the current assignment resolves, preventing a backlog of preclaimed native operations. Reconnect reuses definitive journal outcomes and preserves missing-completion uncertainty.

Native completion reports now bind an immutable Worker-private continuation checkpoint by SHA-256 after native and workspace-process cleanup. The checkpoint preserves exact native defaults/input identity without prompt, answer or credential contents. Its absence, alteration or mismatch with the accepted server report requires recovery; legacy completion evidence is not silently promoted. This retention boundary prepares safe later-turn execution but does not itself resume a session or grant fresh API authority.

### Retained native questions
`interaction list|get` also exposes `native-approval` records with pinned harness/version and dedicated command, file or permission request payloads. The native Worker retains these requests and unread inbox entries atomically; closure/Stop preserves their original contents without approving them. `interaction respond` remains the question-only response operation and rejects approval records. `interaction approve --id ID --revision N --input FILE|-` accepts a dedicated approval response through owner/paired-client `RespondApproval`, using the common `--request-id` receipt. For Codex, the document selects exactly one `decision` object (`kind`, with the original `execpolicy` or `network_policy` where applicable), or one `grant` object with explicit `permissions` and `scope`. Command choices must match the original offered list; grants preserve requested restrictions and never expand path/network authority. Credential stdin requires a response file. Server acceptance queues one immutable response, and the owning Worker separately claims, journals, delivers and publishes transport evidence. Current-state receipt replay cannot resend or reopen a request. An exact live Codex permission-tool output can now record separate `accepted` evidence for its original grant and scope. A pinned single-use `accept` can also gain separate acceptance from its uniquely matched successful original command/file execution, committed with the tool record. Other command/file decisions, ambiguous or unsuccessful execution and lost-event/history recovery remain pending: unconfirmed transmitted approvals retain a recovery gate after native turn completion, even when process cleanup succeeds.

`interaction list --session-id ID` and `interaction get --id ID` read durable native question records through authenticated resource RPCs. The Worker retains exact original questions, native request ownership, waiting observations and unanswered native/terminal closure. Waiting-clear and closure do not imply answer acceptance or grant approval. `interaction respond --id ID --revision N --input FILE|-` accepts non-secret answers through the dedicated owner/paired-client RPC, with common `--request-id` receipt retry. For Codex, its JSON document has `answers` keyed by every original question ID, preserving ordered arrays and explicit empty arrays. Credential stdin requires an answer file. The server validates the exact original revision, options and current execution authority before queued acceptance; the Worker independently claims, journals, sends and publishes delivery. An exact accepted retry returns current interaction state without resending, including after closure. Matching live Codex tool output now records separate `accepted` evidence while preserving transport/closure; missing evidence still requires recovery. Protected answers and lost-event/history reconciliation remain pending; see the [session contract](cmds-delidev-sessions-contract.md).

### Retained inbox
Native question publication and native completion/failure/interruption create independent unread inbox entries atomically with their source. `inbox list` supports session/project/source/read-state filters and bounded pages; `inbox get|inspect --id ID` returns the entry together with its original interaction and current session. `inbox mark-read|mark-unread --id ID --revision N` uses the inbox entry revision and common request receipt. Read state never changes the question revision, answers, cleanup or execution authority. Exact receipt replay returns current read/source state without reapplying an old mark. Source/read-state changes expire filtered pagination cursors; original content is never truncated to fit a page. See the [inbox contract](cmds-delidev-inbox-contract.md).

### Provider and model catalog
`provider presets` lists nine API/local defaults with explicit server-relative endpoint and compatibility guidance. Six hosted presets are saved On by default; `provider create --preset PRESET` creates an unsaved preset and reports a duplicate conflict for one already present. `provider discover --account-id ID --revision N` publishes a durable catalog observation; enabled connected accounts also refresh automatically while the server runs. `model search` supports provider groups, display preferences and bounded scoped pages; `model resolve` returns one canonical provider/model identity or an ambiguity error. General `model create/edit/delete` supports manual registration, display names/aliases/order/hiding and NEW acknowledgement. Catalog discovery preserves manual/user-declared data and never changes health, compatibility or session configuration. See the [catalog contract](cmds-delidev-catalog-contract.md) for scheduling, failure/replay and deletion suppression.

Input modes and transaction-assigned order remain immutable; removed content cannot return through old receipts. Restore preserves pause and outcome. ### Worker executable discovery
`machine discover --id ID --revision N [--input FILE|-] [--protocol] [--wait]` saves executable selections and queues a durable Worker job atomically. Without `--input`, it refreshes the existing selections. A supplied document requires an explicit `executables` array and replaces all four selections; an empty array resets every harness to PATH, while omitted harnesses in a nonempty array use that Worker's PATH:

```json
{"executables":[{"harness":"codex","path":"/absolute/worker/path/codex"}]}
```

Only owner/client authorization may change selections. A monotonically increasing machine `discovery_revision` binds every refresh to its selections independently of connection metadata revisions. An older result becomes a typed failed job and cannot replace newer observations. Repeated request IDs reuse the same accepted job. Completion and machine observations commit together after job revision and Worker-instance authorization checks. Remote diagnostic text is reconstructed from a closed local classification before persistence.

The Worker checks explicit absolute paths first and never falls back after their failure. Unset paths search only absolute PATH entries on that Worker. Symlinks resolve to the installed file; a found but broken or denied candidate remains visible. The current Windows discovery launcher accepts native `.exe` files; shell wrappers are explicitly incompatible rather than interpolated through a shell. Native launch failures preserve typed missing/interpreter, permission, incompatible-format, and unavailable classifications.

Version probes use ten-second deadlines and independent 64 KiB stdout/stderr bounds, private per-harness home/config/cache/temp directories, an explicit environment without inherited account tokens, SSH agents, proxies or loader options, and the owned process start/cleanup contract. Grok receives `--no-auto-update`, private `GROK_HOME` and `GROK_DISABLE_AUTOUPDATER`; its optional bounded source-hash suffix is separated from the detected version. Claude Code and OpenCode receive their documented update-disabling settings ([Claude Code environment](https://code.claude.com/docs/en/env-vars), [OpenCode CLI environment](https://opencode.ai/docs/cli/)). No harness is downloaded, installed, updated, or invoked for inference. Runtime deletion follows proof of owned descendant termination; uncertain ownership retains the runtime and a recovery error. Logs contain job/harness identities and typed states, never raw probe output or executable paths.

Installation states are `unchecked`, `detected`, `missing`, `permission-denied`, `incompatible`, and `failed`. `detected` means only that the executable returned a bounded recognizable version. Version-only discovery leaves `protocol_verified=false` and capabilities empty. The optional `--protocol` performs a separate non-inference native handshake, records `verified`, `unsupported` or `failed`, and still grants no execution capabilities or selected-account readiness. The initial Codex `0.151.0` discovery profile validates native initialization and a bounded read-only readiness operation. Claude Code `2.1.236` now has a separate private bare-mode stream-json initialization profile; its exact unauthenticated response and owned cleanup are verified without prompts, login or inference. This observation grants no Claude execution capabilities, and Claude session/account integration remains pending. Grok Build `1.0.41` additionally performs private native configuration inspection and ACP initialization, requiring the original empty startup MCP inventory and rejecting inherited settings/extensions before ACP. Its descriptors remain private and capabilities empty; authentication/session/Worker integration is separate. OpenCode `1.18.32` now verifies a newly owned authenticated loopback server, original startup/health/version, empty global configuration and bounded static operation advertisements, with fresh state separate from version probing and no native project/session calls. Actual negative and positive authentication checks remain independent of schema metadata, and no execution capability follows. A separate private thread-control mode creates, inspects and resumes native root threads with exact settings validation, additive instructions and retained acceptance uncertainty. Internal Execute/Plan turns, expected-turn Steer, interruption and typed core message/lifecycle events are now implemented; the first-turn Worker runner now binds them to immutable accepted assignments, account authority and durable publication, while the public coordinator now queues the first native assignment; FIFO continuation and explicit Resume now preserve the initial snapshot/account and exact predecessor evidence; complete native lifecycle handling remains pending. A private Worker outbox and publication RPC now retain core input/message/terminal events, observed settings, dedicated command/patch tool records, plan/reasoning artifacts, immutable turn-plan/diff observations, attributed native token observations and generic warning notices; the first dispatcher is integrated and remaining event families still require their own adapters. Interruption/terminal observations do not replace native ownership cleanup. Remaining rich events, unproven command/file approval acceptance, lost permission-output recovery, protected answers, the remaining profiles and full execution adapters are pending. See the [harness contract](cmds-delidev-harness-contract.md) for bounded streams, late acknowledgments, profile validation and cleanup. Server timestamps distinguish observed results from pending refreshes. Ordinary tests use temporary executable fixtures and never discover or launch a user's installed harnesses.

The private first-execution workspace lease verifies the exact prepared manifest and native Git ownership, retains the preparation/recovery session lock, and persists an active claim outside the workspace before native work may start. It independently proves execution-job process cleanup before recording closed state. Lost Worker locks, missing workspaces or missing process indexes cannot authorize replacement execution. The Worker job loop now uses this lease for accepted first Codex assignments. Public first dispatch uses this lease. A private continuation lease now retains closed predecessor evidence and preserves agent commits/dirty files under the same workspace/Git identity; the server/Worker now integrate its native history and current-authority checks for subsequent turns. Local execution now uses secondary paired Worker authentication and captured checkout identity, including explicit unborn-branch preparation without creating commits. Original-journal Local preparation recovery supports ready inspection and explicit metadata-only cleanup; live native claim recovery remains pending.

### Project and Agent configuration deletion
`project delete` and `agent delete` use the ordinary expected-revision and request-receipt boundary. Retained sessions do not block removal of selectable configuration. Matching schedules become disabled with a reconfiguration problem in the same transaction. Existing session snapshots/history/workspaces remain unchanged; this operation does not stop or permanently delete them. Continued execution uses the immutable Agent snapshot and, after project deletion, the project's final retained Agent/account restrictions. Current account, Worker, native ownership and cleanup gates remain mandatory. New selection and first dispatch require live configuration, and missing retained policy cannot widen permission. ### Local desktop credential bootstrap
`device pair-local --device-dir PATH` explicitly registers or reuses a separate client against the local owner data scope, without starting any server. It refuses remote/token-stdin selection, using the owner directory as the client directory, incompatible/current foreign server identity and altered private attempts. It journals the original pairing request under an exclusive private scope lock before Connect registration and composes the existing once-only PairDevice receipt. Existing revoked/corrupt credentials are never replaced automatically.

Fresh fixed-scope local client pairing retains a private version-1 `desktop-registration.json` commitment to the exact credential bytes after server pairing acceptance and authentication, before publishing `device.json` or removing the original `pairing-pending.json`. A failed proof write or interruption at either publication boundary leaves that same request/token available for receipt replay; an already written identical commitment is reused. Existing credential reuse never invokes this fresh-pairing publication hook. Before a first revoked-registration inspection or recovery, the saved credential (including token and pairing ID) must match that original commitment. Subsequent recoveries use the prior immutable completed recovery receipt and its replacement commitments instead. Missing or altered proof fails closed before a recovery intent or replacement is created. Ordinary reuse never reconstructs missing evidence; legacy clients already revoked without either proof require original evidence restoration and cannot use automatic or speculative replacement.

`device inspect-local` checks the fixed `desktop-client` scope through the original local server owner and returns only `authorized`, `revoked`, or `recovering`, original server/device IDs, a decimal-string revision and, for pending recovery, its original request ID. It never starts a server. Remote/token-stdin overrides, missing or foreign owner identity, incompatible servers, damaged private files and contradictory registrations fail explicitly.

`--request-id UUID device recover-local --id UUID --revision N` explicitly replaces only that verified revoked client registration. It never unrevokes the original device, resets the server, changes account/session/Worker state, or becomes part of ordinary bootstrap/supervision. Both registration commands accept an optional `--expected-endpoint URL` guard, never an endpoint override. The native desktop always supplies its compiled `http://127.0.0.1:46310` endpoint; Go compares it with the same authenticated local owner client used for recovery before writing intent or issuing pairing mutations. A mismatch returns `unsupported` without changing registration or recovery state. The original owner stays inside Go. The fixed client scope, its stable owner-level recovery lock and existing pairing locks serialize publication. A private versioned `desktop-recovery.json` journal binds the request, old device/revision, server/endpoint, phase and exact original/replacement file commitments. At most 256 request-owned `desktop-recoveries/<request>` directories retain original files, a separate candidate pairing scope and completed receipt metadata; no history is automatically discarded.

Require the original `local-pairing.json` before inspection reports revoked eligibility or a new recovery intent is written. Validate its canonical request identity, server and endpoint, and require its retained private grant to match the credential's pairing identity. The recovery journal requires both original credential and local-pairing commitments; retries also validate the archived pairing relationship before any further pairing operation. Archive the original credential and pairing files before contacting the pairing services. Preserve the original CreatePairing request and the candidate's PairDevice journal/token across response loss. After the pairing-start barrier, a missing candidate journal/credential requires inspection even when a crash might have preceded the first send; absence is never authority to mint another token. Validate the candidate's current authentication before publication. Synchronize the new local-pairing record, removal of the exact old pending file, credential replacement last, the immutable completed receipt, and finally the completion marker. A missing or altered completed receipt blocks later recovery instead of being reconstructed. Each file replacement is atomic; the journal and shared locks gate the multi-file transition. Interrupted publication accepts only the pinned old or replacement bytes and resumes the original request. Changed, linked, foreign or missing evidence is preserved and refused. Completed retries verify the same currently active replacement; superseded requests cannot reactivate prior registrations. Ordinary fixed-scope pairing/inspection reject pending recovery or altered completed files. Logs contain only operation, opaque request ID, phase and stable error classification.

`device inspect --device-dir PATH` and `worker inspect --worker-dir PATH` validate private storage and type offline. Their version/type/endpoint/server/device/machine/pairing metadata excludes the token; inspection never establishes current server authorization. Pair-local reuse checks live authorization separately.

The local `connection list|pair|inspect|retry|verify` infrastructure manages separately pinned client profiles under the [saved connection contract](cmds-delidev-connections-contract.md). It retains original pairing identities through response loss and never initializes or supervises a server. Explicit `connection worker-register|worker-inspect|worker-status|worker-start|worker-stop` controls a separate Worker on this computer for that profile; registration uses the original paired client, retained grant/pairing requests and independent device/machine credentials, while lifecycle preserves the original generation and offline stop.

The read-only `doctor` CLI and System RPC expose version-2 storage, retained Worker and exact protected-reference observations under the [diagnostics contract](cmds-delidev-diagnostics-contract.md). Partial inventories and unavailable measurements remain explicit; no repair, native discovery, credential initialization or inference is performed.

`session terminal create|list|inspect|input|resize|output|reattach|close` exposes the [Worker-owned terminal contract](cmds-delidev-terminals-contract.md). Mutations retain UUID-v7 receipts and revisions, input preserves original bytes, and JSON output frames retain Base64 bytes with exact decimal sequence cursors. Views disconnect independently from native ownership; Agent Stop preserves terminals and Archive joins their original process cleanup.

## Storage
The server exclusively locks its private data scope and initializes only schema 32, with foreign keys, WAL and transactions. Before recovery or writable opening, existing DBs are inspected without changing their source bytes or sidecars. Earlier and unknown schemas are unsupported. A failed first initialization removes only the database/sidecars created by that attempt; pre-existing files stay preserved. No upgrade chain, migration backup, layout repair, retirement-only projection or historical backfill remains.

Current schema 32 directly creates indexed model identities and deletion suppressions; session visibility and ordered queues; job cancellation and immutable claimed envelopes; execution credential bindings and native ownership; native message/request indexes; Inbox source/read state; calendars, occurrences and Worker continuity; tombstone-bound project restrictions; transcript search; exact response and native usage; immutable pricing and response estimates; lifetime budget subtotals; PR feedback and OAuth ownership. Mutation events and actor-bound receipts commit atomically and survive restart. Current backup images include committed WAL state, validate exact schema/integrity and synchronize both the file and published directory entry. Current restore rechecks deletion obligations and protected ownership before replacement. Secrets stay outside SQLite, transcripts, snapshots and ordinary output. Worker workspaces/snapshots and local retained-content search retain their existing ownership.

## Security
Secrets enter through stdin/hidden input and authenticated transport only. The protected storage primitive and its native/file crash boundaries are specified in the [credential storage contract](cmds-delidev-credentials-contract.md); API account connect/disconnect/status RPC and CLI behavior is implemented in the [account lifecycle contract](cmds-delidev-accounts-contract.md), with unverified readiness and durable cleanup retries. `account validate` records a bounded non-inference observation through the [provider inspection contract](cmds-delidev-providers-contract.md); public model catalogs do not establish credential validity, and validation does not grant native harness capabilities or quota recovery. Managed credentials use protected secure storage; GitHub PATs use the OS credential store and never enter Worker environments. The [native API relay](cmds-delidev-proxy-contract.md) implements scoped JSON/SSE forwarding, server-only key injection, fixed `HTTP-Referer`, bounded cancellation and redaction without translation or retries. The server router now enforces digest-only Worker registration, exact durable job/session/account authority, process-epoch revocation, scoped native-reference ownership and account-disconnect/shutdown request cleanup. Codex now has a private execution-token/provider configuration with effective authority verification and native/server relay composition evidence. The Worker generates/registers a fresh scoped token for each accepted Codex turn and runs it through terminal cleanup reporting. Public first dispatch creates an immutable assignment only after current installation/account/workspace/Worker and configuration checks. This is a native attempt, not proof that the selected provider/model will complete successfully. Workspace operations preserve original Local checkouts. No secret-bearing raw child stderr, provider bodies, or URL credentials enter diagnostics.

Provider reflection protection includes SSE field names across frames, sanitized standalone error envelopes even under HTTP 200, and numeric model context limits before catalog publication. Resource snapshots enforce the same aggregate binary/JSON budget as paginated lists, but return explicit narrower-scope failure instead of partial coherent state. Remote checkout syntax is preserved across server operating systems until the owning Worker performs canonical filesystem inspection.

Stream reflection checks include decoded JSON key fragments at both global and original parent paths, so repeated wrappers and JSON escaping cannot bypass protected-name checks.

Locally generated relay errors use every protected value already acquired by the request. A colliding fixed error body is omitted while preserving failure status and safe headers. Pre-key denials do not load credentials for error construction, and failures after SSE output starts retain stream-abort behavior. See the [relay contract](cmds-delidev-proxy-contract.md).

Controller creation failure before native startup removes only the current attempt's original empty scope and synchronizes its parent. Nonempty/replaced evidence and uncertain durability remain recoverable failures; native-started scopes always require their existing ownership proof.

Native relay cancellation retains its original response-writer ownership until
all started body/deadline callbacks finish. A downstream connection's later
request cannot inherit an earlier cancellation deadline; revoked tokens fail
without another key read or upstream attempt. See the
[relay contract](cmds-delidev-proxy-contract.md).

### Codex follow-up execution

Native failure/interruption stays paused until explicit Resume, and uncertain acceptance/cleanup requires recovery. Current restrictions and the retained account connection still apply (original unless changed by the explicit stopped Codex API operation); changed Agent/templates never replace the first snapshot or rerun routing. Every turn has a fresh execution/job/grant and retains its exact predecessor before resuming the original private native history. The pinned Codex API profile exposes `session steer --id SESSION --input-id INPUT --revision INPUT_REVISION --execution-id EXECUTION --turn-id TURN`. Native acknowledgement or exact history proof removes FIFO eligibility; definite rejection leaves the entry queued, and uncertainty triggers automatic native inspection followed by paused recovery if still inconclusive. Late proof preserves the earlier observation and never resumes execution. See the session contract for concurrency, current authority, bounds and journal ownership.


Question and approval response controllers now automatically inspect native state after uncertain pipe delivery. Generic resource lists bound each page by both count and encoded bytes. ### Local Worker registration and controller lifecycle
`worker pair-local [--worker-dir PATH]` explicitly creates or reuses a separate Worker registration against the existing same-owner loopback server. It journals the original grant and pairing request, checks exact server/version/type on reuse, and refuses revoked, foreign, damaged or incompatible identities. It cannot start the server or accept remote/token-stdin authority. The default scope is `<data-dir>/worker`; the desktop client remains independently paired.

`worker start --detach` reserves a UUID-v7 controller generation, launches the same CLI with private log redirection and waits up to 15 seconds for its authenticated first attachment. Ordinary `worker start` remains foreground and participates in the same lifecycle. Retries reuse a reserved or active generation without launching a duplicate. A reserved child cannot cross its start barrier after explicit cancellation or supersession. An existing legacy active Worker without lifecycle evidence is preserved. Server instance leases remain authoritative: a replacement may need to wait for the previous 45-second lease and bounded reconnect backoff, so startup timeout retains `starting` rather than claiming failure or stealing authority.

`worker status` reads bounded private lifecycle evidence and exclusive controller ownership. `worker stop --generation UUID-V7` durably requests cancellation of exactly the observed generation, waits up to 15 seconds for joined controller exit, and remains usable while the server is offline. Status probes and startup share the lifecycle barrier so a probe cannot steal the new process lock. A previous stop cannot cancel a replacement; explicit stop of a reserved child rejects its delayed launch. Missing process ownership is `uncertain`, never an exit or native cleanup proof. The short interval after joined exit publication but before the original process lock closes stays `stopping`; readers must wait for that lock release rather than misclassify the publication barrier as lost ownership. Explicit replacement archives superseded infrastructure evidence and leaves every job/workspace/native journal intact. Startup/status/stop never open an inbound Worker port, send a PID signal, automatically resume sessions or erase a registration. Controller exit, server connectivity and per-session cleanup are separate facts. Quitting the desktop or its short startup command leaves a detached Worker alive; no automatic Worker-process restart or remote setup is implied by this controller boundary. Optional current-user OS registrations are exposed separately through the [user-service contract](cmds-delidev-user-services-contract.md).

### Final shutdown and explicit restart ownership
Detached `server start`/`ensure` holds controller/lifecycle serialization, probes compatibility and then joins the original private store lock before writing a new running intent or spawning a child. Endpoint-file removal can precede final database cleanup and cannot authorize replacement by itself. Waiting is cancellable and bounded to five seconds; a still-owned scope returns an explicit conflict without changing intent or signaling the original process. Release the provisional store lock while lifecycle serialization is still held, then let the validated child acquire its ordinary startup/store ownership. Automatic startup continues to respect stopped intent and original configuration.

The same question/approval CLI commands now accept original OpenCode direct responses through disjoint JSON: `{"opencode":{"answers":[["First"],[]]}}` preserves one ordered row per original question, and `{"opencode":{"decision":"once"}}` grants one original permission request. Inspect the original native proposal/revision before responding; there are no invented per-question IDs. Preserve empty-string choices versus explicit unanswered rows and native multiple/custom flags. Dedicated Worker claims, exact native body digests, HTTP delivery, original native reply acceptance and request closure remain independently retained. Exact server receipt/outbox retry never resends a native reply or clears earlier uncertainty. The same disjoint JSON also supports native `always`/`reject`, optional `feedback` on rejection and question `reject:true` instead of an answer matrix. Automatic native policy closure is retained independently without another response. The original production Worker now schedules these controls and targeted Stop under its authenticated job lifecycle. Public first dispatch now accepts the exact verified default OpenCode Build/Plan Chat Completions profile. Protected responses, continuation and remaining native profiles stay pending; see the harness and session contracts.

## Current Agent Worker saves

`agent create|edit|save` uses `SaveAgentWorker`. Single-source documents require
`--model-revision N` for their canonical `model_id`, or `--native-model-id ID` for
an exact native selection. Ordered-source documents use `--route-models-file PATH`
instead. The bounded JSON file contains one selection per route, in source order:
`{"model_id":"UUID","model_revision":N}` or `{"native_id":"exact-native-id"}`.
Canonical IDs must match the document and include their current revision; native
selections have no canonical revision. Both current Agent formats require at
least one account in every source. All account/model validation and Worker/model
saves share one receipt transaction. Generic configuration saves cannot write
Agents. Exact retries retain their request ID, document and selections.

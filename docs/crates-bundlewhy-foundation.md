# bundlewhy Rust foundation

## Scope

`crates/bundlewhy` owns the `bundlewhy` binary: CLI, project and engine detection, adapter process lifecycle, analysis rules, size measurement, result bundle storage, the loopback Connect server and self-contained HTML export. It owns and embeds the collector adapters in `crates/bundlewhy/adapters` (dependency-free Node.js ESM, kept inside the crate so Cargo change detection selects only this crate when they change) and the built UI document from `apps/bundlewhy-web`.

## Runtime and Language

Rust (workspace edition) with tokio, hyper 1 and serde. The analyzed project's build runs in Node.js 22.18 or newer through the adapters (the first 22.x release that strips TypeScript types by default, which TypeScript Rspack configurations require). Rust is a documented deviation from the repository Go default; see [the project index](project-bundlewhy.md).

## Users and Operators

Application developers analyzing a trusted local Vite or Rspack project, and maintainers validating fixtures and real applications. Support is through GitHub issues without an SLA.

## Interfaces and Contracts

### Commands

- `bundlewhy analyze --out-dir <dir> [--project <dir>] [--config <file>] [--config-name <name>] [--bundler vite|rspack] [--allow-unsupported-engine] [--no-open] [--no-serve] [--exclude-sources]` collects one diagnostic build into a new run directory, serves the UI and opens the browser unless `--no-open`. `--no-serve` exits after saving. `--out-dir` is required: results are stored only where the user chooses.
- `bundlewhy open <run-dir> [--no-open]` validates and serves a saved result bundle.
- `bundlewhy export <run-dir> --output <file.html> [--exclude-sources] [--force]` writes a self-contained interactive HTML report. It never writes through a symbolic link: an existing link is refused, a new file is created exclusively, and `--force` replaces a regular file by renaming a new file over it. Project, configuration and output paths must be valid UTF-8; others fail with `BW_USAGE` before any run directory is created. It states on stderr whether source content is included.
- `bundlewhy engines` prints the frozen engine compatibility matrix.
- Global flags: `--no-color` (also `NO_COLOR`), `--verbose`, `--help`, `--version`. Exit codes: `0` success, `1` failure, `2` usage error, `130` cancelled.

### Selection

The project defaults to the current directory. The bundler is detected from `package.json` dependencies (`vite`, `@rspack/core`) and configuration files (`vite.config.{js,mjs,cjs,ts,mts,cts}`, `rspack.config.{js,mjs,cjs,ts,mts,cts}`). Auto-selection happens only when exactly one bundler and one configuration file are candidates. Otherwise analysis fails with `BW_BUNDLER_AMBIGUOUS` or `BW_CONFIG_AMBIGUOUS`, lists the candidates and explains the selecting flag. Rspack configurations exporting several builds require `--config-name`. Library builds (`output.library` or a per-entry `library`), SSR and Node-target builds (including target arrays with a Node entry) are rejected before any rule runs, so their results carry no diagnostics, and Vite configurations with several Rolldown outputs fail with `BW_UNSUPPORTED_BUILD`. Node targets are also detected from the resolved compiler platform (defaults and Browserslist queries), and an entry function is resolved once before the build so per-entry `library` descriptions are seen. An Rspack `optimization.minimizer: []` counts as disabled minification, an explicit SWC minimizer with `compress: false`, `mangle: false`, any disabled compression pass (for example `compress: { dead_code: false }`) or a `keep_*` mangle option counts as non-default, and a pipeline with any JavaScript minimizer other than the default SWC one (for example `["...", custom]`) counts as a non-default minifier.

### Engine compatibility matrix (frozen for 0.1.0)

| Bundler | Package        | Version                     | Default JavaScript minifier          |
| ------- | -------------- | --------------------------- | ------------------------------------ |
| Vite    | `vite`         | `8.3.4` (Rolldown `1.2.13`) | Oxc minifier (`build.minify: 'oxc'`) |
| Rspack  | `@rspack/core` | `2.2.9`                     | `SwcJsMinimizerRspackPlugin`         |

An installed version outside the matrix fails with `BW_ENGINE_VERSION_UNSUPPORTED` before the build. `--allow-unsupported-engine` is the explicit selection that analyzes with that installed engine; the run records `ENGINE_SUPPORT_UNSUPPORTED_SELECTED`. A non-default minifier keeps module-graph categories but marks the minifier categories (dead-code elimination and name mangling) `UNAVAILABLE` with `BW_MINIFIER_NON_DEFAULT`; disabled minification produces a confirmed configuration diagnostic and `BW_MINIFICATION_DISABLED`, and marks dead-code elimination and name mangling not applicable.

### Diagnostic engine

The diagnostic build always runs the project's own installed engine with collection overrides recorded in `EngineIdentity.overrides`: Vite forces a bundlewhy output directory, `emptyOutDir`, source maps and a post collector plugin; Rspack forces production mode, a bundlewhy output path, `output.clean` and `devtool: source-map`. Findings describe that diagnostic build, `diagnostic_engine` is always true and the notice states that output equivalence with the original build is not guaranteed. Adapter identity is `bundlewhy-collector-vite` / `bundlewhy-collector-rspack` with an adapter version.

### Rules and coverage

Each rule has a stable identifier, a category, conditions with outcomes, evidence provenance and a corrective direction with safety conditions. Every rule has a fixture blocker and a counterexample.

| `vite/side-effect-retained`            | Vite   | Tree shaking          | Confirmed                                                                                    | Module rendered with no rendered exports while its exports exist                                           |
| `vite/tree-shaking-disabled`           | Vite   | Tree shaking          | Confirmed                                                                                    | Configuration sets `build.rolldownOptions.treeshake: false`; tree-shaking coverage is then not applicable  |

Inlining and constant folding are `COVERAGE_STATE_UNAVAILABLE` for both engines: neither engine exposes those decisions and no verified detector exists. Module concatenation is covered for both engines. Source-map `sourceRoot` and `sources` are joined with a single separator that never trims the root, so URL roots such as `webpack:///` keep their scheme. A failed run's engine identity leaves support unspecified because no version was discovered. A source binding named `eval` (a parameter, variable or function) makes `eval(...)` calls inside that binding's scope ordinary calls; shadowing is decided per call, so the source-scan fallback still reports a direct eval elsewhere in the module. `BW_MINIFIER_NON_DEFAULT` is reported only when minification runs. Missing source maps mark the affected chunk's attribution `UNAVAILABLE`, fall back to generated locations and record `BW_SOURCE_MAP_MISSING`. A partial collection keeps usable results, sets `RUN_STATUS_PARTIAL` and marks affected categories `COVERAGE_STATE_PARTIAL`; an emitted chunk that cannot be read marks dead-code elimination and name mangling partial. The env-condition scan and the source scan for direct `eval` ignore string, template, comment and regular expression literal text. Retained code alone is never reported as a defect.

### Dependency paths and locations

Dependency paths are the shortest static importer chains from an entry to the module (up to three). Dynamic `import()` edges are not part of a dependency path. Name-mangling checks consider every binding of a declaration (including `for … of` / `for … in` loop bindings) and function and arrow parameters (destructured, defaulted, rest and annotated), including comma-separated declarators and destructuring patterns. Before the adapter starts, `node --version` is probed and runtimes older than 22.18 fail with `BW_NODE_VERSION_UNSUPPORTED`. Saved bundles must use unique `d-<12 hex>` diagnostic IDs. TypeScript annotations on declared bindings are ignored when checking name mangling. Diagnostic IDs include the location column and the finding title, so distinct findings on one line stay separate. Cycles are excluded per candidate path, so distinct shortest chains through different importers are all kept. Locations use original source positions when a source map maps them; otherwise generated chunk positions. Snippets carry at most nine lines of 240 characters each.

### Sizes

Each emitted JavaScript chunk records raw, gzip (level 9) and Brotli (quality 11) bytes. When the chunk has a source map, generated bytes are attributed to sources by splitting the generated text at mapping boundaries; each byte belongs to at most one segment, so attribution never double counts and never exceeds raw bytes. Unmapped bytes are reported separately. Sizes are measurements, never savings.

### Lifecycle

Every run gets a new UUID v7 directory. Progress stages are published as they start and timed separately in the run log (`MEASURING` covers chunk size measurement): `DETECTING`, `BUILDING`, `COLLECTING`, `ANALYZING`, `MEASURING`, `SAVING` and `FINISHED`. Ctrl+C or `CancelRun` terminates the owned adapter process (on Unix, SIGTERM to its process group and, after the full three-second grace period, SIGKILL to the whole group even if the adapter already exited), writes a `RUN_STATUS_CANCELLED` bundle with `BW_RUN_CANCELLED` and keeps the `INCOMPLETE` marker. Cancellation stays available while analysis and measurement run (checked between chunks). Cancellation observed after collection, during analysis or measurement, also produces the cancelled result. Saved-run listings apply the same status normalization as opening a run. Exported reports are created exclusively (never through an existing file or symlink), with a numeric suffix when the name is taken. Adapter stdout lines longer than 1 MiB are discarded while the pipe keeps draining. A bundle left `RUNNING` by an interrupted process reopens as `RUN_STATUS_FAILED` with `BW_RUN_INTERRUPTED`. There is no automatic retry or resume; a retry is a new run. Project `package.json`, the selected configuration and lockfiles (the project's own and those of the nearest ancestor directory that has one, up to the repository root) are hashed before and after the build; a change is reported as `BW_PROJECT_MODIFIED`, downgrades a complete run to `RUN_STATUS_PARTIAL`, keeps the `INCOMPLETE` marker and makes `analyze` exit with a failure code.

### Error codes

`BW_USAGE`, `BW_PROJECT_NOT_FOUND`, `BW_BUNDLER_NOT_DETECTED`, `BW_BUNDLER_AMBIGUOUS`, `BW_CONFIG_NOT_FOUND`, `BW_CONFIG_AMBIGUOUS`, `BW_CONFIG_LOAD_FAILED`, `BW_BUNDLER_NOT_INSTALLED`, `BW_ENGINE_VERSION_UNSUPPORTED`, `BW_NODE_NOT_FOUND`, `BW_NODE_VERSION_UNSUPPORTED`, `BW_BUILD_FAILED`, `BW_COLLECTION_FAILED`, `BW_UNSUPPORTED_BUILD`, `BW_SOURCE_MAP_MISSING`, `BW_SOURCE_UNREADABLE`, `BW_MINIFIER_NON_DEFAULT`, `BW_MINIFICATION_DISABLED`, `BW_PROJECT_MODIFIED`, `BW_RUN_CANCELLED`, `BW_RUN_INTERRUPTED`, `BW_SCHEMA_UNSUPPORTED`, `BW_RESULT_INVALID`, `BW_OUTPUT_DIR_INVALID`, `BW_SERVER_BIND_FAILED`, `BW_BROWSER_OPEN_FAILED`, `BW_EXPORT_FAILED`, `BW_ACCESS_DENIED`, `BW_SOURCE_STALE`, `BW_SOURCE_NOT_FOUND`, `BW_RESULT_TOO_LARGE`, `BW_ACCESS_TOKEN_MISSING` (UI only). Each user-facing error prints the code, message and a recovery instruction.

## Storage

`<out-dir>/<run-id>/` contains `analysis.json` (versioned result bundle, `schemaVersion: 1`, at most 512 MiB: a larger result drops source content and snippets with `BW_RESULT_TOO_LARGE`), `run-summary.json` (small summary read by run listings, which select the newest 200 UUID directories before reading anything), `collect.json` (adapter collection), `build/` (diagnostic build output), `adapter/` (adapter scripts written for this run), `bundlewhy.log` (JSON lines) and `INCOMPLETE` while a run is unfinished. The result bundle contains the analysis (diagnostics, coverage, sizes, engine identity, safe configuration summary, problems) and source files with project-relative or dependency display paths, SHA-256 and content unless `--exclude-sources`. Results are kept until the user deletes them; bundlewhy never uploads or deletes them. Unknown schema versions fail with `BW_SCHEMA_UNSUPPORTED`; there are no migrations. This local storage is a documented deviation from the repository R2 default.

## Security

Project configuration, plugins and adapters execute with the user's permissions; bundlewhy supports trusted local projects and does not sandbox plugin filesystem or network effects. The server binds `127.0.0.1` on an OS-assigned port, requires a per-run 256-bit bearer token (delivered in the URL fragment), rejects requests whose `Host` is not the bound address and whose `Origin` is not exactly the server origin, and sends `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and a CSP without network sources. RPC methods take no filesystem paths: sources are looked up by bundle-local identifiers and runs by UUID within the output directory. Live source files are read only when they are regular files of at most 16 MiB inside the project root or module paths reported by the bundler; paths named only by a source map rely on its `sourcesContent`. Saved bundles are untrusted: `analysis.json` must be a regular file (never a symlink; opened with no-follow semantics on Unix) and is read through a bounded reader; structure, enum values, identifiers and display paths are validated, and stale checks read only project-relative paths without `..` that resolve (after symlinks) to regular files of at most 16 MiB inside the recorded project root. With `--exclude-sources`, a failed build saves only the error code and a generic message, because build errors can quote source code; details stay on the terminal. Source maps without any source-bearing mapping count as missing. A stale check that cannot verify a file (too large, special or outside the root) does not mark it stale; only removed or changed files are stale. Sources without a build snapshot whose live file is not text (an imported PNG, or any file that is not UTF-8 text without NUL bytes) and sources whose `sourcesContent` is a bundler-generated asset module are not freshness-checked: they keep their path and identifier for attribution, but have no stored content, no code snippet and no entry in the project-relative map used when a saved run is reopened, so they are never reported with `BW_SOURCE_STALE` (an asset module whose live file was removed still is). A generated asset module is `export default` followed by exactly one of: a single string literal (the `"__VITE_ASSET__<id>__"` marker of earlier Vite releases, an inlined `data:` URL, a `?url` path, or the text of a `?raw` or `?inline` import) or the `import.meta.ROLLDOWN_FILE_URL_<id>` placeholder Rolldown-based Vite releases emit. Every shape additionally requires an asset path: a file that is not JavaScript-family source, or a path whose import query contains the `raw`, `url`, `inline` or `no-inline` key (a fragment ends the query). Any other expression, or text after the complete expression, is ordinary code, and so is a string-only default export (including a marker-like string) in a script file without such a query. An ordinary text snapshot is always compared with the live file, so a changed source stays stale even when its live file became non-text. When a saved run is reopened, `mark_stale` also skips stored asset modules, so runs saved before this contract (which keep the generated module text and its hash) do not report unchanged assets as stale; a run saved with `--exclude-sources` has no stored text, so only a binary asset path (such as `.png` or `.woff2`) with non-text live bytes is skipped. Stored source text comes from the build's source-map `sourcesContent` when available, so the analysis describes the revision the bundler read; a live file that changed since then is marked stale with `BW_SOURCE_STALE`. Dependency display paths keep their full ancestry relative to the project root (for example `node_modules/a/node_modules/b/index.js` or a pnpm store path under `node_modules/.pnpm`), so nested and pnpm copies of the same package display distinctly; paths outside the project root use a `..`-relative form and never expose an absolute prefix. Source files are identified by their resolved path, not by display path. A module path that carries an import query or fragment (for example `/src/a.js?raw`) keeps it for identity, display and asset-module classification, but live reads, vetting and the project-relative map used when a saved run is reopened use the file that backs the module: an existing literal file name wins, otherwise the path without its query and then without its fragment is used, so the documented `?raw`, `?inline` and `?url` imports are not reported with `BW_SOURCE_STALE` merely because the query is not part of the file name. `--exclude-sources` also removes diagnostic snippets from result bundles and exports. Exported HTML embeds JSON with `<`, `>`, `&`, U+2028 and U+2029 escaped and a CSP that forbids network access. Reports that include source content are not claimed to be secret-free.

## Logging

`tracing` writes human-readable, ANSI-colored stderr logs by default (`--no-color` or `NO_COLOR` disables color, `--verbose` adds debug detail). Each run writes `bundlewhy.log` JSON lines with timestamp, run ID, stage, duration, engine versions and error codes. Logs never include source content, environment variable values, credentials or access tokens.

## Build and Test

Run root `cargo test` after Rust changes. Unit tests cover every rule with committed fixture collections for its blocker and counterexample, size attribution without double counting, schema rejection, result validation, path validation, token and Origin enforcement, HTML escaping and log redaction. `packages/bundlewhy` acceptance (`pnpm --filter @delino/bundlewhy test:acceptance`) runs real Vite and Rspack fixture builds through the binary and verifies project files stay unchanged. The UI document is embedded from `apps/bundlewhy-web/dist/index.html` when present at build time; otherwise development and test builds embed a minimal page that explains how to build it. Release-profile builds fail without the UI unless `BUNDLEWHY_ALLOW_MISSING_UI=1` is set for a build that is never distributed.

## Dependencies and Integrations

Consumes the [Connect protocol](protos-bundlewhy-v1-contract.md) through hand-written serde types that follow the proto3 JSON mapping, the [adapters](packages-bundlewhy-distribution-contract.md) and the [web UI](apps-bundlewhy-web-contract.md). Uses `sourcemap`, `flate2`, `brotli`, `sha2`, `uuid` (v7), `hyper`, `tokio` and `clap`.

## Change Triggers

Update this contract, the project index and the public docs when commands, flags, error codes, rules, the engine matrix or storage change. Update the protocol contract with Rust JSON types.

# bundlewhy Rust foundation

## Scope

`crates/bundlewhy` owns the `bundlewhy` binary: CLI, project and engine detection, adapter process lifecycle, analysis rules, size measurement, result bundle storage, the loopback Connect server and self-contained HTML export. It owns and embeds the collector adapters in `crates/bundlewhy/adapters` (dependency-free Node.js ESM, kept inside the crate so Cargo change detection selects only this crate when they change) and the built UI document from `apps/bundlewhy-web`.

## Runtime and Language

Rust (workspace edition) with tokio, hyper 1 and serde. The analyzed project's build runs in Node.js 22.18 or newer through the adapters (the first 22.x release that strips TypeScript types by default, which TypeScript Rspack configurations require). Rust is a documented deviation from the repository Go default; see [the project index](project-bundlewhy.md).

## Users and Operators

Application developers analyzing a trusted local Vite or Rspack project, and maintainers validating fixtures and real applications. Support is through GitHub issues without an SLA.

## Interfaces and Contracts

### Commands

- `bundlewhy analyze --out-dir <dir> [--project <dir>] [--config <file>] [--config-name <name>] [--bundler vite|rspack] [--allow-unsupported-engine] [--no-open] [--no-serve] [--exclude-sources]` collects one diagnostic build into a new run directory, serves the UI and opens the browser unless `--no-open`. `--no-serve` exits after saving. `--out-dir` is required: results are stored only where the user chooses.
- `bundlewhy open <run-dir> [--no-open]` validates and serves a saved result bundle.
- `bundlewhy export <run-dir> --output <file.html> [--exclude-sources] [--force]` writes a self-contained interactive HTML report. It never writes through a symbolic link: an existing link is refused, a new file is created exclusively, and `--force` replaces a regular file by renaming a new file over it. Project, configuration and output paths must be valid UTF-8; others fail with `BW_USAGE` before any run directory is created. It states on stderr whether source content is included.
- `bundlewhy engines` prints the frozen engine compatibility matrix.
- Global flags: `--no-color` (also `NO_COLOR`), `--verbose`, `--help`, `--version`. Exit codes: `0` success, `1` failure, `2` usage error, `130` cancelled.

### Selection

The project defaults to the current directory. The bundler is detected from `package.json` dependencies (`vite`, `@rspack/core`) and configuration files (`vite.config.{js,mjs,cjs,ts,mts,cts}`, `rspack.config.{js,mjs,cjs,ts,mts,cts}`). Auto-selection happens only when exactly one bundler and one configuration file are candidates. Otherwise analysis fails with `BW_BUNDLER_AMBIGUOUS` or `BW_CONFIG_AMBIGUOUS`, lists the candidates and explains the selecting flag. Rspack configurations exporting several builds require `--config-name`. Library builds (`output.library` or a per-entry `library`), SSR and Node-target builds (including target arrays with a Node entry) are rejected before any rule runs, so their results carry no diagnostics, and Vite configurations with several Rolldown outputs fail with `BW_UNSUPPORTED_BUILD`. Node targets are also detected from the resolved compiler platform (defaults and Browserslist queries), and an entry function is resolved once before the build so per-entry `library` descriptions are seen. An Rspack `optimization.minimizer: []` counts as disabled minification, an explicit SWC minimizer with `compress: false`, `mangle: false`, any disabled compression pass (for example `compress: { dead_code: false }`) or a `keep_*` mangle option counts as non-default, and a pipeline with any JavaScript minimizer other than the default SWC one (for example `["...", custom]`) counts as a non-default minifier.

### Engine compatibility matrix (frozen for 0.1.0)

| Bundler | Package        | Version                     | Default JavaScript minifier          |
| ------- | -------------- | --------------------------- | ------------------------------------ |
| Vite    | `vite`         | `8.3.4` (Rolldown `1.2.13`) | Oxc minifier (`build.minify: 'oxc'`) |
| Rspack  | `@rspack/core` | `2.2.9`                     | `SwcJsMinimizerRspackPlugin`         |

An installed version outside the matrix fails with `BW_ENGINE_VERSION_UNSUPPORTED` before the build. `--allow-unsupported-engine` is the explicit selection that analyzes with that installed engine; the run records `ENGINE_SUPPORT_UNSUPPORTED_SELECTED`. A non-default minifier keeps module-graph categories but marks the minifier categories (dead-code elimination and name mangling) `UNAVAILABLE` with `BW_MINIFIER_NON_DEFAULT`; disabled minification produces a confirmed configuration diagnostic and `BW_MINIFICATION_DISABLED`, and marks dead-code elimination and name mangling not applicable.

### Diagnostic engine

The diagnostic build always runs the project's own installed engine with collection overrides recorded in `EngineIdentity.overrides`: Vite forces a bundlewhy output directory, `emptyOutDir`, source maps and a post collector plugin; Rspack forces production mode, a bundlewhy output path, `output.clean` and `devtool: source-map`, and appends an observation-only `RsdoctorPlugin` (export usage graph) after the project's own plugins. The plugin changes no build output and never replaces the project's engine; the added plugin is recorded as a collection override. Vite keeps a configured relative or absolute root and uses the selected project directory only when the configuration has no root. The Vite adapter synchronizes each known root protection snapshot with the Rust supervisor before loading user configuration or starting Vite. A plugin `config` hook that selects a different root is rejected with `BW_UNSUPPORTED_BUILD` because that root could have changed before it was known and hashed; select the final root in the Vite configuration instead. Findings describe that diagnostic build, `diagnostic_engine` is always true and the notice states that output equivalence with the original build is not guaranteed. The Vite adapter imports the entry that the project's `require.resolve("vite")` selects and normalizes the module namespace: it uses named exports when present and otherwise the `default` export, because a CommonJS entry (Vite 5) exposes the API only there. It validates that `loadConfigFromFile`, `build`, `mergeConfig` and `createLogger` are functions before it evaluates any project configuration; a missing function is an adapter/engine compatibility failure reported as `BW_COLLECTION_FAILED` (the recovery points to the supported Vite version or a compatible adapter), never as `BW_CONFIG_LOAD_FAILED` or `BW_BUILD_FAILED`. `BW_CONFIG_LOAD_FAILED` stays reserved for errors thrown while Vite evaluates the project configuration. When a configuration file is selected, the adapter evaluates it exactly once, with `loadConfigFromFile`, to capture the root and classify configuration errors, then starts the build with the loaded config object and `configFile: false`, so a stateful configuration factory (one with process-level side effects or one-shot resources) is never evaluated a second time. A leading `bundlewhy:config-file` plugin (`enforce: "pre"`) sets `resolvedConfig.configFile` and `configFileDependencies` to the loaded file in its `configResolved` hook, which runs before the project's plugins read them (React Router's Vite plugin requires `configFile`). Without a configuration file nothing is loaded and no such plugin is added. The Rspack adapter likewise imports the configuration module and calls a configuration function once. An error thrown during the build, including from a plugin hook, is `BW_BUILD_FAILED` with recovery text that names the diagnostic-build difference (forced output directory, source maps and collector plugin) instead of asserting that the project's own build is broken. Adapter identity is `bundlewhy-collector-vite` / `bundlewhy-collector-rspack` with an adapter version.

Collection (Vite adapter version `5`, `collectVersion` stays `1`): each collected chunk also records `imports`, `externalImports` and `dynamicImports`. `imports` and `dynamicImports` are the chunk files from Rolldown's `OutputChunk` static and dynamic import lists. Rolldown mixes emitted chunk files with external specifiers in these lists, so `externalImports` names the `imports` entries that refer to an external module, found by module id (an external has no source in `getModuleInfo()`) or by its `output.paths` replacement when `output.paths` is a record (plain data, read as is). The adapter never calls a function-valued `output.paths`: the bundler already called it while it rendered the chunks, a stateful function can answer differently when it is called again, and a replayed answer would name an external the output does not contain while missing the one it does. For a function (and for any value that is neither a record, `undefined` nor `null`) the rendered external names are unknown, and an `imports` entry that names an emitted chunk cannot be told from an external rendered under the same string. The adapter then lists every `imports` entry of every chunk in `externalImports` (an entry that names no emitted chunk is an external leaf either way) and reports the situation in a progress message; the choice is made for all chunks of the build rather than only for colliding names, because every internal edge is an entry that names an emitted chunk. The adapter does not wrap or memoize the user's callback to recover the mapping, so the user's build behavior is untouched. All three fields are optional; an older collection omits them, which differs from an empty list. The adapter snapshots modules and chunks in a post-ordered `generateBundle` hook (`order: "post"`, in addition to the plugin's `enforce: "post"`), then replaces every chunk's `imports`, `externalImports` and `dynamicImports` with the lists of the bundle that `build()` returns, which is the bundle after every `generateBundle` hook, including hooks of output-only plugins (`output.plugins`) that run after the collector whatever their ordering. The final lists are only valid together with the snapshot's module placement (each chunk's `modules` and each module's `chunks`), so the adapter also compares, for every chunk file, the module ids of the finished chunk with the snapshot as a set (order is not placement), and the SHA-256 digest of its generated `code` with the digest taken in the collector's hook, because a later hook can edit `OutputChunk.code` without `OutputChunk.modules` following; any changed, unreadable or missing code counts as a difference. An output-only plugin can move a module to another chunk, remove it from the output or add one while it keeps every chunk file name; combining the final edges with the stale placement would describe two different output graphs. When the finished bundle cannot be read as a single output, its chunk files differ from the snapshot, or any chunk's module membership or generated code differs from the snapshot (a chunk without a readable module record counts as different), the three lists are omitted for every chunk, all or nothing; the adapter does not rebuild partial module facts from mixed snapshots and leaves the snapshot placement, sizes and source maps unchanged. The analysis treats a chunk without lists as missing chunk import data (never as proof) and does not trust the placement of such a chunk either: the graph search needs both `imports` and `externalImports` on every chunk it visits, including the requesting chunk and the chunk that holds the target, before it accepts that chunk as holding the target, so a stale same-chunk membership cannot be proven either. When the final membership is unchanged the final import lists replace the snapshot lists as before. `vite/ineffective-dynamic-import` evaluates every dynamic importer of a module separately against the emitted chunk graph through one classification (`classify_requester`) with three outcomes. Proven: every chunk that holds the importer also holds the module or reaches the module's chunk through trusted `imports` edges (transitively); the finding keeps one route per requesting chunk and lists all of them in an `emitted chunk graph` evidence entry. Separate chunk: the graph is complete for every requesting chunk and at least one reaches the module only through a dynamic request; the importer is named as not affected. Unknown: the importer is not emitted, the module has no chunk, or a chunk on the way has no `imports` or `externalImports` data or an ambiguous edge; the importer is named as neither reported nor ruled out, in an `Unavailable` evidence entry, and is never presented as unaffected. An `imports` entry is a trusted edge only when it names an emitted chunk and is not listed in `externalImports`; an entry that names no emitted chunk is an external leaf, and an entry that names an emitted chunk and an external module is ambiguous and makes the search incomplete. With a function-valued `output.paths` no static edge between emitted chunks is trusted, so a requester that does not already share its chunk with the module is Unknown (precision loss for those builds, never a false Confirmed finding); a requester whose chunk holds the module itself is still proven, since that proof needs no import edge, and a matching Rolldown log still reports the module as engine-reported evidence. Known limits: an external that Rolldown renders under a string other than its module id or its record `output.paths` replacement (for example a path made relative to the output) is read as an emitted chunk when that string equals a chunk file. The same collision in `dynamicImports` is not marked; that list only selects among copies of one module, where an extra name demands one more reached copy, so it can hide a finding but never create one. Module placement is compared by module id only: a change that keeps every chunk's module ids (for example a different rendered size) keeps the final lists. The finding wording follows the proven chunk layout (`ChunkLayout`) and never asserts more than the chunk graph shows: when every proven route stays in the requesting chunk (the module is folded into its importer's chunk), the title says the import `does not create a separate chunk`; when every route reaches another emitted chunk through static imports, the title says the import `does not defer loading`, the `The module is emitted in a chunk separate from the requesting chunk` condition is Met with the module's emitted chunk files, and the `The dynamic import loads that chunk only when it runs` condition is Unmet with the static-import route; mixed routes and engine-reported-only findings (no proven route) use the neutral `does not defer loading` title and make no claim about whether a separate chunk exists. HTML `modulepreload` links are not collected, so the loading claim rests only on static-import routes. The title is part of the diagnostic id hash, so ids of this rule differ from reports made before this wording change. A matching Rolldown `INEFFECTIVE_DYNAMIC_IMPORT` log still reports the module as engine-reported evidence. When the module is printed in several chunks (Rolldown's `inlineCommonChunks` copies a module into every chunk that uses it), the `import()` loads one specific copy, so the route is matched to that copy: when the requesting chunk's `dynamicImports` name copies of the module, `dynamicImports` is a per-chunk list rather than a per-request one, so a request is only associated with a copy when a dynamic target names that copy directly. When every dynamic target names a copy, each named copy must itself be reached through trusted `imports` edges (a route to any other copy proves nothing). When a collected `dynamicImports` list is empty, the request resolved to an already loaded copy and a route to any copy proves it. When any dynamic target names no copy of the module (for example a facade chunk that statically loads a different copy, directly or transitively), the request may load a copy that no route reaches and facade closures are not attributed, so the requester is Unknown even when other dynamic targets name a copy; it is named as neither reported nor ruled out in the `Unavailable` evidence entry and never yields a Confirmed source-only finding. Any unrelated lazy route of a requesting chunk therefore makes the multi-copy module Unknown for that chunk (conservative precision loss). A requesting chunk without collected `dynamicImports` is Unknown. Importer lists alone never prove the claim: a requester whose chunk, or whose target chunk, has no chunk import data is Unknown, including the same-chunk case (a collection from an older adapter version or one whose placement was invalidated proves nothing from the graph), and a module with no proven importer and no engine log is not reported. A matching Rolldown `INEFFECTIVE_DYNAMIC_IMPORT` log is independent of the chunk graph: it still reports the module as engine-reported evidence, with every importer named as neither reported nor ruled out when the graph data is missing.

Known limits: the adapter matches an external to an `imports` entry by module id or by its record `output.paths` replacement; a function-valued `output.paths` is never called and makes every static import ambiguous. When Rolldown renders an external under any other string that differs from its module id and that string equals an emitted chunk file, the entry is read as the emitted chunk. bundlewhy does not parse Rolldown's rendered import paths. Pinned by the `requester_classification_cells` test.

For `vite/side-effect-retained`, `renderedExports` lists only the exports that Rolldown renders as chunk-level bindings. An importer bundled in the same chunk can read a re-export facade, a default re-export, a directly exported component or a forwarded value without one, and the collection holds no per-importer binding data. The condition "No export of the module is used" is therefore Met only for a module that declares no export. For a module that declares exports it is Unknown, the finding is Inferred whatever the side-effect declaration says, the title and summary state only what Rolldown reported, and the direction asks to check the importers first instead of changing side-effect declarations. The declaration is still reported in its own condition. The title does not depend on the export-use state or the declaration, so a retained module keeps one diagnostic ID. The effective-declaration guidance below applies to modules that declare no export.

For `vite/side-effect-retained`, the effective side-effect declaration follows Rolldown's precedence, highest first: a `moduleSideEffects` value set by a resolve, load or transform hook, the configured `build.rolldownOptions.treeshake.moduleSideEffects`, the package `sideEffects` field, and then Rolldown's own analysis of the code. The collector records only what it can observe: the value that JavaScript hooks set (`getModuleInfo()`), the configured option evaluated for each module, and the nearest package `sideEffects` value. Vite's resolver is a native Rolldown plugin that reports a declared package `sideEffects` field as a hook value for the import it resolves (`true` for a `true` field or a matching list entry, `false` otherwise), and that value outranks the configured option. `getModuleInfo()` does not list it, and resolving a retained module's absolute ID again does not reproduce it, because Vite attaches it while it resolves the original import. The collector therefore does not infer it: when no JavaScript hook set a value and the package declares `sideEffects`, the condition is Unknown whatever the declaration and the configured option say, and the direction names the package entry to narrow or remove. The collector evaluates the configured option for each module: `false`, a module ID list (an empty list included, which marks no module as having side effects), a rule list and `"no-external"` decide, while `true` and a rule list without a matching rule give no verdict; a function is not evaluated and leaves the declaration unknown. Without a JavaScript hook value, the option decides for a package that declares nothing; with no verdict from the option either, the module is undeclared and Rolldown analyzes the code. A hook value of `true` is not a declaration: it asks Rolldown to analyze the code and skips both the configured option and the package field, so the finding is inferred, the "declared side-effect free" condition is unmet, and the direction names the plugin that returns the value. An effective `false` reports the condition as met. Rolldown may discard such a module even when its code has side effects, so the finding is inferred from another use of the module (a side-effect import, namespace or re-export use, or an entry) and does not claim top-level side effects. An effective `"no-treeshake"` from a hook or `true` from the configured option reports the condition as unmet, with Confirmed status only for a module that declares no export; a module that declares exports stays Inferred. Any unrecognized hook value also leaves the condition unknown, and the direction names the unresolved source (the plugin hook, the configured option or the package declaration). The finding title does not depend on the declaration, so a retained module keeps one diagnostic ID when its declaration changes.

The `vite/side-effect-retained` rule also checks the final emitted code. Rolldown's `renderedLength` is measured before minification, so the diagnostic labels it intermediate Rolldown output and never treats it alone as proof that the module is shipped. For each chunk that lists the module, bundlewhy attributes the chunk's generated bytes to source files through the final chunk source map. When every listing chunk has a usable source map and none attributes a generated byte to the module (the source is listed with zero segments or is missing from the map's `sources`), minification removed the module and the rule reports nothing. When some chunk attributes generated bytes, the finding adds a Confirmed `final chunk source maps` evidence entry with the byte count. A source-map source belongs to the module only when its file, its import query and its fragment all match the module's resource identity exactly (`Comp.vue?vue&type=style` is a different resource from `Comp.vue`, and `a.js?raw#one` from `a.js?raw#two`). A source that omits the query or the fragment of the module is a different resource, never a match, even when no other module shares the file. An exact match is Confirmed only when no other collected module could own the same source: for a module with a fragment, none has the identical identity; for a module with a query and no fragment, none shares the file and query under any fragment; for a module with neither, none is backed by the same file. Final emission is unverified, never absent, when a listing chunk is unreadable or has no usable source map, when a chunk leaves generated bytes without any source mapping and attributes none to the module, when the map attributes bytes only to the same file under a different, omitted or additional query or fragment, or when an exact match is shared with sibling modules. An unverified finding is always Inferred, even when the effective declaration would otherwise confirm it, its evidence states that final emission is not verified, and its `No rendered code remains` condition is Unknown (Unmet only when final bytes are attributed to the module). Each chunk's per-source attribution is computed once and shared by size measurement and this check.

Resource identity is decided in one place for collected modules, source-map sources and shared-resource counting: the module identifier or source path is split into a backing file, an import query and a fragment. Query and fragment are part of the identity because bundlers derive different modules from one file with either; only the file names the backing file on disk.

| Input                         | File           | Query        | Fragment                                                                                                                                                                         |
| ----------------------------- | -------------- | ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/app/a.js`                   | `/app/a.js`    | none         | none                                                                                                                                                                             |
| `/app/a.js?raw`               | `/app/a.js`    | `raw`        | none                                                                                                                                                                             |
| `/app/a.js?raw#one`           | `/app/a.js`    | `raw`        | `one`                                                                                                                                                                            |
| `/app/a.js#one`               | `/app/a.js`    | none         | `one`                                                                                                                                                                            |
| `/app/a.js#one?raw`           | `/app/a.js`    | none         | `one?raw` (a `?` after `#` belongs to the fragment)                                                                                                                              |
| `/app/a.js?` and `/app/a.js#` | `/app/a.js`    | empty / none | none / empty                                                                                                                                                                     |
| `\0virtual:a?x#y`             | `virtual:a`    | `x`          | `y` (leading NUL bytes mark a virtual module, which has no backing file)                                                                                                         |
| `C:\app\a.vue?x#y`            | `C:/app/a.vue` | `x`          | `y` (a drive-letter or UNC path uses `\` as separator on every host, so Windows source maps compare equal to collected paths; a `\` in a POSIX path stays a file-name character) |
| `css-loader!/app/a.vue?x`     | `/app/a.vue`   | `x`          | none (the loader prefix ends at the last `!`)                                                                                                                                    |

The query starts at the first `?` and ends at the first `#` after it; the fragment starts at the first `#`. File paths are then lexically normalized. A webpack-style source (`webpack://<namespace>/<path>`) carries the module file only, so its query and fragment are dropped and it matches a module with a query or fragment only as unverified. The number of modules a map source could stand for is counted at the specificity of the module: by file for a module without query and fragment, by file and query for a module with a query only, and by full identity for a module with a fragment. The same count decides the "share the resource" outcome above, so two modules that differ only by fragment never both claim the bytes of one map source.

Source maps that omit the query or fragment of a derived module therefore leave the module unverified (Inferred) instead of attributing the file's bytes to it, even when no sibling shares the file. Emitted-code requirement of `minifier/direct-eval-blocks-mangling`: a direct eval call in the original module source is only a candidate, because the build can remove it before output (for example `return value; eval(value);`). The rule scans every chunk the module is listed in with the same call classifier as the source scan (strings, comments, regular expressions, shadowing and method declarations are not calls) and keeps only the calls attributed to the module: the chunk source map must attribute the call's generated position to the module's resource (file, import query and fragment, with the sharing rules of the final-emission check), mapped positions are the only attribution. A direct eval call in a chunk without a usable source map is never attributed to a module, whether the chunk lists one module or many, whether the module is printed once or in several chunks, and whatever the call counts are: the chunk can hold copies of a module, code of other modules, or code that a banner, a runtime or a late output plugin injected, and being the only listed module does not prove ownership of generated bytes. Such a call, a call whose position no mapping covers, a differing resource query, a resource that other collected modules share, a listed chunk that cannot be read and a module that no output chunk lists are unverified, never proof of absence. An unverified copy stays listed next to the attributed calls of another copy: it adds an Inferred `emitted chunk scan` entry, and it keeps the finding even when the attributed copy mangled its names, because the other copy may still spell them. A map-less chunk that holds no direct eval call at all still proves the build removed the call from that chunk. Retained names are counted only in chunks that hold an attributed call, and within such a chunk only at positions the source map attributes to the module's resource (file, import query and fragment), so a name that a sibling module of a shared chunk spells the same way, or that no mapping covers, never supports the finding. A chunk without a usable source map is never counted for retained names; when such a chunk holds a direct eval call, an Inferred `generated chunk text` evidence entry states that the names were not counted there. Without an attributed call no chunk is scanned for names at all, so a name in a copy that holds no call is never evidence against a call in a different copy. When any copy is unverified and no name was counted in a chunk with an attributed call, the `Declared names are shortened in the output` condition is Unknown and states the unverified reasons; it is Unmet only for a retained name in such a chunk, and the finding is omitted only when every copy is verified and the attributed copies retain no name. Engine-reported `EVAL` logs and Rspack eval bailouts are emitted while the engine scans modules, before tree shaking and minification, so they do not prove emission either: with every chunk checked and no attributed call, the finding is omitted even when the engine reported eval; when attribution is unverified, an engine-reported eval keeps the finding as Inferred with an Inferred `emitted chunk scan` evidence entry that states the limit, whatever the chunks hold (no listed output chunk, an unreadable chunk, a call in an unmapped segment, a chunk without a usable source map); that path does not depend on retained names or on a chunk without a source map being present. A source-scan-only candidate is omitted. The finding is located at the first attributed emitted call, not at the first candidate of the engine log or the source scan, because the build can remove that candidate while a later call survives: for a call attributed by the source map, the original location is the position the map gives the emitted call and the generated location is its chunk position; without an attributed call (every call sits in a chunk without a usable source map, or the emitted code cannot be checked) no emitted position is claimed from call counts: the finding has no generated location, and its location is the original-source candidate: the engine-reported line and column, else the first source-scan call, else the first line of the module file, shown with a snippet of the module source. That location has kind original but is a candidate only; it is not derived from the emitted code. Evidence keeps the roles apart: `bundlewhy source scan` is the Inferred, noncausal original-source candidate (original location), `emitted chunk scan` is the Confirmed blocker evidence with the generated position of the emitted call (diagnostic `generatedLocation`), and `generated chunk text` lists the retained names. The status is Confirmed only when an engine report and an attributed emitted call are both present.

Known limits of the direct-eval source scan: it is a lexical scan, not a TypeScript parser. One recognizer finds `namespace` and `module` bodies for every `var`, exported-member and nested-declaration decision. It accepts Unicode identifier names, dotted names and quoted ambient module names (`declare module "pkg" {}`), and it requires the keyword and the name or literal on the same line, as TypeScript does, so `module` followed by a line break stays an ordinary expression and block. Whitespace and same-line comments between the keyword and the name are trivia (`namespace/* note */N {}` is a declaration), while a comment that contains a line terminator counts as a line break. `export` may be followed by the modifiers `declare` and `async` in any order before the declaration keyword (`export async function eval() {}`), through one shared table. Namespace names may spell identifier characters with Unicode escapes (`namespace \u004e {}` and `namespace \u{4e} {}`); the recognizer decodes each escape and accepts the name only when every escape is a valid scalar value that is an identifier start (first position) or identifier part (later positions) by the ECMAScript `ID_Start` and `ID_Continue` properties (plus `$`, `_`, ZWNJ and ZWJ), not the stricter `XID_*` sets, so `namespace \u037a {}` is a declaration, while malformed sequences such as `\u004`, `\u{}` or `\u{110000}` and escapes of non-identifier characters leave the braces an ordinary block. This applies only to namespace names: the single-parameter arrow recognizer still reads literal identifier characters. Declarations merge when their written qualified names match (quoted module names match after their quotes are removed, without decoding escapes, and escaped identifier names match by their written spelling, so `namespace \u004e {}` does not merge with `namespace N {}`). An exported `var`, `let`, `const` or `function` named `eval` is visible in every merged declaration of its namespace; a non-exported binding stays in its own body. A nested namespace merges across outer declarations only when it is exported. An ambient namespace body is an export context, as in TypeScript: a body declared with `declare` (including `export declare`, where `declare` must share its line with the keyword), a body with a quoted module name, and a body nested in an ambient namespace export every member and nested namespace implicitly, so `declare namespace N { var eval: any; }` shadows a call in `namespace N { eval(code); }` in any order of the declarations and for `module` too. An ambient body that contains an export declaration or export assignment among its own statements (`export {}`, `export { a }`, `export * from "m"`, `export type { T }`, `export = value`, `export default value`) stops exporting implicitly, and only members with an explicit `export` modifier stay exported. A property named `export` after a dot (`x.export`, `x. export`, or a dot followed by a comment or line break) is a member access, not an export statement, and an identifier that ends in `$export` is not one either. After `export default`, the words `class`, `function`, `interface` and `enum` and a decorator start a declaration, while `async` and `abstract` do so only when `function` or `class` follows on the same line (a comment that contains a line break counts as a line break); otherwise they are identifier expressions, so `export default async;` is an export assignment. A binding in a non-ambient namespace without `export` stays private. The scan does not recognize `declare global` blocks or the outer exports seen by the body of a dotted name such as `namespace N.M`, and it compares quoted module names without decoding escapes. A `var` named `eval` in a construct that is not recognized keeps the whole-source boundary and suppresses the finding elsewhere, and a call that a missed merge should have shadowed is reported as an Inferred finding. Unit tests pin each of these limits.

Known limits of the comment, literal and direct-eval scans, which stay lexical. When a case cannot be decided without a parse, the scan takes the conservative direction: the finding is omitted or stays Inferred rather than invented.

- Identifier escapes such as `\u0069f` are not decoded, so they are never keywords, and `\u0061sync` or `aw\u0061it` never makes `await(` an operator.
- `await(` is the unary operator in a module (a chunk with an `import` or `export` declaration or `import.meta`) and inside the body of an `async` function, arrow or method, and a call to a function named `await` elsewhere. One token pass per chunk decides this for the branch-evidence scan, and the scan reads every other `await` as the operator. The parameter list of a plain `function` (`function (`, `function name (`, `function* (`, `function* name (`) is not an async context even inside an `async` function, so `await(` in a default initializer (`async function outer() { function inner(x = await(f) ? 1 : 2) {} }`) stays an ordinary call, including in nested parentheses and brackets of the initializer; a property named `function` (`obj.function(`) is not the keyword, an `async function` header keeps the async context, and the enclosing async context resumes after the nested function. Method and arrow parameter lists are not reset. Whether a `{` after `)` is a function body is decided from the tokens before it: a header that is not a plain `function`, method or arrow header, such as a return type annotation (`async function f(): T {`), is read as a block, so `await(` inside it stays an ordinary call. A method body exists only in an object literal or class body; when the enclosing brace cannot be classified, the brace is read as holding members and `await(` inside it stays an ordinary call. The initializer of a class field (`field = value`, also `static`, private and computed-name fields) is read as a separate non-async function: `await(` in it is an ordinary call in a script even when the class is nested in an async function, because the surrounding async state is not inherited. The initializer starts at the first `=` directly inside a class body and ends at `;`, at a line break that ends the statement by automatic semicolon insertion, or at the closing brace of the class body. A computed key (`[await(x)] = 1`), a method body, a later member and an async function, arrow or method nested in the initializer keep their own contexts; a class nested in an initializer inherits the initializer's context, and a static block is not an initializer. In a module `await(` stays the operator. A concise arrow body ends at a line break by automatic semicolon insertion. Like `return` and `throw`, `yield` is a restricted production, so a line break after it always ends the statement and the next `await(` is outside the arrow body (`const g = async () => yield` + line break + `if (await(x)) run()` reads `await(` as a call); a continuation token such as `+` or `??` on the next line keeps the body open, and so does a slash (`var yield = 1` + `const g = async () => yield` + line break + `/ 2 / await(x)`), because `yield` is an identifier in a script and the slash divides. In a generator the same slash starts a regular expression; the scan cannot tell them apart without a parse, so it keeps the body open, the direction that was in place before `yield` became a restricted production. A brace after a `case` clause head or `default:` is a statement block, so an `if` inside it keeps the enclosing async context. The clause head is read with comments as blanks and a string, template or regular-expression literal as one operand: trivia between `case` and its expression (`case/*c*/1:`, `case/*c*/ 1:`, `case/*;*/1:`) and a literal or parenthesized expression without whitespace (`case"a":`, `case(1):`) do not change the decision, and `default/*c*/:` is still `default`. `case` must be followed by a character that cannot continue an identifier and by an expression, so `casey:` and a property named `case` (`{ case: {`, `{ case/*c*/: {`) are not clause heads. Known limit: the clause head is read back only to the previous `{`, `}`, `;` or line terminator outside a comment or literal, so a line break between `case` and its expression (`case\n1:`, `case // c` + line break + `1:`) is not recognized and the block is read as holding members, which keeps `await(` an ordinary call.
- A comma inside TypeScript type arguments in an arrow body (`(eval) => f<A, B>(eval(code))`) looks like the end of the body, so the call stays an Inferred finding. A method declaration named `eval` (`eval(code) {}`, with `async`, `*`, `static`, `get`/`set`, access modifiers, a decorator on the same line and a TypeScript signature) is not a call. One rule set decides it, and an `eval` name is skipped only when both parts match unambiguously. **Signature:** after the name come an optional balanced type-parameter list (`eval<T extends { a: 1 }>(value: T) {}`; brackets nest, and the `>` of `=>` closes nothing), a balanced parameter list, an optional return-type annotation and a `{` body. The annotation runs to the first `{` that does not start a type: a brace after `:`, `?`, `<`, `(`, `[`, `,`, `|`, `&`, `=>`, `extends`, `is` or `keyof` is an object type (`keyof { a: 1 }`) and is skipped as a whole, unless the keyword is a member name after a dot (`typeof obj.keyof {`), which ends the type so the brace is the body, so object branches of a conditional return type (`T extends U ? { a: 1 } : V`) never end it. A line break right after a type operator that needs a type (`extends`, `keyof`, `typeof`, `infer`, `unique`, `readonly`, `is`) continues the annotation (`T extends` + line break + `string ? T : never`). A signature without a body (an `abstract` or `declare` member, an overload signature, an interface or type-literal member) keeps its `eval(...)` reported: the annotation ends at the member's own `;`, at the `}` that closes its block, and at a line break that cannot continue the type (automatic semicolon insertion), so the body of the next member is never read as its body. **Context:** the name sits directly in a class body at a member position (after `{`, `;`, `}`, or after a complete field on an earlier line, a private name such as `#state`, a member access such as `a.b` and a postfix update such as `x = value++` included; a field named like an expression keyword, such as `typeof`, `void` or `await`, is a name when it starts its own member (an `accessor` modifier on the same line, as in `accessor typeof`, belongs to that member), so `class C { typeof` + line break + `eval(v) {} }` is a declaration while `x = typeof` + line break + `eval(v) {}` keeps the finding) or in an object literal after a comma or its brace. A class body is recognized by a `class` keyword in the header before its brace, read by character so non-ASCII names work; TypeScript type-argument lists with braces or defaults (`class C<T extends { a: 1 }> {`, `extends B<{ a: 1 }>`) are skipped as a whole. A class or function expression in the heritage clause (`class C extends class {} { ... }`, `class C extends function () {} { ... }`) has a body of its own: a `}` that closes a class expression whose `class` keyword follows `extends`, or a function expression (`async` and `*` included) that follows `extends`, is skipped, and the scan keeps reading the outer header. The same rule lets the `await` classifier see the members of such a class body, so an `async` method after a heritage expression keeps its async context. The scan runs on an explicit stack and remembers each decided brace pair, so a long run of sibling braces or deeply nested heritage expressions cannot overflow the stack. A class expression that does not follow `extends` ends the header. An object literal is recognized by the previous significant token before its brace: an opener or comma (`(`, `[`, `,`), a spread (`...`), any unary, binary, logical, nullish, assignment or conditional operator (`!`, `~`, `+`, `-`, `*`, `/`, `%`, `^`, `<`, `>` that is not a closing type-argument bracket or an arrow, `=`, `?`, `|`, `&`), the alternate of a conditional (`c ? a : {`), a property value (`:` inside an object literal), the `${` of a template substitution, the `{` of a JSX attribute container (`value={{ ... }}`: a brace after `name=`), or an expression keyword (`return`, `typeof`, `void`, `delete`, `new`, `in`, `of`, `instanceof`, `await`, `yield`, `throw`, `case`, `default`). After `return`, `throw`, `yield`, `break` or `continue` a line terminator, including one inside a comment, ends the statement, so the next brace is a block; the other keywords continue across line breaks. A `<` opens a type-argument list only when it directly follows a name (`f<A>`, `class C<T>`), so `left < right > { ... }` is a comparison chain and its brace an object literal. The same rule decides a call: `eval<T>(code)` with the `<` touching the name is read as a generic call (a comparison written without spaces, `eval<value>(code)`, keeps its finding), while `eval < value > (code)` and `eval <T>(code)` with whitespace or a comment before the `<` are comparison chains and are not reported (a TypeScript generic call written with a space is therefore missed, which is the safe direction); an arrow body is an object literal only inside parentheses (`() => ({ ... })`). A brace the scan cannot place (a statement block, a labeled block, a `case` clause, an arrow function body) keeps its `eval(...)` reported, so an undecidable case stays an Inferred finding. Known limits that need a real parser: a comparison whose `<` touches its left operand (`a<b>{ eval(x) {} }`) reads as a type-argument list and keeps its finding; a field that ends in `?` or `!` on its own line (`x?` + line break + `eval(v) {}`) is not recognized as complete and keeps its finding; none of these hides a real call. A real `eval(code)` call elsewhere in the same module, including inside a method body, is still reported at its own line and column. A slash after `)` or `}` divides, even where a statement block or `if (x)` makes it a regular expression.
- `await` is always read as the unary operator, so a script that uses `await` as a plain identifier and divides right after it (`await / 2`) reads the slash as the start of a regular expression; text up to the next slash is then ignored and a finding there is omitted rather than invented.
- A dot right after a number is a property access unless it ends a decimal integer literal. One helper decides it for every scan that reads the previous token: `0x1.eval(code)`, `0b1.`, `0o7.`, `017.` (legacy octal), `1n.`, `1e3.`, `1e+3.`, `1.e+3.`, `1.5.` and `.5.` use the dot as a property access (a member name is never a call to the global `eval`), while `1. in x`, `x = 1. + eval(code)` and `08.` keep the dot inside the number literal. `1..eval(code)` and `1 .eval(code)` are member accesses. A separator form (`1_0.`) reads like its digits. Unit tests pin each form.
- The scans that read masked code (comments, strings, templates and regular expressions replaced by spaces) keep every ECMAScript line terminator (LF, CR, U+2028 and U+2029) inside a masked range with its original bytes, so a line break inside a comment still ends a bodyless signature (`abstract eval(): void /*` + CR + `*/ run() {}`) whichever terminator it is, and the masked text keeps the length and UTF-8 validity of the source.
- Source snippets split lines on LF and CRLF only. For a source that uses a lone CR, U+2028 or U+2029 as line terminator, the reported line follows ECMAScript while the displayed snippet is not re-split.

The branch-evidence scan reads a generated chunk as a token stream without comments and builds one expression tree per expression. Every ECMAScript line terminator (`\n`, `\r`, U+2028 and U+2029), including one inside a block comment, still ends a restricted production such as `return`. The scan then asks, for every branch site, which retained environment reads may determine the truth value of the tested expression. Branch sites are the left operand of `&&`, `||`, `??`, `&&=`, `||=` and `??=`, the test of `?:`, the condition of `if`, `while`, `do ... while` and `switch`, and the test clause of `for`. A read in no tested value set has no branch evidence and produces no finding. A read in several sets takes the evidence of the first site in source order. Operator precedence, parentheses, automatic semicolon insertion, `in` inside a `for` initializer and the statement forms of the language follow the language rules. Parentheses and sequence expressions create no node of their own: `(e)` is `e` and `(a, b)` is `b`. Nodes are created only for expressions that can carry a read.

Branches found inside any node still guard their own reads, so `[read && run()]` and `` `${read ? a : b}` `` produce findings.

Statement and function rules:

- `{` starts a block where a statement starts and an object literal where an operand starts. A function body collects its `return` expressions; a `return` followed by a line terminator of any kind, including one inside a comment, returns `undefined`.
- A `return`, `throw`, `break` or `continue`, an `if`/`else` whose branches all end that way, or a block made of those, completes its path: the `return` statements after it in the same block are unreachable and contribute no value. Any other statement (a loop, a `switch`, a `try`, a label, an `if` without `else`) is taken to complete normally, so a `return` after it still counts.
- A `return` or `throw` in a `finally` block replaces the values returned by the `try` and `catch` blocks, so those values are dropped, unless the `throw` is caught inside the `finally` block (it sits in a `try` block that has a `catch` clause) and so does not leave it.
- A parameter list is parsed as expressions so that default values keep their branches. The initializer of a `for` head does not treat `in` as an operator; `for (x in y)` and `for (x of y)` are loops without a condition.
- A right-associative `**` chain is read iteratively, so a chain of any length is parsed without recursion.
- A construct that cannot be parsed is skipped token by token. Input nested deeper than the parser limit is skipped as opaque, so the scan never overflows its stack.

### Known limits

The scan is a lenient expression parser, not a full JavaScript parser. When a construct cannot be decided without runtime knowledge or a complete grammar, the read is not treated as guarded, so the finding is not produced and no branch is claimed. These cases are pinned by `read_propagation_known_limits_are_not_guarded` and `expression_tree_known_limits_are_not_guarded`:

- An object literal at the start of a statement is read as a block with a label (`{a: read}.a && run()`); the same literal after an operator, `(`, `=` or `return` is an object literal.
- An array element selected by a negative, string or non-literal index (`.at(-1)`, `["0"]`, `[index]`), or through a method such as `find`. `.at(N)` selects only from an array literal; an object with an own `at` method, or one returned where an array is expected, is not selected from.
- An object property with a computed key, a getter, an escaped key, or a property replaced by a later spread or computed key.
- A numeric key or selector whose property name is not known without evaluating it: a legacy octal literal (`010`), an integer beyond 2^53 and a value that JavaScript prints in exponent form (`1e21`, `1e-7`). Such a property may replace any earlier property, and such a selector selects nothing.
- A value that is stored in a variable and read later (`var o = [read]; o[0] && run()`), a function value invoked through `call`, `apply` or a variable, a function returned by an invoked function, and a value that passes through a promise.
- A selector is not carried through `&&`, `||`, `??` or arithmetic operands (`(a || {x: read}).x`), through a constructor that returns something other than an array or object literal (a call result, a conditional), or through a class constructor.
- A template literal with a substitution used as an arithmetic or unary operand (`` +`${read}` ``) or tested directly is not derived from its substitutions.
- A `finally` block with a conditional `return` or `throw` is treated like one with an unconditional one: the values returned by the `try` and `catch` blocks are dropped.

Vite's unresolved-environment detector confirms a generated `({}).NAME` against verified original source text. If a generated environment candidate maps to a source that is unreadable or has no build-time text snapshot, the candidate is skipped and dead-code elimination coverage is `PARTIAL` with a note that environment-variable findings may be missing. A guarded candidate that lies in a source-less (generated-only) segment of an otherwise usable source map, or that precedes the first segment of its generated line, has no original path to record: it is skipped without a diagnostic, counted by chunk file and generated offset, and dead-code elimination coverage is `PARTIAL` with a distinct note that guarded environment candidates have no source mapping. A source-map segment covers text only up to the end of its own generated line, so a segment that ends an earlier line never maps a later line; generated lines are separated by LF only, and a CR (including the one in CRLF) or U+2028 is an ordinary in-line character. This gap is not an unreadable-file problem, does not change the run status, and is not counted for chunks without a usable map (covered by the missing-map path), for tokens whose source is a bundler virtual module, for unrelated unmapped text, or for unguarded value-only reads. Other source gaps do not downgrade Vite dead-code coverage. Name-mangling coverage is partial when original source text is unverifiable for its direct-eval detector. Rspack's environment detector does not require that Vite-specific confirmation, so unreadable source text alone does not downgrade Rspack dead-code elimination coverage. Disabled minification remains `NOT_APPLICABLE`; a non-default minifier remains `UNAVAILABLE`.

#### Known limits of the environment-condition scan

The optional-chain guard of `minifier/unresolved-env-condition` is reported when the read itself (possibly parenthesized, with whitespace and comments around it) is the base of `?.`. A member, call or operand built from the read, such as `process.env.FLAG.length?.x`, `run(process.env.FLAG)?.x` or `(process.env.FLAG === "on")?.x`, is not the base. A string, template or regular expression literal, a called function expression or a class expression right before the parenthesis makes it a call on that value, so `/x/(process.env.FLAG)?.value` reports no finding. The expression tree keeps one statically nullish primary: `null`, alone or inside balanced parentheses. When `?.` follows it directly, JavaScript short-circuits the whole chain and evaluates no later key or argument, so the parser discards every following selector and call argument of that chain (`null?.[process.env.FLAG]`, `(null)?.a[process.env.FLAG]`, `null?.(process.env.FLAG)`), together with every branch site inside them (`null?.[process.env.FLAG && run()]`, `null?.(process.env.FLAG?.x)`), and a `&&`, `||`, `??`, `?:`, `if` or loop test around it gets no guard from them. Only `null` counts: a shadowable name such as `undefined`, a comma expression such as `(null, obj)`, `void 0` and a chain that already did something before `?.` (`null.x?.[key]`) are not recognized as statically nullish, and an unknown base (`obj?.[process.env.FLAG]`) and ordinary computed access (`obj[process.env.FLAG]`) keep their guard evidence. A separately evaluated read, for example `null?.[a] && process.env.FLAG`, is unaffected. Unit tests in `env_guard.rs` pin these cases. Any other guard on the same read, for example `process.env.FLAG?.x && run()`, keeps its own evidence, whatever the source order. The contextual words `of`, `yield` and `await` can also name a function, so `of(process.env.FLAG)?.x` is read as a call whose argument is the read and reports no finding, which can miss a true guard but never reports an argument as one. One keyword table in `crates/bundlewhy/src/rules/common.rs` decides whether a `/` after a keyword starts a regular expression literal; unit tests pin every table row.

### Dependency paths and locations

Dependency paths are the shortest static importer chains from an entry to the module (up to three). Dynamic `import()` edges are not part of a dependency path. Name-mangling checks consider every binding of a declaration (including `for … of` / `for … in` loop bindings) and function and arrow parameters (destructured, defaulted, rest and annotated), including comma-separated declarators and destructuring patterns. Before the adapter starts, `node --version` is probed and runtimes older than 22.18 fail with `BW_NODE_VERSION_UNSUPPORTED`. Saved bundles must use unique `d-<12 hex>` diagnostic IDs. TypeScript annotations on declared bindings are ignored when checking name mangling. Diagnostic IDs include the location column and the finding title, so distinct findings on one line stay separate. Cycles are excluded per candidate path, so distinct shortest chains through different importers are all kept. Export-level chains are a separate, additive evidence list described under Export usage paths. Locations use original source positions when a source map maps them; otherwise generated chunk positions. Snippets carry at most nine lines of 240 characters each.

### Export usage paths

Rspack diagnostics that already carry module dependency paths (`rspack/side-effect-retained`, `rspack/module-concatenation-bailout`, `rspack/module-in-multiple-chunks`) also carry an optional `Diagnostic.export_usage`. Vite diagnostics and rules without a module scope never carry it.

Collection (adapter version `2`, `collectVersion` stays `1`): the Rspack adapter taps the `moduleGraph` hook of `experiments.RsdoctorPlugin` (`moduleGraphFeatures: ['graph']`, `chunkGraphFeatures: false`, `exportUsageGraph: true`) and stores the optional collection field `exportUsage { available, reason, skippedEdges, skippedProviders, unattributedEdges, edges }`. `skippedProviders` is a list of `{ module, scope, export, edges }` sorted by module, scope and export: the dropped edges whose provider is that collected module, grouped by what is known about the provider export. `scope` is `named` (`export` holds the path), `module` (module or namespace scope, empty `export`) or `unknown` (the export could not be read, for example an empty path or tuple that is too short, empty `export`). An entry without `scope`, with an unrecognized `scope` or with a `named` scope and no readable path is read as `unknown`. `unattributedEdges` counts dropped edges whose provider module cannot be determined. Each edge is `{ consumer: { module, export }, provider: { module, export }, dependencyId, location }`; `export` is an export path array or `null` for module or namespace scope. Rspack reports edges as positional tuples whose module keys are only valid inside the same payload; the adapter maps keys to stats module identifiers through that payload. Plugin API access is internal and unstable, so construction, `apply`, every hook and the payload are guarded, and a failed build with the plugin is repeated once without it (see the adapter outcomes below).

Repeat build. A compiler can use up state that the project's configuration created, for example a plugin instance that rejects a second compiler, and every module that the configuration imports (directly, through a re-export or through a dynamic import) stays cached for the life of a Node.js process. The adapter therefore never repeats a build in the process that failed: it starts itself again as a repeat process, which loads the configuration and everything it imports from scratch, builds once without the observer, writes the collection and exits. Only the first attempt can fail because of the observer; the repeat decides the result.

Repeat process protocol. The parent writes one JSON line to the repeat's stdin (`{ "entry": ... }` or `{}`) and keeps the pipe open; the repeat ends when the pipe closes, so a parent that is killed (on every platform) does not leave the repeat running. The repeat shares stdout and stderr with the parent, so project output and protocol frames reach the same reader. It frames only an `error` event: the engine, progress and end events of the run come from the parent, so a reader sees one engine event, stages that never go back and one end. The exit status tells the parent what happened.

| no edge                      | No edge targets the module and no dropped edge could have targeted it | Rspack reported no export usage edge that targets this module, so no export-level chain is available for it.                                                                                                                                                  |
| no usable edge               | No edge targets the module but a dropped edge could have targeted it  | No export usage edge that bundlewhy could use targets this module. Edges that involve modules bundlewhy could not identify (for example concatenated module containers) or export references bundlewhy could not read were not used and may account for this. |

A collection without `exportUsage` (older adapter versions) deserializes with the field absent. `reason` holds one of the codes in the tables above; the analysis displays the fixed note for that code and nothing else, so no error message, source text or user path can reach a saved or exported report through it.

Analysis: `Context` indexes edges once per analysis, by provider export and by provider module, so each diagnostic reads its starting edges without scanning the whole edge list. For a diagnostic module, the traversal starts from every edge whose provider is an export of that module and follows edges toward consumers: the next edge must provide exactly the current outermost consumer's export (module and export path equal). A named export is never linked to a module-scope reference of the same module, so a gap in Rspack's edges ends the chain instead of being bridged. Chains are produced breadth first (shortest first) from edges sorted by provider, consumer, dependency ID and location, so input order never changes the result. A chain that closes a cycle is queued like any other chain and is emitted in its breadth-first turn, so a shorter chain is never listed after a longer cycle chain, and the chain cap keeps the shortest chains. Chains are stored from the outermost consumer to the diagnostic module. The traversal never infers function calls; a `null` export stays module scope.

| Limit                           | Value | Effect                                                                                   |
| ------------------------------- | ----- | ---------------------------------------------------------------------------------------- |
| Chains per diagnostic           | 5     | More chains stop the search; `truncation = PATH_COUNT`                                   |
| Edges per chain                 | 24    | The chain ends `TRUNCATED`; `truncation = DEPTH`                                         |
| Chain extensions per diagnostic | 10000 | Remaining chains end `TRUNCATED`; `truncation = EXPANSION_BUDGET`                        |
| Chains waiting in the queue     | 10000 | Chains that do not fit are not queued; `truncation = EXPANSION_BUDGET` (see Queue bound) |

Queue bound. A dense graph can give one chain as many extensions as it has edges, so the number of chains waiting in the queue is bounded, not only the number of extensions. A chain is queued only while fewer than 10000 chains wait (a bound below one is treated as one, so a diagnostic with edges always shows a chain). Chains that do not fit are dropped whole, in the stable edge order, so a chain that was queued earlier is never replaced by a later one. Memory is bounded by the queue bound and the 24 edge depth, not by the edge count.

| Queue state                          | Event                                                                     | Result                                                                                                                         |
| ------------------------------------ | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Starting edges at most the bound     | The traversal starts                                                      | Every starting edge is queued                                                                                                  |
| Starting edges above the bound       | The traversal starts                                                      | The first starting edges in stable order are queued; `truncation = EXPANSION_BUDGET`                                           |
| Fewer chains waiting than the bound  | A chain is extended by each consuming edge                                | Every extension is queued                                                                                                      |
| The bound is reached while extending | The next consuming edge of the chain                                      | It and the rest of that chain's extensions are not queued; `truncation = EXPANSION_BUDGET`                                     |
| Any                                  | A starting edge consumes the export it provides (self-referencing export) | The chain is terminal when it is queued: it ends `CYCLE` once and is never extended, whatever the queue state                  |
| Any                                  | A chain is taken from the queue                                           | It ends, or at least one extension is queued (the queue has room because the chain just left), so no chain disappears silently |

Cancellation. Deriving chains is analysis work, so Ctrl+C or `CancelRun` must stop it. The shared cancellation signal is polled at fixed points and a set signal ends the work at the next one; the partial result is discarded with the rest of the cancelled analysis and is never saved.

| Work                                                                       | Polled                                    | Signal set                                                                                                                                      |
| -------------------------------------------------------------------------- | ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Each Rspack module detector (side effects, concatenation, multiple chunks) | Before each module                        | The detector returns; the later detectors stop at their first module                                                                            |
| Traversal for one diagnostic                                               | Before each chain is taken from the queue | The traversal stops without extending another chain                                                                                             |
| Work between two polls                                                     | Not polled                                | At most one chain extension (bounded by the queue bound and the 24 edge depth), one module's dependency paths, or the one-time edge index build |
| Signal never set                                                           | Polled at the same points                 | No effect on the result                                                                                                                         |

`truncation` records the first limit reached; `NONE` means nothing was cut. A chain ends `ROOT` when no edge consumes its first export and no dropped edge could have (see the chain end table), `INCOMPLETE` when no usable edge consumes its first export but a dropped edge could have, `CYCLE` when the next edge would revisit an export already in the chain (the closing edge is included as the first edge, and a self-referencing edge ends the chain once; see Cycle detection), and `TRUNCATED` at a limit. A chain whose root is reached does not prove that no other consumer exists.

Chain end. Every way a chain can stop, in the order the traversal checks them, and what is shown. "Dropped edge into the first export" means a dropped edge that could have been an edge into exactly that export: one attributed to that module and export, one attributed to that module with an unreadable export, or any edge with an unknown provider module. The UI text for `INCOMPLETE` therefore says that a dropped edge may be an earlier edge, never that one is.

A diagnostic module without any usable starting edge is the exception: there any dropped edge into the module, whatever its export, gives the "no usable edge" note, because the starting edges of a diagnostic are the edges into any export of the module.

A dropped edge at an inner position changes no chain end: a chain that continues past the module through a usable edge is still a faithful chain, and the dropped edge only means that further chains may exist, which the count in the note discloses. A `TRUNCATED` or `CYCLE` chain never reached a first export without consumers, so a dropped edge cannot change it. The chain cap (`PATH_COUNT`) drops whole chains, not ends, so each kept chain keeps the end that the table gives it. `INCOMPLETE` does not need a truncation marker; `TRUNCATED` still requires one.

Cycle detection. A chain is terminal (`CYCLE`) at the moment it is created, never later, so a chain that contains a cycle is never extended and a self-referencing export never produces a second, longer chain that contains it. A terminal chain waits in the queue like any other chain and keeps `CYCLE` under every limit (a depth limit, a spent expansion budget, a full queue). Another consumer of the same export is a separate starting chain.

### Known limits

- Backing-file lookup for a module path with an import query or fragment (`a.js?raw`) cannot tell a derived module from a file whose real name contains `?` or `#` without inspecting the filesystem. The literal name wins only when it is positively found. When the literal name cannot be inspected (for example a transient permission error), the query-free path is chosen and persisted for reopening, because import queries are far more common than such file names. A file whose literal name contains `?` or `#` and whose directory was not inspectable during the analysis is therefore reopened by its query-free name and can be reported with `BW_SOURCE_STALE` until the run is analyzed again. A project directory whose own name contains `?` or `#` has the same limit. Pinned by the `filesystem_path_selects_the_backing_file_table` test.

### Sizes

Each emitted JavaScript chunk records raw, gzip (level 9) and Brotli (quality 11) bytes. When the chunk has a source map, generated bytes are attributed to sources by splitting the generated text at mapping boundaries; each byte belongs to at most one segment, so attribution never double counts and never exceeds raw bytes. A segment ends at the end of its generated line, so text on a later line before that line's first segment is unmapped. Unmapped bytes are reported separately. Sizes are measurements, never savings.

### Lifecycle

Every run gets a new UUID v7 directory. Progress stages are published as they start and timed separately in the run log (`MEASURING` covers chunk size measurement): `DETECTING`, `BUILDING`, `COLLECTING`, `ANALYZING`, `MEASURING`, `SAVING` and `FINISHED`. The completed elapsed duration ends after the `analysis.json` write and the optional `run-summary.json` write attempt; it includes result serialization and those writes. The Saving-stage and run-finished log entries and live progress use that same boundary. A small completion record is written afterward and excluded from the duration so the record does not time its own write. A complete run loses `INCOMPLETE` only after this record is committed; a failed final write or interrupted finalization stays incomplete. Ctrl+C or `CancelRun` terminates the owned adapter process (on Unix, SIGTERM to its process group and, after the full three-second grace period, SIGKILL to the whole group even if the adapter already exited), writes a `RUN_STATUS_CANCELLED` bundle with `BW_RUN_CANCELLED` and keeps the `INCOMPLETE` marker. Cancellation stays available while analysis and measurement run (checked between modules, before each chunk is expanded while the dynamic-import chunk graph is traversed, between chains while export usage paths are derived, and between chunks). Cancellation observed after collection, during analysis or measurement, also produces the cancelled result. Saved-run listings apply the same status normalization as opening a run. Exported reports are created exclusively (never through an existing file or symlink), with a numeric suffix when the name is taken. Adapter stdout lines longer than 1 MiB are discarded while the pipe keeps draining. A bundle left `RUNNING` by an interrupted process reopens as `RUN_STATUS_FAILED` with `BW_RUN_INTERRUPTED`. There is no automatic retry or resume; a retry is a new run. Project `package.json`, the selected configuration and lockfiles are hashed before and after the build. Protected lockfiles include the project's own and candidates in every ancestor directory through the repository root, even when absent before the build; a repository-root project never checks a parent lockfile. A protected file change is reported as `BW_PROJECT_MODIFIED`, downgrades a complete run to `RUN_STATUS_PARTIAL`, keeps the `INCOMPLETE` marker and makes `analyze` exit with a failure code.

The server's `ExportReport` writes and syncs a newly created HTML file before it returns a filename. If either step fails, it attempts to remove that file and returns `BW_EXPORT_FAILED`. If removal also fails, the error keeps the original write failure and identifies the leftover path for manual cleanup. Existing reports and symlinks remain untouched.

## Storage

`<out-dir>/<run-id>/` contains `analysis.json` (versioned result bundle, `schemaVersion: 1`, at most 512 MiB: a larger result drops source content and snippets with `BW_RESULT_TOO_LARGE`), `run-summary.json` (small summary read by run listings, which select the newest 200 UUID directories before reading anything), `collect.json` (adapter collection), `build/` (diagnostic build output), `adapter/` (adapter scripts written for this run), `bundlewhy.log` (JSON lines) and `INCOMPLETE` while a run is unfinished. The result bundle contains the analysis (diagnostics, coverage, sizes, engine identity, safe configuration summary, problems) and source files with project-relative or dependency display paths, SHA-256 and content unless `--exclude-sources`. Results are kept until the user deletes them; bundlewhy never uploads or deletes them. Unknown schema versions fail with `BW_SCHEMA_UNSUPPORTED`; there are no migrations. This local storage is a documented deviation from the repository R2 default.

## Security

Project configuration, plugins and adapters execute with the user's permissions; bundlewhy supports trusted local projects and does not sandbox plugin filesystem or network effects. The server binds `127.0.0.1` on an OS-assigned port, requires a per-run 256-bit bearer token (delivered in the URL fragment), rejects requests whose `Host` is not the bound address and whose `Origin` is not exactly the server origin, and sends `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and a CSP without network sources. RPC methods take no filesystem paths: sources are looked up by bundle-local identifiers and runs by UUID within the output directory. Live source files are read only when they are regular files of at most 16 MiB inside the project root or module paths reported by the bundler; paths named only by a source map rely on its `sourcesContent`. Saved bundles are untrusted: `analysis.json` must be a regular file (never a symlink; opened with no-follow semantics on Unix) and is read through a bounded reader; structure, enum values, identifiers and display paths are validated, and stale checks read only project-relative paths without `..` that resolve (after symlinks) to regular files of at most 16 MiB inside the recorded project root. With `--exclude-sources`, a failed build saves only the error code and a generic message, because build errors can quote source code; details stay on the terminal. Source maps without any source-bearing mapping count as missing. A stale check that cannot verify a file (too large, special or outside the root) does not mark it stale; only removed or changed files are stale. Sources without a build snapshot whose live file is not text (an imported PNG, or any file that is not UTF-8 text without NUL bytes) and sources whose `sourcesContent` is a bundler-generated asset module are not freshness-checked: they keep their path and identifier for attribution, but have no stored content, no code snippet and no entry in the project-relative map used to re-hash text sources when a saved run is reopened. Such a source, and a source whose module path carries an import query other than an asset query (a derived module such as `Comp.vue?vue&type=style`, whose transformed code is not expected to equal the file), is listed instead in the existence-only map (`existenceRelative` in `analysis.json`, subject to the same safe-path validation): a reopened run keeps checking that the backing file exists and ignores its content, so these sources are never reported with `BW_SOURCE_STALE` for an edit, but are when their file is removed and cleared again when it is restored, including a file removed after the analysis. A source that was already missing during the analysis is saved stale and follows the same rule. A generated asset module is `export default` followed by exactly one of: a single string literal (the `"__VITE_ASSET__<id>__"` marker of earlier Vite releases, an inlined `data:` URL, a `?url` path, or the text of a `?raw` or `?inline` import) or the `import.meta.ROLLDOWN_FILE_URL_<id>` placeholder Rolldown-based Vite releases emit. Every shape additionally requires an asset path: a file that is not JavaScript-family source, or a path whose import query contains the `raw`, `url`, `inline` or `no-inline` key (a fragment ends the query). Any other expression, or text after the complete expression, is ordinary code, and so is a string-only default export (including a marker-like string) in a script file without such a query. An ordinary text snapshot is always compared with the live file, so a changed source stays stale even when its live file became non-text. When a saved run is reopened, `mark_stale` also skips stored asset modules, so runs saved before this contract (which keep the generated module text and its hash) do not report unchanged assets as stale; a run saved with `--exclude-sources` has no stored text, so only a binary asset path (such as `.png` or `.woff2`) with non-text live bytes is skipped. Stored source text comes from the build's source-map `sourcesContent` when available, so the analysis describes the revision the bundler read; a live file that changed since then is marked stale with `BW_SOURCE_STALE`. Only a byte mismatch or a removed file (`NotFound`) is a change. When a source has a build snapshot but its live file cannot be read for any other reason (for example a permission or I/O error), the source is not stale and gets no `BW_SOURCE_STALE`; its snapshot text stays usable (stored content, snippets and evidence, `BUILD_SNAPSHOT` provenance), it is not counted as `BW_SOURCE_UNREADABLE` and does not downgrade category coverage. The analysis instead carries one `BW_SOURCE_FRESHNESS_UNVERIFIED` warning with the count of such sources ("freshness of N source file(s) could not be checked; analysis uses the build snapshot"); the warning never makes the run partial. The failed read is logged with the display path and I/O error kind. Reopening a saved run recomputes this warning together with the stale check: each reopen drops every earlier `BW_SOURCE_FRESHNESS_UNVERIFIED` problem and adds one warning only for rechecked text sources that still exist but cannot be read, so the warning clears once the file is readable and equal, and an unreadable file stays unverified without a changed claim. Sources that cannot be rechecked on reopen do not carry the warning forward. Every filesystem failure that decides whether a source is removed, changed or unverified is classified by one `LiveFileFailure` enum, on the first run and on reopen, for text and existence-only sources alike: `Missing` (only `std::io::ErrorKind::NotFound`, including a symlink whose target is gone and a file removed between the metadata check and the read) proves removal and makes the source stale; `NotPermitted` (outside the project root, not a regular file, or over 16 MiB) and `Unreadable(kind)` (permission denied, not a directory, a symlink loop, interrupted or any other I/O error kind) never claim a change and only leave freshness unverified, so a reopened run reports `BW_SOURCE_FRESHNESS_UNVERIFIED` rather than `BW_SOURCE_STALE`. This holds for every refusal on the first run as well (a snapshot-backed source or a generated asset module whose file is over 16 MiB, not a regular file or outside the vetted root gets the warning). The existence probe of an existence-only source is vetted exactly like a read (one shared check resolves symlinks, enforces the project root, the regular-file requirement and the 16 MiB limit), so a symlink whose target was removed is `Missing` (stale) on reopen for imported assets too, while a directory, an oversized or special file and a symlink leaving the root are `NotPermitted` and leave freshness unverified instead of verifying existence. `BW_SOURCE_FRESHNESS_UNVERIFIED` is one warning built by one helper on the first run and on reopen: it counts sources that keep build snapshot text (`BUILD_SNAPSHOT` evidence, including a derived module that is only checked for existence) separately from sources without it (binary assets, generated asset modules, readable sources without `sourcesContent`). Only the first group is described with "analysis uses the build snapshot"; the second is reported as an unchecked existence ("existence of N source file(s) without a build snapshot could not be checked"), and a run with both groups reports both in the same warning. The I/O error kind is kept and logged with the display path. A run whose `INCOMPLETE` marker cannot be inspected is presented as partial, never complete (the marker entry itself is inspected without following symlinks, so a dangling `INCOMPLETE` symlink counts as a present marker and only an absent entry means complete), and a result bundle that cannot be inspected for a reason other than `NotFound` is reported as inaccessible rather than missing. The stale check is idempotent: each reopen replaces every earlier `BW_SOURCE_STALE` problem (including the build-time "changed after the build read them" warning) with at most one warning carrying the current count, and none when no source is stale (the count includes sources that cannot be rechecked and keep their saved stale flag, such as a source without a project-relative or existence-only entry, which is the case for a dependency source or a run saved before the existence-only map existed); other problems keep their order. When the recorded project root cannot be verified (empty, relative or unresolvable), no check is made and saved flags and warnings stay untouched. Exports are snapshots: they never recheck files, keep the source and summary stale flags and the single `BW_SOURCE_STALE` warning as observed at export time, and `--exclude-sources` neither adds nor removes them. Dependency display paths keep their full ancestry relative to the project root (for example `node_modules/a/node_modules/b/index.js` or a pnpm store path under `node_modules/.pnpm`), so nested and pnpm copies of the same package display distinctly; paths outside the project root use a `..`-relative form and never expose an absolute prefix. Source files are identified by their resolved path, not by display path. A module path that carries an import query or fragment (for example `/src/a.js?raw`) keeps it for identity, display and asset-module classification, but live reads, vetting and the project-relative map used when a saved run is reopened use the file that backs the module: an existing literal file name wins, otherwise the path without its query and then without its fragment is used, so the documented `?raw`, `?inline` and `?url` imports are not reported with `BW_SOURCE_STALE` merely because the query is not part of the file name. `--exclude-sources` also removes diagnostic snippets from result bundles and exports. Exported HTML embeds JSON with `<`, `>`, `&`, U+2028 and U+2029 escaped and a CSP that forbids network access. Reports that include source content are not claimed to be secret-free.

When a source map lacks `sourcesContent`, a safe live read may establish that a path exists but cannot prove the revision read by the build. Such text is not stored as analyzed content, used for an original snippet, or hashed as the analyzed revision. The source and its summary carry `SourceRevisionEvidence.UNAVAILABLE`; saved and exported reports preserve it. A mapped location without verified original text falls back to generated chunk location and snippet. `BW_SOURCE_UNVERIFIED` marks readable executable source text without a build snapshot, and the run is partial. The asset exemption is engine specific (`AssetExemption`, default `None`). Only a Vite collection uses `ViteUrlModules`: known Vite asset imports, including SVG files and `?raw`, `?url`, `?inline`, and `?no-inline` imports, are URL or string modules rather than executable source text; without a build snapshot, they retain existence-only source evidence and do not create direct-eval or name-mangling coverage gaps. Other engines such as Rspack run the same paths through configured loaders that can emit executable code, so a readable `.svg` or query module without a build snapshot there records `BW_SOURCE_UNVERIFIED` and a partial name-mangling coverage like any other text source, unless the engine itself reports the module as an asset module (an Rspack `moduleType` of `asset` or `asset/*`), which keeps existence-only evidence. Adapters strip loader prefixes and queries from module identifiers, so source evidence is keyed by backing path: a path is exempt only when every collected module with that path is an asset module, and an executable loader or query variant of the same resource keeps the gap. A build snapshot always takes precedence over the exemption, and disabled-minification (`NOT_APPLICABLE`) and non-default-minifier (`UNAVAILABLE`) coverage keep precedence over the source-gap state. `BW_SOURCE_UNREADABLE` remains the problem for a source that cannot be read at all. A snapshot-present ordinary source carries `BUILD_SNAPSHOT` and keeps the established live-file drift comparison and `BW_SOURCE_STALE` behavior. `UNSPECIFIED` in an older bundle makes no provenance claim. Saved/opened and embedded exported report validation cross-checks every `BUILD_SNAPSHOT` source summary against its matching source record before the UI can display an original diagnostic snippet; an absent or inconsistent record cannot authorize the snippet. Unverified text sources use existence-only reopening checks, so a later edit is not incorrectly reported as a comparison with analyzed text; removal can still be reported.

## Logging

`tracing` writes human-readable, ANSI-colored stderr logs by default (`--no-color` or `NO_COLOR` disables color, `--verbose` adds debug detail). The loopback listener logs accept failures with the bound address and error, then waits 250 ms before retrying; a later successful accept resumes normal connection handling. Each run writes `bundlewhy.log` JSON lines with timestamp, run ID, stage, duration, engine versions and error codes. Logs never include source content, environment variable values, credentials or access tokens. A bundler module identifier can carry inline loader options or resource queries, so logs never name a module by its raw identifier:

| Module in a log line                                                                               | Logged as                                                                   |
| -------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Collected module with a resource path                                                              | Its display path (project-relative or dependency display path)              |
| Collected module without a resource path, or module that is not collected                          | `module-` plus the first 16 hex digits of the SHA-256 of its identifier     |
| Backing-file candidate path (absolute, possibly with a query or fragment) that has no display path | `module-` plus the first 16 hex digits of the SHA-256 of the candidate text |

## Build and Test

Run root `cargo test` after Rust changes. Unit tests cover every rule with committed fixture collections for its blocker and counterexample, size attribution without double counting, schema rejection, result validation, path validation, token and Origin enforcement, HTML escaping and log redaction. `packages/bundlewhy` acceptance (`pnpm --filter @delino/bundlewhy test:acceptance`) runs real Vite and Rspack fixture builds through the binary and verifies project files stay unchanged. The UI document is embedded from `apps/bundlewhy-web/dist/index.html` when present at build time; otherwise development and test builds embed a minimal page that explains how to build it. Release-profile builds fail without the UI unless `BUNDLEWHY_ALLOW_MISSING_UI=1` is set for a build that is never distributed.

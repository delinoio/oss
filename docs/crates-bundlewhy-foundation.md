# bundlewhy Rust foundation

## Scope

`crates/bundlewhy` owns the `bundlewhy` binary: CLI, project and engine detection, adapter process lifecycle, analysis rules, size measurement, result bundle storage, the loopback Connect server and self-contained HTML export. It owns and embeds the collector adapters in `crates/bundlewhy/adapters` (dependency-free Node.js ESM, kept inside the crate so Cargo change detection selects only this crate when they change) and the built UI document from `apps/bundlewhy-web`.

## Runtime and Language

Rust (workspace edition) with tokio, hyper 1 and serde. The analyzed project's build runs in Node.js 22.18 or newer through the adapters (the first 22.x release that strips TypeScript types by default, which TypeScript Rspack configurations require). Rust is a documented deviation from the repository Go default; see [the project index](project-bundlewhy.md).

## Users and Operators

Application developers analyzing a trusted local Vite or Rspack project, and maintainers validating fixtures and real applications. Support is through GitHub issues without an SLA.

## Interfaces and Contracts

### Commands

- `bundlewhy analyze --out-dir <dir> [--project <dir>] [--config <file>] [--config-name <name>] [--bundler vite|rspack] [--allow-unsupported-engine] [--no-open] [--no-serve] [--exclude-sources]` collects one diagnostic build into a new run directory, serves the UI and opens the browser unless `--no-open`. `--no-serve` exits after saving. `--out-dir` is required: results are stored only where the user chooses.
- `bundlewhy open <run-dir> [--no-open]` validates and serves a saved result bundle.
- `bundlewhy export <run-dir> --output <file.html> [--exclude-sources] [--force]` writes a self-contained interactive HTML report. It never writes through a symbolic link: an existing link is refused, a new file is created exclusively, and `--force` replaces a regular file by renaming a new file over it. Project, configuration and output paths must be valid UTF-8; others fail with `BW_USAGE` before any run directory is created. It states on stderr whether source content is included.
- `bundlewhy engines` prints the frozen engine compatibility matrix.
- Global flags: `--no-color` (also `NO_COLOR`), `--verbose`, `--help`, `--version`. Exit codes: `0` success, `1` failure, `2` usage error, `130` cancelled.

### Selection

The project defaults to the current directory. The bundler is detected from `package.json` dependencies (`vite`, `@rspack/core`) and configuration files (`vite.config.{js,mjs,cjs,ts,mts,cts}`, `rspack.config.{js,mjs,cjs,ts,mts,cts}`). Auto-selection happens only when exactly one bundler and one configuration file are candidates. Otherwise analysis fails with `BW_BUNDLER_AMBIGUOUS` or `BW_CONFIG_AMBIGUOUS`, lists the candidates and explains the selecting flag. Rspack configurations exporting several builds require `--config-name`. Library builds (`output.library` or a per-entry `library`), SSR and Node-target builds (including target arrays with a Node entry) are rejected before any rule runs, so their results carry no diagnostics, and Vite configurations with several Rolldown outputs fail with `BW_UNSUPPORTED_BUILD`. Node targets are also detected from the resolved compiler platform (defaults and Browserslist queries), and an entry function is resolved once before the build so per-entry `library` descriptions are seen. An Rspack `optimization.minimizer: []` counts as disabled minification, an explicit SWC minimizer with `compress: false`, `mangle: false`, any disabled compression pass (for example `compress: { dead_code: false }`) or a `keep_*` mangle option counts as non-default, and a pipeline with any JavaScript minimizer other than the default SWC one (for example `["...", custom]`) counts as a non-default minifier.

### Engine compatibility matrix (frozen for 0.1.0)

| Bundler | Package        | Version                     | Default JavaScript minifier          |
| ------- | -------------- | --------------------------- | ------------------------------------ |
| Vite    | `vite`         | `8.3.4` (Rolldown `1.2.13`) | Oxc minifier (`build.minify: 'oxc'`) |
| Rspack  | `@rspack/core` | `2.2.9`                     | `SwcJsMinimizerRspackPlugin`         |

An installed version outside the matrix fails with `BW_ENGINE_VERSION_UNSUPPORTED` before the build. `--allow-unsupported-engine` is the explicit selection that analyzes with that installed engine; the run records `ENGINE_SUPPORT_UNSUPPORTED_SELECTED`. A non-default minifier keeps module-graph categories but marks the minifier categories (dead-code elimination and name mangling) `UNAVAILABLE` with `BW_MINIFIER_NON_DEFAULT`; disabled minification produces a confirmed configuration diagnostic and `BW_MINIFICATION_DISABLED`, and marks dead-code elimination and name mangling not applicable.

### Diagnostic engine

The diagnostic build always runs the project's own installed engine with collection overrides recorded in `EngineIdentity.overrides`: Vite forces a bundlewhy output directory, `emptyOutDir`, source maps and a post collector plugin; Rspack forces production mode, a bundlewhy output path, `output.clean` and `devtool: source-map`, and appends an observation-only `RsdoctorPlugin` (export usage graph) after the project's own plugins. The plugin changes no build output and never replaces the project's engine; the added plugin is recorded as a collection override. Findings describe that diagnostic build, `diagnostic_engine` is always true and the notice states that output equivalence with the original build is not guaranteed. Adapter identity is `bundlewhy-collector-vite` / `bundlewhy-collector-rspack` with an adapter version.

For `vite/side-effect-retained`, the effective side-effect declaration follows Rolldown's precedence, highest first: a `moduleSideEffects` value set by a resolve, load or transform hook, the configured `build.rolldownOptions.treeshake.moduleSideEffects`, the package `sideEffects` field, and then Rolldown's own analysis of the code. The collector records only what it can observe: the value that JavaScript hooks set (`getModuleInfo()`), the configured option evaluated for each module, and the nearest package `sideEffects` value. Vite's resolver is a native Rolldown plugin that reports a declared package `sideEffects` field as a hook value for the import it resolves (`true` for a `true` field or a matching list entry, `false` otherwise), and that value outranks the configured option. `getModuleInfo()` does not list it, and resolving a retained module's absolute ID again does not reproduce it, because Vite attaches it while it resolves the original import. The collector therefore does not infer it: when no JavaScript hook set a value and the package declares `sideEffects`, the condition is Unknown whatever the declaration and the configured option say, and the direction names the package entry to narrow or remove. The collector evaluates the configured option for each module: `false`, a module ID list (an empty list included, which marks no module as having side effects), a rule list and `"no-external"` decide, while `true` and a rule list without a matching rule give no verdict; a function is not evaluated and leaves the declaration unknown. Without a JavaScript hook value, the option decides for a package that declares nothing; with no verdict from the option either, the module is undeclared and Rolldown analyzes the code. A hook value of `true` is not a declaration: it asks Rolldown to analyze the code and skips both the configured option and the package field, so the finding is inferred, the "declared side-effect free" condition is unmet, and the direction names the plugin that returns the value. An effective `false` reports the condition as met. Rolldown may discard such a module even when its code has side effects, so the finding is inferred from another use of the module (a side-effect import, namespace or re-export use, or an entry) and does not claim top-level side effects. An effective `"no-treeshake"` from a hook or `true` from the configured option reports the condition as unmet with Confirmed status. Any unrecognized hook value also leaves the condition unknown, and the direction names the unresolved source (the plugin hook, the configured option or the package declaration). The finding title does not depend on the declaration, so a retained module keeps one diagnostic ID when its declaration changes.

Therefore, `vite/side-effect-retained` remains Inferred unless the effective declaration is known to retain the module; a package `sideEffects` field alone does not make the finding Confirmed.

Inlining and constant folding are `COVERAGE_STATE_UNAVAILABLE` for both engines: neither engine exposes those decisions and no verified detector exists. Module concatenation is covered for both engines. Source-map `sourceRoot` and `sources` are joined with a single separator that never trims the root, so URL roots such as `webpack:///` keep their scheme. A failed run's engine identity leaves support unspecified because no version was discovered. A source binding named `eval` (a parameter, variable or function) makes `eval(...)` calls inside that binding's scope ordinary calls; shadowing is decided per call, so the source-scan fallback still reports a direct eval elsewhere in the module. `BW_MINIFIER_NON_DEFAULT` is reported only when minification runs. Missing source maps mark the affected chunk's attribution `UNAVAILABLE`, fall back to generated locations and record `BW_SOURCE_MAP_MISSING`. A partial collection keeps usable results, sets `RUN_STATUS_PARTIAL` and marks affected categories `COVERAGE_STATE_PARTIAL`; an emitted chunk that cannot be read marks dead-code elimination and name mangling partial. The env-condition scan and the source scan for direct `eval` ignore string, template, comment and regular expression literal text. Retained code alone is never reported as a defect.

### Dependency paths and locations

Dependency paths are the shortest static importer chains from an entry to the module (up to three). Dynamic `import()` edges are not part of a dependency path. Name-mangling checks consider every binding of a declaration (including `for … of` / `for … in` loop bindings) and function and arrow parameters (destructured, defaulted, rest and annotated), including comma-separated declarators and destructuring patterns. Before the adapter starts, `node --version` is probed and runtimes older than 22.18 fail with `BW_NODE_VERSION_UNSUPPORTED`. Saved bundles must use unique `d-<12 hex>` diagnostic IDs. TypeScript annotations on declared bindings are ignored when checking name mangling. Diagnostic IDs include the location column and the finding title, so distinct findings on one line stay separate. Cycles are excluded per candidate path, so distinct shortest chains through different importers are all kept. Export-level chains are a separate, additive evidence list described under Export usage paths. Locations use original source positions when a source map maps them; otherwise generated chunk positions. Snippets carry at most nine lines of 240 characters each.

### Export usage paths

Rspack diagnostics that already carry module dependency paths (`rspack/side-effect-retained`, `rspack/module-concatenation-bailout`, `rspack/module-in-multiple-chunks`) also carry an optional `Diagnostic.export_usage`. Vite diagnostics and rules without a module scope never carry it.

Collection (adapter version `2`, `collectVersion` stays `1`): the Rspack adapter taps the `moduleGraph` hook of `experiments.RsdoctorPlugin` (`moduleGraphFeatures: ['graph']`, `chunkGraphFeatures: false`, `exportUsageGraph: true`) and stores the optional collection field `exportUsage { available, reason, skippedEdges, skippedProviders, unattributedEdges, edges }`. `skippedProviders` is a list of `{ module, edges }` sorted by module: the dropped edges whose provider is that collected module. `unattributedEdges` counts dropped edges whose provider module cannot be determined. Each edge is `{ consumer: { module, export }, provider: { module, export }, dependencyId, location }`; `export` is an export path array or `null` for module or namespace scope. Rspack reports edges as positional tuples whose module keys are only valid inside the same payload; the adapter maps keys to stats module identifiers through that payload. Plugin API access is internal and unstable, so construction, `apply`, every hook and the payload are guarded, and a failed build with the plugin is repeated once without it (see the adapter outcomes below).

Adapter outcomes. Exactly one row applies to a build; when several failures happen, the first one recorded is kept (a later failure never replaces it). The adapter stores only the reason code, never error text, source text or a project path.

Plugin configuration. The adapter changes only the diagnostic build's copy of the selected configuration; the project's file and objects are never modified (a frozen list works). It reads `plugins` once, from the copy that the build receives. A list is never edited in place: the build gets a new list with the project's entries first, in their original order and including falsy entries, followed by the observer. Any value that is not a list is passed to Rspack exactly as written, whatever Rspack does with it, and the observer is not added. When the build with the observer fails, the repeat builds from a freshly loaded configuration, so it receives the project's `plugins` value as the project wrote it (or no `plugins` key when the project had none) with new instances. When several conditions apply, the first row of the adapter outcomes table in this order wins: not a list, API missing, already configured, construction failed.

| `plugin-already-configured`  | Reason code                                                           | The project already configures RsdoctorPlugin, so bundlewhy did not add a second instance.                                                                                                                                                                    |
| `plugins-not-array`          | Reason code                                                           | The project sets plugins to a value that is not a list, so bundlewhy passed it to Rspack unchanged and did not add the RsdoctorPlugin observer.                                                                                                               |
| `plugin-construction-failed` | Reason code                                                           | bundlewhy could not create the RsdoctorPlugin observer with this Rspack version.                                                                                                                                                                              |
| `plugin-apply-failed`        | Reason code                                                           | The RsdoctorPlugin observer could not be applied to the Rspack compiler.                                                                                                                                                                                      |
| `hook-registration-failed`   | Reason code                                                           | bundlewhy could not use the RsdoctorPlugin module graph hook of this Rspack version.                                                                                                                                                                          |
| `build-failed-with-observer` | Reason code                                                           | The diagnostic build failed with the RsdoctorPlugin observer attached, so it was repeated without it.                                                                                                                                                         |
| `graph-not-delivered`        | Reason code                                                           | Rspack did not deliver the RsdoctorPlugin module graph for this build.                                                                                                                                                                                        |
| `modules-payload-invalid`    | Reason code                                                           | The RsdoctorPlugin payload has an unexpected shape: its module list is missing.                                                                                                                                                                               |
| `edges-payload-invalid`      | Reason code                                                           | The RsdoctorPlugin payload has an unexpected shape: its export usage edge list is missing.                                                                                                                                                                    |
| `edge-limit-exceeded`        | Reason code                                                           | Rspack reported more export usage edges than the storage limit, so none were stored.                                                                                                                                                                          |
| unknown code                 | A reason code that this version does not know                         | The adapter reported an export usage reason that this bundlewhy version does not recognize.                                                                                                                                                                   |
| no edge                      | No edge targets the module and no dropped edge could have targeted it | Rspack reported no export usage edge that targets this module, so no export-level chain is available for it.                                                                                                                                                  |
| no usable edge               | No edge targets the module but a dropped edge could have targeted it  | No export usage edge that bundlewhy could use targets this module. Edges that involve modules bundlewhy could not identify (for example concatenated module containers) or export references bundlewhy could not read were not used and may account for this. |

A collection without `exportUsage` (older adapter versions) deserializes with the field absent. `reason` holds one of the codes in the tables above; the analysis displays the fixed note for that code and nothing else, so no error message, source text or user path can reach a saved or exported report through it.

Analysis: `Context` indexes edges once per analysis, by provider export and by provider module, so each diagnostic reads its starting edges without scanning the whole edge list. For a diagnostic module, the traversal starts from every edge whose provider is an export of that module and follows edges toward consumers: the next edge must provide exactly the current outermost consumer's export (module and export path equal). A named export is never linked to a module-scope reference of the same module, so a gap in Rspack's edges ends the chain instead of being bridged. Chains are produced breadth first (shortest first) from edges sorted by provider, consumer, dependency ID and location, so input order never changes the result. A chain that closes a cycle is queued like any other chain and is emitted in its breadth-first turn, so a shorter chain is never listed after a longer cycle chain, and the chain cap keeps the shortest chains. Chains are stored from the outermost consumer to the diagnostic module. The traversal never infers function calls; a `null` export stays module scope.

| Limit                           | Value | Effect                                                                                   |
| ------------------------------- | ----- | ---------------------------------------------------------------------------------------- |
| Chains per diagnostic           | 5     | More chains stop the search; `truncation = PATH_COUNT`                                   |
| Edges per chain                 | 24    | The chain ends `TRUNCATED`; `truncation = DEPTH`                                         |
| Chain extensions per diagnostic | 10000 | Remaining chains end `TRUNCATED`; `truncation = EXPANSION_BUDGET`                        |
| Chains waiting in the queue     | 10000 | Chains that do not fit are not queued; `truncation = EXPANSION_BUDGET` (see Queue bound) |

Queue bound. A dense graph can give one chain as many extensions as it has edges, so the number of chains waiting in the queue is bounded, not only the number of extensions. A chain is queued only while fewer than 10000 chains wait (a bound below one is treated as one, so a diagnostic with edges always shows a chain). Chains that do not fit are dropped whole, in the stable edge order, so a chain that was queued earlier is never replaced by a later one. Memory is bounded by the queue bound and the 24 edge depth, not by the edge count.

| Queue state                          | Event                                                          | Result                                                                                                                         |
| ------------------------------------ | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Starting edges at most the bound     | The traversal starts                                           | Every starting edge is queued                                                                                                  |
| Starting edges above the bound       | The traversal starts                                           | The first starting edges in stable order are queued; `truncation = EXPANSION_BUDGET`                                           |
| Fewer chains waiting than the bound  | A chain is extended by each consuming edge                     | Every extension is queued                                                                                                      |
| The bound is reached while extending | The next consuming edge of the chain                           | It and the rest of that chain's extensions are not queued; `truncation = EXPANSION_BUDGET`                                     |
| The bound is reached while extending | The chain also consumes its own edge (self-referencing export) | The chain still ends `CYCLE` once; the check does not depend on the queue                                                      |
| Any                                  | A chain is taken from the queue                                | It ends, or at least one extension is queued (the queue has room because the chain just left), so no chain disappears silently |

Cancellation. Deriving chains is analysis work, so Ctrl+C or `CancelRun` must stop it. The shared cancellation signal is polled at fixed points and a set signal ends the work at the next one; the partial result is discarded with the rest of the cancelled analysis and is never saved.

| Work                                                                       | Polled                                    | Signal set                                                                                                                                      |
| -------------------------------------------------------------------------- | ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Each Rspack module detector (side effects, concatenation, multiple chunks) | Before each module                        | The detector returns; the later detectors stop at their first module                                                                            |
| Traversal for one diagnostic                                               | Before each chain is taken from the queue | The traversal stops without extending another chain                                                                                             |
| Work between two polls                                                     | Not polled                                | At most one chain extension (bounded by the queue bound and the 24 edge depth), one module's dependency paths, or the one-time edge index build |
| Signal never set                                                           | Polled at the same points                 | No effect on the result                                                                                                                         |

`truncation` records the first limit reached; `NONE` means nothing was cut. A chain ends `ROOT` when no edge consumes its first export and no dropped edge could have (see the chain end table), `INCOMPLETE` when no usable edge consumes its first export but a dropped edge could have, `CYCLE` when the next edge would revisit an export already in the chain (the closing edge is included as the first edge, and a self-referencing edge ends the chain once), and `TRUNCATED` at a limit. A chain whose root is reached does not prove that no other consumer exists.

Chain end. Every way a chain can stop, in the order the traversal checks them, and what is shown. "Dropped edge into the module" means a dropped edge attributed to the module that consumes the chain's first export, or any edge with an unknown provider.

| Situation at the chain's first export                                                                          | Chain end    | `truncation`       | UI text                                                                                                                                                                                                                                          |
| -------------------------------------------------------------------------------------------------------------- | ------------ | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| The expansion budget is spent before the chain is extended (a chain that already closed a cycle keeps `CYCLE`) | `TRUNCATED`  | `EXPANSION_BUDGET` | Traversal stopped at a limit before the start of this chain was reached.                                                                                                                                                                         |
| No usable edge consumes it, and no dropped edge into the module                                                | `ROOT`       | Unchanged          | Chain start: Rspack reported no earlier edge that consumes the first export. This does not prove that no other consumer exists.                                                                                                                  |
| No usable edge consumes it, and a dropped edge into the module                                                 | `INCOMPLETE` | Unchanged          | Chain start not confirmed: Rspack reported an earlier edge into the first export that bundlewhy could not use, because an endpoint is not a module it can identify or an export reference it can read. The chain may continue beyond this point. |
| The chain already has 24 edges and usable edges consume it                                                     | `TRUNCATED`  | `DEPTH`            | Traversal stopped at a limit before the start of this chain was reached.                                                                                                                                                                         |
| An edge consumes it and returns to an export already in the chain (or is already in it)                        | `CYCLE`      | Unchanged          | The first edge returns to an export that is already in this chain (a cycle). Traversal stopped here.                                                                                                                                             |
| Usable edges consume it                                                                                        | none yet     | Unchanged          | The chain is extended by each consuming edge                                                                                                                                                                                                     |

A dropped edge at an inner position changes no chain end: a chain that continues past the module through a usable edge is still a faithful chain, and the dropped edge only means that further chains may exist, which the count in the note discloses. A `TRUNCATED` or `CYCLE` chain never reached a first export without consumers, so a dropped edge cannot change it. The chain cap (`PATH_COUNT`) drops whole chains, not ends, so each kept chain keeps the end that the table gives it. `INCOMPLETE` does not need a truncation marker; `TRUNCATED` still requires one.

| Diagnostic situation                                                                           | `export_usage`                                                                                                        |
| ---------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Collection has no `exportUsage`                                                                | `UNAVAILABLE`, collection not recorded                                                                                |
| Collection `available: false`                                                                  | `UNAVAILABLE` with the fixed note for the reason code                                                                 |
| No edge provides an export of the module (for example a module loaded only through `import()`) | `UNAVAILABLE`, "no edge" note when no dropped edge could have targeted the module, "no usable edge" note otherwise    |
| At least one edge                                                                              | `AVAILABLE` with chains, the truncation marker and, when edges were skipped or dropped, a note disclosing their count |

Unavailable export usage never changes the diagnostic's status, evidence, conditions or module dependency paths. Saved bundles validate `export_usage` on load (`BW_RESULT_INVALID`): a specified state, no paths when unavailable, at least one and at most 5 chains when available, a specified truncation marker, 1 to 24 edges per chain, a specified chain end (`TRUNCATED` requires a truncation marker other than `NONE`, and `INCOMPLETE` requires a non-empty note), a non-empty module on every reference, a named reference with a non-empty export path and a module-scope reference with none, and consecutive edges where each provider equals the next consumer. A bundle without the field opens unchanged. `--exclude-sources` keeps export usage because it holds module display paths, dependency IDs and positions, not source text.

Provenance wording. Edges are what Rspack reported; chains, their order and the choice of chains are derived by bundlewhy. Every surface keeps that split, and none says that Rspack reports a path or chain.

| Surface                    | Edges                                                                                           | Chains                                                        |
| -------------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Protocol and Rust contract | Engine observations                                                                             | Derived by bundlewhy                                          |
| Web UI                     | Tagged "Observed by Rspack"                                                                     | Tagged "Derived by bundlewhy"                                 |
| Diagnostic notes           | "Rspack reported no export usage edge" only when no dropped edge could have targeted the module | Never described as reported by Rspack                         |
| Public documentation       | Export dependencies that Rspack reports                                                         | Export usage paths that bundlewhy derives from Rspack's edges |

### Sizes

Each emitted JavaScript chunk records raw, gzip (level 9) and Brotli (quality 11) bytes. When the chunk has a source map, generated bytes are attributed to sources by splitting the generated text at mapping boundaries; each byte belongs to at most one segment, so attribution never double counts and never exceeds raw bytes. Unmapped bytes are reported separately. Sizes are measurements, never savings.

### Lifecycle

Every run gets a new UUID v7 directory. Progress stages are published as they start and timed separately in the run log (`MEASURING` covers chunk size measurement): `DETECTING`, `BUILDING`, `COLLECTING`, `ANALYZING`, `MEASURING`, `SAVING` and `FINISHED`. The completed elapsed duration ends after the `analysis.json` write and the optional `run-summary.json` write attempt; it includes result serialization and those writes. The Saving-stage and run-finished log entries and live progress use that same boundary. A small completion record is written afterward and excluded from the duration so the record does not time its own write. A complete run loses `INCOMPLETE` only after this record is committed; a failed final write or interrupted finalization stays incomplete. Ctrl+C or `CancelRun` terminates the owned adapter process (on Unix, SIGTERM to its process group and, after the full three-second grace period, SIGKILL to the whole group even if the adapter already exited), writes a `RUN_STATUS_CANCELLED` bundle with `BW_RUN_CANCELLED` and keeps the `INCOMPLETE` marker. Cancellation stays available while analysis and measurement run (checked between modules, between chains while export usage paths are derived, and between chunks). Cancellation observed after collection, during analysis or measurement, also produces the cancelled result. Saved-run listings apply the same status normalization as opening a run. Exported reports are created exclusively (never through an existing file or symlink), with a numeric suffix when the name is taken. Adapter stdout lines longer than 1 MiB are discarded while the pipe keeps draining. A bundle left `RUNNING` by an interrupted process reopens as `RUN_STATUS_FAILED` with `BW_RUN_INTERRUPTED`. There is no automatic retry or resume; a retry is a new run. Project `package.json`, the selected configuration and lockfiles are hashed before and after the build. Protected lockfiles include the project's own and candidates in every ancestor directory through the repository root, even when absent before the build; a repository-root project never checks a parent lockfile. A protected file change is reported as `BW_PROJECT_MODIFIED`, downgrades a complete run to `RUN_STATUS_PARTIAL`, keeps the `INCOMPLETE` marker and makes `analyze` exit with a failure code.

The server's `ExportReport` writes and syncs a newly created HTML file before it returns a filename. If either step fails, it attempts to remove that file and returns `BW_EXPORT_FAILED`. If removal also fails, the error keeps the original write failure and identifies the leftover path for manual cleanup. Existing reports and symlinks remain untouched.

### Error codes

`BW_USAGE`, `BW_PROJECT_NOT_FOUND`, `BW_BUNDLER_NOT_DETECTED`, `BW_BUNDLER_AMBIGUOUS`, `BW_CONFIG_NOT_FOUND`, `BW_CONFIG_AMBIGUOUS`, `BW_CONFIG_LOAD_FAILED`, `BW_BUNDLER_NOT_INSTALLED`, `BW_ENGINE_VERSION_UNSUPPORTED`, `BW_NODE_NOT_FOUND`, `BW_NODE_VERSION_UNSUPPORTED`, `BW_BUILD_FAILED`, `BW_COLLECTION_FAILED`, `BW_UNSUPPORTED_BUILD`, `BW_SOURCE_MAP_MISSING`, `BW_SOURCE_UNREADABLE`, `BW_MINIFIER_NON_DEFAULT`, `BW_MINIFICATION_DISABLED`, `BW_PROJECT_MODIFIED`, `BW_RUN_CANCELLED`, `BW_RUN_INTERRUPTED`, `BW_SCHEMA_UNSUPPORTED`, `BW_RESULT_INVALID`, `BW_OUTPUT_DIR_INVALID`, `BW_SERVER_BIND_FAILED`, `BW_BROWSER_OPEN_FAILED`, `BW_EXPORT_FAILED`, `BW_ACCESS_DENIED`, `BW_SOURCE_STALE`, `BW_SOURCE_NOT_FOUND`, `BW_RESULT_TOO_LARGE`, `BW_ACCESS_TOKEN_MISSING` (UI only). Each user-facing error prints the code, message and a recovery instruction.

## Storage

`<out-dir>/<run-id>/` contains `analysis.json` (versioned result bundle, `schemaVersion: 1`, at most 512 MiB: a larger result drops source content and snippets with `BW_RESULT_TOO_LARGE`), `run-summary.json` (small summary read by run listings, which select the newest 200 UUID directories before reading anything), `collect.json` (adapter collection), `build/` (diagnostic build output), `adapter/` (adapter scripts written for this run), `bundlewhy.log` (JSON lines) and `INCOMPLETE` while a run is unfinished. The result bundle contains the analysis (diagnostics, coverage, sizes, engine identity, safe configuration summary, problems) and source files with project-relative or dependency display paths, SHA-256 and content unless `--exclude-sources`. Results are kept until the user deletes them; bundlewhy never uploads or deletes them. Unknown schema versions fail with `BW_SCHEMA_UNSUPPORTED`; there are no migrations. This local storage is a documented deviation from the repository R2 default.

## Security

Project configuration, plugins and adapters execute with the user's permissions; bundlewhy supports trusted local projects and does not sandbox plugin filesystem or network effects. The server binds `127.0.0.1` on an OS-assigned port, requires a per-run 256-bit bearer token (delivered in the URL fragment), rejects requests whose `Host` is not the bound address and whose `Origin` is not exactly the server origin, and sends `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and a CSP without network sources. RPC methods take no filesystem paths: sources are looked up by bundle-local identifiers and runs by UUID within the output directory. Live source files are read only when they are regular files of at most 16 MiB inside the project root or module paths reported by the bundler; paths named only by a source map rely on its `sourcesContent`. Saved bundles are untrusted: `analysis.json` must be a regular file (never a symlink; opened with no-follow semantics on Unix) and is read through a bounded reader; structure, enum values, identifiers and display paths are validated, and stale checks read only project-relative paths without `..` that resolve (after symlinks) to regular files of at most 16 MiB inside the recorded project root. With `--exclude-sources`, a failed build saves only the error code and a generic message, because build errors can quote source code; details stay on the terminal. Source maps without any source-bearing mapping count as missing. A stale check that cannot verify a file (too large, special or outside the root) does not mark it stale; only removed or changed files are stale. Sources without a build snapshot whose live file is not text (an imported PNG, or any file that is not UTF-8 text without NUL bytes) and sources whose `sourcesContent` is a bundler-generated asset module are not freshness-checked: they keep their path and identifier for attribution, but have no stored content, no code snippet and no entry in the project-relative map used to re-hash text sources when a saved run is reopened. Such a source, and a source whose module path carries an import query other than an asset query (a derived module such as `Comp.vue?vue&type=style`, whose transformed code is not expected to equal the file), is listed instead in the existence-only map (`existenceRelative` in `analysis.json`, subject to the same safe-path validation): a reopened run keeps checking that the backing file exists and ignores its content, so these sources are never reported with `BW_SOURCE_STALE` for an edit, but are when their file is removed and cleared again when it is restored, including a file removed after the analysis. A source that was already missing during the analysis is saved stale and follows the same rule. A generated asset module is `export default` followed by exactly one of: a single string literal (the `"__VITE_ASSET__<id>__"` marker of earlier Vite releases, an inlined `data:` URL, a `?url` path, or the text of a `?raw` or `?inline` import) or the `import.meta.ROLLDOWN_FILE_URL_<id>` placeholder Rolldown-based Vite releases emit. Every shape additionally requires an asset path: a file that is not JavaScript-family source, or a path whose import query contains the `raw`, `url`, `inline` or `no-inline` key (a fragment ends the query). Any other expression, or text after the complete expression, is ordinary code, and so is a string-only default export (including a marker-like string) in a script file without such a query. An ordinary text snapshot is always compared with the live file, so a changed source stays stale even when its live file became non-text. When a saved run is reopened, `mark_stale` also skips stored asset modules, so runs saved before this contract (which keep the generated module text and its hash) do not report unchanged assets as stale; a run saved with `--exclude-sources` has no stored text, so only a binary asset path (such as `.png` or `.woff2`) with non-text live bytes is skipped. Stored source text comes from the build's source-map `sourcesContent` when available, so the analysis describes the revision the bundler read; a live file that changed since then is marked stale with `BW_SOURCE_STALE`. The stale check is idempotent: each reopen replaces every earlier `BW_SOURCE_STALE` problem (including the build-time "changed after the build read them" warning) with at most one warning carrying the current count, and none when no source is stale (the count includes sources that cannot be rechecked and keep their saved stale flag, such as a source without a project-relative or existence-only entry, which is the case for a dependency source or a run saved before the existence-only map existed); other problems keep their order. When the recorded project root cannot be verified (empty, relative or unresolvable), no check is made and saved flags and warnings stay untouched. Exports are snapshots: they never recheck files, keep the source and summary stale flags and the single `BW_SOURCE_STALE` warning as observed at export time, and `--exclude-sources` neither adds nor removes them. Dependency display paths keep their full ancestry relative to the project root (for example `node_modules/a/node_modules/b/index.js` or a pnpm store path under `node_modules/.pnpm`), so nested and pnpm copies of the same package display distinctly; paths outside the project root use a `..`-relative form and never expose an absolute prefix. Source files are identified by their resolved path, not by display path. A module path that carries an import query or fragment (for example `/src/a.js?raw`) keeps it for identity, display and asset-module classification, but live reads, vetting and the project-relative map used when a saved run is reopened use the file that backs the module: an existing literal file name wins, otherwise the path without its query and then without its fragment is used, so the documented `?raw`, `?inline` and `?url` imports are not reported with `BW_SOURCE_STALE` merely because the query is not part of the file name. `--exclude-sources` also removes diagnostic snippets from result bundles and exports. Exported HTML embeds JSON with `<`, `>`, `&`, U+2028 and U+2029 escaped and a CSP that forbids network access. Reports that include source content are not claimed to be secret-free.

## Logging

`tracing` writes human-readable, ANSI-colored stderr logs by default (`--no-color` or `NO_COLOR` disables color, `--verbose` adds debug detail). The loopback listener logs accept failures with the bound address and error, then waits 250 ms before retrying; a later successful accept resumes normal connection handling. Each run writes `bundlewhy.log` JSON lines with timestamp, run ID, stage, duration, engine versions and error codes. Logs never include source content, environment variable values, credentials or access tokens. A bundler module identifier can carry inline loader options or resource queries, so logs never name a module by its raw identifier:

| Module in a log line                                                      | Logged as                                                               |
| ------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Collected module with a resource path                                     | Its display path (project-relative or dependency display path)          |
| Collected module without a resource path, or module that is not collected | `module-` plus the first 16 hex digits of the SHA-256 of its identifier |

## Build and Test

Run root `cargo test` after Rust changes. Unit tests cover every rule with committed fixture collections for its blocker and counterexample, size attribution without double counting, schema rejection, result validation, path validation, token and Origin enforcement, HTML escaping and log redaction. `packages/bundlewhy` acceptance (`pnpm --filter @delino/bundlewhy test:acceptance`) runs real Vite and Rspack fixture builds through the binary and verifies project files stay unchanged. The UI document is embedded from `apps/bundlewhy-web/dist/index.html` when present at build time; otherwise development and test builds embed a minimal page that explains how to build it. Release-profile builds fail without the UI unless `BUNDLEWHY_ALLOW_MISSING_UI=1` is set for a build that is never distributed.

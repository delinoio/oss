# Project: devhud

## Goal

DevHud is a coordinated desktop and mobile developer utility. V1 contains the desktop-only RealQA capture and GitHub issue workflow, the desktop/mobile Deck pull-request monitor, and native one-Deck home-screen widgets. The deterministic bilingual frontend, complete guest/Logto identity and synchronized Settings boundary, direct-client GitHub.com issue/pull-request provider and credential setup, desktop RealQA capture/editor/encrypted drafts/direct official and BYO R2 uploads/issue submission, populated Deck surfaces, pinned Tauri CEF desktop host, target-isolated Tauri iOS/Android system-webview hosts, WidgetKit/AppWidgetProvider targets, administrator SPA, versioned protocol, generated client, and Bootstrap/Settings/Upload/Account/Admin API services are implemented. The host foundation exposes composed product states and a closed mobile-native bridge. Remaining populated product surfaces and the other planned domains remain documentation-first contracts.

Issue [#815](https://github.com/delinoio/oss/issues/815) is the current product contract. It supersedes closed historical DevHud issues #729, #755, and #757; those issues are historical context only and must not supply architecture or scope.

Official uploads return a header-bound 15-minute direct-R2 PUT and a separate 24-hour staging deadline, use 256-bit opaque identifiers, and publish exactly `<configured-public-base>/<opaque-id>.png`. One-use is an application reservation/key/finalization invariant; finalization conditionally validates the recorded generation and ETag after reading only a 33-byte PNG prefix, never an API upload body. The committed exact R2 CORS and 300-public-GET/IP/minute Cloudflare artifacts are operator-applied and production-startup validated. The bilingual removal marker is embedded; owner deletion, administrator hooks, and account purge replace origin bytes before purge/revalidation. The sweeper owns staging expiry and deferred cleanup.

## Local development environment

The repository environment contract defines two modes. `pnpm dev` is the authorized-team path: it checks the pinned Infisical CLI and local authentication/project binding only when needed, validates the API and administrator allowlists plus their exact issuer parity, privately pins that comparison through migration and both service launches, and launches the frontend, administrator, and API at fixed ports `46305`, `46306`, and `46307`. It fails closed on authentication, path, cross-service issuer, or mid-startup configuration-generation errors and never wraps the root Turbo process with secrets.

`pnpm dev:oss` is the public-contributor path and never invokes Infisical. It acquires exclusive startup ownership for the checkout, requires the effective Docker endpoint to be a local socket, named pipe, or loopback TCP endpoint, then starts digest-pinned PostgreSQL and Logto dependencies on `5432`, `3001`, and `3002`, creates a checkout-local identity key, scopes the Compose project and persistent data to a one-way digest of that key, idempotently repairs missing Logto database creation in a preserved PostgreSQL volume, waits for health, runs migrations, and launches the same application boundary. Guest/bootstrap development works without shared identity setup. Authenticated/admin flows require contributor-owned Logto configuration, and official uploads remain unavailable because OSS mode omits the API R2/Cloudflare group. `pnpm dev:oss:down` stops only that checkout's dependencies without deleting its persistent volumes.

Team DevHud API/admin development values are the only shared development-secret scope. GitHub PATs, BYO R2 credentials, public mobile application configuration, generated local material, and production/deployment/release/signing credentials remain outside it. See [Repository environment contract](repository-environment-contract.md).

## Private Build Packaging

DevHud uses the repository release pattern `<project>@v*` exactly as `devhud@v<MAJOR.MINOR.PATCH>`. The version is stable three-component SemVer with no prefix, build metadata, or prerelease suffix; every component must be in Chrome's `0..65535` range. For the current coordinated v1 candidate the source version is `0.1.0`, the tag-shaped release identity is `devhud@v0.1.0`, and the independent App Store/Play build number is `1`. `packaging/devhud/release-metadata.json` is the operator-edited release input, and its version must exactly match both package manifests, the Tauri configuration and Cargo package, and the Native Messaging host Cargo package before any signed work starts.

`.github/workflows/package-devhud-private.yml` has no automatic trigger: it supports explicit manual dispatch and an explicit reusable-workflow call from the coordinated public release. Its `plan-only` mode is credential-free, prints only signing-variable names and presence booleans, and produces no package. Its `signed-private` mode is protected by the `devhud-private-build` environment and fails closed unless every platform/store/updater signing input is present, `apps/devhud/updater-trust-root.json` declares the matching production-ready public root, and `pnpm --filter devhud release:validate-updater` confirms exactly one active matching native declaration for every trust-root constant. Output readiness is always `private-signed-candidate` with `publicReady: false`; unsigned output must never be renamed, described, or uploaded as public-ready. This workflow has no tag push, GitHub Release creation, store submission, OCI registry push, or deployment step.

The exact primary artifact names are:

- macOS: `devhud-macos-x64.dmg`, `devhud-macos-x64-macos-app.tar.gz`, `devhud-macos-arm64.dmg`, and `devhud-macos-arm64-macos-app.tar.gz`.
- Windows: `devhud-windows-x64-windows-msi.msi`, `devhud-windows-x64-windows-nsis.exe`, `devhud-windows-arm64-windows-msi.msi`, and `devhud-windows-arm64-windows-nsis.exe`.
- Ubuntu: `devhud-ubuntu-x64-linux-appimage.AppImage`, `devhud-ubuntu-x64-linux-deb.deb`, `devhud-ubuntu-arm64-linux-appimage.AppImage`, and `devhud-ubuntu-arm64-linux-deb.deb`.
- Stores: `devhud-ios-arm64-app-store.ipa` and `devhud-android-arm64-armv7-google-play.aab`.
- Extension: `devhud-chrome-web-store.zip` and its byte-equivalent `devhud-chrome-github-validation.zip`.
- OCI layouts: `devhud-api-linux-amd64-arm64.oci.tar` and `devhud-api-sweeper-linux-amd64-arm64.oci.tar`, each containing linux/amd64 and linux/arm64 images and never being pushed by this workflow.

The two macOS apps use the hardened runtime and Developer ID signature before their DMGs are notarized and stapled. Windows executables and both installer formats use only the configured PFX through `signtool` with SHA-256 and an HTTPS RFC 3161 timestamp. The App Store IPA embeds the signed Deck widget and intent extensions; every embedded bundle must use an unexpired App Store profile and Apple Distribution certificate bound to its exact team and bundle ID, with production entitlements including `get-task-allow=false`, before IPA evidence is recorded. The signed Play AAB contains both production ABIs and the Deck widget provider; its self-signed upload certificate is authenticated by the configured SHA-256 fingerprint rather than public PKIX trust. Desktop packages retain the exact `cef-pins.json` runtime/helpers, CEF sandbox, tray lifecycle, package-kind updater marker, and Native Messaging host. Private macOS builds compile the explicit `macos-app` marker, and AppImage lifecycle smoke supplies the installed image and extracted AppDir as one correlated updater environment. NSIS registers the installer-owned host manifest after installation and unregisters it before removal. MSI performs checked per-user registration as a deferred action before installation commits and unregisters it during rollback; the shared idempotent host lifecycle is exercised for every other desktop package during clean install/launch/quit/uninstall validation.

Google Play widget evidence is fail-closed: checksum-pinned bundletool inspection of the signed AAB's final merged base manifest must confirm the exact non-exported `DevHudWidgetProvider` receiver, `APPWIDGET_UPDATE` action, and provider metadata.

Updater material is generated independently for the ten exact installed package targets under `updater/manifests/stable/<platform>/<architecture>/<package-kind>.json`, and artifacts above the native client's 512 MiB limit fail before signing. Detached artifact and manifest Ed25519 signatures live only under the parallel `updater/signatures/` tree. They are not platform code-signing evidence and are not Sigstore bundles. Component-bearing SPDX 2.3 SBOMs live under `sbom/`; each producing job scans the unpacked application, installed package layout, or explicit OCI archive source before upload, and assembly rejects a missing or empty inventory instead of scanning an opaque outer file or creating a placeholder. SLSA v1 in-toto provenance statements under `provenance/` bind the exact GitHub Actions run attempt and actual workflow build start/finish timestamps, target validation evidence lives under `validation/`, and keyless Sigstore bundles live under `sigstore/`. Every bundle is verified against the exact executing `delinoio/oss/.github/workflows/package-devhud-private.yml` GitHub workflow identity and the `https://token.actions.githubusercontent.com` issuer. `scripts/release/generate-checksums.sh` recursively sorts relative artifact paths and writes deterministic `SHA256SUMS`; its `--sigstore-dir` keeps Sigstore output separate and it never removes `.sig`, `.pem`, or updater signatures.

Before the private candidate is retained, release validation checks exact names, source/store versions and targets, CEF helpers and sandbox metadata, tray behavior, Native Messaging identity/registration/removal, mobile widget and ABI inclusion, extension ZIP parity, platform and updater signatures, all checksums, component-bearing SPDX documents, run-attempt-bound provenance subject digests and timestamps, non-root dual-architecture OCI layouts, embedded migrations and administrator assets, PostgreSQL-backed migration/API health/sweeper schema readiness, desktop clean lifecycle behavior, and raw or Base64-decoded signing-secret absence. Mobile store inputs receive signature and static archive/widget/ABI validation, including the embedded iOS profile, signer, identity, and production-entitlement policy and the pinned Android upload-certificate fingerprint; this workflow does not claim that those device-only artifacts passed install, launch, or quit checks. A failed or incomplete check leaves no candidate classified as signed.

## Coordinated Public Release

Maintainer procedures for the exact private/public job, artifact, service, store, extension, widget, OCI, backup/recovery, support, and high-severity boundaries are in `docs/apps-devhud-operations-contract.md`. The monthly read-only CEF comparison is defined by `.github/workflows/devhud-cef-security-review.yml`; it never changes the committed pin or publishes a release. A high-risk CEF response requires a reviewed pin update in `apps/devhud/cef-pins.json`, every authoritative Cargo and verifier pin consumer, matching `Cargo.lock` entries and contract evidence, a complete compatibility matrix, a new signed candidate, and an explicit all-ten-manifest updater decision.

`.github/workflows/release-devhud.yml` is the dedicated manual public-release controller. One fixed project-wide concurrency group serializes every requested version. It accepts only the exact stable version in `packaging/devhud/release-metadata.json`, passes dispatch input through the environment before shell use, runs only from `refs/heads/main`, derives `devhud@v<version>`, and rejects an existing tag unless it already targets the same 40-hex source commit. `dry-run` produces the redacted plan and invokes the reusable private workflow in `plan-only` mode. `release` retains its sole complete revision/run/attempt-bound candidate and a candidate-bound non-secret release-configuration fingerprint for 35 days so both survive the protected review window. A later dispatch or rerun attempt discovers and downloads the oldest retained candidate for the exact version and source revision across every attempt of every matching historical or current recovery run instead of signing new bytes; historical recovery fails when the original configuration binding is absent, expired, duplicated, or differs from the current protected environment. It preserves the original provenance run identity and validates the destination binding before any external release access, submission, image push, deployment, release, updater exposure, or documentation publication.

The ordered public state machine is private validation, complete live preflight, held store review, infrastructure preparation, all stores public, regular GitHub Release, all desktop updater manifests public, public documentation, independent verification, and finally GA. App Store manual release, Google Play managed publishing, and Chrome deferred publication keep approved packages held. App Store package processing is polled read-only before one idempotently reconciled submission sequence; an absent exact version is created only after the exact uploaded build is processed, while an existing processing or processed build suppresses another transporter upload. An exact pending-review, approved-held, or public status is reconciled without another package upload or submission. Store review delays leave the protected `devhud-store-review-approved` job pending; the operator resumes it only after each service reports the exact approved-and-held version. Before live access, the OCI registry credential username must match the protected `DEVHUD_OCI_PRODUCTION_PUSH_PRINCIPAL` that operators have confirmed can push both exact configured repositories; the authenticated registry-root probe remains connectivity evidence and is not treated as repository authorization. A recovery dispatch after one store became public accepts the exact mixed public/approved-held set, skips every completed store mutation, and rolls the remaining approved provider forward. Every downstream environment-bound OCI, infrastructure, updater, public-doc, store-publication, cleanup, and GA job must match the complete preflight release-variable fingerprint, including the Chrome extension and OCI push-principal identities, before its first external check or mutation. `devhud-store-publication` is the protected point at which managed Google Play publication is confirmed; after its fingerprint match, it idempotently releases the approved Apple and Chrome packages and polls all three exact versions for up to 30 minutes until independently public. A same-commit retry, which can exist only after the regular release created its tag, instead requires every exact store version to remain public and performs no store submission or publication mutation. It reconciles and publishes an existing draft GitHub Release, but downloads and authenticates an already-published immutable release against the retained candidate without deleting, replacing, uploading, or editing its assets before resuming the remaining idempotent channel work. Final verification requeries all three exact stores, resolves the live remote release tag to the workflow source revision, downloads the exact regular GitHub Release asset inventory, and requires the release index plus every keyless-signed provenance statement to bind that revision. It also authenticates the checksum manifest, every public asset, and every extracted SBOM, provenance, validation, and updater-signature payload with its included keyless bundle, then validates every public updater manifest against its downloaded package bytes. After its protected approval wait, `devhud-ga` again matches the preflight fingerprint, repeats the complete remote verification, and permits final bilingual release notes and the GitHub latest marker only while API, sweeper, stores, GitHub Release, updater, and public docs remain verified. There is no beta, fractional rollout, phased release, partial GA, or early announcement path.

The API host is not selected by repository automation. An operator-provided OIDC-authenticated release controller maps immutable signed API and sweeper image digests, migrations, embedded administrator assets, and signed updater inputs to the chosen hosting platform. Every controller request binds the selected release revision separately from the workflow authorization revision in the GitHub OIDC `sha` claim; historical recovery is accepted only when the controller independently verifies that the selected revision is an ancestor of the newer authorization revision. Updater controller input is rebuilt deterministically from only the signed manifests and signatures with normalized ordering, ownership, modes, timestamps, and gzip headers so an identical candidate produces an identical request digest on retry. Its contract is documented in `docs/servers-devhud-release-controller-contract.md`. Every failure or cancellation after store submissions begin and before publication, including a failure or timeout while polling the final store-publication gate, enters exact-provider cleanup. Cleanup queries every exact store state before any withdrawal and stops without mutation if one is public. When API promotion was attempted, cleanup rolls back only after withdrawals are verified and the exact controller status reports both candidate API and sweeper channels authoritative, including when the promotion response was lost; an inconsistent pair fails closed. Automatic rollback is permitted only before the first store becomes public; afterward recovery is roll-forward or coordinated emergency withdrawal, never an automatic cross-channel rollback.

The workflow starts with `permissions: {}`. Read-only jobs request `contents: read`; only controller-facing jobs request `id-token: write`; only the GitHub Release and final GA jobs request `contents: write`. Store and deployment credentials are protected environment inputs rather than repository output, and plans, fixtures, status artifacts, and errors contain names or presence booleans only.

## Implemented Diagnostics Boundary

Diagnostics reporting is implemented without analytics, a persistent user/device identifier, or remote feature flags. The app generates UUID v7 report correlations, physically prunes structured redacted local events and Connect breadcrumbs to their bounded retention at startup and on later reads, and remains useful offline. Both collections retain their bounded session-memory fallback when Web Storage writes fail, persist it when storage recovers, and clear it at destructive cleanup boundaries. Local normalization and recursive export redaction decode percent-encoded octets and rescan to a bounded fixed point before applying the locator and sensitive-content exclusions, rejecting input that remains unstable beyond the bound. Native snapshots report the installed operating-system version. Browser execution is represented by its own diagnostic platform with empty native runtime revisions; it uses architecture Client Hints when available, maps unsupported browser ARM32 hints to the browser-only unknown architecture, and otherwise uses unknown when the hint is unavailable, so browser guests retain truthful preview/export instead of impersonating a native desktop host. Guests may preview and explicitly export a bounded redacted JSON bundle to a user-selected destination, but cannot submit, and the empty-event status appears only after Preview inspects storage. An authenticated, unblocked user must preview the exact immutable protobuf payload and consent to its SHA-256-bound contents for every individual submission; reporting is otherwise off, and stale completions from a superseded preview cannot update its state or correlation. Export activations serialize until the active destination request settles. Desktop logout and account-deletion purge invalidate any older pending save-dialog result before purge completes, so it cannot write a captured pre-purge bundle afterward; local diagnostic event and correlation writers also remain suppressed through logout and purge-claimed irreversible cleanup transactions. Blocked/deletion-pending users are denied, and typed authorization/unavailability failures retain safe codes and correlation IDs in the UI. Export returns saved/cancelled/initiated without exposing the selected path and does not expose a generic filesystem primitive; initiated means an unobservable browser download was requested rather than confirmed saved. Failed iOS temporary-copy or Android partial-destination cleanup returns a storage failure and remains retryable instead of reporting success while retaining data. Android excludes the System WebView directory containing local diagnostics from cloud backup and device transfer. Connect response correlations, client failures, Go request logs, traces, and metrics use request/report UUIDs only; TypeScript and Go crash-report validation accept only HTTP(S) diagnostic URLs and reject credential-bearing URLs, standalone credential assignments, and non-web schemes before persistence, including when the URL scheme follows identifier characters, while unexpected diagnostics repository failures add only bounded cause categories and validated SQLSTATE values. Server reports cascade on account purge and expire exactly 30 days after acceptance.

The retained crash-report cap is exposed to clients as the typed `QUOTA_KIND_CRASH_REPORTS` quota failure with its fixed 100-report limit; the app renders that classification and server-provided limit separately from transient submission failures.

## Implemented Local-Agent Boundary

Desktop RealQA can optionally use existing local Codex `0.147.0`, Claude Code `2.1.233`, or OpenCode `1.18.18` executables. The feature is absent on mobile and browser hosts, disabled by default, accepts only exact versions found on `PATH` (including Windows `PATHEXT` shims) or at an explicit absolute device-local path, reports typed health, and never installs an agent. Repository prompts include the issue tracker but remain device-local; legacy v6 prompt/profile records are migration input only and schema-v7 synchronized writes reject them. Draft mode runs with read-only/no-tool-network controls and returns schema-validated title/body JSON for user review. Direct mode is separately warned at enablement and confirmed for every submission, but every adapter remains read-only and credential-free, receives neither the selected PAT nor the writer input/command, and returns only marker-bound readiness. DevHUD alone resolves the device-local PAT and runs the exact argv-based `gh api` write over a private issue-input file. It validates the host-written canonical URL and UUID-v7 submission marker against the fixed repository and reconciles the marker through GitHub before deleting a draft. Finalized official uploads are deleted after definite pre-write failures and preserved only once the DevHUD writer starts and a write becomes ambiguous.

Every run receives an immutable, bounded envelope fixing repository, labels, projected public images, sanitized diagnostics, repository prompt, and marker. Public images may use HTTPS or loopback HTTP in development, always without credentials, queries, or fragments, and issue bodies retain the shared 65,536-character limit across TypeScript and Rust boundaries. Prompts and untrusted repository instructions cannot widen that envelope; argv/stdin invocation avoids renderer or shell interpolation, child environments are allowlisted, and prompts/output/environments/full paths are never logged. Runs use a private full-history managed clone fetched before reuse plus a disposable full clone, never a user working copy; LFS smudging and submodules are disabled. The managed cache is limited to 50 GiB with LRU eviction, refreshes the remote default branch, supports never-pushed repositories, removes interrupted unmanifested publications, and reclones once when disposable cloning exposes corruption. Private HTTPS clone authentication uses ephemeral askpass, an empty private global Git configuration, disabled credential helpers, and no credential-bearing URL, argv, log, or Git config. Cancellation is retained across registration races, terminates the process tree, and every run has a 15-minute ceiling. Every error retains the draft and presents explicit retry/manual choices without automatic fallback.

## Cross-Domain Invariants

Each fresh supported DevHud desktop process creates its CEF main window with native maximization (not fullscreen), retaining native decorations and the operating system work area; its restored and minimum inner sizes remain 960×640 and 640×480. Tray, deep-link, and shortcut restoration only unminimize, show, and focus an existing window, preserving any later user-selected size or maximization state for that process.

Server-settings adoption rehydrates the current device's shortcut bindings and repository prompts for retained agent descriptors before updating the authenticated cache, and clears a guest import only after that cache write succeeds. A synchronized replacement response or conflict rehydrates from the latest completed device-local save instead of overwriting it with the request-time shortcut or repository-prompt snapshot.

Native Messaging configuration is accepted only when every concrete Chrome origin is covered by its mapping scheme, host, and normalized port, every mapping ID is a canonical lowercase UUID v7, and the projected configuration fits inside both complete 256 KiB IPC and Chrome response envelopes before settings persistence. Native validation repeats those checks defensively. Renderer replacements serialize in publication order so stale invocations cannot overwrite newer settings, and the latest snapshot retries with capped backoff after a transient bridge failure. Host-side IPC applies one absolute five-second deadline to every complete framed authentication or forwarded read/write, including waits and retries when every Windows named-pipe instance is busy. The desktop Tauri wrapper rejects caller `-t`/`--target` overrides and copies the exact host executable reported by Cargo under Cargo's effective artifact target and suffix.

Chrome capture rechecks the configured origin's Chrome-valid scheme-and-host optional permission before injection, passes the exact configured origin including its normalized port into the injected function for validation before any page context is read, refreshes configuration after every injected capture, chooses a mapping from the fresh configuration and post-capture live URL, binds native authorization to that response's opaque revision, and cancels abandoned selections after 30 seconds without sending the live URL to the host. Sanitized URLs use canonical serialization and the native boundary rejects noncanonical originals before persistence. UTF-8 truncation bounds work and temporary allocation by the configured output cap even for extremely large untrusted page strings, and ill-formed UTF-16 page strings become well-formed Unicode before crossing the JSON boundary; fixed allowlisted attributes are read directly by name without enumerating untrusted attribute collections, and capture excludes zero-area or fully clipped elements before selection or subtree traversal. Interactive selection scans at most 10,000 page elements, degrades to manual repository selection beyond that bound, keeps the complete pointer, touch, and compatibility mouse sequence inside an isolated full-viewport iframe presented through a modal top-layer dialog, performs coordinate hit testing before suppressing completion, and retains that shield long enough that inspecting a control cannot activate the page even when page top-layer content is open. Selected-subtree serialization separately visits at most 10,000 total nodes, including text nodes, and degrades to capture without browser context when that bound is exceeded. Its localized focusable dialog also cycles eligible elements with `Tab`/`Shift+Tab`, confirms with `Enter` or `Space`, cancels with `Escape`, and restores prior focus. After successful pairing, the extension popup refreshes configured origins immediately so their permission actions are available without reopening it, and each action has a localized accessible name containing its concrete origin. The service worker removes optional HTTP(S) grants that are no longer configured after every successful configuration refresh, including capture refreshes while the popup is closed, while failed or superseded refreshes preserve existing grants and superseded successful responses become non-authoritative before callers can use their payloads. Native IPC mutually authenticates the host and app, recovers once without a nonce when a completed pairing's initial authentication result is lost, reauthenticates a closed idle session once without reusing a pairing nonce already consumed by successful authentication, skips canonical host registration in development launches, and removes pairing credentials when the host is unregistered. A secret-bound revocation-only authentication scope lets a live app acknowledge generation invalidation before unregister succeeds, including while first pairing is pending; an absent app is cleaned up directly. Windows registry cleanup treats a missing key as idempotent success, while every other deletion failure makes unregister fail so NSIS removal aborts before deleting installer-owned files. The desktop pairing UI refreshes until extension pairing completes or the native-returned code lifetime expires, then clears the code and stops polling.

Debian removal discovers affected users from that marker independently of the optional Chrome manifest, enters every affected active user session, and completes authenticated revocation plus pairing-secret cleanup before deleting user or system registration; a missing session or cleanup failure retains the marker and aborts removal while the package host remains available for retry.
- Deck refresh intervals of 1/5/15/30 minutes apply only while a client is active and able to poll. Mobile widgets and local notifications use OS-controlled best-effort refresh scheduling, show stale state with the last successful refresh, and never imply freshness when suspended execution has delayed polling.
- Account recovery is exposed as authenticated, ownership-checked, idempotent `AccountService.RestoreAccount` during the 30-day window; restore clears only the deletion-state block and never clears an independent administrative block. Restore and final purge serialize on the account state, and after purge claims the account no restore can succeed. Calls after the window fail with `FailedPrecondition`.
- After deletion, clients immediately delete PAT/R2 secrets and account-local data except unsubmitted RealQA drafts, which remain encrypted through recovery, retry cleanup whenever pending deletion is observed, and retain the current Logto recovery session until restore, logout, recovery expiry, or completion of irreversible purge-claimed cleanup. Pending-deletion Web Storage cleanup is best-effort and cannot block native PAT/R2 credential purge, but incomplete enumeration or removal is surfaced and retained as retry state. Logout requires contracted local cleanup to complete before the authoritative secure-store purge; an incomplete local wipe leaves the secure session available and delays the completed signed-out transition so the logout action can retry without exposing prior diagnostics to a later guest session. Purge-claimed accounts never expose Restore or authenticated product access; they retain the session only as a restart-safe cleanup marker and defer native purge until contracted local cleanup succeeds. Logout remains the complete local wipe boundary; operating-system permission grants remain OS-controlled while DevHud deletes its consent and permission records.
- Official desktop updates use the fixed HTTPS manifest endpoint `https://devhud.api.delino.io/updates/{channel}/{platform}/{architecture}.json`, served by the API deployment; v1 exposes the `stable` channel and maps `darwin-x86_64`, `darwin-aarch64`, `windows-x86_64`, `windows-aarch64`, `linux-x86_64`, and `linux-aarch64` artifacts explicitly. Installers pin the `devhud-release-root-v1` public-key fingerprint, key rotation requires signed successor metadata chained to that root, unknown or invalid signatures are rejected, versions cannot roll back without signed rollback authorization, pre-install failures and successful rollbacks preserve the last known-good installation, and committed or uncertain on-disk changes retain restart-only recovery.
- Updater cancellation remains authoritative over late worker results; open approvals defer Deck-link consumption; AppImage selection and replacement require the running executable to belong to the `APPDIR` paired with `APPIMAGE`; and unsuccessful NSIS exits retain uncertain-install restart-only recovery. API observability classifies concrete updater manifest paths under one fixed route-template label.
- Linux package builds derive exactly one compiled `linux-deb` or `linux-appimage` marker from an explicit bundle selection and reject default, mixed, or conflicting selections; unmarked Linux binaries without a correlated AppImage environment remain unsupported instead of assuming the running binary came from a Debian package.
- The implemented updater follows `docs/apps-devhud-updater-contract.md`: bootstrap cannot override discovery; checks return and emit `checking` before launching discovery with blocking-client ownership confined to generation-guarded blocking workers at 30 seconds and each 24 visible, unminimized, focused hours with an overdue-resume check, while a due attempt colliding with an active updater flow is consumed without overwriting its state; stored manifests must be structurally valid schema-one signed envelopes and verified manifests reject non-canonical artifact digests before approval, while large artifact transfers use an async-only transport with one bounded two-hour deadline across redirects and the streamed body, retain typed bounded HTTP failure metadata, and authenticate incrementally without a second package buffer, preserving only provider-issued signed redirect queries; installed package type is selected natively, with exactly one MSI/NSIS or Debian/AppImage bundle marker compiled into each Windows or Linux package; the Settings UI exposes no action while updater support is loading or unsupported; English/Korean release notes and separate focus-trapped download/install/restart confirmations are required, with download approval bound to the displayed candidate, connected focus restoration, modal stacking above persistent capture UI, and native global shortcuts suppressed without replay while an approval is open; final restart approval publishes `restarting` before package installation and restart waits execute on a generation-guarded blocking worker, then emits the committed terminal snapshot before returning or exiting; terminal failures release verified package bytes; replacement restart hands off single-instance ownership and the Unix Native Messaging listener, reaps a timed-out child, restores both explicitly, and exits the old process if restoration fails; macOS swaps bundles atomically on the destination volume and does not claim either candidate-sync or relaunch rollback is preserved until the rollback parent sync succeeds; committed Debian/Windows installs cache their pre-install executable path for restart-only retry when relaunch fails, Debian `pkexec` authorization exits remain pre-install failures while other unsuccessful installer results retain the same recovery path and preserve their uncertain-install diagnostic across failed restart retries, byte-preserving AppImage sibling backup, replacement, rollback, and cleanup directory entries are made durable, failed AppImage rollback retains restart-only recovery, and MSI exit code 3010 enters the confirmed recovery state; updater networking is absent from frontend capabilities; and non-cancellation worker and restart-retry failures are logged with typed, redacted diagnostic metadata. Release publication remains blocked by the exact-declaration production trust-root readiness gate until release engineering supplies the production public key, while native signature fixtures use a separately injected public test root.
- Administration requires the `devhud-admin` Logto role, recoverable rejection of callbacks whose tab-local nonce is unavailable, mandatory Unicode-trimmed and NFC-normalized non-blank NUL-free mutation reasons capped at 4 KiB of well-formed UTF-8 with credential patterns, configured public asset locators including recursively percent-encoded forms, and local-path patterns rejected before submission and persistence while ordinary percent signs remain valid, audit records that return only validated reasons and use a bounded client-cancellation-independent context for synchronous rejections, claim-time authorization and prior-state projection for irreversible upload removal, capability-gated and request-scoped quota inspection that rejects missing users, reads global and per-submission counters from one database snapshot, and preserves typed recovery metadata, pending mutation dialogs that cannot close before their request settles, explicit conflict refresh, 512-byte UTF-8 search validation, guarded query-scoped continuation, complete English/Korean labels, browser-locale fallback when Web Storage is unavailable at startup, and no synchronized-settings-content display.

# servers-devhud-api-contract

## Scope

`servers/devhud-api` is an implemented stateless Go foundation backed by PostgreSQL and external Logto. It registers `BootstrapService`, `SettingsService`, and `AccountService`; Upload, Diagnostics, Admin, R2 integration, embedded admin assets, and updater serving remain planned and are deliberately not registered as placeholder handlers. Its fixed development port is `46307`. The separate implemented `devhud-api-sweeper` Go worker/OCI job performs bounded post-recovery account purge and request/audit retention cleanup and is not part of request-serving API replicas; R2 staging cleanup is added with UploadService.

## Runtime and Language

Go service using `log/slog`, Connect RPC, embedded migrations, database-independent `/healthz` and schema-aware `/readyz`, OpenTelemetry-compatible traces/metrics, Prometheus `/metrics`, and separate non-root OCI targets for the API and sweeper. Liveness requests are not persisted to PostgreSQL request logs. The implemented REST surface is limited to health/readiness and metrics. Future REST remains limited to embedded admin assets, public CDN behavior, and the signed updater manifest route at `/updates/{channel}/{platform}/{architecture}.json`; the API deployment will serve that route from the fixed `https://devhud.api.delino.io` origin.

Run migrations with `go run ./servers/devhud-api/cmd/devhud-api migrate`, run the API with the `serve` argument, and run the sweeper continuously or once with `--once`. The API image defaults to `serve`, while a runtime argument such as `migrate` replaces that default command. Runtime configuration uses `DEVHUD_DATABASE_URL`, `DEVHUD_PUBLIC_API_URL`, `DEVHUD_LOGTO_ISSUER`, `DEVHUD_LOGTO_AUDIENCE`, the four `DEVHUD_LOGTO_{DESKTOP,IOS,ANDROID,ADMIN}_CLIENT_ID` values, `DEVHUD_ADMIN_REDIRECT_URI`, `DEVHUD_PUBLIC_ASSET_BASE_URL`, and a comma-separated Base64 `DEVHUD_IDENTITY_HMAC_KEYS` key ring whose first value is active. Production additionally requires `DEVHUD_LISTEN_ADDRESS` and at least one `DEVHUD_TRUSTED_PROXY_CIDRS` entry because TLS terminates at a trusted reverse proxy before the plaintext service listener; that origin listener accepts HTTP/1 and h2c so the proxy can preserve native gRPC. The sweeper accepts bounded `DEVHUD_SWEEPER_BATCH_SIZE` (1–500) and `DEVHUD_SWEEPER_INTERVAL` (1 second–1 hour), and its PostgreSQL pool must allow at least two connections so coordinated work retains capacity behind the session-level lock. Sweeper pool creation and schema readiness share a signal-aware 15-second startup deadline; each continuous or `--once` iteration has a fixed 25-second execution deadline and preserves an earlier parent cancellation or deadline. Optional standard OpenTelemetry exporter variables enable OTLP traces. Development rejects any listen address other than `127.0.0.1:46307`.

A trusted direct proxy must provide exactly one `X-Forwarded-Proto` value equal to `https`; comma-separated chains and repeated fields are rejected. Direct loopback HTTP is a development-only exemption, so production loopback proxies must also be configured as trusted and provide forwarded HTTPS. API request execution is bounded to 25 seconds even when a client omits `Connect-Timeout-Ms`, while a shorter caller deadline remains authoritative; PostgreSQL repository calls inherit that bound. OIDC verification, including a remote JWKS refresh, is bounded to five seconds or the caller's earlier deadline. Invalid tokens return `Unauthenticated`; transient JWKS timeouts, network failures, rate limits, and upstream server failures are safely logged with correlation/procedure metadata and return `Unavailable` without exposing credentials. Either the standard generic `OTEL_EXPORTER_OTLP_ENDPOINT` or trace-specific `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` enables OTLP traces, with exporter-defined signal-specific precedence. Release API images pass `VERSION` as a Docker build argument, which is linked into the Bootstrap API version; omitted local builds retain `0.1.0-dev`.

## Users and Operators

DevHud guest/authenticated clients, self-hosting operators, `devhud-admin` operators, and deployment/release operators.

## Interfaces and Contracts

Services in package `devhud.v1`: `BootstrapService.GetBootstrap`; `SettingsService.GetSettings`/`ReplaceSettings`; `UploadService.CreateUpload`/`FinalizeUpload`/`ListUploads`/`DeleteUpload`; `AccountService.GetAccount`/`DeleteAccount`/`RestoreAccount`; `DiagnosticsService.SubmitCrashReport`; and `AdminService.ListUsers`/`SetUserBlocked`/`GetUserUsage`/`ListUploads`/`QuarantineUpload`/`DeleteUpload`/`ListAuditEvents`. The implemented foundation registers Bootstrap, Settings, and Account only; the other generated services retain this contract for later slices. `GetBootstrap` is unauthenticated. Settings require an authenticated, unblocked user; account methods require authenticated ownership, with `RestoreAccount` limited to the 30-day recovery window. Future uploads and diagnostics require an authenticated, unblocked user; user `ListUploads` returns only actor-owned records and user `DeleteUpload` requires ownership; future admin methods require the `devhud-admin` role. Bootstrap supplies protocol/API version, Logto issuer/audience, the native callback URI `devhud://auth/callback`, public client IDs keyed by `desktop`, `ios`, `android`, and `admin`, the deployment-configured exact admin redirect URI, public asset base URL, static capabilities, and enforced protocol limits; it is not a remote feature-flag channel. The foundation advertises only `SETTINGS_SYNC` and `ACCOUNT_RECOVERY`. The admin SPA uses Authorization Code with PKCE and state/nonce validation: development uses `http://localhost:46306/auth/callback`, while the embedded deployment uses the API origin's `/admin/auth/callback` path.

The server implements the generated Connect-Go handlers directly; no duplicate REST business API is permitted. Service-owned identifiers are canonical lowercase RFC 9562 UUID v7 values and schema versions are unsigned. Every successful response contains `ResponseMetadata` and every Connect error, including handler-generated decoding and protocol errors, carries `ErrorMetadata`; their UUID-v7 correlation ID matches the exposed `x-devhud-correlation-id` header. Bootstrap uses explicit platform client fields and explicit native/admin redirects, and its capability enum values are static compatibility declarations.

Use `Unauthenticated`, `Unavailable`, `PermissionDenied`, `InvalidArgument`, `Aborted`, `ResourceExhausted`, and `FailedPrecondition` for the contracted failure classes. Invalid administrator mutation reasons return `InvalidArgument`. `RestoreAccount` requires authenticated ownership, is idempotent during the 30-day recovery window, cancels only the pending deletion-state block, and never clears an independent `AdminService.SetUserBlocked` administrative block; calls after the window return `FailedPrecondition`. An administrative block continues to gate all operations that require an unblocked user. Attach a UUID v7 correlation ID to every response/log context and return it in the `x-devhud-correlation-id` response header. The API never proxies GitHub or R2 upload bodies, stores Deck results, polls Decks, receives webhooks, or acts as a GitHub credential broker.

Settings snapshots are at most 1 MiB of RFC 8785 canonical UTF-8 JSON bytes. No stored snapshot is represented by absence; expected revision zero creates revision one, every matching replacement increments the revision exactly once, and stale writes return `Aborted` with `SettingsRevisionConflict`. List RPCs default to 50 records, reject page sizes above 100, reject opaque tokens above 2 KiB, scope tokens to the authenticated actor plus normalized filters, and order newest-first with UUID descending as the tie-breaker. Invalid page input returns `InvalidArgument`.

The API CORS allowlist is exact: `http://localhost:46305`, `http://127.0.0.1:46305`, `http://localhost:46306`, `http://127.0.0.1:46306`, and the pinned Tauri shell origin `http://tauri.localhost`. The implemented Connect handlers and preflight permit only `POST` and `OPTIONS`; GET may be enabled per procedure only when a read-only handler explicitly declares no-side-effects idempotency. Preflight permits `Content-Type`, `Connect-Protocol-Version`, `Connect-Timeout-Ms`, and `Authorization`, exposes `x-devhud-correlation-id`, and otherwise exposes only required Connect response metadata. Origins, methods, and headers are not wildcarded. The private R2 staging bucket uses a separate exact CORS policy with the same five origins, `PUT` and `OPTIONS` methods, `Content-Type` and `x-amz-checksum-sha256` request headers, and `ETag` response exposure; it has no wildcard origin, method, or header.

## Storage

Readiness resolves the migration ledger through the database connection's configured search path and compares the exact ordered embedded migration-name set with that ledger; a missing expected migration or an unknown ledger entry is not current. The restore-retry migration retains an internal copy of the original recovery deadline so retries are idempotent only while that window remains open.

Request logs retain HTTP transport status and, for registered Connect/gRPC procedures, the canonical protocol status independently so gRPC and gRPC-Web failures carried over HTTP 200 remain observable.

The implemented migration persists users, schema-versioned settings snapshots/revisions, purged-identity tombstones, request logs, and pseudonymized audit events in PostgreSQL. It constrains request-log expiry to 30 days and audit expiry to 180 days at the database boundary. Future migrations persist official uploads/tombstones, upload groups, submission counters, blocks/admin actions, and opt-in crash reports, with private R2 staging/public assets. Signed upload URLs are one-time; staging expires after 24 hours. `CreateUpload` requires an explicit `CreateUploadTarget`: `new_submission` carries no IDs and creates a server-owned UUID v7 submission and first group, `new_group` carries an owned submission ID and creates a group, and `existing_group` carries both owned IDs for another upload in that group. Reject an absent request target or unset target oneof; `FinalizeUpload` must provide both IDs returned by the reservation. Enforce 50 MiB/object, 10 finalized images per submission across all groups, 1 GiB rolling-24-hour, 20 GiB stored, 120 signed URLs/rolling-hour, and 300 public GETs/IP/minute. `ListUploads` is bounded with the shared page size/token/order contract and is filtered to the authenticated owner. `CreateUpload` atomically reserves the signed-URL issuance quota before issuing a URL and rolls back the reservation if issuance fails. `FinalizeUpload` validates that reservation without charging the signed-URL quota again; it revalidates authentication, block status, ownership, exact staging-key, submission, and upload-group binding, size, checksum, allowed image content, PNG signature, safe raster dimensions, and every other applicable quota. It must atomically recheck or reserve the submission image-count, rolling-byte, and stored-byte quota state so concurrent finalizations and multiple groups cannot bypass limits; quota failures return `ResourceExhausted`. It rejects replay and deletes invalid staging objects. Deleted/quarantined objects must first be replaced at the origin with a non-sensitive localized removal PNG, then have the public CDN purged or revalidated for the stable URL; the operation is not considered effective deletion while a cached original remains retrievable. SHA-256 values are stored and carried by protobuf as exactly 32 raw bytes; the R2 `x-amz-checksum-sha256` value is standard Base64 of those same bytes.

`CreateUploadTarget` explicitly distinguishes a new submission and first group, a new group under an owned submission, and an existing owned submission/group. The server issues and persists the upload, submission, group, quota-reservation, staging key, nonzero staging generation, expected size/checksum, expiry, and future public URL bindings. `FinalizeUpload` repeats the reservation, generation, checksum, size, and observed ETag and may promote only the exact staged generation. These bindings are immutable after issuance.

Retain request logs and crash reports 30 days; retain pseudonymized security/admin audit events at most 180 days. Account deletion blocks immediately, permits 30-day recovery, then purges synchronized settings, users, reports, official image bytes, and official-upload/tombstone metadata. Purged identities retain only a domain-separated, key-rotation-independent SHA-256 digest of the length-delimited issuer/subject identity, so removing a retired operational HMAC key cannot bypass the permanent tombstone. Restore and final purge serialize through an atomic account-state transition or row lock: purge claims the account before destructive work, records that first claim transactionally in the audit history, and restore cannot succeed after that claim. Owner IDs, object keys, checksums, and timestamps are deleted or irreversibly pseudonymized; any retained security/admin audit subset follows the explicit 180-day limit. The implemented sweeper processes recovery-complete accounts and request/audit retention idempotently in transaction-bounded batches, drains additional retention batches until both tables return a partial batch or the iteration deadline ends, prioritizes newly expired pending accounts so failed retries cannot starve them, retries safe failures without duplicating claim audits, and uses a PostgreSQL lease or advisory lock for multi-instance coordination. Expired R2 staging cleanup is added with UploadService. An indeterminate advisory-lock acquisition or failed unlock discards its database session instead of returning a possibly locked session to the pool. Release the sweeper as a separate signed/provenanced non-root OCI image alongside the API image.

## Security

Upload hardening: the first upload request creates a server-owned UUID v7 submission with its first group; later groups and finalizations carry both IDs and the submission owns the maximum of 10 finalized images across all groups. Signed URLs bind the expected 32-byte SHA-256 checksum and versioned staging object. Finalization checks PNG IHDR dimensions before decoding, rejecting width or height above 4096 or total pixels above 16,777,216, and promotes only the recorded version with conditional ETag/checksum validation.

Validate Logto credentials and admin role. Never persist or log PATs, R2 secrets, Logto tokens, DOM, screenshots outside upload ownership, issue bodies, agent output, or local paths. Official uploads require authenticated, unblocked users. BYO R2 credentials never reach this service.

Crash reports accept a schema version and typed build, platform, component, severity, code, and correlation fields. Build/code identifier strings are capped at 256 UTF-8 bytes; user-previewed redacted diagnostic summary is capped at 4 KiB and stack trace at 32 KiB. Credential patterns and local-path content are invalid in every crash string. Administrator mutation reasons must contain non-whitespace, well-formed Unicode text capped at 4 KiB of UTF-8 and reject the same credential and local-path patterns before storage. Mutation responses and `ListAuditEvents` return only reasons that passed this validation. Administrator responses and error details use only the schema's admin-safe user, usage, metadata-only upload, and audit projections; their message graph cannot reach the user-facing upload object, settings bodies, secrets, DOM, screenshots, public or signed asset locators, Deck results, agent output, or local paths.

## Logging

Use `log/slog` structured logs with correlation IDs and redaction. Request logs and metrics record canonical RPC status separately from HTTP transport status; unexpected authentication and settings repository failures retain safe diagnostic causes without exposing tokens or settings bodies. Provide safe diagnostics, health/readiness, traces, and metrics without product analytics. Crash reporting is opt-in and user-previewed.

## Build and Test

The implemented foundation validates Go format/vet/unit tests, PostgreSQL migration/integration tests including configured-schema readiness, credential-safe database configuration errors, database-independent liveness, default handler execution deadlines, Connect and JWT authentication behavior, Connect-formatted panic recovery, exact CORS/preflight/correlation behavior, HTTPS enforcement, authorization blocking, settings-read serialization with account deletion, concurrent revision conflicts, recovery and restore-versus-purge boundaries, purge-claim fairness and audit idempotency, idempotent bounded sweeper coordination, minimum pool capacity, advisory-lock acquisition/cleanup session discard, graceful request draining, request/audit retention, settings backup/restore round trips, and fixed port `46307` conflict failure. Later slices extend these gates with owner-filtered user upload listing/deletion, bounded user-upload pagination, submission-scoped quota enforcement across multiple groups and concurrent finalization, raw-byte checksum/Base64 R2 conversion, concurrent CreateUpload reservation and issuance rollback, finalization non-double-charging, empty/oversized/sensitive administrator reason rejection and audit safety, origin replacement before CDN purge/revalidation for user deletion, admin quarantine, and account purge, non-root OCI execution, SBOM/signature/provenance.

## Dependencies and Integrations

Consumes generated `protos/devhud/v1` bindings and is consumed by `apps/devhud` through `packages/devhud-api-client`. The foundation requires PostgreSQL, Logto, the public API/asset URLs, public Logto client identifiers, and an HMAC identity key ring supplied through deployment configuration; secrets never enter bootstrap. Future Upload/Admin work adds R2/public asset hosting and serves `apps/devhud-admin`. Official hosting platform remains unspecified.

## Change Triggers

Update the project index, protocol/client/admin contracts, root and server `AGENTS.md`, migrations, CI, and release contracts when RPCs, storage, retention, security, quotas, or deployment requirements change.

# typeopt Rust foundation

## Scope

`crates/typeopt` owns the CLI, private compiler integration, shared whole-program analysis, the eighteen optimization passes, the transformation pipeline, the stage-2 bundle mode, fixtures, Vite example adapter and Excalidraw benchmark harness. The CLI and output interfaces are experimental; `report.json` is schema v1 and `modules.json`/`properties.json` are schema v0. Incompatible changes require explicit documentation.

## Runtime and Language

Rust, with Node.js 24 for fixture execution and integration tooling. Pin the tsrs compiler crates to upstream revision `00f16261082fbb2465f0603c667b450d5aa6694b`; manually validate upstream changes. Keep optimizer code separate from upstream compiler code. Initial distribution is Cargo source builds for macOS arm64 and Linux x64.

## Users and Operators

Application maintainers invoke the optimizer, then separately run their bundler and behavior tests. GitHub issues provide support, without a support SLA.

## Interfaces and Contracts

Optimization has two stages with one pass inventory. Stage 1, `typeopt --project <tsconfig> --entry <file>... --out-dir <new-dir>`, analyzes application TypeScript before bundling and emits ESM. Stage 2, `typeopt --bundle <bundler-output-dir> --out-dir <new-dir>`, analyzes bundler output chunks after bundling (see Bundle Mode). `--check` performs the same analysis, in-memory transformation and size decisions without publishing output and does not require an output directory. Repeatable `--disable-pass <id>` excludes passes; unknown IDs are invalid CLI arguments. Support `--help`, `--version` and `--verbose`.

The fixed pass inventory and its stable IDs are: `property-shortening`, `property-disambiguation`, `property-ambiguation`, `finite-key-rewriting`, `unused-method-removal`, `unused-field-removal`, `constant-property-inlining`, `method-devirtualization`, `call-inlining`, `function-specialization`, `signature-reduction`, `type-directed-control-flow`, `primitive-operation-simplification`, `enum-runtime-reduction`, `discriminant-compaction`, `aggregate-elimination`, `intrinsic-specialization` and `residual-dependency-removal`. All are enabled by default. Skip reasons use stable snake_case codes.

Shared analysis covers every reachable application TS/TSX module from one tsconfig and the explicit entries: alias-resolved symbol references with their kind (declaration, alias, call, construction, write, type-only, read), public entry exports, symbols referenced from application JavaScript, computed accesses, mentioned names, names declared by external declarations, expression purity and module initialization purity. Internal exports are eligible for analysis; public entry exports, JavaScript references, module namespace objects, external declarations, unknown calls, unresolved keys, reflection, serialization, prototype mutation, decorators and declaration merging are boundaries. Type information only nominates candidates. Runtime evidence comes from source, control flow and uses; an annotation never proves a closed call graph, immutable value, impossible branch or intact intrinsic. Preserve evaluation order, effects, exceptions, property descriptors, object/function identity and observable names or arity, and preserve code when an obligation cannot be proven. Purity proofs treat runtime `typeof` of a name that resolves to no declaration, or only to ambient declarations (project `.d.ts` files, `declare` statements and libraries), as non-throwing. A declared application binding (including an imported one) needs an initialization proof because it still throws `ReferenceError` in its temporal dead zone: a class must be declared earlier in the same function, a top-level non-const enum is a hoisted `var`, and a parameter read inside its own or an earlier parameter list entry is uninitialized. An unused `typeof` initializer without such a proof is retained.

External runtime boundary for intrinsic proofs: a runtime (non-type-only) import, re-export, dynamic import or JavaScript `require` of code outside the application (an external package, a declaration-only package whose runtime is invisible, an ambient `declare module`, an unresolved specifier or a computed specifier) may replace any built-in member at initialization. Analysis treats it as an unknown patch of every built-in, so every rewrite that depends on an intact intrinsic is skipped with `intrinsic_may_be_replaced`. `import type`, `export type`, JSON, `node:` and Node core module imports, application modules (which the scan inspects itself) and bundle mode (which rejects imports outside the bundle) are exempt. The scan reads syntax and checker resolution only; it never executes or rewrites dependencies, never reads `node_modules` contents beyond normal program loading and does not change the CLI or report schema. `--disable-pass intrinsic-specialization` remains the opt-out.

Pass planners produce transformation bundles: TypeScript source edits (insertions, deletions and replacements, possibly across modules) with a stable identity, a primary pass and the cleanup passes the bundle includes. The pipeline evaluates each bundle by transpiling the affected modules before and after with equal emitter settings and accepts it only when the total emitted ESM byte count strictly decreases; source maps and reports are excluded. A bundle that needs a disabled pass is skipped; disabled transformations never run as cleanup. When a bundle removes the last runtime use of an import, the pipeline keeps module initialization with a bare import unless residual-dependency-removal is enabled and the module initialization is proven pure. Accepted bundles are type-checked; a bundle that introduces type errors is rolled back by bisection and recorded as `recheck_failed`. Syntax errors in transformed code and compiler failures fail the operation. Every round recomputes all facts from the current text; rounds repeat in deterministic order until no reduction is accepted, and property passes run once afterward.

The property passes use a whole-program, context-insensitive points-to analysis over object literals, key literals, bindings, contained objects and internal function arguments and returns across imports, re-exports and module cycles. Functions get trusted summaries only when internal, declared once and referenced only by direct fixed-arity calls or module aliases. Unknown values taint joined regions; an escape in any joined region preserves the entire group. Named and generic annotations, `typeof` queries, namespace objects and JavaScript remain property boundaries.

TypeScript modules with a leading `@ts-nocheck` comment are unchecked boundaries like JavaScript, because they disable the semantic recheck behind every transformation.

Resolve reachable workspace sources using the project's configuration. Declaration files provide external types. JavaScript passes through unchanged; node_modules is read-only external code. Reject syntax/type errors, eval, with, CommonJS module syntax (`import = require()` and `export =`, which `module: Preserve` would emit as CommonJS), unsupported configuration and project-reference orchestration with actionable diagnostics. Read configuration as data; do not execute it. Compatibility adjustments must be explicit and semantics-preserving.

Emit JS and source maps plus versioned `modules.json`, `properties.json` and `report.json`. Source maps compose every round's edits; inserted, deleted, inlined or moved code maps to the original range it replaced. Module mappings link original paths to output JS/maps, record the SHA-256 of each analyzed source and mark any module with an accepted runtime transformation as `optimized`. The `inputs` list records SHA-256 digests of configuration files and every other file the compiler read, including module-resolution metadata; consumers must reject output when any module or input changed. Property mappings include stable group identities and original/final names and describe property transformations only. Report v1 keeps the applicable v0 statistics and adds enabled/disabled pass IDs, rounds, emitted size before and after, per-pass applied/skipped counts with reason codes, accepted bundles with locations and measured byte changes, and skipped locations with reasons. Bundle savings are attributed to the whole bundle, never split among its passes. Identical inputs/configuration/options/tool versions produce identical code, mappings and reports. Exclude time and peak-memory measurements from deterministic comparisons. Zero safe changes is a valid explained result.

The Vite example validates the whole analysis snapshot at build start and substitutes mapped JS for `optimized` modules under original module identities; preserved TS modules retain the original Vite transpilation. Compose source maps through the original module identities. Keep assets in the original project and preserve resolution context. It is not a separately published plugin. Roll back one optimization by excluding its pass and rebuilding into a new directory; roll back adoption by restoring original build inputs/configuration.

## Bundle Mode

Stage 2 loads every `.js`/`.mjs` file of a bundler output directory as one closed ES module program with the standard DOM libraries and no `@types` packages; `--project` and `--entry` are not used. Static imports and literal dynamic imports in the parsed chunks link them. A chunk that no other chunk imports, or that an inline HTML script, event handler or `javascript:` URL imports, is an entry whose exports are public. HTML (`.html`/`.htm`) script URLs resolve with URL semantics against the `<base href>` parsed before each script, after decoding character references; an import map, an inline import with a non-literal or undecodable specifier, an event handler attribute (`on*`) or a `javascript:` URL in a navigating attribute (`href` of `a`/`area`, `action`, `formaction`, `src` of `iframe`/`frame`/`embed`, `data` of `object`) with a character reference this parser cannot decode (the browser decodes it before running the code, so its imports are unknown; undecodable references in other attributes are ignored), or a computed `import(…)` in any chunk makes every chunk a public entry; and classic scripts are recognized by every JavaScript MIME type essence. Chunks that import modules outside the bundle directory, including package specifiers when no page defines an import map, are rejected. A chunk is transformed only when it is known to be an ES module (an `.mjs` file, ESM statements or `import.meta`, imported by a chunk or loaded by an HTML module script); classic scripts (including chunks an HTML page loads with a classic `<script>`, even when a module also imports them, chunks that call `importScripts` and the chunks it loads (a literal target resolves relative to the calling chunk, or, for a root-relative URL, under the bundle directory after dropping leading deployment-base segments as for root-relative module imports; every chunk without ESM syntax when a target is computed), which stay in the program so that what they reach remains observed) and chunks matched by repeatable `--bundle-exclude <text>` stay unchanged unchecked boundaries. A chunk is also an unchanged boundary when its syntax needs it: a `with` statement; the global `eval` used as a value (a direct call or an alias such as `const e = eval`, `globalThis.eval`, or a destructuring such as `const { importScripts: load } = self`); and `importScripts` called through any callee form (`importScripts(…)`, `self.importScripts(…)`, `globalThis.importScripts(…)`, `self["importScripts"](…)`, parenthesized forms) or used as a value that can alias it. A chunk that a worker loads through any of these callee forms is a classic script. Mentions that run no code are not boundaries: `typeof eval`, `typeof (eval)`, `typeof importScripts`, `typeof self.importScripts`, property names such as `obj.eval`, property keys such as `{ eval: 1 }` and module export names such as `import { eval as helper }` or `export { helper as eval }`. At debug level the optimizer logs the rule (`excluded-or-classic-script`, `with-statement`, `eval-reference`, `import-scripts-call` or `import-scripts-reference`) that made each chunk a boundary. Every chunk that a boundary chunk can import, statically or through a literal dynamic `import()`, directly or through other chunks, is frozen with it: it is not edited, renamed or rewritten, because the boundary chunk keeps importing the original name and a renamed copy would be a second instance of the module. A chunk in another directory with the same file name as a frozen chunk is frozen as well (with what it imports), because references name only the file name and an edited copy could not be renamed, so immutable caches could serve its old hash with new content. Frozen chunks are reported in the report's `frozen_chunks` list (omitted when empty) with the stable reason `boundary_reachable` and the causing boundary chunk (the first one in path order), and logged at info level per boundary chunk; a warning names a boundary that a page loads as a script, because everything it imports then stays unoptimized. A boundary chunk that mentions a renamed chunk's name without importing it (for example in a string) still keeps the original, as described below.

Bundled JavaScript is not type-checked, so inferred and JSDoc types can be wrong. The bundle pass set is fixed to the passes whose proofs do not depend on static types: `property-shortening`, `property-disambiguation`, `property-ambiguation`, `call-inlining`, `signature-reduction`, `type-directed-control-flow`, `primitive-operation-simplification` and `residual-dependency-removal`. The other ten passes are reported as disabled and cannot be enabled in bundle mode; `--disable-pass` narrows the set. Identifier-like tokens of string and template literals count as mentioned names. Candidates are not parsed individually; the recheck after each round treats syntax errors (including TypeScript-only syntax) and semantic diagnostics that the original chunk did not have (chunks may opt into checking with `// @ts-check`) as failures and rolls the responsible bundles back with `recheck_failed`. Input chunks with syntax errors are rejected.

Edits apply to the chunk text, and the size gate compares the edited chunk text bytes without emitting. Output is a staged copy of the input directory with edited chunks replaced (publication fails when the copied directory differs from the fingerprint taken before analysis), source maps (located through `sourceMappingURL`, including inline `data:` maps, or adjacent `<chunk>.map` files) composed with the edits (uncomposable map references of edited chunks, such as remote, missing or outside maps, are removed; an existing local map that is malformed or unsupported is removed from the output together with its trailing `sourceMappingURL` directive, and a malformed hidden adjacent map is removed without adding a directive), and edited content-hashed chunks and text assets (`<name>-<hash>.<ext>` or `<name>.<hash>.<ext>` for `js`, `mjs`, `cjs`, `css`, `json` and `webmanifest` with an 8-character base64url hash that contains a digit, an uppercase letter, `-` or `_`) plus every hashed chunk that references a renamed chunk renamed deterministically (each new hash covers the final content of the chunk and of every renamed chunk it reaches) with every reference position in text assets rewritten (a name follows `/`, a quote, `(` or `=`; whitespace may separate it from `=` or from the `(` of a CSS `url(` token that starts its own identifier (`myurl(` and `--url(` do not count), case-insensitively, and absolute or protocol-relative URLs keep their names); names that a reference spells with URL or HTML escapes keep their original files (with the renamed files those originals reference) beside the renamed ones, and boundary chunks are never rewritten or renamed and, because the chunks they import are frozen, keep originals only for non-import mentions of renamed names; report `size.retained` discloses the code bytes of kept originals in addition to `size.after`; `--keep-chunk-names` disables renaming. Bundles with symbolic links and pages with Subresource Integrity attributes or a Content Security Policy with hash sources are rejected before analysis in check and output modes. The report v1 is printed to standard output; its `size.metric` is `chunk_text_bytes` instead of `emitted_esm_bytes`, and the gate and the report both exclude trailing source map comments. Behavior tests against the optimized directory remain the operator's responsibility.

## Storage

One-shot, in-memory analysis; no daemon, watch mode or persistent cache. Each round rebuilds the program from in-memory texts in an operation-owned allocation region. Release checker handles and the unshared program before freeing its region. Keep the checker single-threaded, leaf-file reclamation disabled and checker recycling disabled so analysis, rechecks and emit never read freed compiler objects. Compiler-owned identities never escape the private adapter. Never modify input files or an existing output destination. Stage output in an operation-owned temporary directory and publish without replacing an existing destination. Error and cancellation paths return failure, remove owned temporary artifacts and never publish a complete result.

## Security

After installation, analysis performs no network access, user-code execution or telemetry. Do not log source contents, credentials or environment values. External APIs and observable object shapes form preservation boundaries.

## Logging

Use structured Rust tracing and English stderr diagnostics. Verbose mode adds diagnostic context without source text or environment values. Measure elapsed time and peak resident memory; no performance threshold or resource ceiling applies.

## Build and Test

Run root `cargo test` after Rust changes and applicable frontend `pnpm test` after frontend changes. Compare original and optimized fixtures in Node, including side effects. Cover each optimization, combinations, structural types, unions, aliases, computed keys, accessors, inheritance, reflection, serialization, external escape, collisions, determinism, maps, malformed input, filesystem failures and Ctrl+C. Verify no input execution or network access in a restricted environment.

Bundle mode needs Node fixtures that compare original and optimized entry chunks, including chunks whose unchecked types lie, runtime-parsed member paths, generated functions, dynamic namespace access, observable arity, unimported entry chunks, classic scripts, exclusion, map composition, rehashing and determinism.

Every pass needs positive fixtures that demonstrate its transformation and size benefit and negative fixtures for its safety boundaries, run with the pass alone, in combinations and with every pass enabled and disabled; every fixture compares original and optimized Node behavior. Cover the measurement script's reference validation with synthetic builds (missing and valid references, harmless strings, remote URLs, removed unreferenced chunks, two- and three-build forms) in `crates/typeopt/tests/benchmark_measure.rs`, which requires the pinned Node and is skipped otherwise. Validate Vite with workspace aliases, TSX, unchanged JS, original assets, non-property transformations and stale transitive inputs. Pin the Excalidraw commit, lockfile, runtime, browser, production settings and compression tools before benchmarking; apply documented compatibility adjustments equally to all builds. Compare three builds: original inputs, existing typeopt at the pinned `existing_typeopt_revision` and the extended optimizer; each optimized build records the clean source revision its optimizer binary was built from. Asset sets may differ; record added and removed assets, verify that every local loading reference (HTML module scripts and modulepreloads, static imports and literal dynamic imports, quoted or a template without substitutions, with JavaScript escapes decoded) resolves to a file of its own build (HTML URLs without a `./` or `/` prefix are document-relative, JavaScript specifiers without one are bare and ignored), independent of any asset another build emits, and sum every production JS asset excluding source maps. The extended build's raw, gzip and Brotli totals must each be strictly smaller than both other builds; no minimum percentage applies.

Chromium acceptance compares drawing shapes/freehand, text/move/resize edits, undo/redo, save/reload/file import and PNG/SVG export across the three builds. Actual application acceptance cannot be replaced by fixtures. Require native build/execution on macOS arm64 and Linux x64. Retain source revision, commands, results and unperformed checks in CI artifacts or PR/issue records. Preserve existing affected CI and macOS runner restrictions.

## Dependencies and Integrations

Use immutable tsrs input and preserve all upstream licenses/notices. Repository-owned code is Apache-2.0. Vite and Excalidraw are validation integrations; the CLI never launches them. Public Rust/Node APIs, library declaration transformation, CommonJS output, JavaScript optimization outside bundle mode, prebuilt distributions and other platforms are out of scope.

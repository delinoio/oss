# DeliDev image input contract

## Scope and ownership

The feature owns first-message and follow-up still-image inputs for project sessions and General Chat. File selection, clipboard images and drag/drop share one ordered draft. Image-only messages are valid. Text retains its independent 256 KiB limit. Each message admits at most eight images, 10 MiB per image and 40 MiB combined. Accept original PNG, JPEG and WebP bytes only after content decoding; reject animation, corruption, mismatched media types and unsafe decode allocations. Do not resize, convert, OCR or replace images with text.

The owner explicitly permits the complete capability/protocol declarations and their activation in one feature PR for this issue. System capability 45, Worker capability 25, and `CreateSessionRequest.attachments` / `EnqueueInputRequest.attachments` field 5 belong exclusively to this feature. All feature allocations follow the [shared allocation workflow](cmds-delidev-structure-contract.md#allocation-workflow); a separate reservation PR or prior merge to main is not required. No SQLite migration is authorized.

## Transfer and immutable input authority

`AttachmentService` owns authenticated BeginUpload, WriteChunk, FinishUpload, GetUpload, ReadAttachment and DeleteDraftAttachment. Worker-only WatchAttachmentTransfers and ReportAttachmentTransfer relay bytes through the owning authenticated Worker stream. A chunk is at most 256 KiB and binds its offset and SHA-256. Identical repeated writes are idempotent; conflicting bytes fail. Finish validates actual content, complete length and full digest before readiness. The server retains bounded metadata only; bytes remain in private DeliDev-owned Worker storage and never enter resource, receipt or assignment JSON.

Staging binds the authenticated actor, original draft/operation UUID-v7 identities, explicit Runner ID/revision and optional original session. Acceptance atomically claims the exact ordered ready references for one original input. Image references contain only opaque ID, Runner ID, media type, length and full SHA-256. Paths and names grant no filesystem authority. Exact uncertain retries retain original input identity and cannot create duplicate claims or native sends. Replacing a Runner invalidates its draft references and requires explicit transfer to the new selection.

## Native delivery and recovery

Adapters deliver actual native image primitives under the selected original account/model/harness, permissions and execution. Enable a route only with positive source/schema and automated fixture evidence; unsupported combinations preserve the draft and report a typed error. Codex source-backed image delivery uses the native image input union, with Worker-owned private paths or data URLs only when required by that original native protocol. OpenCode uses its file-part primitive under the OpenCode profile below. Other harnesses require their independent image-input and history proofs. Image-bound Steer remains unavailable without a complete separate proof.

Ordered image identity joins immutable assignment, acknowledgment, transcript and recovery comparisons. Continuation, compaction, original lost-report recovery and first Fork-child dispatch retain the complete ordered input. Original queue-to-assignment authority and startup retries compare text, mode, skill bindings and attachment references; a matching prompt alone cannot authorize native publication or recovery. Legacy text-only identities remain byte-compatible. Empty image selections do not require an active Runner or Worker registration at queue acceptance; ordinary session, archive, queue and receipt rules remain authoritative. Nonempty image claims retain the original Runner revision and Worker Device checks. Never reconstruct missing native image history, silently omit a part, infer successful native delivery or resend an uncertain input. Image readback is authenticated and scoped to the retained session/reference; no public URLs or desktop-local paths are authority.

## Lifetime and deletion

Same-identity project and General Chat drafts survive ordinary navigation, Settings and reconnect. Identity changes dispose draft presentation and private preview URLs. Explicit removal deletes only owned unclaimed staging, through a durable pending obligation while the Runner is offline. Archive preserves accepted bytes. Independent Fork retains attachment ownership throughout its own lifetime; Sidechat workspace references acquire no parent attachment deletion ownership.

Each session retains at most 4,096 distinct unresolved image references across accepted or removed inputs, current independent Fork ownership and session-tied unclaimed drafts. Upload admission, input claims and Fork owner publication enforce this capacity in the same transaction before new metadata or Worker bytes. Replays and existing-reference transitions do not consume another slot. Deleting or quarantined obligations retain their slots; only confirmed terminal byte removal or release to another independent owner frees the original scope. Cleanup and Fork inventory use this same current-obligation set, excluding terminal draft history without erasing its receipt or proof. Keep the per-input eight-image, per-file ten-MiB and per-input forty-MiB bounds independently.

Accepted attachment cleanup joins the existing durable session deletion and backup/restore quarantine boundaries. Removal completion requires observed absence on the original Worker. Preserve images while independently owned, preserve unsettled obligations across restart, and never delete original Local files or shared account resources. No automatic retention eviction is authorized.

## Validation and observability

Log safe operation/session/Runner IDs, phases, counts and typed failures only. Exclude image bytes, filenames, paths, prompts and native payloads. Automated validation covers content/limits, chunk replay/conflicts, actor/Runner/session/reference authority, atomic acceptance, restart/uncertainty, readback, archive/Fork/Sidechat and confirmed cleanup.

The owner assigns real-account, installed-native, remote-machine and platform acceptance to their separate verification work. These checks do not block this feature's source/schema and automated-fixture acceptance. Record unperformed acceptance separately from passing fixtures/builds in PRs and CI; this exception does not weaken runtime ownership, capability negotiation or recovery authority.

## Closed adapter profiles

Codex, OpenCode and Claude Code are the enabled image routes. For Codex, the official V2 `UserInput` union at `0.151.0` revision `d8673cb68e349c208659b986697773d3145dbb14` and `0.159.2` revision `8b9fa496bbf2c47aebd62e85a080b9a522a455b5` defines `localImage` with a native path and preserves that primitive in user-message history. See the pinned [0.151.0 turn schema](https://github.com/openai/codex/blob/d8673cb68e349c208659b986697773d3145dbb14/codex-rs/app-server-protocol/src/protocol/v2/turn.rs), [0.159.2 turn schema](https://github.com/openai/codex/blob/8b9fa496bbf2c47aebd62e85a080b9a522a455b5/codex-rs/app-server-protocol/src/protocol/v2/turn.rs), and [original user-message item](https://github.com/openai/codex/blob/d8673cb68e349c208659b986697773d3145dbb14/codex-rs/protocol/src/items.rs). DeliDev resolves only validated private Worker bytes into this primitive. The pinned [image loader](https://github.com/openai/codex/blob/d8673cb68e349c208659b986697773d3145dbb14/codex-rs/utils/image/src/lib.rs) detects format from bytes, so the opaque private filename supplies no media authority. Before acceptance, every configured first-input source model must positively declare image input in saved metadata. The selected declaration is frozen as the optional `image_input_declared` configuration value; absent text-only profiles retain their original omission and digest. Follow-ups use this original snapshot, and receipt retries do not rerun current catalog selection. This declaration is an eligibility check and grants no native input authority. Before sending, a validated custom API execution requires the frozen `image_input_declared` value and does not consult the native model inventory, because Codex's bundled inventory is advisory for arbitrary provider models; an absent or false declaration rejects before input delivery with the private rejection proof, and a later upstream rejection stays an ordinary original execution error without model change, image omission or automatic resend. For managed subscriptions, the exact immutable native model must advertise the `image` input modality through the bounded native model snapshot. Text-only models, missing bytes and unresolved native metadata fail before input delivery. For managed subscriptions, only a successful complete inventory whose entry for the exact model lacks the `image` modality proves the original image rejection and its private proof. A canceled, timed-out, transport-failed, native-error or malformed model snapshot returns its original typed failure, grants no rejection proof or private rejection wrapper, and sends no turn/start. Native user-message and continuation comparisons resolve the original journal and compare the complete ordered input digest.

Claude Code accepts image-only and text-with-image inputs through its original stream-json user message: a text block when nonempty, followed by ordered `image` blocks with `source.type: base64`, the original `media_type` and original encoded bytes. Worker capability 71 `CLAUDE_IMAGE_INPUTS_V1` and System capability 106 with the same name independently negotiate this profile in addition to 25/45. Workers advertise 71 only after the server echoes it. A missing pair leaves uploads ready and unclaimed. Freeze the model image declaration only for a Worker holding the pair, and fence dispatch and queued claims against downgraded Workers. No public field or migration is added.

The original protected stdin write binds exact validated Worker bytes and ordered immutable product references. Claude Code owns image preprocessing, including resizing before replay and provider delivery; DeliDev never resizes or replaces these bytes. The native replay must use the original input UUID, exact text and ordered closed base64 image blocks with validated still-image content and matching media types. The native preprocessed bytes are not represented as the original attachment digest. Retain the exact native replay payload hash and compare its original JSONL payload before checkpoint acceptance or continuation. Native hidden image-context records require the original input ancestor, exact original/displayed dimensions and ratio, an inert absolute native-cache location under the original private native profile and scoped to the same session, and a complete ordered text-block list whose native-cache locations are distinct within the record: a record that repeats one location fails with the same history-uncertainty error (structured `claude_image_context_invalid` warning with numeric stage 8 only) before any proof is retained or any pending expectation is cleared, because equal media types and dimensions do not prove image identity. The distinctness rule adds no monotonicity or contiguity requirement and keeps the expected block order. Every expected image input must have its own hidden record: retained-history verification fails with the existing history-uncertainty error (structured `claude_image_context_invalid` warning with numeric stage 7 only) when any expected input is left without one, so a missing record grants no checkpoint or continuation authority. Pin `CLAUDE_CODE_TMPDIR` to the original native profile’s private `image-tmp` directory so native cached originals follow existing session-profile cleanup. These records add private history proofs and native identities only; their locations grant no read or deletion authority. Compaction restore and the immutable lost-report recovery comparison retain the original image-stream profile flag. Product checkpoint input digests include the original ordered references; native history hashes include Claude's actual preprocessed blocks. Never synthesize a replay, substitute text for an image or infer acceptance from a pipe write. Stream frames admit 64 MiB and the queue 128 MiB only for the declared image profile; text-only streams keep their existing bounds. History retains its independent 64 MiB total bound.

The official [Python SDK streaming transport](https://github.com/anthropics/claude-agent-sdk-python/blob/c10b52c674e5c709c7263544b38e8a5dad10e01d/src/claude_agent_sdk/_internal/transport/subprocess_cli.py) forwards original input JSON, independently of its narrower retained Python message union. DeliDev uses the native stream protocol directly. Installed-native tests must verify image blocks reach a scripted provider, original UUID replay, clean completion and exact retained history. Real-account acceptance remains separate. Grok Build retains the explicit unsupported-image error before acceptance.

OpenCode is an enabled image route for non-Sidechat Build and Plan sessions whose selected model declares the `image` input modality. Every first-input source model must declare it, and the selected declaration is frozen in `image_input_declared`; follow-ups use that original snapshot, and a text-only model, Sidechat and Grok Build return the unsupported-image error before session acceptance, leaving the upload `ImageReady` and unclaimed. The route requires the independent System 105 / Worker 70 pair `OPENCODE_IMAGE_INPUTS_V1` in addition to System 45 / Worker 25, and allocates no field or migration. Capability 25 cannot imply OpenCode support: a Worker that predates this profile advertises 25 and its shared assignment validation rejects every OpenCode configuration that declares image input, even a text-only job, before native work. The server therefore freezes `image_input_declared` for OpenCode at first execution only for a Runner Device that reports Worker 70; other devices keep the text-only snapshot and dispatch exactly as before. Admission (creation, enqueue and follow-up) and dispatch require Worker 70 for OpenCode, so no image is silently dropped and no older Worker receives a declared OpenCode assignment. A session whose first execution froze no declaration keeps rejecting later image attachments with the unsupported-image error. A Worker holding 70 without 25 is invalid peer state: AttachWorker rejects it as `InvalidArgument` and Machine validation never accepts it. The Worker advertises 70 only after the original server echoed it. OpenCode requires a nonempty text part and accepts at most 384 KiB (`domain.MaxOpenCodeInputImagesBytes`) of combined original image bytes per input, because the native server stores every image as a base64 data URL inside one message and every native response and event must stay inside the adapter's 1 MiB bound. Larger or text-less inputs fail before native work with a typed error and keep the draft. Editing an undelivered queued OpenCode message applies the same text rule for the frozen session harness, so blank text cannot keep the immutable references; removal remains allowed and an edit never reruns catalog or Worker eligibility for the already admitted references. Creation, enqueue, queued edit and every dispatch of a queued, retried, continued or forked input share this text rule; Steer rejects attachments on either side.

The pinned HTTP input part is `FilePartInput` (`id`, `type: file`, `mime`, `filename`, `url`) in the [session schema](https://github.com/anomalyco/opencode/blob/545f51d26cc39a907d2867492d498d9607ea5fa4/packages/schema/src/v1/session.ts), and the [prompt pipeline](https://github.com/anomalyco/opencode/blob/545f51d26cc39a907d2867492d498d9607ea5fa4/packages/opencode/src/session/prompt.ts) reads `file:` URLs and keeps `image/png`, `image/jpeg` and `image/webp`. DeliDev's `prompt_async` body is the text part followed by one file part per attachment in attachment order. Part identifiers derive deterministically from the text part identifier by advancing its timestamp/counter field. `filename` is the opaque ordinal `image-N.png|jpg|webp` and never the user's name. `url` is the `file://` URL of the validated private Worker file returned by `imageinput.Manager.Resolve`. Text-only bodies and `TextInputClaimDigest` stay byte-identical. The input claim digest covers the text and the ordered media type and SHA-256 of every attachment but never a Worker path, so the Worker recomputes it from its immutable assignment.

A probe of an installed OpenCode `1.18.20` (below the DeliDev baseline, used for wire behavior only) showed that the native server expands one input into the original text part, one synthetic text part per image, and one file part per image whose `url` is rewritten to `data:<mime>;base64,<bytes>`. The pinned source (anomalyco/opencode `545f51d26cc39a907d2867492d498d9607ea5fa4`, `session/prompt.ts`) renders the synthetic text for an image file URL as `Called the Read tool with the following input: {"filePath":"<path>"}`, interpolating the resolved private Worker path without JSON escaping. Stored-input verification accepts exactly that closed set: the original text part first, one flagged synthetic Read part per image whose complete text equals that payload for the corresponding image's private path (in attachment order; a prefix-only match, trailing or leading text, extra JSON keys, another path, a duplicated phrase or reordered payloads fail closed, because the model consumes this text while the transcript hides it) and one file part per attachment with the deterministic identifier, the attachment media type, an opaque filename if present, no native `source` annotation and a data URL whose decoded length and SHA-256 equal the attachment. The native server orders stored parts by identifier, so synthetic parts may interleave with files; file parts must still follow attachment order. A strict prefix of the expansion is an unconfirmed intermediate row, never storage. The live observer accepts the same parts in creation order (each file after its synthetic part) and reports the input stored only after the complete expansion arrived. History comparison matches this one message by part identity. Any other part, a changed or swapped digest, a different media type or filename, reordered attachments, a repeated part or a missing part fails closed with the existing typed errors and never resends. The Worker publishes the original text with the ordered attachment references and keeps the expansion parts out of the transcript.

The original image-bearing execution retains a verified checkpoint, but it is not a replacement source. The Worker checkpoint reference, the native checkpoint input identity, the stored checkpoint value, its comparison and the continuation and Fork comparisons use one attachment-aware input digest (`SessionInput.InputDigest`: text only for a text-only input, otherwise the text with the ordered references), which the Worker passes to `OwnedAPI.StartInput`; the adapter still verifies the stored original text part against the SHA-256 of the text alone. The resume, Fork, Sidechat and compaction profiles keep rejecting any history that contains an image file part with their existing unsupported errors, so a session cannot continue an OpenCode history after an image turn in this profile. A queued follow-up with images works when its predecessor history is text-only. Logs carry attachment counts, media types and digests only, never bytes, names or paths. The installed-native acceptance of this probe shape at or above `1.18.32` and real-provider acceptance remain owner-assigned and nonblocking.

Grok Build's official [ACP image implementation](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-shell/src/session/acp_session_impl/prompt_build.rs) can describe images and render the description into a textual user message. That route cannot satisfy this contract's original image delivery requirement. This source revision also does not establish an image/history profile at or above `domain.GrokSubscriptionBaselineVersion` (`1.0.46`). DeliDev retains its closed original text-only ACP input and makes no image claim for Grok Build.

Automated route fixtures stage real owned images and assert that Grok Build, Sidechat, text-only OpenCode models and text-less OpenCode inputs leave the original upload ready and unclaimed. The compatibility matrix of new and old servers against new and old Workers for text-only and image-bearing input is a table test. Positive OpenCode fixtures use a 1x1 PNG, assert the exact `prompt_async` body, the path-free ordered claim digest, the closed three-part stored expansion and its mutations (changed bytes, swapped or reordered attachments, wrong media type, extra, missing or repeated parts) and the unchanged text-only digest. Unsupported guidance preserves the draft. Positive Codex fixtures use the schema-defined primitive, image-only and text-with-images requests, exact selected model modality, ordered receipt/history metadata and changed-byte rejection. These controlled fixtures do not execute an installed native harness or establish real-account/platform acceptance.

Queued edits include typed attachment field 5. Explicit selections must match the immutable original ordered references; old-client omission preserves them. Mixed skill/image Fork proofs retain the original Worker image lookup while copying child-owned skill packages; no new byte ownership or native call is inferred.

## OpenCode image declaration across Worker reconnects

A frozen `image_input_declared` OpenCode declaration is only valid for a Runner Device that currently reports Worker 70. A Worker build that predates the pair can reconnect on the same machine and replaces the reported capability list, so the server checks the current list at each point where a declaration meets a Worker. Every cell below is covered by a test in `cmds/delidev-cli/internal/server`.

| State                                                                                                                                | Event                                      | Result                                                                                                                                                                             |
| ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| First execution preview, Runner without Worker 70                                                                                    | Agent model declares `image`               | Declaration is not frozen; snapshot stays text-only and dispatches as before                                                                                                       |
| First execution preview, Runner with Worker 70                                                                                       | Agent model declares `image`               | Declaration is frozen                                                                                                                                                              |
| Creation, enqueue or follow-up with images                                                                                           | Runner without Worker 70                   | Unsupported-image error; the upload stays unclaimed                                                                                                                                |
| Dispatch of an assignment that declares OpenCode images                                                                              | Runner without Worker 70                   | Typed unsupported error; the saved input stays queued and no image is dropped                                                                                                      |
| Queued execution, compaction (restore or assignment) or Fork (source assignment or child snapshot) job that declares OpenCode images | Claimed by a Worker that reports Worker 70 | Claimed and assigned                                                                                                                                                               |
| Same queued job                                                                                                                      | Claimed by a Worker without Worker 70      | Not claimed: the job stays queued under the existing skipped-job ordering rules, the wait is logged once per job and stream, and no failure, uncertainty or image loss is recorded |
| Same job still waiting                                                                                                               | A Worker reporting Worker 70 attaches      | Claimed and assigned in the normal order                                                                                                                                           |
| Queued job with a text-only OpenCode snapshot or a Codex declaration                                                                 | Claimed by a Worker without Worker 70      | Claimed; the OpenCode pair is irrelevant                                                                                                                                           |
| Job already claimed by an instance                                                                                                   | Same instance reconnects its stream        | Resent unchanged; a different instance follows the existing replaced-instance reconciliation                                                                                       |
